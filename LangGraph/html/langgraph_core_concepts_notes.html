01 · Foundation

What is LangGraph?

LangGraph is an orchestration framework for building stateful, multi-step LLM workflows. It represents a workflow as a graph and executes the tasks according to the graph's connections.

Rather than treating an AI application as one large prompt, you break it into smaller tasks: call a model, call a tool, evaluate a result, make a decision, or ask the user for more information. LangGraph lets you define how those tasks connect and what should happen next.

Core building blocks

  • Nodes: tasks or functions.
  • Edges: execution transitions.
  • State: data shared across the run.
  • Reducers: rules for applying state updates.

Capabilities highlighted in the lecture

  • Sequential and parallel execution
  • Conditional branching and loops
  • Conversation/workflow state
  • Persistence and resuming after interruption
Mental model: LangGraph describes both what each step does and how execution moves between steps.
02 · Design before code

What is an LLM workflow?

A workflow is a sequence of tasks executed to achieve a goal. An LLM workflow is a workflow in which one or more steps use an LLM—for example, to generate text, reason over information, classify a request, call tools, or make a decision.

Example: automated hiring

Other workflows can be non-linear. Some tasks can run concurrently, some require a conditional decision, and some repeat until a quality condition is met.

ShapeExecution ideaExample
LinearStep A → B → COutline, then draft a report
ParallelIndependent tasks run concurrentlyRun several content checks
BranchingChoose a path based on a conditionRoute refund vs technical support
LoopedRepeat a task until a stopping conditionRevise an essay after feedback
03 · Common patterns

Five common LLM workflow patterns

The lecture introduces five reusable patterns. Real applications often combine more than one of them.

1. Prompt chaining

Use multiple LLM calls in sequence, where a later call uses the earlier call's output. This is useful when a large task can be decomposed into smaller, more manageable subtasks.

Use it when: the task benefits from intermediate representations or checkpoints. A check between calls can reject an output that violates a constraint, such as a maximum word count.

2. Routing

A router interprets the request and directs it to the most appropriate specialist or processing path.

Example: a customer-support request is classified as refund-related, technical, or sales-related, then sent to the relevant handler.

Use it when: different request categories require different prompts, tools, policies, or specialist models.

3. Parallelization

Split one task into known, independent subtasks, execute them concurrently, and combine their results.

Use it when: subtasks are independent and can be performed at the same time. Parallelism may reduce latency, but the aggregation rule must be explicit.

4. Orchestrator–workers

This also distributes work across multiple workers, but the orchestrator decides dynamically what subtasks are needed based on the input. The exact tasks are not all predefined.

Parallelization

Known work

Checks and their responsibilities are specified ahead of time.

Orchestrator–workers

Dynamic work

An orchestrator plans tasks and assigns them to workers according to the request.

Lecture example: a research assistant may search academic papers for a scientific query and news sources for a current social or political topic. The query influences which sources and tasks are assigned.

5. Evaluator–optimizer

A generator creates a solution; an evaluator judges it against explicit criteria. If the solution is rejected, the evaluator provides feedback and the generator tries again.

Use it when: output quality is iterative—such as drafting an email, blog post, poem, or story—and evaluation criteria can guide revisions.

Production note: never rely only on an evaluator eventually accepting an answer. Define a maximum iteration count and a fallback path to avoid an endless loop.
04 · Graph structure

Graphs, nodes, and edges

In LangGraph, a workflow is represented as a graph. In the lecture's simplified model, a node is a Python function that performs one task; edges define which node may execute next.

ElementMeaningQuestion it answers
NodeA unit of work, typically a function that reads state and returns updates.What should this step do?
EdgeA connection describing the next step or steps.Where does execution go next?
Conditional edgeSelects the next path based on state or a routing decision.Which path should run?
LoopAn edge that returns execution to an earlier node.Should a step be repeated?

Thinking in graph form makes sequential, parallel, branching, and iterative behavior explicit. It also makes it easier to inspect the workflow before implementing it.

05 · Shared data

State: the information that travels through a graph

State is the shared data structure that carries information between nodes while the workflow runs. It holds the values needed to make progress, and those values may change as execution proceeds.

For the essay-evaluation application described in the lecture, state might include:

Input

Essay topic and current essay text.

Evaluation

Clarity, depth, and language scores.

Decision

Total score, threshold result, feedback, and revision history.

How state moves

In Python, the lecture introduces a TypedDict as a common way to describe the keys and types in state. Pydantic models can also be used when runtime validation is desirable.

from typing import TypedDict

class EssayState(TypedDict):
    topic: str
    essay: str
    clarity_score: int
    depth_score: int
    language_score: int
    total_score: int
    feedback: str
Design rule: define the state schema before writing nodes. Ask what data each step needs, what it produces, and what must survive across a loop or interruption.
06 · State updates

Reducers: how state updates are applied

Nodes can return updates to state. A reducer defines how a new value is combined with the existing value for a particular state key. The update policy can differ from one key to another.

PolicyWhat happensExample
ReplaceNew value replaces the old value.Current essay text or latest calculated score.
Append / accumulateNew item is added while earlier items remain.Conversation messages or essay attempts.
MergeNew information is merged according to a defined rule.Combining partial structured results.

Why replacement is sometimes wrong

For a calculation workflow, replacement is reasonable: a node may write a sum of 11, and the next node can replace it with the doubled result 22.

For a chatbot, replacing the entire message history with the latest message loses context. If a user first says “My name is Nitesh” and later asks “What is my name?”, the model needs the earlier message or a separately stored memory field to answer correctly.

Likewise, for essay feedback, overwriting essay with each revision preserves only the latest draft. If the user needs to compare progress, keep a separate list of attempts or history.

from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    # Appends/merges messages using LangGraph's message-aware reducer.
    messages: Annotated[list, add_messages]
Important distinction: a reducer is not a node and does not decide the next node. It determines how an update to a state key is applied. Edges control execution flow.

Reducers matter especially in parallel workflows

When multiple branches return values for the same key, the graph needs a clear aggregation strategy. A list-accumulating reducer can preserve all branch results; a replacement-style key may not represent multiple independent outputs appropriately. Design and test these rules deliberately.

07 · Runtime lifecycle

LangGraph execution model

The lecture describes the execution model as inspired by Google's Pregel graph-processing approach. Its key teaching sequence is: define the graph, compile it, and then invoke it with input.

1
Define the graph

Create the state schema, define node functions, and connect nodes with edges. This describes the workflow structure.

2
Compile the graph

Compile the graph into an executable application. Compilation is also a place for the framework to validate graph structure and prepare execution.

3
Invoke with input

Start execution by supplying initial state. LangGraph runs eligible nodes according to the graph's edges and state updates.

4
Update state and continue

Nodes return updates. Reducers apply them; edges determine subsequent work. Conditional edges can branch, and loops can revisit earlier nodes.

5
Stop at a terminal condition

The graph finishes when execution reaches an ending path, such as END, or when the run is interrupted or fails.

Keep the concepts separate: compilation prepares the graph; invocation starts a run; state carries data; reducers apply updates; edges determine the next task.

The transcript excerpt names graph definition and compilation and discusses the Pregel inspiration. This section summarizes those ideas at a conceptual level rather than treating it as a complete specification of every runtime detail.

08 · From concept to code

Minimal LangGraph code walkthrough

The following example makes the lecture's graph concepts concrete: a state schema, Python-function nodes, a conditional edge, compilation, and invocation. It is an illustrative starter example; install a compatible version of langgraph before running it.

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END

class EssayState(TypedDict):
    essay: str
    score: int
    feedback: str
    passed: bool

def evaluate_essay(state: EssayState) -> dict:
    # Replace this simple rule with an LLM or rubric-based evaluator.
    score = min(len(state["essay"].split()) // 10, 15)
    return {
        "score": score,
        "passed": score >= 10,
        "feedback": "Good work." if score >= 10 else "Add depth and supporting examples."
    }

def route_after_evaluation(
    state: EssayState
) -> Literal["accepted", "revise"]:
    return "accepted" if state["passed"] else "revise"

def accepted(state: EssayState) -> dict:
    return {"feedback": "Essay accepted. " + state["feedback"]}

def revise(state: EssayState) -> dict:
    # In a real app, this could return feedback to the user
    # and pause for a revised essay rather than looping blindly.
    return {"feedback": "Please revise and submit again. " + state["feedback"]}

builder = StateGraph(EssayState)
builder.add_node("evaluate", evaluate_essay)
builder.add_node("accepted", accepted)
builder.add_node("revise", revise)

builder.add_edge(START, "evaluate")
builder.add_conditional_edges(
    "evaluate",
    route_after_evaluation,
    {
        "accepted": "accepted",
        "revise": "revise",
    },
)
builder.add_edge("accepted", END)
builder.add_edge("revise", END)

graph = builder.compile()

result = graph.invoke({
    "essay": "A sample essay with enough supporting discussion ...",
    "score": 0,
    "feedback": "",
    "passed": False,
})
print(result)

Read the example through the core concepts

  • State: EssayState describes the data that moves between nodes.
  • Nodes: evaluate_essay, accepted, and revise are Python functions.
  • Edges: START leads to evaluation; conditional routing selects the next node.
  • Compile: builder.compile() prepares the graph for execution.
  • Invoke: graph.invoke(...) runs it with an initial state.
Note on this teaching example: it ends after returning feedback. It does not automatically collect a new essay from a human. A real human-in-the-loop revision flow needs an interaction mechanism, persistence/checkpointing where appropriate, and a deliberate resume path.

Example: append message history instead of overwriting it

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langchain_core.messages import HumanMessage, AIMessage

class ConversationState(TypedDict):
    messages: Annotated[list, add_messages]

def greet(state: ConversationState) -> dict:
    # Illustrative fixed response; a real node would call a chat model.
    return {"messages": [AIMessage(content="Hello! How can I help?")]}

builder = StateGraph(ConversationState)
builder.add_node("greet", greet)
builder.add_edge(START, "greet")
builder.add_edge("greet", END)
chat_graph = builder.compile()

result = chat_graph.invoke({
    "messages": [HumanMessage(content="Hi, my name is Nitesh.")]
})

This snippet illustrates a message-aware reducer. In a production conversational application, model invocation, turn management, persistence, and privacy controls would need to be implemented as well.

10 · Practical cautions

Common mistakes to avoid

  • Starting with code instead of the workflow. First write down the tasks, decisions, loops, and stopping conditions.
  • Putting everything in one node. Split distinct responsibilities when it improves observability, testing, or routing.
  • Designing state after nodes. Define the fields and their lifecycle first, then implement nodes around them.
  • Overwriting information that should be retained. Chat history, parallel branch outputs, and revision history often need accumulation rather than replacement.
  • Leaving conditional routes incomplete. Ensure each possible outcome has a valid next step and a defined terminal path.
  • Creating unbounded loops. Set maximum attempts, timeouts, or other termination conditions.
  • Assuming parallel results automatically combine correctly. Decide how multiple updates to a state key should be reduced.
  • Confusing workflow state with durable memory. State used during a run is not automatically a complete long-term memory or persistence strategy; configure persistence/checkpointing when the application requires it.
