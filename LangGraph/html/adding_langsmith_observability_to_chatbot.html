Adding Observability to a LangGraph Chatbot

Practical learning notes on tracing executions with LangSmith, inspecting latency and token usage, and organizing chatbot turns into conversation threads.

Technical tutorialPython examplesArchitecture diagramsSource-based notes

1. Overview

This lesson adds observability to an existing LangGraph chatbot by integrating LangSmith. It then connects each execution trace to a conversation thread so that separate conversations are easy to inspect independently.

Central idea: enable LangSmith tracing through environment configuration, then pass a stable thread identifier in the run configuration and attach that identifier as trace metadata. This gives you both execution-level detail and conversation-level organization.
Conceptual view: the application continues to respond normally while execution details are captured for later debugging and analysis.

2. Project recap: what already exists?

The lesson continues an incremental chatbot project. Before adding observability, the chatbot already has several capabilities:

Capability 01

GUI

A user interface through which a person can interact with the chatbot.

Capability 02

Streaming

The response can appear progressively, rather than making the user wait for the entire answer before seeing anything.

Capability 03

Database persistence

Chat history survives a program restart. A user can reopen the application later and recover previous chats.

Capability 04

Observability (this lesson)

Execution details are recorded in LangSmith so developers can inspect what happened during a turn.

Keep the concepts separate: database persistence stores application conversation state for the chatbot to use again. LangSmith tracing stores execution telemetry for developers to understand and debug the system.

3. What is observability?

In this lesson, observability means being able to follow a chatbot execution end to end. For a given interaction, a developer can inspect the user's input, the model's output, timing information, token usage, status, and internal steps represented in the trace.

Why it matters

  • Debugging: find which node or model call produced an unexpected result.
  • Performance: identify slow executions and examine time to first token and overall latency.
  • Cost awareness: inspect input and output token counts, which can help estimate model usage costs.
  • Learning complex flows: as tools, RAG, agents, or MCP integrations are added, traces reveal how the components execute.
  • Production monitoring: use run histories and telemetry as evidence when diagnosing incidents.

Observability is more than logging the final answer

Only saving a chat transcriptTracing with observability
User message and final assistant responseInput/output plus execution hierarchy and component-level runs
Usually insufficient to explain slownessTiming and latency details can help localize slow steps
Usually lacks model usage telemetryToken usage may be available when supported by the integration/provider
Useful for conversation historyUseful for debugging, evaluation, performance analysis and operational visibility
Privacy note: traces may contain user prompts, model responses, and metadata. Do not send secrets or sensitive personal data to a tracing service unless your organization's policies, configuration, access controls, and retention requirements permit it.

4. Set up LangSmith tracing

The transcript's setup flow is: create or sign in to a LangSmith account, generate an API key, place the tracing settings in the project's environment configuration, then run the existing chatbot. With tracing configured, the lesson demonstrates that the main chatbot logic does not need to be rewritten just to capture traces.

Step 1 — Create an API key

  1. Open the LangSmith website and sign in.
  2. Go to the account or workspace settings and find the API keys section.
  3. Create a key with a recognizable description and copy it securely.
  4. Store it in your local environment configuration. Do not commit it to source control.

Step 2 — Add environment variables

The transcript refers to these variables. The endpoint shown here is the common LangSmith API endpoint; use the endpoint documented for your workspace if it differs.

# .env — example only; replace the placeholder with your own key
LANGSMITH_TRACING=true
LANGSMITH_ENDPOINT=https://api.smith.langchain.com
LANGSMITH_API_KEY=your_langsmith_api_key
LANGSMITH_PROJECT=chatbot-project

The lesson uses the project name chatbot-project as an example. Runs that inherit this environment configuration are grouped under that project in the LangSmith dashboard.

Never paste a real API key into notes, screenshots, public repositories, or chat messages. If a key is exposed, revoke it and create a replacement.

Step 3 — Load the environment

For a Python project using a .env file, a typical setup is:

from dotenv import load_dotenv

load_dotenv()

# The LangChain/LangGraph integration reads the relevant
# LANGSMITH_* variables from the process environment.
# Continue to run your existing graph/chatbot normally.

Install the relevant packages in your project's environment if needed:

pip install langsmith python-dotenv

Package requirements depend on the rest of the project; the chatbot will also need its existing LangGraph, LangChain integration, and model-provider packages.

Step 4 — Run a normal chat turn

Run the same chatbot code and send a message. Open the matching LangSmith project and check that a trace appears. In the transcript's demonstration, the chatbot behaves normally while LangSmith records the run behind the scenes.

5. Understand projects, traces and runs

Three related terms are important. A project groups related tracing activity; a trace represents a top-level execution associated with an interaction; and runs are the individual steps/components inside that trace, such as a graph node or model call. Exact hierarchy and labels depend on the integration and SDK version.

Simplified hierarchy for learning. A real trace can include several nested graph nodes, tool calls, and model invocations.

In the demonstration, a message such as “Give me a roadmap to study AI engineering” produces a trace. A later message produces another trace. Opening a trace reveals details such as the graph node (for example, a chat node), the model call, input/output, start and end time, token counts, and latency when available.

6. Why threads matter

Without an explicit conversation/thread identifier in tracing metadata, separate chats can appear together in a project's trace list without an obvious grouping that reflects the application's conversation structure. The lesson solves this by attaching the current chatbot thread ID to each trace.

The intended organization

The application creates a distinct thread ID for each conversation. Every turn in that conversation reuses the same ID.

The transcript's example uses two separate conversations: one with greetings and follow-ups, and another with a different user's study-roadmap question. With thread IDs, the dashboard can show each conversation as its own thread, with its own turn traces nested beneath it.

Thread ID, trace metadata and run name have different roles

FieldPurposeExpected behavior
configurable.thread_idLangGraph execution/checkpoint thread identifierReuse it for turns in the same conversation; use a different one for a new conversation.
metadata.thread_idTrace metadata used to associate/filter traces by conversationSet it to the same current thread ID so the tracing view can group or identify the conversation.
run_nameHuman-readable label for a run/traceOptional. The lesson uses “Chat Turn” instead of a generic “LangGraph” label.
Important distinction: LangGraph's configurable.thread_id controls graph/checkpointer thread behavior. Adding metadata.thread_id labels the trace; metadata alone should not be assumed to create or persist application conversation state.

7. Implementation pattern

The exact surrounding code depends on the chatbot project, but the lesson's key change is to keep the existing configurable thread ID and add metadata plus an optional descriptive run name to the invocation config.

Example A — Invoke a compiled LangGraph graph

# Example pattern; adapt `graph` and `thread_id` to your application.
thread_id = "conversation-123"

config = {
    "configurable": {
        "thread_id": thread_id
    },
    "metadata": {
        "thread_id": thread_id
    },
    "run_name": "Chat Turn"
}

result = graph.invoke(
    {"messages": [{"role": "user", "content": "Hi"}]},
    config=config
)

This is an illustrative invocation pattern. If your graph expects a different state schema (for example, a LangGraph MessagesState schema), adapt the input shape to match it.

Example B — Stream a turn using the same config

for event in graph.stream(
    {"messages": [{"role": "user", "content": "Explain LangGraph"}]},
    config=config,
    stream_mode="updates"
):
    print(event)

Use the same thread ID for subsequent turns in the same conversation. If your application streams tokens through a different API, preserve the same tracing/configuration information in that call.

Example C — Create a new conversation correctly

from uuid import uuid4

# Generate once when a new conversation is created.
new_thread_id = str(uuid4())

# Store this ID in the session / database with the conversation.
# For every later turn in that conversation, load and reuse it.
config = {
    "configurable": {"thread_id": new_thread_id},
    "metadata": {"thread_id": new_thread_id},
    "run_name": "Chat Turn",
}
Rule of thumb: create a thread ID when a new conversation begins, persist it with that conversation, and reuse it for all later turns. Do not generate a fresh ID for every message, or each turn will look like a separate conversation.

Example D — Minimal .env template

LANGSMITH_TRACING=true
LANGSMITH_ENDPOINT=https://api.smith.langchain.com
LANGSMITH_API_KEY=replace_me
LANGSMITH_PROJECT=chatbot-project

Environment variable names and tracing behavior can vary with library versions. The lesson uses the LangSmith environment configuration approach, which lets supported LangChain/LangGraph integrations report traces without adding manual tracing calls around every node.

9. Common pitfalls and good practices

  • One trace project, many unrelated conversations: use consistent thread metadata so the conversations can be identified and grouped.
  • New ID for every turn: breaks conversation grouping. Reuse the ID for the lifetime of a conversation.
  • Same ID for every user: risks mixing unrelated conversations and may also cause incorrect checkpoint state. Generate IDs per conversation and enforce authorization at the application layer.
  • Metadata mistaken for persistence: trace metadata labels telemetry; the graph checkpointer/database manages application state.
  • API key committed to Git: load it from environment/secrets management and keep it out of code and version control.
  • Assuming tracing is free of privacy risk: inspect what is captured and apply appropriate redaction, access control, retention, and data-handling rules.
  • Dashboard is empty: confirm the tracing flag, endpoint, API key, project name, network access, package versions, and that the code path actually invokes an instrumented integration.

10. End-to-end workflow checklist

  1. Create/sign in to LangSmith and generate an API key.
  2. Set tracing, endpoint, API key, and project environment variables.
  3. Load environment variables before invoking the chatbot.
  4. Run the existing application and send a test message.
  5. Confirm that the trace appears in the intended LangSmith project.
  6. Inspect input/output, model or graph-node runs, duration, tokens and status.
  7. Pass the current conversation ID as configurable.thread_id.
  8. Attach the same ID as metadata.thread_id for trace organization.
  9. Optionally set run_name to a meaningful label such as Chat Turn.
  10. Test two different conversations and verify their traces remain separately grouped.
  11. Restart the app and verify that application persistence still behaves as designed.

11. Interview-ready recap

What is LangSmith observability?

It is the ability to inspect an LLM application's execution through traces, including inputs, outputs, component runs, timing, token usage, and errors where available. It helps debug, evaluate, and monitor complex LLM workflows.

What is the difference between a project, trace, and thread?

  • Project: organizes related tracing activity.
  • Trace: captures one execution or interaction, with nested component runs.
  • Thread: represents a conversation across multiple turns; a thread can contain multiple traces.

Why add thread IDs to metadata?

To associate each trace with the application's conversation identifier, making it easier to browse turns belonging to the same conversation. The thread ID should be stable for a conversation and different for a new one.

Does LangSmith require changing the main chatbot code?

In the lesson's setup, supported LangGraph/LangChain integrations begin tracing from environment configuration, so basic tracing can work without rewriting the main execution logic. Explicit thread metadata and a custom run name require an invocation-config change.

Why is this useful before adding tools or RAG?

Tools, retrieval, and agent loops introduce more steps and failure points. A trace makes the execution path visible so developers can see which calls happened, where latency accumulated, and what data moved between components.
