1. What is persistence?

Persistence is the ability to save and restore the state of a workflow over time.

In LangGraph, a workflow's state changes as nodes execute. Persistence records snapshots of that state as checkpoints, allowing an application to inspect earlier progress, resume work, retain conversation history, and recover from interruptions.
In one sentence: state is the data your graph is working with; persistence makes that data recoverable beyond a single step or invocation.

Why it matters

  • A workflow may need to continue after a crash, timeout, or manual interruption.
  • A chatbot may need to remember messages from a previous turn in the same conversation.
  • A person may need to approve a proposed action before the graph continues.
  • A developer may need to inspect or replay a previous point in a run to debug behavior.

2. Two foundations: graph and state

Graph

A graph breaks a high-level goal into tasks. Nodes perform work; edges define the path or execution order.

A simple sequential graph: each node can read state and return updates to it.

State

State is the structured data shared across graph execution. In simple examples it may look like a Python dictionary, with keys such as messages, topic, joke, or explanation. Nodes read the relevant values and return updates.

# Conceptual state
state = {
    "topic": "pizza",
    "joke": "",
    "explanation": ""
}

Without persistence, your application may still receive the final result of a run, but it does not automatically have durable access to all earlier state snapshots. Persistence adds a mechanism to save and retrieve those snapshots.

3. Checkpoints and the checkpointer

A checkpoint is a saved snapshot of graph progress and state. A checkpointer is the component responsible for saving and retrieving checkpoints.

  • LangGraph saves checkpoints at graph superstep boundaries.
  • A superstep can include multiple nodes that run in parallel.
  • Each checkpoint preserves the state/progress needed to inspect or resume the workflow.
  • State history can include intermediate snapshots—not only the final output.
Illustrative sequence. Actual checkpoint count depends on graph structure and execution.

Example: a list that grows

Suppose the state has a numbers list and a reducer that merges new values rather than replacing the existing list:

CheckpointUpdate receivedState after merge
1Initial input: [1][1]
2Node adds 2[1, 2]
3Parallel nodes add 3, 4, 5[1, 2, 3, 4, 5]
4Graph reaches end[1, 2, 3, 4, 5]
Important distinction: a reducer determines how updates combine with existing state. Persistence records snapshots of the state; it does not itself decide whether values are appended, merged, or overwritten.

4. Threads: keep executions separate

A thread groups the checkpoints belonging to one ongoing conversation or workflow instance. When invoking a graph with persistence, pass a stable thread_id in the config. The same ID lets you retrieve that thread's state and continue it; a different ID creates a separate checkpoint history.

Separate thread IDs prevent one conversation's checkpoint history from being confused with another's.
config = {
    "configurable": {
        "thread_id": "conversation-1"
    }
}

result = graph.invoke(
    {"topic": "pizza"},
    config=config
)

For a chatbot, create or assign a thread ID when a conversation starts, reuse it for later turns in that conversation, and use another ID for a separate conversation. In a real application, map user-visible conversation IDs to thread IDs carefully and enforce authorization.

5. Implementation: a small persistent joke workflow

The source lesson demonstrates a sequential graph with two nodes: generate a joke for a topic, then explain the joke. It uses an in-memory checkpointer for a simple demo.

Demo vs production: an in-memory saver is useful for learning, but its checkpoint data is lost when the process ends. For durable production persistence, configure a supported database-backed checkpointer (for example, a PostgreSQL integration) and follow that integration's setup/migration instructions.

Install the core packages

pip install -U langgraph langchain-openai

Set your model-provider API key in the environment before running the example. This version uses a chat model and a typed state schema; model names and provider setup may need adjustment for your environment.

Complete example

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langchain_openai import ChatOpenAI

class JokeState(TypedDict):
    topic: str
    joke: str
    explanation: str

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)

def generate_joke(state: JokeState):
    response = llm.invoke(
        f"Tell one short, clean joke about {state['topic']}."
    )
    return {"joke": response.content}

def explain_joke(state: JokeState):
    response = llm.invoke(
        "Explain this joke briefly and clearly: "
        + state["joke"]
    )
    return {"explanation": response.content}

builder = StateGraph(JokeState)
builder.add_node("generate_joke", generate_joke)
builder.add_node("explain_joke", explain_joke)

builder.add_edge(START, "generate_joke")
builder.add_edge("generate_joke", "explain_joke")
builder.add_edge("explain_joke", END)

# In-memory persistence for demos and learning.
checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {
    "configurable": {
        "thread_id": "joke-thread-1"
    }
}

result = graph.invoke(
    {
        "topic": "pizza",
        "joke": "",
        "explanation": ""
    },
    config=config
)

print(result["joke"])
print(result["explanation"])

# Read the latest saved state for this thread.
snapshot = graph.get_state(config)
print(snapshot.values)

# Inspect earlier checkpoints in this thread.
for checkpoint in graph.get_state_history(config):
    print(checkpoint.values, checkpoint.next)

6. Four key capabilities enabled by persistence

1. Short-term conversational memory

Store messages and other conversation state against a thread. Reusing that thread lets later turns access the saved context.

2. Fault tolerance

After an interruption, the graph can continue from saved progress instead of repeating completed work, where the execution and side-effect semantics permit it.

3. Human-in-the-loop (HITL)

Pause before a sensitive action, persist the checkpoint, collect a human decision, and then resume.

4. Time travel

Inspect a previous checkpoint, replay from a chosen point, or fork a new path by updating state at that checkpoint.

Memory scope

Thread-backed persistence is commonly used for short-term memory within a conversation/thread. It is not automatically the same as long-term memory shared across different conversations or users; that usually needs an explicit memory design and retrieval strategy.

7. Fault tolerance: resume after interruption

Imagine a three-step graph. Step 1 completes, Step 2 is interrupted, and Step 3 has not run. The saved checkpoint records the completed progress. Once the same graph and same thread are invoked with the appropriate resume input, execution can continue from the pending work rather than starting the whole workflow over.

Conceptual illustration; exact resume behavior depends on the interruption type and graph design.

For a deliberate interrupt/resume pattern, the same thread ID is essential. The source lesson demonstrates stopping during a delayed second step and then invoking the graph again with None and the same config to resume the pending execution.

# First invocation: start a new run
config = {"configurable": {"thread_id": "run-1"}}
graph.invoke({"input": "start"}, config=config)

# Resume a previously interrupted run using the same thread.
# This pattern is for a graph designed to resume this way.
graph.invoke(None, config=config)
Production caveat: checkpointing does not make external side effects automatically exactly-once. If a node charges a card, sends an email, or calls an API, design idempotency, retries, and transaction boundaries explicitly.

8. Human-in-the-loop (HITL)

HITL means the workflow pauses for a human decision before continuing. The lesson's example is an agent that drafts a LinkedIn post and asks for approval before publishing it.

A modern LangGraph implementation commonly uses interrupt() to pause and Command(resume=...) to supply the human response. The graph must be compiled with a checkpointer and invoked with a thread ID.

from langgraph.types import interrupt, Command

def approval_node(state):
    decision = interrupt({
        "question": "Approve this draft for publishing?",
        "draft": state["draft"]
    })
    return {"approval": decision}

# Initial run pauses at interrupt; use a persistent checkpointer.
config = {"configurable": {"thread_id": "post-review-42"}}
graph.invoke({"draft": "Draft post text"}, config=config)

# Later, after the human responds:
graph.invoke(
    Command(resume={"approved": True}),
    config=config
)

This is a structural example, not a complete publishing application. In practice, validate the resumed payload and route approved/rejected outcomes explicitly before performing the external action.

9. Time travel: inspect, replay, and branch

Time travel uses checkpoint history to revisit an earlier state. It is especially useful for debugging complex workflows, testing alternate decisions, or exploring how a different state would affect downstream nodes.

  1. Inspect history: call get_state_history(config) and review the saved snapshots and pending nodes.
  2. Choose a checkpoint: select the historical snapshot from which you want to continue.
  3. Replay or fork: invoke from that checkpoint, or update its state and then continue from the updated checkpoint.
# 1. Inspect checkpoint history
history = list(graph.get_state_history(config))
for snapshot in history:
    print(snapshot.config)   # includes checkpoint identity
    print(snapshot.values)   # state at this point
    print(snapshot.next)     # next node(s), if any

# 2. Update state at a chosen checkpoint
# Use the config belonging to the selected snapshot.
chosen_checkpoint_config = history[1].config
graph.update_state(
    chosen_checkpoint_config,
    {"topic": "samosa"}
)

# 3. Continue from the new/updated checkpoint
# Pass the checkpoint config returned by update_state.
updated_config = graph.update_state(
    chosen_checkpoint_config,
    {"topic": "samosa"}
)
graph.invoke(None, config=updated_config)
Read carefully: checkpoint selection and branching APIs can be easy to misuse. Keep the exact checkpoint config returned by the selected history item or by update_state, and invoke from the intended branch. Updating a past state creates a new path; it does not rewrite the meaning of already completed external side effects.

In the lesson's example, a checkpoint where the topic was pizza is used to create an alternate branch with samosa. The downstream joke and explanation are then generated for the new branch, while the original history remains available for inspection.

10. Practical patterns and common mistakes

Pattern A — resume a conversation

config = {"configurable": {"thread_id": conversation_id}}

# Reuse this config for each turn in the same conversation.
answer = graph.invoke(
    {"messages": [user_message]},
    config=config
)

Pattern B — start a separate conversation

Use a new unique thread ID rather than reusing an unrelated conversation's ID.

Common mistakes

  • Forgetting to compile the graph with a checkpointer.
  • Omitting thread_id or changing it when trying to resume an existing thread.
  • Assuming InMemorySaver persists across program restarts.
  • Confusing the final state with the full checkpoint history.
  • Assuming a reducer is required for persistence; reducers control how state updates merge.
  • Assuming checkpoints alone guarantee safe retries of payments, publishing, or other side effects.
  • Using the same thread ID for unrelated users or conversations without access controls.

11. Final recap

  • State: the data being passed and updated by graph nodes.
  • Persistence: saves state snapshots so they can be inspected and restored later.
  • Checkpoint: one saved snapshot of execution state/progress.
  • Checkpointer: saves and loads checkpoint data.
  • Thread ID: groups checkpoints for a conversation or workflow instance.
  • Four headline benefits: short-term memory, fault tolerance, human-in-the-loop, and time travel.
