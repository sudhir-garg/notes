1. What is Corrective RAG (CRAG)?

Corrective Retrieval-Augmented Generation (CRAG) is a RAG design that evaluates retrieved evidence before asking the language model to answer. Instead of blindly trusting the retriever, it chooses how to proceed based on the usefulness of the retrieved documents.

Core idea: retrieve → evaluate evidence → refine relevant information and/or search externally → generate an answer from the selected context.

Traditional RAG usually assumes the top retrieved passages are useful. CRAG adds a corrective decision step because a vector database may return only loosely related material—or no adequate evidence for the question.

What CRAG is trying to improve

  • Reduce answers grounded in irrelevant or weakly relevant passages.
  • Filter away unrelated sentences that happen to share a chunk with useful content.
  • Use an external source such as web search when the private corpus is insufficient.
  • Combine internal evidence with external evidence when the internal corpus helps but does not fully answer the question.
  • Rewrite vague user questions into search-engine-friendly queries before web search.

2. Traditional RAG: the baseline

The three conceptual stages are:

  1. Retrieval: embed the user query and find semantically similar document chunks.
  2. Augmentation: combine the query and retrieved text in the prompt.
  3. Generation: the LLM produces a response using the supplied context.

The transcript’s example pipeline loads three machine-learning/deep-learning books, splits them into chunks, embeds them, stores them in a FAISS vector store, and retrieves the top four documents for a query.

3. Why traditional RAG can fail

The “blind trust” problem

A vector database generally returns the closest matches it can find; that does not guarantee the matches contain the answer. If the corpus lacks the right information, the retriever may return nearby but incorrect topics. The LLM may then answer from those passages or fall back on its learned, parametric knowledge.

Transcript demonstration:

  • In-corpus query: “What is the bias-variance trade-off?” The retrieved passages discuss bias and variance, and the answer is well grounded.
  • Out-of-corpus query: “What are the top AI news from last month?” The books are old machine-learning texts and cannot reliably answer a recent-news question.
  • Missing-topic query: “What is a transformer in deep learning?” The retriever returns passages about MLPs, CNNs, regularization, and related topics—but not transformer architecture. The LLM still provides a plausible answer from its parametric knowledge.
Important distinction: an answer can be factually plausible while not being supported by the retrieved context. CRAG is designed to assess the evidence path, not merely whether the generated prose sounds confident.

4. CRAG architecture and the three retrieval outcomes

CRAG inserts a retrieval evaluator between retrieval and generation. It examines the user query and retrieved documents, then determines whether the evidence is strong, weak, or mixed.

CORRECT

Strong evidence

Use the relevant internal documents. Refine them to remove unrelated text, then generate.

INCORRECT

Weak / irrelevant

Rewrite the query if useful, search the web, then generate from external results.

AMBIGUOUS

Partially useful

Keep useful internal documents, also search the web, merge the evidence, refine it, and generate.

Conceptual view of the complete workflow. In the tutorial’s final graph, the ambiguous path is simplified: both INCORRECT and AMBIGUOUS route through query rewriting and web search; the refine node decides which evidence to use.

Internal and external knowledge

  • Internal knowledge: the refined content from the system’s own vector database.
  • External knowledge: documents returned by web search.
  • Generation: the LLM receives the question and the evidence selected for that route.

5. Iteration 1 — Knowledge refinement

Retrieved chunks are often imperfect because fixed-size chunking does not respect topic boundaries. One chunk may contain a useful explanation plus unrelated sentences from the next paragraph.

The three refinement steps

1
Decomposition
Split each retrieved document into small sentence-level “strips” (often one sentence, sometimes a small group).
2
Filtration
For every strip, ask a relevance filter whether it directly helps answer the query. Keep useful strips; discard unrelated ones.
3
Recomposition
Join the kept strips to create a refined context for answer generation.

Example from the lesson: for “What is gradient descent?”, keep the sentences explaining gradient descent and loss minimization. Discard sentences about neural-network layers or convolutional networks if they do not help answer that query.

The research paper described in the transcript used a fine-tuned T5-large model for filtering. The tutorial does not have access to that task-specific checkpoint, so it uses a chat LLM to return a structured true/false relevance judgment instead.

6. Iteration 2 — Retrieval evaluation and thresholding

The evaluator scores each retrieved document for its usefulness to the current query. The tutorial uses a 0–10 scale with two thresholds:

ParameterExample valueMeaning
Lower threshold3Below this, a document is considered too weak to use.
Upper threshold7Above this, at least one document is strong enough for a CORRECT verdict.
The transcript describes scores inconsistently in one spoken example (for instance, “0.8” versus “8”). The intended scoring logic is a 0–10 scale: higher means more relevant, lower means less relevant.

Verdict rules

  • CORRECT: at least one document score is greater than the upper threshold (greater than 7 in the example).
  • INCORRECT: no document score is greater than the lower threshold (none is greater than 3).
  • AMBIGUOUS: neither condition above applies. Some evidence exists, but no document is strong enough to call retrieval fully correct.
Scores (example)VerdictEvidence used for generation
8, 4, 2CORRECTKeep scores greater than 3: 8 and 4. Exclude 2.
1, 2INCORRECTInternal documents are insufficient; use web search.
5, 4, 6AMBIGUOUSKeep sufficiently useful internal evidence and supplement with web results.

Subtle but important: the verdict is based on the strongest score, but generation does not automatically use every retrieved document. The tutorial’s rule is to keep only documents whose score is greater than the lower threshold.

7. Iteration 3 — External web search with Tavily

When retrieval is INCORRECT, the system cannot rely on the internal corpus. The tutorial adds a web-search node using Tavily.

1
Receive the query (later, the rewritten query) and call the Tavily search API.
2
Extract each result’s title, URL, and content.
3
Convert results into document objects and store them in the graph state.
4
Refine the selected context and generate an answer grounded in the web results.
Production note: web search adds freshness, not automatic truth. Treat external pages as untrusted evidence, inspect source quality, and retain citations/URLs in the answer when possible.

8. Iteration 4 — Query rewriting

User questions are optimized for conversation, not necessarily for search engines. A vague question can produce weaker web results. A query-rewriting node uses an LLM to convert the original question into a short, specific search query.

Original user questionRewritten search query
“Who was the screenwriter for Death of a Batman?”“Death of a Batman screenwriter Wikipedia”
“Recent AI news”“Recent AI news last 30 days”

The rewrite prompt in the transcript tells the model to keep the query short, add a time constraint when recency is implied, and return a structured JSON object containing one query. The Tavily node searches using this rewritten query rather than the original user wording.

Flow change: INCORRECT / AMBIGUOUS → Rewrite query → Tavily search → Refine context → Generate.

9. Handling AMBIGUOUS retrieval: merge internal and external evidence

An ambiguous result means internal passages are not strong enough to answer the full question alone, but they are not useless. The system should not throw away that partial evidence.

  • Retain internal documents with scores greater than the lower threshold.
  • Rewrite the query and retrieve external web documents.
  • Combine the selected internal documents and web documents.
  • Run knowledge refinement over the combined material.
  • Generate using the resulting refined context.

In the final tutorial graph, this is simplified into two routing branches: CORRECT goes directly to refinement; both INCORRECT and AMBIGUOUS go to query rewriting and web search. The refine node checks the verdict and chooses internal docs, web docs, or both.

10.1 Define graph state

from typing import TypedDict, Literal
from langchain_core.documents import Document

class CRAGState(TypedDict, total=False):
    question: str
    docs: list[Document]          # internal retrieval results
    scores: list[float]
    verdict: Literal["correct", "incorrect", "ambiguous"]
    kept_docs: list[Document]
    web_query: str
    web_docs: list[Document]
    refined_context: str
    answer: str

10.2 Classify retrieval scores

LOWER_THRESHOLD = 3
UPPER_THRESHOLD = 7

def classify_retrieval(scores: list[float]) -> str:
    # No evidence at all: treat as insufficient.
    if not scores:
        return "incorrect"

    if any(score > UPPER_THRESHOLD for score in scores):
        return "correct"

    if all(score <= LOWER_THRESHOLD for score in scores):
        return "incorrect"

    return "ambiguous"
Threshold comparisons follow the lesson’s “greater than” wording: > 7 means CORRECT; if no score is > 3, INCORRECT; otherwise AMBIGUOUS. If your evaluator returns scores on a 0–1 scale, change the thresholds accordingly—do not mix scales.

10.3 Keep only documents above the lower threshold

def select_useful_docs(docs, scores):
    return [
        doc for doc, score in zip(docs, scores)
        if score > LOWER_THRESHOLD
    ]

10.4 Decompose text into sentence strips

import re

def decompose_to_sentences(text: str) -> list[str]:
    # Simple demonstration splitter. For robust multilingual/PDF text,
    # use a sentence tokenizer suited to your documents.
    parts = re.split(r"(?<=[.!?])\s+", text.strip())
    return [part.strip() for part in parts if part.strip()]

10.5 Filter strips with a structured LLM response

from pydantic import BaseModel, Field

class StripVerdict(BaseModel):
    keep: bool = Field(
        description="True only when this strip directly helps answer the question"
    )

# Pseudocode: adapt to the structured-output API of your chat model.
filter_chain = llm.with_structured_output(StripVerdict)

def refine_text(question: str, document_text: str) -> str:
    strips = decompose_to_sentences(document_text)
    kept = []

    for strip in strips:
        verdict = filter_chain.invoke(
            f"""Question: {question}
Sentence strip: {strip}

Keep only if the strip directly helps answer the question."""
        )
        if verdict.keep:
            kept.append(strip)

    return " ".join(kept)

10.6 Rewrite a question before web search

class SearchQuery(BaseModel):
    query: str

# Pseudocode: structured LLM output
rewrite_chain = llm.with_structured_output(SearchQuery)

def rewrite_query(question: str) -> str:
    result = rewrite_chain.invoke(
        f"""You compose web-search queries.
Keep the query short and specific.
If the question implies recency, include a suitable time window.
Do not answer the question. Return one search query.
Question: {question}"""
    )
    return result.query

10.7 Routing and context selection

def route_after_evaluation(state: CRAGState) -> str:
    if state["verdict"] == "correct":
        return "refine"
    # Both weak and mixed retrieval need external evidence.
    return "rewrite_query"

def choose_documents_for_refinement(state: CRAGState):
    verdict = state["verdict"]
    if verdict == "correct":
        return state.get("kept_docs", [])
    if verdict == "incorrect":
        return state.get("web_docs", [])
    # ambiguous: combine useful internal evidence + web evidence
    return state.get("kept_docs", []) + state.get("web_docs", [])

12. Revision checklist

  • Traditional RAG has retrieval, augmentation, and generation.
  • Top-k similarity does not guarantee evidence relevance.
  • CRAG evaluates retrieved documents before trusting them.
  • Knowledge refinement = decomposition → filtration → recomposition.
  • In the lesson’s example: lower threshold = 3; upper threshold = 7.
  • CORRECT: at least one score is greater than 7.
  • INCORRECT: no score is greater than 3.
  • AMBIGUOUS: some useful evidence exists, but no score exceeds 7.
  • Only documents scoring greater than 3 are retained for internal evidence.
  • INCORRECT uses external search; AMBIGUOUS merges internal and external evidence.
  • Query rewriting makes a vague user question more useful to a search engine.
  • The final graph can route CORRECT directly to refinement and route other verdicts through rewrite + web search.

Self-test

1. Why can traditional RAG hallucinate even when retrieval succeeds?

Retrieval may return loosely related documents. If the model treats them as trustworthy evidence, it can produce an unsupported answer or fall back on parametric knowledge.

2. What are the three knowledge-refinement steps?

Decomposition into sentence strips, filtration by relevance to the query, and recomposition of the kept strips.

3. Scores are 8, 4, and 2. What is the verdict and which documents are retained?

CORRECT, because one score is greater than 7. Retain scores greater than 3: the documents scored 8 and 4; exclude the document scored 2.

4. What should happen when internal evidence is ambiguous?

Keep useful internal evidence, retrieve external web evidence, merge both sources, refine the combined context, then generate.

5. Why rewrite a query before web search?

It can add missing keywords or time constraints and make a vague conversational question more explicit for a search engine.
