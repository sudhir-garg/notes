1. What is long-term memory?

In an LLM application, a user may reveal useful facts across many separate conversations. Long-term memory stores selected facts outside the current conversation so that later conversations can retrieve and use them to personalize answers.

Core idea: capture useful user facts → save them in persistent storage → retrieve relevant facts later → inject them into the LLM’s context.

Examples of useful memories include a user's preferred programming language, answer format, ongoing project, profession, or a future travel plan. The goal is not to save every sentence; it is to retain relevant information that improves future assistance.

Example

A user once says, “I prefer Python and concise bullet-point answers.” Days later they ask, “Show me a Fibonacci program.” The application can retrieve those preferences and answer in Python, using concise bullets.

2. Short-term memory vs long-term memory

AspectShort-term memoryLong-term memory
ScopeOne conversation/threadCan span multiple threads and sessions
Typical contentRecent messages and current task contextStable preferences, profile facts, ongoing plans
PurposeMaintain conversational continuityPersonalize future interactions
Storage conceptOften managed through graph state/checkpointingA separate memory store, organized by namespace
LifecycleUsually tied to a thread/checkpoint policyDesigned to remain available beyond a single thread
Important distinction: long-term memory does not mean “send the entire history to the model.” Retrieve only the relevant facts, otherwise the context can become noisy and expensive.

4. LangGraph store concepts and API

The lesson describes BaseStore as the abstract interface for memory stores. Implementations expose operations for creating, retrieving, searching, updating, and deleting stored items. The examples focus on InMemoryStore for quick experiments and PostgresStore for persistence.

put(namespace, key, value)

Create or write a memory item under a namespace and unique key.

get(namespace, key)

Retrieve one item when its exact key is known.

search(namespace, ...)

Find items within a namespace; with an embedding index and query, search by meaning.

Update / delete

Stores support memory maintenance too. The lesson’s main hands-on examples emphasize write and read/search.

# API shape shown in the lesson
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
namespace = ("users", "U1")

store.put(
    namespace,
    "1",
    {"text": "User prefers Python"}
)

item = store.get(namespace, "1")
items = store.search(namespace)

print(item)
for memory in items:
    print(memory)
This is an illustrative API example based on the lesson. Check the installed LangGraph version for exact imports, return types, and method signatures.

5. Namespaces: folders inside the store

A namespace is a tuple that organizes memory records. The lesson compares the store to Google Drive: the store is the drive and the namespace is a folder path.

Separate namespaces keep one user’s memories separate from another user’s memories.
# Tuple path: each element is one level of the namespace
user_id = "U1"
namespace = ("users", user_id, "details")

store.put(namespace, "name", {"text": "Nitesh"})
store.put(namespace, "language", {"text": "Prefers Python"})

Design rule: derive the namespace from authenticated application identity, not from untrusted user-supplied text. This helps prevent one user’s memory from leaking into another user’s conversation.

6. Semantic search: retrieve by meaning

get is useful when the exact key is known. A namespace-only search can return every memory in that area. But a chatbot often needs only the few facts relevant to the current question.

Semantic search compares the meaning of a query with the meaning of stored memories, commonly using embeddings. For example, the query “What is the user learning?” can match a memory that says “User is learning machine learning,” even when the wording differs.

Without semantic retrieval

Fetch 100 memories and add all of them to the prompt. The model may be distracted, and token usage increases.

With semantic retrieval

Return only the top few relevant memories, such as the 2–3 facts related to a travel plan or learning goal.

# Illustrative semantic-search setup
from langchain_openai import OpenAIEmbeddings
from langgraph.store.memory import InMemoryStore

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

store = InMemoryStore(
    index={
        "embed": embeddings,
        "dims": 1536,
    }
)

namespace = ("users", "U1")
store.put(namespace, "learning", {
    "text": "User is learning machine learning"
})
store.put(namespace, "style", {
    "text": "User prefers step-by-step explanations"
})

matches = store.search(
    namespace,
    query="What is the user currently learning?",
    limit=1
)
for match in matches:
    print(match.value)
Embedding dimensions must match the embedding model and store configuration. Some LangGraph versions use slightly different index configuration or package imports; verify against your installed version.

Key parameters

  • Embedding model: converts text into vectors representing semantic content.
  • Query: the current need expressed in natural language.
  • Limit: how many top matching memories to return.
  • Namespace: constrains search to the intended user or memory category.

7. Read existing memories inside a LangGraph chatbot

The lesson first builds a one-node graph that can use prefilled memories, but cannot yet create new ones. At invocation time, the graph receives a user ID in the config. The node uses it to build the namespace, searches the store, formats retrieved items as text, and inserts that text into the system prompt.

1
Read user identity from config.
configurable.user_id identifies whose memory namespace to read.
2
Retrieve memory records.
Search the namespace. In the first simple version, all records are fetched rather than semantic top-k results.
3
Build a memory context string.
Convert the returned records into a compact text block.
4
Inject into the prompt.
The LLM receives the user’s message plus a system instruction that tells it how to use relevant memories.
# Simplified node logic — adapt imports/types to your LangGraph version
def chat_node(state, config, *, store):
    user_id = config["configurable"]["user_id"]
    namespace = ("users", user_id, "details")

    memories = store.search(namespace)
    memory_text = "\n".join(
        item.value.get("text", str(item.value))
        for item in memories
    )

    system_message = (
        "You are a helpful assistant. Use the following user "
        "memories only when relevant. Do not invent facts.\n"
        f"User memories:\n{memory_text}"
    )

    response = llm.invoke(
        [SystemMessage(content=system_message), *state["messages"]]
    )
    return {"messages": [response]}

The demonstration uses memories such as the user’s name, profession, preference for concise answers, interest in Python examples, and current projects. The model can then personalize tone and examples accordingly.

A system prompt can guide personalization, but it does not guarantee perfect behavior. Treat memories as contextual hints, resolve conflicts carefully, and never let stored text override security or system instructions.

8. Extract new memories from user messages

The next workflow is a remember node. It is not a full chatbot by itself: its job is to inspect the latest user message, decide whether anything is worth remembering, and write extracted facts to the store.

The extractor makes a structured decision before anything is saved.

The lesson uses a structured output schema (with Pydantic) to constrain the extractor’s response. The initial version returns a boolean decision and a list of memory strings.

from pydantic import BaseModel, Field

class MemoryDecision(BaseModel):
    should_write: bool = Field(
        description="Whether the message contains durable, useful information"
    )
    memories: list[str] = Field(
        description="Short factual memories extracted from the message"
    )

# Conceptual extractor usage:
decision = extractor_llm.with_structured_output(
    MemoryDecision
).invoke([
    SystemMessage(content=memory_extraction_prompt),
    HumanMessage(content=latest_user_message),
])

if decision.should_write:
    for i, memory_text in enumerate(decision.memories):
        store.put(
            namespace,
            f"memory-{i}",
            {"text": memory_text}
        )

Examples that may be worth storing: “My name is Nitesh,” “I teach AI on YouTube,” or “My favorite programming language is Python.” A one-off request such as “Explain generative AI simply” usually does not need to become a long-term memory.

The key-generation snippet above is intentionally simplified. In a real application, avoid reusing fixed keys in a way that overwrites unrelated facts; use stable IDs, update logic, or a deliberate memory schema.

9. Prevent duplicate memories

The first extraction implementation has a major flaw: repeating the same message can create duplicate records. The lesson’s improvement gives the extractor both the latest message and existing memories, then asks it to label each extracted fact as new or already known.

FieldMeaningAction
textThe concise fact extracted from the messageCandidate memory
is_new = trueThe fact adds information not already presentWrite it
is_new = falseThe fact duplicates an existing memorySkip it
class MemoryItem(BaseModel):
    text: str
    is_new: bool

class MemoryDecision(BaseModel):
    should_write: bool
    memories: list[MemoryItem]

# Existing memories should be supplied to the extractor prompt.
# Then only new items are written:
if decision.should_write:
    for memory in decision.memories:
        if memory.is_new:
            save_new_memory(memory.text)

The lesson recommends atomic, factual memories and avoiding speculation. The model-based duplicate check is a useful first layer, but production systems may also need normalized text comparison, stable identifiers, update/merge rules, or semantic similarity checks.

10. Combined workflow: remember + chat

The full chatbot combines the two flows in sequence:

  1. Remember node: inspect the latest user message, extract useful facts, check existing memories, and save only new facts.
  2. Chat node: retrieve relevant memories and use them to personalize the response.
  3. End: return the assistant response.
Separation of responsibility: the remember node writes memories; the chat node reads memories. Keeping these tasks distinct makes the workflow easier to reason about and test.

The demonstration’s behavior: after the user says their name and that they teach AI on YouTube, those facts are stored. When the user later asks for a simple explanation of generative AI, the answer can use their name, bullet points, and relevant examples. A generic question does not automatically create another memory.

11. Persistent storage with PostgreSQL

InMemoryStore stores data in RAM. It is useful for learning and prototypes, but memory disappears when the process/kernel restarts. The lesson replaces it with PostgresStore, using a PostgreSQL database running locally through Docker.

In-memory store

Prototype

  • Quick setup
  • Useful for testing
  • Volatile across restarts

PostgreSQL store

Persistent backend

  • Data survives process restarts
  • Appropriate when persistence is required
  • Requires database setup and operations

Docker setup sequence from the lesson

  1. Install Docker Desktop and start it.
  2. Check that Docker is available with docker --version.
  3. Run the PostgreSQL container command provided by the project/lesson.
  4. Confirm the container is running with docker ps.
  5. Install the PostgreSQL store dependencies and configure the database connection URL.
  6. Initialize the store using the supported context-manager/setup pattern for the installed LangGraph version.
  7. Run the combined remember/chat workflow, then restart the kernel/process and query the store again.

Conceptually, the graph is compiled with the persistent store supplied to it, and the same namespace and read/write logic can continue to be used. The lesson verifies persistence by restarting the kernel and confirming that previously saved facts remain available.

Connection details matter: use the exact host, port, database, username, password, and connection options configured for your PostgreSQL container. Do not commit credentials to source control. Package names and setup methods can vary by version; follow the compatible LangGraph/Postgres integration instructions for your environment.

Production notes

  • Use authenticated user IDs and strict namespace boundaries.
  • Set retention and deletion rules for user data.
  • Handle stale, contradictory, or corrected facts instead of only appending.
  • Monitor database connections, latency, failures, and store size.
  • Request consent where appropriate and avoid storing sensitive facts unnecessarily.

The lesson also names Redis as another possible persistent store option, alongside PostgreSQL.

12. End-to-end implementation outline

The following is a teaching skeleton that connects the concepts. It is not a drop-in replacement for the lesson notebook: graph-state types, model initialization, PostgreSQL setup, and exact store APIs should be adapted to the versions in your environment.

# PSEUDOCODE / IMPLEMENTATION OUTLINE
# 1. Create a store (InMemoryStore for local experiments;
#    a configured PostgresStore for persistence).
# 2. Define a memory extractor with structured output.
# 3. Define a remember node:
#    - get user_id from config
#    - construct namespace = ("users", user_id, "details")
#    - load existing memories
#    - extract atomic facts from the latest user message
#    - skip duplicates; write genuinely new facts
# 4. Define a chat node:
#    - use user_id to construct the same namespace
#    - retrieve relevant memories (semantic search where configured)
#    - place compact memory context in the system prompt
#    - invoke the chat LLM with current conversation messages
# 5. Build graph: START -> remember -> chat -> END
# 6. Compile graph with the store.
# 7. Invoke with configurable user_id and a user message.
# 8. Restart the app and verify stored memories still exist
#    when using a persistent backend.

Recommended prompt rules for a memory extractor

  • Store only information likely to help in future conversations.
  • Represent each memory as one short, factual statement.
  • Do not infer unstated details.
  • Compare extracted facts with existing memories.
  • Mark genuinely new facts and avoid duplicates.
  • Prefer updating a corrected fact over keeping conflicting versions forever.

13. Common pitfalls and practical safeguards

PitfallWhy it mattersSafeguard
Using in-memory storage in productionMemories vanish on restartUse a persistent backend such as PostgreSQL or Redis
Injecting every memory into the promptNoise, extra tokens, less relevant answersUse semantic retrieval and a small top-k limit
Duplicate writesStore fills with redundant factsDeduplicate and define update/merge behavior
Mixing user namespacesPrivacy breach across usersUse authenticated IDs and test isolation
Saving transient or speculative detailsMemory becomes inaccurate or unhelpfulExtract only useful, user-stated facts
Never updating old factsOutdated preferences/plans persistSupport edits, expiry, confidence and deletion
Trusting memory as instructionsStored content may be stale or adversarialTreat it as data, not as privileged instructions

14. Plan of action: how to learn and implement

1
Explore the store API.
Create an InMemoryStore, make namespaces for two users, write a few items with put, retrieve one with get, and list items with search.
2
Practice namespace design.
Try paths such as ("users", user_id, "profile") and ("users", user_id, "preferences"). Confirm that U1 cannot read U2’s data.
3
Add semantic search.
Configure a compatible embedding model and index. Test queries whose wording differs from the stored memory, then adjust the result limit.
4
Build a read-only memory chatbot.
Prefill sample memories, retrieve them in the chat node, and observe how prompt context changes the answer.
5
Add the remember node.
Use structured output to extract facts from the latest user message. Test both memory-worthy and ordinary requests.
6
Prevent duplicates and support updates.
Repeat the same messages and verify the store does not grow with duplicates. Then test a changed preference and define whether to update or retain history.
7
Combine remember and chat.
Build START → remember → chat → END. Confirm newly stored facts can be used in the response flow.
8
Switch to persistent storage.
Set up PostgreSQL locally, configure the persistent store, restart the process, and verify that memories remain.
9
Harden for production.
Add access controls, observability, data deletion, retention, error handling, and tests for stale or conflicting memories.

Hands-on checklist

  • Two users have isolated memory namespaces.
  • put, get, and search behave as expected.
  • Semantic retrieval returns relevant memories rather than the entire store.
  • Non-memory-worthy messages do not create records.
  • Repeated messages do not create duplicates.
  • New memories influence later answers when relevant.
  • Persistent backend retains memories after restart.
  • Users can correct or delete stored information.
