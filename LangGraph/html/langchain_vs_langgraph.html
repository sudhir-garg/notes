LangGraph vs LangChain: Why LangGraph Exists

A deep, example-driven explanation of why linear LLM chains become difficult to maintain when a workflow needs branching, loops, persistent state, events, recovery, human approvals, nested workflows, and production observability.

Stateful workflows Conditional routing Long-running execution Human-in-the-loop Subgraphs Fault recovery

1. The Big Picture

The central question of this lesson is not simply “What is LangGraph?” It is “Why did LangGraph become necessary when LangChain already existed?”

The lecture begins by shifting from the conceptual study of agentic AI toward the practical problem of building agentic applications. The key observation is that a serious agentic application is often much more than a single prompt → model → response pipeline. Once the system has to make decisions, loop, pause, remember progress, wait for external events, recover from failures, or ask a human for approval, orchestration becomes the hard part.

Core intuition: LangChain excels at composing components; LangGraph is introduced as a graph-based orchestration model for complex workflows.

2. LangChain Recap

The lecture defines LangChain as an open-source library intended to simplify the construction of LLM-based applications. Its main value comes from reusable, modular building blocks.

Model

Unified model interface

Interact with different model providers through a common abstraction, reducing provider-specific application code.

Prompt

Prompt engineering

Templates and prompt components help structure the instructions sent to models.

Retriever

Knowledge retrieval

Retrieve relevant documents from vector stores or other knowledge sources for RAG-style applications.

Chain

The important orchestration abstraction

A chain connects components so that the output of one component becomes the input to the next. This is particularly natural for sequential workflows.

prompt → model → parser

Good fits for LangChain

3. The Automated Hiring Workflow

The lecture uses an automated hiring scenario as the stress test. This is intentionally more complex than a normal prompt chain.

A conceptual rendering of the lecture's automated hiring example. The important property is not the domain; it is the non-linear, long-running orchestration.

Workflow steps

  1. Receive a hiring request, such as hiring a remote backend engineer with a specified experience range.
  2. Use an LLM to generate a job description.
  3. Ask a human supervisor to approve or request changes.
  4. Post the approved JD using external job-platform tools/APIs.
  5. Wait and monitor applications.
  6. If the application count is below the threshold, modify the JD, wait again, and re-check.
  7. Once enough candidates apply, parse and score resumes and shortlist candidates.
  8. Use calendar/email integrations to schedule interviews.
  9. Conduct interviews and determine selection outcomes.
  10. Send regret emails or generate and send offers.
  11. If an offer is rejected, allow negotiation and issue a revised offer.
  12. When accepted, trigger onboarding actions such as HR-system updates, welcome email, knowledge-transfer scheduling, and equipment provisioning.

4. Workflow vs Agent: A Critical Distinction

Predefined workflow

The developer decides the execution path in advance. If you run it repeatedly, the control flow is essentially the same unless explicit conditions route it elsewhere.

Think: developer-authored flowchart.

Agent

The system uses an LLM to dynamically decide what steps to take and which tools to use to accomplish the task.

Think: the system determines its path at runtime.

Key mental modelThe hiring diagram in this lesson is initially a workflow, not an agent. The lecture uses it as a concrete way to expose the orchestration problems that LangGraph is designed to address.

5. Challenge 1 — Control-Flow Complexity

A conventional chain naturally expresses a mostly linear path. The hiring workflow is non-linear because it contains conditional branches, loops, and jumps/backward transitions.

ConstructHiring exampleWhy it matters
Conditional branchEnough applications → continue; otherwise modify JD.Execution can move down different paths.
LoopKeep modifying and monitoring the JD until enough applications arrive.The same nodes may execute repeatedly.
Backward jumpRejected JD → return to JD generation.Control does not only move forward.

What happens if you force this into a chain?

You end up writing Python control logic around the chain. The lecture calls this glue code: custom code needed to stitch framework components together into the desired workflow.

# Illustrative LangChain-style orchestration

approved = False

while not approved:
    jd = jd_chain.invoke({"hiring_request": request})
    approved = get_human_approval(jd)

post_jd(jd)

The problem is not that Python loops are impossible. The problem is that as the workflow grows, the orchestration logic becomes scattered across application code, making the overall execution graph harder to maintain and reason about.

LangGraph's core ideaRepresent the workflow directly as a graph: tasks become nodes, and control-flow relationships become edges. Conditional edges can route execution, including back to earlier nodes.

6. Challenge 2 — State Handling

Complex workflows need more than a sequence of messages. They need a structured representation of the workflow's current situation.

What belongs in hiring-workflow state?

JD

Current job description.

Approval

Whether the JD has been approved.

Posting

Whether the JD has been posted.

Applications

Current application count.

Threshold

Minimum applications required.

Candidates

Shortlisted candidates and contact details.

Offers

Offer information and status.

Onboarding

Current onboarding status.

Progress

Where the workflow currently is.

State is the evolving set of key-value data that describes the current workflow situation.

Why a dedicated graph state helps

The lecture contrasts conversational memory with workflow state. A complex workflow needs structured fields whose values change as nodes execute. LangGraph exposes a shared state object to nodes; nodes read the current state and return updates to it.

Do not interpret that as saying LangChain can never store any information; the lecture itself discusses conversational memory. The distinction is about persistent, structured workflow state and execution context.

7. Challenge 3 — Event-Driven Execution

A sequential chain normally runs from one step to the next. Complex workflows often need to pause and wait for an external event before continuing.

Sequential

Start → Step A → Step B → Step C → finish.

The next step follows immediately after the previous step completes.

Event-driven

Start → Step A → pause → external event → resume → Step B.

The continuation is triggered later.

EventPause pointResume trigger
Application monitoringAfter posting JDSeven days have elapsed.
JD modificationAfter changing JDMonitoring window completes.
Offer decisionAfter sending offerCandidate accepts/rejects.

Why this creates glue code in a chain

With a chain-based design, the lecture's approach is to split the workflow into separate chains and write external code that tracks time/events and transfers state from one chain to the next. That increases orchestration complexity.

LangGraph's approachBecause graph execution is stateful, the current state can be persisted at a checkpoint, the workflow can pause, and a later event can resume execution from the saved context.

8. Challenge 4 — Fault Tolerance

Long-running workflows have more opportunities for failure. The lecture distinguishes between local failures and larger system failures.

Small / node-level fault

Example: the job-platform API is temporarily unavailable when posting the JD.

Desired behavior: retry the failed operation rather than restart everything.

Large / system-level fault

Example: the server or container hosting the workflow goes down.

Desired behavior: restore the saved workflow context and continue from the appropriate point.

Checkpointing intuition

The lecture explains that LangGraph can create checkpoints after node execution and persist the workflow state. If the system later fails, execution can resume using the previously saved state instead of replaying the entire workflow from the beginning.

9. Challenge 5 — Human in the Loop

Real-world systems often should not have unrestricted autonomy. A human may need to approve a high-impact or risky action.

Hiring example

After the LLM creates a JD, a human supervisor can approve it. The system should not continue until the human makes the decision.

Generate JDLLM node
→
Pauseawait human
→
Approvalyes / revise
→
Continueresume state

A short-lived input request can be implemented in many application designs. The difficult case is a long-lived approval—for example, when a manager may take a day to respond. Holding a synchronous chain open for that period is undesirable.

LangGraph's modelThe lecture presents human-in-the-loop as a first-class capability: persist the graph state at the pause point, wait for human input, and resume from the saved context later.

Useful analogy: a video game save point. If you stop playing at stage 3 today, you save progress and continue from stage 3 tomorrow. The lecture uses essentially this intuition for workflow execution.

10. Nested Workflows and Subgraphs

LangGraph can represent a workflow as a graph and then use another graph as a node inside a larger graph. This is the idea of a subgraph.

A subgraph encapsulates a complex workflow and exposes it as a node in a parent workflow.

Why this matters

Multi-agent systems

A larger orchestration graph can coordinate multiple specialized agent graphs. The lecture uses a self-driving-car analogy: separate capabilities can be modeled as cooperating components under higher-level coordination.

Reusability

A reusable workflow such as an approval process can be embedded at multiple points in a larger application rather than reimplemented each time.

11. Observability

Observability is the ability to monitor, debug, and understand what a workflow is doing at runtime. It becomes especially important in production, where unexpected decisions or failures need to be investigated.

Why observe?

  • Understand execution paths.
  • Debug failures.
  • Audit decisions.
  • Inspect model inputs and outputs.
  • Investigate unexpected tool usage.

What the lecture highlights

LangSmith can record LLM calls, prompts, responses, token information, latency, and execution traces. The challenge described is that glue code around a chain is outside the chain's native execution structure.

Lecture's key distinctionIf a complex LangChain workflow relies heavily on custom glue code, the observability picture can become partial because the orchestration logic is spread outside the chain. The lecture presents LangGraph's explicit graph/state execution as making the workflow timeline easier to trace.

12.2 Graph-based workflow

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class HiringState(TypedDict, total=False):
    hiring_request: str
    jd: str
    jd_approved: bool
    jd_posted: bool

def create_jd(state: HiringState):
    jd = generate_jd(state["hiring_request"])
    return {"jd": jd}

def check_approval(state: HiringState):
    approved = human_approval(state["jd"])
    return {"jd_approved": approved}

def post_jd(state: HiringState):
    publish_job(state["jd"])
    return {"jd_posted": True}

def route_after_approval(state: HiringState):
    return "post_jd" if state["jd_approved"] else "create_jd"

builder = StateGraph(HiringState)

builder.add_node("create_jd", create_jd)
builder.add_node("check_approval", check_approval)
builder.add_node("post_jd", post_jd)

builder.add_edge(START, "create_jd")
builder.add_edge("create_jd", "check_approval")

builder.add_conditional_edges(
    "check_approval",
    route_after_approval,
    {
        "post_jd": "post_jd",
        "create_jd": "create_jd",
    },
)

builder.add_edge("post_jd", END)

graph = builder.compile()
What changed?The branching and loop are represented as graph structure rather than as a large external while/if orchestration layer.

14. When Should You Use What?

Choose LangChain

When the workflow is simple and mostly linear

  • Prompt → model → parser.
  • Summarization pipeline.
  • Basic RAG system.
  • Simple conversational flow.
  • Small tool-enabled workflow.
Choose LangGraph

When orchestration is the hard problem

  • Conditional branches.
  • Loops and backward transitions.
  • Structured, evolving workflow state.
  • Long-running or asynchronous execution.
  • Human-in-the-loop approvals.
  • Retry and recovery requirements.
  • Nested workflows / multi-agent coordination.
  • Detailed execution tracing.

A practical decision test

  1. Can I draw the whole execution as one straight line? If yes, a chain may be enough.
  2. Do I need to branch based on state? Consider graph orchestration.
  3. Do I need to revisit an earlier step? Graphs become more natural.
  4. Can the workflow pause for hours/days? Prefer a stateful, resumable orchestration model.
  5. Can the process fail after running for a long time? Plan for persistence and recovery.
  6. Does a human need to approve something? Design an explicit pause/resume boundary.
  7. Do I have a workflow inside another workflow? Consider subgraphs.

15. Interview & Revision Notes

Q1. What is LangGraph?

In the lecture's framing, LangGraph is an orchestration framework for building stateful, multi-step, event-driven workflows using LLMs. It models workflow steps as nodes and transitions/control flow as edges.

Q2. Why was LangGraph needed if LangChain already existed?

LangChain's chain abstraction is especially natural for linear composition. Complex agentic workflows introduce branching, loops, structured state, pauses, external events, failure recovery, human approval, nested workflows, and richer runtime tracing. LangGraph provides a graph-oriented orchestration model for those requirements.

Q3. What is glue code?

Custom application code written around framework components to implement orchestration logic that the framework abstraction does not directly express. In the lecture's example, Python loops and control logic around LangChain chains become glue code.

Q4. What is workflow state?

The collection of evolving data values needed to understand the current condition of a workflow and determine what should happen next—for example JD content, approval status, application count, shortlisted candidates, offer status, and onboarding status.

Q5. What is event-driven execution?

Execution that pauses until an external event occurs and then resumes. Examples include waiting seven days before checking applications or waiting for a candidate's offer response.

Q6. What is fault tolerance?

The ability of a system to continue or recover after failures. The lecture discusses retrying node-level failures and recovering from larger system failures using persisted execution state.

Q7. What is human-in-the-loop?

A workflow design in which a human participates in a decision at a defined point. The workflow can pause, wait for the human, and continue after receiving the decision.

Q8. What is a subgraph?

A graph used as a node inside another graph. This enables encapsulation, nested workflows, reusable workflow components, and multi-agent architectures.

Q9. Is LangGraph a replacement for LangChain?

No. The lecture explicitly says the two work together. LangChain provides many reusable LLM/application components; LangGraph is used to orchestrate those components in more complex workflows.

Q10. What is the simplest mental model?

LangChain helps you build the pieces and simple chains.
LangGraph helps you orchestrate those pieces when the workflow becomes stateful and non-linear.

One-line memory hookLinear chain → compose. Complex graph → orchestrate.
