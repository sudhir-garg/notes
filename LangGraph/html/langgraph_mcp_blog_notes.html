2. Why direct tool integrations become brittle

In a direct integration, the chatbot contains code for calling a service API, authenticating, building requests, parsing the response, and exposing the result to the model as a tool.

Example: a custom GitHub pull-request tool

A sample tool might accept a repository owner, repository name or URL, pull-request state (open or closed), and a result limit. It then calls the GitHub API, parses the JSON response, and displays fields such as PR number, title, author, state, and URL.

What happens when an API changes?

If an API version changes its endpoint or response schema—for example, a field is renamed—the tool may fail until the application code is updated. The video uses a hypothetical API v1-to-v2 change to illustrate this maintenance risk.

  • One service may require several custom tools for different operations.
  • Several chatbots may duplicate similar integration code.
  • Adding more services multiplies the places where changes may be needed.
Maintenance pattern: with n tools and m chatbot applications, duplicated integrations can create an n × m maintenance burden. This is an illustrative model, not a universal complexity formula.

3. MCP: a standardized connection layer

Model Context Protocol (MCP) provides a standard interface for applications to connect to servers that expose tools and other capabilities. In the lesson’s simplified framing, the chatbot is the client, and the system that exposes the tools is the server.

Client responsibilities
  • Configure server connections
  • Connect using a suitable transport
  • Discover available tools
  • Make tools available to the LLM
Server responsibilities
  • Implement tools and their schemas
  • Handle service-specific logic
  • Communicate with the underlying API or data source
  • Expose available capabilities over MCP
Core benefit: the chatbot can often keep the same connection configuration while server-side tool implementations evolve, provided the server endpoint and protocol contract remain compatible.

Important nuance: MCP does not magically eliminate all maintenance. Breaking changes to server addresses, transport, authentication, protocol compatibility, or tool contracts can still require client-side updates.

4. Why asynchronous programming enters the picture

The lesson’s MCP client library is used in async mode. The original chatbot was synchronous, so the first migration step is to convert the relevant LangGraph execution path to asynchronous code.

ConceptSynchronous styleAsynchronous style
Functiondef node(...):async def node(...):
LLM callllm.invoke(...)await llm.ainvoke(...)
Graph executiongraph.invoke(...)await graph.ainvoke(...)
Entry pointNormal function callasyncio.run(main())

Async concepts to remember

  • async def defines a coroutine function.
  • await yields control while awaiting an async operation.
  • Use async-compatible methods such as ainvoke when available.
  • For independent I/O tasks, concurrency can be coordinated with tools such as asyncio.gather.
Do not overgeneralize: async is not synonymous with CPU parallelism. It mainly helps applications handle waiting efficiently. The lesson converts to async because the MCP client path requires it, not because every chatbot must always be async.

5. Converting the LangGraph chatbot to async

The lesson keeps the existing graph structure—state, chat node, tool node, edges, and conditional routing—but changes the custom node and invocation path to async.

Illustrative conversion pattern

import asyncio
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.prebuilt import ToolNode

class State(TypedDict):
    messages: list

async def chat_node(state: State):
    # Use the async LLM method
    response = await llm_with_tools.ainvoke(state["messages"])
    return {"messages": [response]}

def build_graph():
    builder = StateGraph(State)
    builder.add_node("chat", chat_node)
    builder.add_node("tools", ToolNode(tools))

    builder.add_edge(START, "chat")
    builder.add_conditional_edges("chat", route_after_chat)
    builder.add_edge("tools", "chat")
    return builder.compile()

async def main():
    graph = build_graph()
    result = await graph.ainvoke({
        "messages": [{"role": "user", "content": "Calculate 17 % 5"}]
    })
    print(result)

if __name__ == "__main__":
    asyncio.run(main())

This is a teaching template, not a copy of the complete original project. The exact message types, routing function, imports, and tool binding depend on the project’s LangChain/LangGraph versions.

What changed?

  1. The custom chat node becomes async def.
  2. The LLM call changes from invoke to await ...ainvoke(...).
  3. The graph is invoked with await graph.ainvoke(...).
  4. The async entry point is started using asyncio.run(main()).

The lesson notes that LangGraph’s prebuilt tool node already supports asynchronous execution, so the custom chat node is the main node requiring an explicit conversion in this example.

6. Building an MCP client in LangGraph

The lesson uses MultiServerMCPClient from langchain-mcp-adapters. It can connect to one or more MCP servers and return their tools so they can be bound to the LLM.

Install the adapter

# pip
pip install langchain-mcp-adapters

# or, when using uv
uv add langchain-mcp-adapters

Basic client configuration

from langchain_mcp_adapters.client import MultiServerMCPClient

client = MultiServerMCPClient({
    "math": {
        "command": "python",
        "args": ["/absolute/path/to/math_server.py"],
        "transport": "stdio",
    }
})

Here, math is a local server configuration name. The process command and arguments tell the client how to launch the server. For a local process, the lesson uses the stdio transport.

Discover tools and bind them to the model

async def build_graph():
    # Ask the MCP client for the tools exposed by configured servers
    mcp_tools = await client.get_tools()

    # Existing tools can be retained and combined with MCP tools
    all_tools = [*existing_tools, *mcp_tools]
    llm_with_tools = llm.bind_tools(all_tools)

    # Build and compile the LangGraph workflow using all_tools
    # ...
    return graph
Key idea: the model sees tool descriptions and schemas returned by the server. The chatbot does not need to reimplement every server operation as a separate local Python function.

API details can vary by package version. Check the installed version’s documentation for client lifecycle, transport configuration, and whether context-manager handling is recommended for your use case.

7. Example A — connect a local math MCP server

The demo server exposes several mathematical operations as separate tools: addition, subtraction, multiplication, division, power, and modulus. The server is located on the developer’s own machine and is launched as a subprocess, so stdio is used.

After discovery, the returned math tools are included in the list bound to the LLM. The chatbot can then answer a request such as “calculate the remainder of 29 divided by 7” by selecting the modulus tool and presenting the result.

Configuration checklist

  • Use the correct Python executable or environment.
  • Use an absolute server file path where practical.
  • Make sure the server process starts successfully and writes protocol traffic correctly over standard I/O.
  • Inspect the discovered tool list during development.

Illustrative interaction

User: "Add an expense of ₹500 for an online course on 10 November."
Assistant: selects the expense-creation tool exposed by the MCP server.
Server: validates and stores the expense.
Assistant: reports the result returned by the server.

The lesson’s demo reports that the expense was added and then retrieved for the requested November date range. It emphasizes that the chatbot code did not contain new expense-tracking functions; the MCP server supplied those capabilities.

Why this matters: adding another compatible MCP server can expand the chatbot’s capabilities mainly through configuration and tool discovery rather than duplicating API integration code inside the client.

9. Integrating MCP into the existing chatbot

The final demo combines MCP tools with existing non-MCP tools. MCP does not require an all-or-nothing migration.

High-level integration steps

  1. Keep the existing search and stock-price tools.
  2. Create one MCP client configuration for the local math server.
  3. Create another configuration for the remote expense server.
  4. Fetch the tools from the configured MCP servers asynchronously.
  5. Merge MCP tools with existing tools and bind the combined list to the LLM.
  6. Keep the LangGraph tool-routing pattern, ensuring the graph’s tool node receives the combined list.

Async changes in the demo application

The video describes four major components: LangGraph, the MCP client, Streamlit, and SQLite. The MCP client path is asynchronous; LangGraph supports sync and async execution; SQLite and Streamlit were treated as synchronous in the described setup.

The presenter suggests a production architecture using FastAPI to expose an API and a React or Next.js frontend for a more natural async interaction model.

10. Production considerations and practical cautions

Do not assume every server is trustworthy

  • Only connect to MCP servers you trust and understand.
  • Protect credentials and tokens; use environment-based secrets or a secret manager rather than hard-coding them.
  • Review what each tool can read or modify, especially tools that write data or trigger external actions.
  • Apply authorization, validation, timeouts, error handling, and logging at the appropriate boundaries.

Tool discovery is not the same as permission

A tool appearing in the discovered tool list does not mean every user should be authorized to invoke it. Enforce permissions in the server or service boundary and design confirmation steps for consequential actions.

Be explicit about local versus remote transport

Server type in this lessonTransport shownConfiguration idea
Local processstdioLaunch a command with arguments and communicate through standard input/output.
Remote serviceStreamable HTTPConnect to the deployed server URL using the supported HTTP transport.

Keep the abstraction boundary healthy

MCP reduces duplicated client-side integration code, but it does not remove the need to version APIs, monitor server health, manage authentication, or test tool schemas. Prefer stable server endpoints and backward-compatible tool changes when possible.

11. Checklist and key takeaways

1
Understand the maintenance problem.
Hand-written integrations couple application code to service endpoints and response schemas.
2
Separate client and server responsibilities.
The server implements capabilities; the client connects and discovers the available tools.
3
Convert the required execution path to async.
Use async nodes, async LLM calls, and async graph invocation when the chosen client requires them.
4
Discover MCP tools dynamically.
Fetch the tools from configured servers and bind them to the LLM.
5
Support multiple servers.
A single multi-server client can be configured for a local math server and a remote expense server.
6
Use a hybrid tool strategy when useful.
Existing custom tools and MCP tools can coexist in the same LangGraph application.
7
Plan for production behavior.
Handle authentication, permissions, async database access, frontend compatibility, failures, and monitoring.
One-sentence summary: MCP lets a LangGraph application consume capabilities exposed by separate servers through a standard client interface, reducing duplicated tool-integration code and making it easier to extend a chatbot with new tools.
