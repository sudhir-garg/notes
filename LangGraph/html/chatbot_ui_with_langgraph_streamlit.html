Build a LangGraph Chatbot UI with Streamlit

A complete, blog-style guide to separating a chatbot into a LangGraph backend and a Streamlit frontend, preserving conversation history with session state, and connecting user messages to the graph.

1. Overview: what are we building?

The starting point is a working LangGraph chatbot that accepts messages in a notebook or terminal. The missing piece is a user interface. We will place a clean web chat UI in front of the existing graph using Streamlit.

The interface displays user and assistant messages with distinct roles, provides a chat input at the bottom, scrolls as the conversation grows, and keeps earlier messages visible. The backend remains responsible for AI responses and graph execution.

Goal: a user types a message in the browser → Streamlit sends it to LangGraph → LangGraph returns an assistant response → Streamlit displays and stores that response.

Prerequisites

  • Basic Python: functions, lists, dictionaries, imports.
  • Basic Streamlit: running a Python app and displaying components.
  • Basic LangGraph: graph state, nodes, compilation, and invocation.
  • An API key for the model provider used by your backend.

2. Application architecture

Separate the application into two modules. This keeps UI code out of the graph logic and makes the backend easier to test or reuse in another interface.

Figure 1. Request and response flow between the UI and the graph.

4. The two core Streamlit chat components

st.chat_message()

Creates a message container styled for a role such as "user" or "assistant". Put text, Markdown, tables, or other Streamlit elements inside it.

with st.chat_message("user"):
    st.write("Hi!")

with st.chat_message("assistant"):
    st.write("Hello! How can I help?")

st.chat_input()

Creates a chat-oriented input box. When the user submits text, the returned value contains that text; otherwise it is usually None.

user_input = st.chat_input("Type here...")

if user_input:
    with st.chat_message("user"):
        st.write(user_input)

The role controls the message identity and default avatar. The content is what appears inside the message bubble. You can customize avatars with the avatar parameter if desired.

Why the simple echo demo is useful

Before connecting an LLM, echoing the user's input back as the assistant is a good way to test the UI and conversation-history logic independently from model or API issues.

5. Preserve conversation history with Session State

Streamlit reruns the script from top to bottom after many interactions, including submitting chat input. A normal variable such as message_history = [] is recreated on each rerun, so older messages disappear.

Figure 2. Session State keeps UI data between reruns in the same user session.

Initialize the history only if the key does not already exist:

import streamlit as st

if "message_history" not in st.session_state:
    st.session_state.message_history = []

Each history item is a dictionary with a role and content. The list preserves message order.

{
    "role": "user",
    "content": "What is the capital of India?"
}

Render the saved history first, then collect the next input:

for message in st.session_state.message_history:
    with st.chat_message(message["role"]):
        st.write(message["content"])

user_input = st.chat_input("Ask me anything...")

if user_input:
    st.session_state.message_history.append({
        "role": "user",
        "content": user_input
    })

    # In an echo-only demo, the assistant repeats the input.
    assistant_response = user_input

    st.session_state.message_history.append({
        "role": "assistant",
        "content": assistant_response
    })

    st.rerun()
Important distinction: Streamlit Session State is UI-session memory. It is not automatically the same as LangGraph's checkpointed conversation memory. Session State typically lasts for a browser session and can be lost on a full reload or new session. LangGraph persistence is managed separately by the graph checkpointer and thread ID.

6. LangGraph backend: a clean, reusable module

The backend from the earlier chatbot lesson can be reused. The key idea is to compile the graph once and expose the compiled object for the frontend to import. Below is a representative example; adapt the model and graph details to match your existing implementation.

# langgraph_backend.py
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv

load_dotenv()

class ChatState(TypedDict):
    messages: Annotated[list, add_messages]

llm = ChatOpenAI(model="gpt-4o-mini")

def chat_node(state: ChatState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(ChatState)
builder.add_node("chat", chat_node)
builder.add_edge(START, "chat")
builder.add_edge("chat", END)

# In-memory checkpointing is useful for development.
checkpointer = MemorySaver()
chatbot = builder.compile(checkpointer=checkpointer)

This example uses LangGraph's message reducer so new messages are appended/merged into the state correctly. If you already have a backend from an earlier lesson, keep your existing state and nodes rather than duplicating them unnecessarily.

What each backend part does

  • State: defines the data moving through the graph, here a list of messages.
  • Node: calls the language model and returns its response as a new message.
  • Edges: define the execution path from START through the chat node to END.
  • Checkpointer: saves graph state per thread so follow-up turns can reuse earlier context.
  • Compiled graph: the chatbot object imported by the frontend.
Model compatibility: the code above is a reference implementation, not a guarantee that every pre-existing backend has the same state schema. The frontend's input payload must match the backend's expected state keys and message format.

7. Connect Streamlit to LangGraph

The frontend has five responsibilities: import the compiled graph, initialize session state, render existing messages, accept the new user input, invoke the graph with a stable thread ID, and save/render the assistant response.

# streamlit_frontend.py
import streamlit as st
from langchain_core.messages import HumanMessage
from langgraph_backend import chatbot

st.set_page_config(page_title="LangGraph Chatbot", page_icon="💬")
st.title("💬 My LangGraph Chatbot")

# UI-level history
if "message_history" not in st.session_state:
    st.session_state.message_history = []

# Graph-level conversation identity
if "thread_id" not in st.session_state:
    st.session_state.thread_id = "thread-1"

config = {
    "configurable": {
        "thread_id": st.session_state.thread_id
    }
}

# 1. Render earlier turns
for message in st.session_state.message_history:
    with st.chat_message(message["role"]):
        st.markdown(message["content"])

# 2. Get new user input
user_input = st.chat_input("Type your message...")

if user_input:
    # 3. Store and show user message
    st.session_state.message_history.append({
        "role": "user",
        "content": user_input
    })
    with st.chat_message("user"):
        st.markdown(user_input)

    # 4. Invoke LangGraph with a HumanMessage and thread config
    result = chatbot.invoke(
        {"messages": [HumanMessage(content=user_input)]},
        config=config
    )

    # 5. Extract and store the latest assistant message
    assistant_message = result["messages"][-1]
    assistant_text = assistant_message.content

    st.session_state.message_history.append({
        "role": "assistant",
        "content": assistant_text
    })
    with st.chat_message("assistant"):
        st.markdown(assistant_text)

Why pass a thread ID?

If the graph has a checkpointer, the thread ID tells it which saved conversation to resume. Use the same ID for turns belonging to one conversation. Use a different ID for a new conversation or a different user. A hard-coded ID is suitable only for a local demonstration; real applications should create and isolate IDs per user/session.

Message flow

  1. Streamlit receives a plain string from st.chat_input().
  2. The frontend wraps it in HumanMessage(content=user_input).
  3. chatbot.invoke(..., config=config) executes or resumes the graph.
  4. The frontend reads the latest message returned by the graph.
  5. The response is saved to UI history and rendered in an assistant message container.
Do not mix memory systems accidentally. The sample keeps a display history in Streamlit and conversation context in LangGraph. If you store the full history in Session State and also send all of it to a checkpointed graph on every turn, you may duplicate messages. With a checkpointer, commonly send only the new user message and reuse the same thread ID. Match the approach to your backend's state design.

8. Run the app

  1. Save both Python files in the same project folder.
  2. Activate the virtual environment.
  3. Confirm the provider API key is available in the environment or loaded from .env.
  4. Start Streamlit from the project directory:
streamlit run streamlit_frontend.py

Streamlit normally opens the app in your browser. Test a few turns:

  • Say “Hi” and check that both roles render correctly.
  • Tell the bot your name, then ask “What is my name?” to test contextual memory.
  • Ask a factual question and a longer question to test response rendering.
  • Check that earlier turns remain visible after each submission.

9. Troubleshooting checklist

SymptomLikely causeWhat to check
Old messages disappearHistory stored in a normal Python list.Initialize and append to st.session_state.message_history.
Assistant repeats the user's inputThe echo-demo logic is still in place.Replace the echo assignment with a backend invocation and extract the model response.
Graph forgets earlier turnsThread ID changes or checkpointing is not configured.Use a stable thread ID and a checkpointer; verify the graph state schema.
Missing configurable thread IDThe compiled graph expects a checkpoint configuration.Pass {"configurable": {"thread_id": "..."}} to invoke.
Key or authentication errorEnvironment variable is missing or invalid.Check .env, provider variable name, and key validity; never print the secret.
Import errorPackage not installed or file/module name mismatch.Install required dependencies in the active environment and verify filenames.
Duplicate messages in contextFull history is resent while the graph also restores history from its checkpointer.Choose one consistent state-management strategy.

Practical improvements for production

  • Use a unique, authorized thread ID for each conversation.
  • Add error handling around model invocation and show a friendly error message.
  • Consider streaming tokens for a more responsive UI.
  • Use durable checkpoint storage if conversations must survive process restarts.
  • Keep secrets outside source control and validate user input where appropriate.
  • Define a clear retention policy for conversation data.

10. Key takeaways

  • Separation of concerns: LangGraph is the backend; Streamlit is the frontend.
  • st.chat_message(): displays a user or assistant message.
  • st.chat_input(): captures the next user message.
  • st.session_state: preserves UI variables across Streamlit reruns within a session.
  • Checkpointer + thread ID: preserves graph state across turns when configured correctly.
  • chatbot.invoke(): sends the new message into the graph and returns the updated state.
Final mental model: render saved UI messages → read new input → save/show the user turn → invoke LangGraph with the right thread configuration → save/show the assistant turn.
