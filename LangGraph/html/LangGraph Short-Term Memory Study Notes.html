2. Memory Fundamentals: Why an LLM Needs Help

A language model does not automatically retain a conversation between independent API/model calls. Unless earlier messages or an equivalent memory representation are sent again, the next call may not know what was said before.

User turn 1
→
LLM response

A later call containing only “What is my name?” has no earlier name statement to use.

+
Current message
→
LLM

Sending relevant conversation history supplies short-term context.

Conversation buffer

A basic approach is to keep prior user and assistant messages and include them in later model input. In LangGraph, the state commonly contains a message list, and the checkpointer saves snapshots of that state between graph runs.

Short-term vs long-term memory

TypePurposeTypical implementation
Short-term memoryContext for a particular conversation/threadMessage state + checkpointer + thread ID
Long-term memoryInformation intended to be reused across conversations or sessionsStore/search user facts or documents separately, often through a database or vector store
Key idea: A checkpointer saves graph state. A thread ID tells LangGraph which conversation's checkpoint history to load and update.

3. Threads and Checkpointers

  • State: the data flowing through a graph; here, typically the conversation messages.
  • Checkpointer: a component that saves state snapshots at graph supersteps so a later run can continue from saved state.
  • Thread ID: a stable identifier for one conversation. Reuse it to continue that conversation; use a different ID for a separate conversation.

→
Node / model

thread_id = conversation key

If the same thread is used for “My name is Nitesh” and then “What is my name?”, the previous message can be available. If the second call uses a new thread ID, that new thread has no prior conversation history.

4. Minimal Short-Term Memory Example (In-Memory)

The following is an illustrative modern LangGraph pattern. It uses a message-state graph and an in-memory checkpointer. Install the required packages and configure your model credentials before running it.

pip install -U langgraph langchain-openai python-dotenv
import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.memory import InMemorySaver

load_dotenv()
model = ChatOpenAI(model=os.getenv("OPENAI_MODEL", "gpt-4o-mini"))

def call_model(state: MessagesState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(MessagesState)
builder.add_node("chat", call_model)
builder.add_edge(START, "chat")
builder.add_edge("chat", END)

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "thread-1"}}

graph.invoke(
    {"messages": [{"role": "user", "content": "Hi, my name is Nitesh."}]},
    config=config,
)
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What is my name?"}]},
    config=config,
)
print(result["messages"][-1].content)
Important: Exact class names and import paths can vary by LangGraph version. The core pattern is stable: compile with a checkpointer and pass the same configurable.thread_id on every turn. The example above is a teaching template, not a substitute for checking the version-specific API docs.

Try a different thread

other_config = {"configurable": {"thread_id": "thread-2"}}
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What is my name?"}]},
    config=other_config,
)
# This separate thread has no name statement in its history.

Because InMemorySaver stores checkpoints in process memory, state generally disappears when the Python process ends. It is convenient for demos and tests, but not durable persistence.

5. Persistence with PostgreSQL

For an application that must recover conversations after a restart, use a durable checkpointer backend. The lecture demonstrates PostgreSQL running in Docker and a PostgreSQL-backed LangGraph checkpointer.

5.1 Start PostgreSQL using Docker Compose

Create a file named compose.yaml. Choose a strong local password; do not commit real credentials to a public repository.

services:
  postgres:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: langgraph
      POSTGRES_PASSWORD: change-this-local-password
      POSTGRES_DB: langgraph
    ports:
      - "5432:5432"
    volumes:
      - langgraph_pgdata:/var/lib/postgresql/data
volumes:
  langgraph_pgdata:

Start the service and check its status:

docker compose up -d
docker compose ps

5.2 Install the PostgreSQL checkpointer package

pip install -U langgraph langgraph-checkpoint-postgres "psycopg[binary,pool]" langchain-openai python-dotenv

5.3 Compile the graph with a PostgreSQL checkpointer

The connection string below is for the example Docker configuration. Put credentials in environment variables in real projects. The context manager manages the connection/checkpointer lifecycle; setup should be run as required by the installed package's documentation.

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.postgres import PostgresSaver

load_dotenv()
model = ChatOpenAI(model=os.getenv("OPENAI_MODEL", "gpt-4o-mini"))
DB_URI = os.environ["LANGGRAPH_DB_URI"]
# Example value:
# postgresql://langgraph:password@localhost:5432/langgraph

def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("chat", call_model)
builder.add_edge(START, "chat")
builder.add_edge("chat", END)

config = {"configurable": {"thread_id": "thread-1"}}

with PostgresSaver.from_conn_string(DB_URI) as checkpointer:
    checkpointer.setup()  # Initialize checkpoint tables if needed
    graph = builder.compile(checkpointer=checkpointer)

    graph.invoke(
        {"messages": [{"role": "user", "content": "My name is Nitesh."}]},
        config=config,
    )
    result = graph.invoke(
        {"messages": [{"role": "user", "content": "What is my name?"}]},
        config=config,
    )
    print(result["messages"][-1].content)

5.4 Verify persistence

  1. Run the app with thread-1 and send a few messages.
  2. Stop and restart the Python process while leaving the PostgreSQL container and its volume intact.
  3. Recreate the graph with the same database and checkpointer configuration.
  4. Call graph.get_state({"configurable": {"thread_id": "thread-1"}}) to inspect the saved state.
  5. Use thread-2 to verify that conversations remain isolated.
Expected result: The thread's saved graph state can be retrieved after restarting the application, provided the database and its persisted data are still available.
Production note: Durable checkpoints are only one part of production readiness. Add authentication, authorization, connection management, backups, retention policies, secrets management, and monitoring. Do not assume a database checkpoint alone is a complete user-memory strategy.

6. Context Window and Context Overflow

A model's context window limits how much input and generated output it can process in one request. The exact limit depends on the model. A growing conversation may exceed the available budget because both user messages and assistant responses consume tokens.

Old turns
+
Recent turns
+
Current prompt
→
Context budget

If the total is too large, the request may fail, be truncated, or leave too little room for a useful answer.

Blindly attaching every past message to every model call is simple, but it becomes expensive and eventually may not fit. The lesson introduces three complementary operations:

  • Trimming: send only a selected subset of recent messages to the model.
  • Deletion: remove selected messages from graph state.
  • Summarization: compress older conversation history into a concise summary and keep recent turns verbatim.

7. Trimming: Keep Recent Messages Within a Budget

Trimming selects a suffix of the conversation that fits a configured token budget. In the lecture's example, the cap is 150 tokens; that number is only a demonstration and should be tuned to the model and application.

from langchain_core.messages import trim_messages

def call_model(state):
    trimmed = trim_messages(
        state["messages"],
        max_tokens=150,
        strategy="last",
        token_counter=model,  # or a supported token counter
        include_system=True,
        allow_partial=False,
        start_on="human",
    )
    response = model.invoke(trimmed)
    return {"messages": [response]}

Use the supported arguments for the version of LangChain installed. Some environments use a model token counter; others may use a tokenizer or a custom approximate counter. Ensure the retained messages form a valid sequence for the model.

What trimming does — and does not do

  • It creates a smaller list for the current model call.
  • It does not necessarily delete old messages from the graph's stored state.
  • Old facts may become unavailable to the model if they are outside the trimmed subset.
  • A strict budget should leave room for system instructions, tool results, and the model's expected output.
Limitation: If the user's name appeared only in a trimmed-away turn, the model may no longer know it. Trimming trades historical detail for a bounded prompt.

8. Deletion: Remove Messages from State

Deletion differs from trimming. It changes the stored message state rather than merely hiding older messages from a single model invocation. LangGraph's message state supports removal instructions through RemoveMessage.

from langchain_core.messages import RemoveMessage

def delete_old_messages(state):
    messages = state["messages"]
    if len(messages) <= 10:
        return {}

    # Example policy: retain the newest four messages.
    old_messages = messages[:-4]
    return {
        "messages": [
            RemoveMessage(id=message.id)
            for message in old_messages
            if message.id is not None
        ]
    }

Attach this cleanup node after the chat node if that is the desired execution order. Test the policy with alternating user and assistant messages so that you do not accidentally leave an invalid or confusing partial exchange.

Lecture example: once the state contains more than 10 messages, remove the earliest six and retain the newest eight when there are 14 total. The precise retention rule is an application decision.

9. Summarization: Preserve the Meaning of Older Turns

Summarization reduces the history's size while preserving important information. Instead of discarding every old turn, a model summarizes the older section; the application then supplies that summary together with recent messages.

Example policy from the lecture

  • Allow ordinary chat while there are six or fewer messages.
  • When the state exceeds six messages, summarize the older portion.
  • Keep the newest two messages verbatim.
  • Store the updated summary in a dedicated state field.
  • Delete the old messages that have been summarized, avoiding duplicate full history plus summary.

Custom state with a summary field

from typing import Annotated
from typing_extensions import TypedDict
from langgraph.graph.message import add_messages
from langchain_core.messages import AnyMessage

class ChatState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    summary: str

For a real implementation, give summary an appropriate default/optional type and ensure message updates use the reducer semantics your graph expects. Below is the core logic in pseudocode-like Python, intended to make the workflow clear:

def should_summarize(state):
    return len(state["messages"]) > 6

def summarize_old_history(state):
    messages = state["messages"]
    recent = messages[-2:]
    older = messages[:-2]

    old_summary = state.get("summary", "")
    if old_summary:
        prompt = (
            "Update the existing conversation summary using the new messages. "
            "Keep stable facts, user preferences, decisions, and unresolved tasks.\\n\\n"
            f"Existing summary:\\n{old_summary}\\n\\n"
            f"New older messages:\\n{older}"
        )
    else:
        prompt = (
            "Summarize the conversation above. Preserve names, preferences, "
            "decisions, constraints, and open questions.\\n\\n"
            f"{older}"
        )

    new_summary = summary_model.invoke(prompt).content

    # In a real graph, return RemoveMessage(id=...) updates for the
    # old messages and retain the newest two, using the correct reducer.
    return {
        "summary": new_summary,
        # "messages": [RemoveMessage(id=m.id) for m in older]
    }
Implementation detail: The summarization example above isolates the idea; it is not a complete drop-in graph because message deletion must be returned using the correct message reducer and every removed message needs a valid ID. Also ensure that the summary is passed to the chat model as context (for example, a system message) on subsequent turns.

What should a good summary preserve?

  • Stable user facts explicitly shared in the conversation.
  • Goals, preferences, constraints, and decisions.
  • Important technical details or code decisions.
  • Pending questions, commitments, and next steps.
  • Uncertainty: do not turn a guess into a fact.

10. Trimming vs Deletion vs Summarization

TechniqueWhat changes?StrengthTrade-off
TrimmingModel input for a particular callSimple, fast, bounded contextOlder facts may be invisible to the model
DeletionStored graph message stateReduces retained state and checkpoint sizeDeleted details cannot be recovered from that state unless stored elsewhere
SummarizationOlder history is compressed into a summary; old turns can be removedPreserves high-value context over long conversationsSummaries can omit nuance or introduce errors; requires extra model work

Practical pattern: Use a token budget for the active prompt, keep a compact summary of older history, and retain a limited recent window verbatim. Delete old messages only after the summary has been successfully produced and validated.

11. Common Pitfalls and Best Practices

  • Changing thread IDs accidentally: a new ID points to a different conversation. Persist the ID in your UI/session metadata.
  • Using in-memory storage in production: it is not durable across process restarts.
  • Assuming checkpoints are long-term memory: checkpoints preserve thread state; they do not automatically create searchable cross-thread user memory.
  • Setting the token limit too high: leave headroom for system messages, tool calls, and output tokens.
  • Trimming without testing: ensure the retained message sequence is valid and contains the context required for the next response.
  • Deleting before summarizing: if summarization fails, important context can be lost. Generate and verify the summary first.
  • Trusting summaries blindly: summaries are lossy. Preserve critical structured facts separately when correctness matters.
  • Ignoring privacy and retention: define who can access each thread, how long checkpoints are kept, and how users can delete their data.

12. Plan of Action: Hands-on Practice

  1. Baseline: create a one-node chat graph with no checkpointer. Ask “My name is Nitesh” and then “What is my name?” in separate calls; observe the missing context.
  2. Add thread memory: compile with InMemorySaver and reuse one thread ID. Verify that the second call can use the first turn.
  3. Test thread isolation: use another thread ID and confirm that the history is separate.
  4. Test restart behavior: restart Python and inspect the in-memory state; it should not be treated as durable.
  5. Add PostgreSQL: configure a PostgreSQL checkpointer and verify the same thread's state after restarting the application.
  6. Add trimming: set a small test token limit and log which messages are passed to the model.
  7. Add deletion: remove older messages by ID and inspect the resulting graph state.
  8. Add summarization: trigger a summary when message count or estimated tokens cross a threshold; keep recent turns and inject the summary into model context.
  9. Evaluate: test recall of user-provided facts, long-running tasks, summary quality, token usage, and cross-thread privacy.

13. Quick Recap

  • LLM calls do not automatically remember previous independent calls; context must be supplied.
  • In LangGraph, short-term conversation memory is commonly implemented with message state, a checkpointer, and a stable thread ID.
  • InMemorySaver is convenient for demos but is not durable across process restarts.
  • A PostgreSQL checkpointer can persist graph checkpoints between application runs.
  • Long histories can exceed the model's context budget.
  • Trimming limits what the model sees on a call; it does not inherently delete saved state.
  • Deletion removes messages from state.
  • Summarization compresses older context and is usually paired with deletion of summarized turns.
Remember this mental model: Thread ID selects the conversation, the checkpointer saves its state, trimming controls the active prompt, and summarization helps preserve useful context as the conversation grows.
