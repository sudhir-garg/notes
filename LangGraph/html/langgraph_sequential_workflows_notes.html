1. Learning goals and context

The lesson moves from conceptual LangGraph discussions into hands-on implementation. Its focus is the simplest workflow pattern: a sequential workflow, where tasks run one after another along a linear path.

What you will build

  • A one-node BMI calculator
  • A two-node BMI categorizer
  • A minimal LLM question-answering graph
  • A prompt chain that generates an outline, then a blog

What you will learn

  • Define typed graph state
  • Register Python functions as nodes
  • Connect nodes with edges
  • Compile and invoke a graph
  • Use LangChain models inside LangGraph nodes
Core idea: LangGraph is not necessary for every simple linear task. The point of these small examples is to learn the graph programming model, which becomes more useful when workflows later need branching, cycles, persistence, or more complex control flow.

2. The mental model: state + nodes + edges

A LangGraph workflow can be understood as a directed graph that passes a shared state through a sequence of node functions. A node reads the current state, performs one unit of work, and returns an update. Edges define which node runs next.

Workflow setup is declarative; invoking the compiled graph runs the workflow.
ConceptMeaningIn code
StateStructured data shared across the workflow, such as input values and intermediate results.class BMIState(TypedDict): ...
NodeA unit of work, implemented as a Python callable that receives state and returns updates.graph.add_node("calculate_bmi", calculate_bmi)
EdgeA connection describing the next step in the graph.graph.add_edge("calculate_bmi", END)
START / ENDSpecial graph markers for the entry and exit points.from langgraph.graph import START, END
CompileBuilds the graph into an executable runnable.workflow = graph.compile()
InvokeRuns the compiled graph with an initial state and returns the final state.workflow.invoke(initial_state)

4. Define state with TypedDict

State is the data contract for the workflow. In these examples, it is represented as a Python TypedDict: a dictionary-shaped object whose expected keys and value types are documented for type checkers and readers.

from typing import TypedDict

class BMIState(TypedDict):
    weight_kg: float
    height_m: float
    bmi: float
    category: str

Each node receives the current state and returns the fields it updates. In LangGraph, returning a partial dictionary is generally enough; LangGraph applies that update to the graph state. Returning the entire state also works in simple examples, but returning only changed fields is often clearer.

Important distinction: TypedDict describes the expected shape of a dictionary; it does not perform runtime validation or automatically populate missing keys.

5. Example 1 — Build a sequential BMI workflow

The BMI example intentionally avoids LLMs. It isolates the LangGraph mechanics: take height and weight as input, calculate BMI, then optionally classify the result.

Linear control flow: every run follows the same path.

Step A — Implement the node functions

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class BMIState(TypedDict):
    weight_kg: float
    height_m: float
    bmi: float
    category: str

def calculate_bmi(state: BMIState) -> dict:
    weight = state["weight_kg"]
    height = state["height_m"]

    if height <= 0:
        raise ValueError("height_m must be greater than zero")

    bmi = weight / (height ** 2)
    return {"bmi": round(bmi, 2)}

def label_bmi(state: BMIState) -> dict:
    bmi = state["bmi"]

    if bmi < 18.5:
        category = "Underweight"
    elif bmi < 25:
        category = "Normal"
    elif bmi < 30:
        category = "Overweight"
    else:
        category = "Obesity"

    return {"category": category}

The first node reads weight_kg and height_m, computes \(BMI = \frac{weight\ (kg)}{height\ (m)^2}\), and returns the new bmi field. The second node reads that field and returns category.

Health note: BMI categories here are illustrative educational logic, not a diagnosis. BMI is a screening measure and must be interpreted in context.

Step B — Register nodes and connect edges

builder = StateGraph(BMIState)

builder.add_node("calculate_bmi", calculate_bmi)
builder.add_node("label_bmi", label_bmi)

builder.add_edge(START, "calculate_bmi")
builder.add_edge("calculate_bmi", "label_bmi")
builder.add_edge("label_bmi", END)

bmi_workflow = builder.compile()

Step C — Invoke the compiled graph

initial_state = {
    "weight_kg": 80.0,
    "height_m": 1.73,
}

final_state = bmi_workflow.invoke(initial_state)
print(final_state)

Expected result (approximately):

{
    'weight_kg': 80.0,
    'height_m': 1.73,
    'bmi': 26.73,
    'category': 'Overweight'
}

The initial state only needs the input fields consumed by the first node. The compiled graph returns the resulting state, including the fields produced by nodes.

6. Visualize the graph

Visual inspection is especially helpful once a workflow has more than one node. LangGraph versions commonly support Mermaid output; in a notebook, you can render it as an image if the required rendering dependencies are available.

# After compiling the graph:
print(bmi_workflow.get_graph().draw_mermaid())

Depending on your installed version and notebook environment, you may also be able to render the graph directly:

# Optional notebook visualization (availability depends on version)
from IPython.display import Image, display
display(Image(bmi_workflow.get_graph().draw_mermaid_png()))
If PNG rendering fails because a renderer or dependency is missing, use the Mermaid text output or the inline diagrams in these notes to verify the intended structure. Visualization is a debugging aid; it does not change graph execution.

7. Example 2 — A minimal LLM question-answering graph

Now the graph contains one node that calls a chat model. LangGraph orchestrates the workflow, while LangChain's ChatOpenAI integration supplies the model interface.

State schema

from typing import TypedDict

class LLMState(TypedDict):
    question: str
    answer: str

Node logic and graph construction

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

load_dotenv()

model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def llm_qa(state: LLMState) -> dict:
    question = state["question"]
    prompt = f"Answer the following question clearly:\n{question}"
    response = model.invoke(prompt)
    return {"answer": response.content}

builder = StateGraph(LLMState)
builder.add_node("llm_qa", llm_qa)
builder.add_edge(START, "llm_qa")
builder.add_edge("llm_qa", END)

llm_workflow = builder.compile()

initial_state = {
    "question": "How far is the Moon from Earth?"
}
final_state = llm_workflow.invoke(initial_state)
print(final_state["answer"])

The transcript's example uses a question about the Moon's distance from Earth. The response is model-generated, so its exact wording can vary. The important mechanics are stable: extract the question from state, construct a prompt, call model.invoke(), extract response.content, and return an answer update.

Why not just call the model directly? For one call, a direct model.invoke(prompt) is simpler. This graph is a learning exercise that introduces the same state, node, edge, compile, and invoke pattern used in larger systems.

8. Example 3 — Prompt chaining for blog generation

Prompt chaining decomposes a larger task into multiple sequential LLM calls. Instead of asking one prompt to produce a complete blog immediately, the workflow first generates an outline, then asks the model to write the blog using that outline.

State and node functions

from typing import TypedDict

class BlogState(TypedDict):
    topic: str
    outline: str
    content: str

def create_outline(state: BlogState) -> dict:
    topic = state["topic"]
    prompt = (
        f"Generate a detailed outline for a blog on: {topic}. "
        "Include a logical sequence of sections and useful subtopics."
    )
    outline = model.invoke(prompt).content
    return {"outline": outline}

def create_blog(state: BlogState) -> dict:
    topic = state["topic"]
    outline = state["outline"]
    prompt = (
        f"Write a detailed blog on: {topic}\n\n"
        f"Use this outline:\n{outline}\n\n"
        "Write clear, cohesive sections and explain key ideas."
    )
    content = model.invoke(prompt).content
    return {"content": content}

Connect, compile, and run

builder = StateGraph(BlogState)
builder.add_node("create_outline", create_outline)
builder.add_node("create_blog", create_blog)

builder.add_edge(START, "create_outline")
builder.add_edge("create_outline", "create_blog")
builder.add_edge("create_blog", END)

blog_workflow = builder.compile()

initial_state = {"topic": "The rise of AI in India"}
final_state = blog_workflow.invoke(initial_state)

print("OUTLINE:\n", final_state["outline"])
print("\nBLOG:\n", final_state["content"])

The model is invoked twice, so execution generally takes longer than a single call. In return, the outline becomes an explicit intermediate artifact that can be inspected, logged, revised, scored, or reused by later nodes.

How the state evolves

MomentState fields availableNew field
Initial inputtopic—
After create_outlinetopic, outlineoutline
After create_blogtopic, outline, contentcontent
Design principle: make intermediate outputs explicit in state when downstream steps need them or when you want to inspect them for debugging and evaluation.

9. Why use LangGraph state instead of a simple chain?

The lesson highlights a practical benefit of stateful orchestration: the final result can retain the topic, generated outline, and generated content together. A simple chain may expose only its final output unless intermediate values are deliberately carried forward.

DimensionSimple direct call / chainLangGraph workflow
Best fitOne prompt or a straightforward fixed sequenceExplicit multi-step orchestration and evolving state
Intermediate dataDepends on chain design and output configurationCan be preserved in shared state across nodes
Control flowOften linear and abstraction-specificGraph structure explicitly represents nodes and edges
Complex workflowsCan become awkward as orchestration growsSupports richer routing and cycles when needed
Do not add LangGraph just to wrap every single LLM call. Choose it when explicit workflow control, shared state, intermediate artifacts, or future complexity justify the additional structure.

10. Common mistakes and debugging checks

  • Wrong interpreter: install packages into the same virtual environment selected by the notebook kernel.
  • Missing API key: call load_dotenv() and verify the environment variable exists without printing the secret.
  • Node not registered: every node referenced by an edge must be added to the graph.
  • Missing edge: define the complete route from START through the intended nodes to END.
  • Incorrect state key: keys used by nodes must match the initial state and the updates produced by earlier nodes.
  • Unexpected return value: a chat model response is a message object; use .content when the next step expects plain text.
  • Graph not compiled: invoke the compiled runnable returned by builder.compile(), not the builder itself.
  • State field not initialized: ensure every field is available before a node reads it. The outline node must run before the blog node.
  • Visualization fails: try Mermaid text output first; PNG rendering may require additional dependencies or a compatible environment.

The lesson's homework is to extend the prompt-chaining graph with a third LLM node that evaluates the generated blog based on the outline and returns an integer score.

  v

Evaluation tip: define the score rubric before prompting the evaluator. For example, score outline coverage, factual coherence, organization, and relevance. A numeric score is more useful when its meaning is consistent across runs.

12. Quick recap

  • A sequential workflow executes nodes in a fixed order without branching.
  • Define the shared state schema before building the graph.
  • LangGraph nodes are Python callables that read state and return updates.
  • StateGraph creates the graph; add_node() registers work; add_edge() connects steps.
  • Use START and END to mark entry and exit points.
  • Call compile() to create an executable graph, then invoke(initial_state) to run it.
  • LangChain model integrations can be called inside LangGraph nodes.
  • Prompt chaining splits a larger task into multiple LLM calls, with intermediate outputs carried through state.
  • The blog workflow preserves both outline and content in the final state, making intermediate results easy to inspect.
One-sentence summary: LangGraph turns a workflow into an explicit stateful graph: define the data, implement each task as a node, connect the path with edges, compile it, and invoke it with an initial state.
