1. Lesson overview

The lesson builds a simple conversational chatbot with LangGraph and then makes it remember earlier messages across repeated user turns.

The instructor positions this as the first part of a larger chatbot project. Later stages are planned to add document-based RAG, tools, a user interface, LangSmith integration, retries, fault tolerance, and human-in-the-loop behaviour. The focus of this lesson is narrower: a chat loop plus conversation memory.

Learning goals

  • Represent chat history in graph state.
  • Use message objects rather than plain strings.
  • Build and compile a one-node graph.
  • Keep chatting in a loop.
  • Persist state between graph invocations.

Core takeaway

Sending only the newest user message to a fresh graph invocation does not give the model earlier context. A checkpointer plus a consistent thread ID lets LangGraph retrieve the state associated with that conversation.

2. Chatbot workflow design

The first chatbot is a sequential workflow with one processing node. The user message enters the graph, the chat node sends the accumulated messages to an LLM, and the generated AI message is returned in the updated state.

Figure 1. The graph handles one turn per invocation. A separate outer loop can repeatedly invoke it.

Execution sequence

  1. The application receives a user message.
  2. The message is placed in the graph input state.
  3. The chat_node passes the state’s messages to the model.
  4. The model returns an AI message.
  5. The node returns the new message; the graph ends.
  6. The console loop waits for another user message and invokes the graph again.
The graph itself does not need a loop for this design. The graph processes one turn; the Python application loop manages the ongoing chat session.

3. State and message types

LangGraph workflows use a state object to carry information between nodes. For a chatbot, the important information is the sequence of messages exchanged between the user and the assistant.

Why use message objects?

The lesson uses LangChain message classes. Common message types include:

TypePurposeExample
HumanMessageMessage from the user“What is the capital of India?”
AIMessageMessage generated by the model“New Delhi.”
SystemMessageInstructions that shape model behaviour“You are a helpful assistant.”
ToolMessageOutput returned by a toolA tool’s result or status

Using a list of base message objects allows the state to hold different message roles, rather than forcing every entry to be a plain string.

The add_messages reducer

When graph nodes update state, fields normally follow their configured update behaviour. The lesson uses the add_messages reducer for the messages field so new messages are merged into the conversation history instead of replacing the whole list.

from typing import Annotated
from typing_extensions import TypedDict
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
Important distinction: the reducer combines messages within the graph’s state updates. It does not, by itself, preserve state across separate invocations. Cross-invocation persistence is configured separately with a checkpointer.

4. Basic one-node implementation

This example follows the lesson’s structure. Model names and provider setup can vary by installed package version; configure your API key in your environment rather than hard-coding it.

from typing import Annotated
from typing_extensions import TypedDict

from langchain_core.messages import BaseMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages

class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

llm = ChatOpenAI(model="gpt-4o-mini")

def chat_node(state: ChatState):
    answer = llm.invoke(state["messages"])
    return {"messages": [answer]}

builder = StateGraph(ChatState)
builder.add_node("chat_node", chat_node)
builder.add_edge(START, "chat_node")
builder.add_edge("chat_node", END)

chatbot = builder.compile()

Try one turn

from langchain_core.messages import HumanMessage

result = chatbot.invoke({
    "messages": [HumanMessage(content="What is the capital of India?")]
})

print(result["messages"][-1].content)

The returned state contains the human message and the model response. The last message is usually the assistant’s latest answer, so result["messages"][-1].content extracts its text.

5. Add a console chat loop

A single invocation answers one turn and ends. To make the program feel like a chatbot, the lesson wraps calls in a Python while loop and stops when the user enters an exit word.

while True:
    user_text = input("You: ").strip()

    if user_text.lower() in {"exit", "quit", "bye"}:
        print("Chat ended.")
        break

    result = chatbot.invoke({
        "messages": [HumanMessage(content=user_text)]
    })

    print("AI:", result["messages"][-1].content)

This creates a working chat interface in the terminal, but there is a subtle problem: every call to invoke above supplies only the latest user message. Without persistence, the next invocation has no stored history from the previous turn.

6. The memory problem: why the bot forgets

The lesson demonstrates two failures:

  • The user says their name, then asks “What is my name?” The chatbot cannot reliably answer because the earlier turn is missing from the new invocation’s input.
  • The user asks “Add 10 to 100,” then “Multiply the result by 2.” If the second call only includes the follow-up question, the model may not know which result “the result” refers to.

Figure 2. An outer Python loop does not automatically carry graph state into the next call.

Root cause

The loop invokes the graph again with a new input dictionary. Unless the application manually sends the previous messages or the graph uses persistence, each invocation is effectively started with the input it receives. The message reducer cannot recover messages that were never loaded into the new state.

Fix introduced in the lesson: compile the graph with a checkpointer, assign a stable thread_id to the conversation, and pass that configuration to every invocation in the same chat.

7. Persistence with a checkpointer

Persistence saves graph state at checkpoints so it can be retrieved in a later invocation. The lesson uses MemorySaver, an in-memory checkpointer, and a thread ID to identify the conversation.

Concepts

ConceptMeaning in this example
CheckpointerComponent that saves and restores graph state at checkpoints.
MemorySaverStores checkpoint data in process memory for development and demonstrations.
thread_idIdentifier for a conversation’s state. Reuse it for turns belonging to the same conversation.
configConfiguration passed to graph calls, including the configurable thread ID.

Configure the graph

from langgraph.checkpoint.memory import MemorySaver

memory = MemorySaver()

# Reuse the graph builder defined earlier.
chatbot = builder.compile(checkpointer=memory)

config = {
    "configurable": {
        "thread_id": "demo-conversation-001"
    }
}

Invoke repeatedly with the same thread

from langchain_core.messages import HumanMessage

first = chatbot.invoke(
    {"messages": [HumanMessage(content="Hi, my name is Nitesh.")]},
    config=config
)
print(first["messages"][-1].content)

second = chatbot.invoke(
    {"messages": [HumanMessage(content="What is my name?")]},
    config=config
)
print(second["messages"][-1].content)

With a checkpointer configured, the same thread ID lets LangGraph resume that thread’s saved state and merge in the new message. The model can then receive the earlier exchange as part of the message history.

Memory scope: MemorySaver is in-memory. Its data is typically lost when the Python process or notebook kernel restarts. For durable production conversations, use an appropriate persistent checkpointer/backend and consider authentication, access controls, retention, and privacy requirements.

Inspect the saved state

snapshot = chatbot.get_state(config)

for message in snapshot.values["messages"]:
    print(type(message).__name__, ":", message.content)

Inspecting the state is a useful debugging technique: it shows whether user and AI messages are actually being retained for that thread.

8. Integrated example: console chatbot with memory

The following combines the main ideas into one runnable-style script. Install compatible versions of LangGraph, LangChain Core, and the OpenAI integration, and set the provider API key in your environment first.

from typing import Annotated
from typing_extensions import TypedDict

from langchain_core.messages import BaseMessage, HumanMessage
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.checkpoint.memory import MemorySaver

# 1. Define state and its message-append/update behaviour.
class ChatState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

# 2. Define the model and graph node.
llm = ChatOpenAI(model="gpt-4o-mini")

def chat_node(state: ChatState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

# 3. Build the one-node graph.
builder = StateGraph(ChatState)
builder.add_node("chat_node", chat_node)
builder.add_edge(START, "chat_node")
builder.add_edge("chat_node", END)

# 4. Compile with an in-memory checkpointer.
checkpointer = MemorySaver()
chatbot = builder.compile(checkpointer=checkpointer)

# 5. Keep a stable thread ID for this conversation.
config = {
    "configurable": {
        "thread_id": "terminal-session-001"
    }
}

# 6. Repeatedly invoke the same conversation thread.
print("Chatbot ready. Type exit, quit, or bye to stop.")
while True:
    user_text = input("You: ").strip()

    if user_text.lower() in {"exit", "quit", "bye"}:
        print("AI: Goodbye!")
        break

    if not user_text:
        continue

    result = chatbot.invoke(
        {"messages": [HumanMessage(content=user_text)]},
        config=config
    )
    print("AI:", result["messages"][-1].content)

Expected interaction (illustrative)

You: Hi, my name is Nitesh.
AI: Hello, Nitesh! Nice to meet you.

You: What is my name?
AI: You told me your name is Nitesh.

You: exit
AI: Goodbye!

The exact wording is generated by the model and may differ. This example demonstrates the intended state flow, not a guarantee about a particular model response.

9. Key concepts to remember

TermPlain-English explanation
StateThe data available to the graph while processing a turn.
NodeA function that reads state and returns an update.
EdgeDefines which node runs next.
ReducerDefines how a state field is updated or merged.
add_messagesReducer specialised for updating message histories.
InvocationOne call to execute the graph, such as chatbot.invoke(...).
PersistenceSaving graph state so a later invocation can continue from it.
ThreadA logically grouped conversation identified by a thread ID.
In-memory storageFast temporary storage that generally does not survive process restarts.

10. Limitations and next steps

  • Not durable across restarts: the in-memory checkpointer is for demos and short-lived processes.
  • Thread IDs must be managed: reuse the same ID for the same conversation; use different IDs to keep conversations separate.
  • Context grows: passing the full message history to the model can eventually increase token usage. Longer-lived applications may need summarisation or trimming strategies.
  • Memory is not the same as factual accuracy: the model may still misinterpret or misremember details even when the history is present.
  • Production hardening is separate: secure per-user thread access, handle errors and retries, monitor model calls, and choose durable storage when needed.

The larger roadmap mentioned in the lesson includes RAG over documents, tools for actions, a UI, LangSmith integration, human-in-the-loop flows, retry logic, and fault tolerance. Those are planned extensions rather than implementations completed in this lesson.
