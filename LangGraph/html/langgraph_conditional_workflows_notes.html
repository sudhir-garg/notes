Conditional Workflows in LangGraph

1. Overview

A conditional workflow chooses the next node according to a condition evaluated during execution. In LangGraph, the routing function reads the current state and returns the name of the node that should run next.

The lesson introduces conditional workflows as the third major workflow pattern after sequential and parallel workflows. It demonstrates the idea first with ordinary Python math, then with an LLM-based customer-review workflow.

Core idea: create a routing function that checks the state, returns a destination node name, and connect it to the graph with add_conditional_edges().

2. Three common workflow types

Sequential

Tasks run one after another in a fixed order.

A → B → C

Parallel

Two or more branches can run during the same workflow stage, and their results can feed a later node.

A → (B + C) → D

Conditional

A condition chooses one branch. The chosen branch runs; the alternatives do not run for that decision.

A → B or C → D

Why it matters

Real agent workflows often need to classify an input, route it to a specialist step, and then produce a suitable result.

3. How conditional routing works

  1. Define the graph state. State carries the input and any intermediate or final values required by nodes.
  2. Write node functions. Each node reads the state and returns a dictionary containing the state updates.
  3. Write a routing function. It inspects state and returns a destination node name, such as "positive_response".
  4. Add conditional edges. Call add_conditional_edges(source, routing_function).
  5. Connect each branch to its next step or to END.
  6. Compile and invoke. Pass an initial state to the compiled graph.

General pattern

def route_by_condition(state):
    if state["condition"]:
        return "branch_a"
    return "branch_b"

builder.add_conditional_edges("decision_node", route_by_condition)
Important: the strings returned by the routing function must match the graph's destination node names (or keys in an explicitly supplied route map). A misspelled name can cause routing errors.

4. Example A — A conditional workflow for a quadratic equation

The first example is deliberately not LLM-based. It shows the branching concept using a familiar mathematical problem, so the routing logic is easy to verify.

4.1 Mathematics recap

A quadratic equation has the form:

ax² + bx + c = 0, where a ≠ 0

Compute the discriminant:

D = b² − 4ac

ConditionMeaningAction
D > 0Two distinct real rootsCalculate both roots using (−b ± √D) / 2a.
D = 0One repeated real rootCalculate −b / 2a.
D < 0No real rootsReturn a message that there are no real roots.

4.2 Workflow diagram

4.3 State and node functions

The state stores the coefficients, a display string for the equation, the discriminant, and the final result.

from typing import TypedDict
from math import sqrt
from langgraph.graph import StateGraph, START, END

class QuadraticState(TypedDict, total=False):
    a: float
    b: float
    c: float
    equation: str
    discriminant: float
    result: str

def show_equation(state: QuadraticState):
    a, b, c = state["a"], state["b"], state["c"]
    equation = f"{a}x² + ({b})x + ({c}) = 0"
    return {"equation": equation}

def calculate_discriminant(state: QuadraticState):
    d = state["b"] ** 2 - 4 * state["a"] * state["c"]
    return {"discriminant": d}

def real_roots(state: QuadraticState):
    a, b, d = state["a"], state["b"], state["discriminant"]
    x1 = (-b + sqrt(d)) / (2 * a)
    x2 = (-b - sqrt(d)) / (2 * a)
    return {"result": f"Two real roots: x1={x1}, x2={x2}"}

def repeated_root(state: QuadraticState):
    root = -state["b"] / (2 * state["a"])
    return {"result": f"One repeated real root: x={root}"}

def no_real_roots(state: QuadraticState):
    return {"result": "The equation has no real roots."}

def route_by_discriminant(state: QuadraticState):
    d = state["discriminant"]
    if d > 0:
        return "real_roots"
    if d == 0:
        return "repeated_root"
    return "no_real_roots"

4.4 Build and run the graph

builder = StateGraph(QuadraticState)
builder.add_node("show_equation", show_equation)
builder.add_node("calculate_discriminant", calculate_discriminant)
builder.add_node("real_roots", real_roots)
builder.add_node("repeated_root", repeated_root)
builder.add_node("no_real_roots", no_real_roots)

builder.add_edge(START, "show_equation")
builder.add_edge("show_equation", "calculate_discriminant")
builder.add_conditional_edges("calculate_discriminant", route_by_discriminant)
builder.add_edge("real_roots", END)
builder.add_edge("repeated_root", END)
builder.add_edge("no_real_roots", END)

quadratic_graph = builder.compile()

result = quadratic_graph.invoke({"a": 1, "b": -5, "c": 6})
print(result["equation"])       # 1x² + (-5)x + (6) = 0
print(result["discriminant"])   # 1
print(result["result"])         # Two real roots: x1=3.0, x2=2.0
What to notice: the three result nodes are all registered in the graph, but the routing function chooses only one of them after the discriminant is calculated.

4.5 Try three test cases

Coefficients (a, b, c)DiscriminantExpected route

(1, 2, 1)0repeated_root → root −1

Validation note: this educational example assumes a ≠ 0, because otherwise the equation is not quadratic. In production code, validate the input before calculating roots. Floating-point computations may also require a tolerance when deciding whether a computed discriminant is effectively zero.

5. Example B — An LLM-based customer-review workflow

The second example applies conditional routing to customer feedback. It first classifies the sentiment, then chooses a response path.

5.1 Business logic

  • Input: a customer review as text.
  • Sentiment classification: an LLM returns either positive or negative in a structured format.
  • Positive branch: generate a warm thank-you reply and invite the customer to leave feedback on the website.
  • Negative branch: diagnose the issue type, emotional tone, and urgency; then generate a more empathetic and relevant support reply.

5.2 State design

The graph state contains four main fields:

FieldPurpose
reviewOriginal review text.
sentimentSentiment label: positive or negative.
diagnosisA dictionary containing issue type, tone, and urgency. It is mainly populated on the negative branch.
responseGenerated reply to the customer.

5.3 Diagnosis categories

The lesson uses a constrained schema so the model returns predictable categories rather than unrestricted prose.

KeyPossible values shown in the lessonInterpretation
issue_typeUX, performance, bug, support, otherWhat kind of issue the review describes.
toneFor example: frustrated, angry, neutralThe emotion expressed by the reviewer.
urgencylow, medium, highHow urgent or critical the issue appears.

The exact allowed labels should be adjusted to the schema used in your own implementation. Constrained labels help make routing and downstream prompt construction more reliable.

6. Structured output with Pydantic

For sentiment and diagnosis, the lesson uses structured output. Instead of asking the model for a free-form paragraph and trying to parse it, define a schema with known fields and allowed values.

from typing import Literal
from pydantic import BaseModel, Field

class SentimentSchema(BaseModel):
    sentiment: Literal["positive", "negative"] = Field(
        description="Sentiment of the customer review"
    )

class DiagnosisSchema(BaseModel):
    issue_type: Literal["ux", "performance", "bug", "support", "other"]
    tone: Literal["frustrated", "angry", "neutral", "disappointed"]
    urgency: Literal["low", "medium", "high"]

Then bind the schema to the chat model. This is the general pattern shown in the lesson:

from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini")
sentiment_model = model.with_structured_output(SentimentSchema)
diagnosis_model = model.with_structured_output(DiagnosisSchema)
Setup: install the required packages and configure your OpenAI API key securely in the environment. Do not hard-code a real API key in a notebook, source file, or HTML page. Structured-output support can vary by provider and package version.

7. Complete code pattern for the review workflow

The following is a cleaned, consolidated reference implementation of the workflow described in the transcript. It uses the same overall stages and conditional routing, with field names made consistent for readability.

from typing import TypedDict, Literal
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

# 1. Structured output schemas
class SentimentSchema(BaseModel):
    sentiment: Literal["positive", "negative"] = Field(
        description="Sentiment of the review"
    )

class DiagnosisSchema(BaseModel):
    issue_type: Literal["ux", "performance", "bug", "support", "other"]
    tone: Literal["frustrated", "angry", "neutral", "disappointed"]
    urgency: Literal["low", "medium", "high"]

# 2. Models
model = ChatOpenAI(model="gpt-4o-mini")
sentiment_model = model.with_structured_output(SentimentSchema)
diagnosis_model = model.with_structured_output(DiagnosisSchema)

# 3. Graph state
class ReviewState(TypedDict, total=False):
    review: str
    sentiment: Literal["positive", "negative"]
    diagnosis: dict
    response: str

# 4. Nodes
def find_sentiment(state: ReviewState):
    prompt = (
        "Classify the sentiment of this review as positive or negative.\n"
        f"Review: {state['review']}"
    )
    result = sentiment_model.invoke(prompt)
    return {"sentiment": result.sentiment}

def positive_response(state: ReviewState):
    prompt = (
        "Write a warm, concise thank-you message in response to this review. "
        "Also kindly invite the customer to leave feedback on our website.\n"
        f"Review: {state['review']}"
    )
    result = model.invoke(prompt)
    return {"response": result.content}

def run_diagnosis(state: ReviewState):
    prompt = (
        "Diagnose the negative customer review. Identify issue type, emotional "
        "tone, and urgency using the provided schema.\n"
        f"Review: {state['review']}"
    )
    result = diagnosis_model.invoke(prompt)
    return {"diagnosis": result.model_dump()}

def negative_response(state: ReviewState):
    diagnosis = state["diagnosis"]
    prompt = (
        "You are a customer-support assistant. Write an empathetic, helpful "
        "resolution message. Acknowledge the reported issue and its urgency. "
        "Do not claim that the issue is fixed unless the review says so.\n"
        f"Review: {state['review']}\n"
        f"Issue type: {diagnosis['issue_type']}\n"
        f"Tone: {diagnosis['tone']}\n"
        f"Urgency: {diagnosis['urgency']}"
    )
    result = model.invoke(prompt)
    return {"response": result.content}

# 5. Router
def check_sentiment(state: ReviewState):
    if state["sentiment"] == "positive":
        return "positive_response"
    return "run_diagnosis"

# 6. Graph construction
builder = StateGraph(ReviewState)
builder.add_node("find_sentiment", find_sentiment)
builder.add_node("positive_response", positive_response)
builder.add_node("run_diagnosis", run_diagnosis)
builder.add_node("negative_response", negative_response)

builder.add_edge(START, "find_sentiment")
builder.add_conditional_edges("find_sentiment", check_sentiment)
builder.add_edge("positive_response", END)
builder.add_edge("run_diagnosis", "negative_response")
builder.add_edge("negative_response", END)

review_graph = builder.compile()

# 7. Example invocation
result = review_graph.invoke({
    "review": (
        "I have been trying to log in for over an hour. "
        "The app keeps freezing on the authentication screen."
    )
})

print("Sentiment:", result["sentiment"])
print("Diagnosis:", result.get("diagnosis"))
print("Response:", result["response"])

What each node does

NodeInput / responsibilityOutput update
find_sentimentReads the review and classifies sentiment.sentiment
positive_responseWrites a friendly reply for a positive review.response
run_diagnosisExtracts issue type, tone, and urgency for a negative review.diagnosis
negative_responseUses the review and diagnosis to write a tailored support reply.response
check_sentimentRoutes based on the sentiment field.Destination node name

8. Testing and debugging tips

  • Test one positive review and confirm the graph goes directly to positive_response.
  • Test one negative review and confirm the graph visits run_diagnosis before negative_response.
  • Inspect the final state, not only the printed response. Check that sentiment, diagnosis, and response contain the expected values.
  • Keep node names consistent across add_node, the router's return values, and any explicit route map.
  • Make the structured schema's allowed values match the values you expect the model to return.
  • Handle malformed, ambiguous, or mixed-sentiment reviews deliberately rather than assuming every review is clearly positive or negative.
  • For customer-facing automation, consider human review for high-urgency or sensitive complaints.

Common mistakes

MistakeWhy it mattersFix
Using a normal edge instead of conditional routingAll fixed edges can run, rather than selecting a branch.Use add_conditional_edges() for decision points.
Router returns the wrong node nameThe graph cannot route to the intended destination.Use exact registered node names or an explicit mapping.
State fields are inconsistentA node may read a key that was never populated.Define the state schema first and standardize key names.
Assuming diagnosis exists on positive reviewsThe positive branch does not run the diagnosis node.Use state.get("diagnosis") where optional, or only access it on the negative branch.
Unvalidated math inputsA zero leading coefficient means the equation is not quadratic.Validate inputs before calculating roots.

9. Quick revision checklist

  • Sequential workflow = fixed, one-after-another execution.
  • Parallel workflow = multiple branches can execute at the same workflow stage.
  • Conditional workflow = choose a branch according to a condition.
  • State stores inputs, intermediate values, and outputs shared between nodes.
  • A routing function reads state and returns the next node name.
  • add_conditional_edges() connects a source node to conditional routing.
  • The quadratic example routes according to the sign of D = b² − 4ac.
  • The review example routes positive reviews to a thank-you response and negative reviews through diagnosis.
  • Structured output schemas constrain model output to predictable fields and values.
  • Compile the graph and invoke it with an initial state to run the workflow.
One-sentence summary: conditional workflows make an agentic system adaptive by letting the current state determine which node should execute next.
