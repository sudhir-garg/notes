Building a Resume Chat Feature

Study notes for turning a basic streaming chatbot into a multi-conversation app: create new threads, keep their IDs, display a conversation list, and reload the messages when a thread is selected.

1. Overview: what are we building?

The lesson extends an existing chatbot that already has a Streamlit user interface and streamed responses. The new feature lets a user start a separate conversation and return to an earlier one without mixing their messages.

Think of each conversation as an independent thread. A user might discuss a Python factorial function in one thread, write a blog post in another, and then switch back to the first thread. Each thread must retain its own identifier so LangGraph can retrieve the matching state.

Illustration: the sidebar manages threads; the main panel renders the selected thread.

What “resume chat” means

  • Every new conversation receives a unique thread ID.
  • The app remembers the thread IDs during the current Streamlit session.
  • Clicking a thread loads its saved LangGraph messages into the UI message history.
  • The user can switch between threads, with each conversation keeping its own context.
Important distinction: the app’s UI message list is not the same thing as LangGraph’s checkpointed thread state. The UI list is formatted for rendering; LangGraph state is fetched by thread ID.

2. Architecture and prerequisites

The source lesson reuses the previous chatbot rather than rebuilding the backend. It has two main parts:

PartResponsibilityChange in this lesson?
LangGraph backendRuns the chatbot graph and stores/checkpoints state by thread ID.Existing backend is reused. The lesson demonstrates reading state with get_state().
Streamlit frontendDisplays the chat, sidebar, buttons, and message history.Most changes happen here.
In-memory checkpointerKeeps thread state in process memory while the program is running.It works for the demo, but does not preserve conversations across a process restart.

Examples below show the core pattern from the lesson. Integrate them into the existing app and keep the names of your chatbot object and message classes consistent with your project.

3. Plan of action: break the feature into small tasks

The lesson’s central programming technique is to split a larger feature into smaller, testable steps.

  1. Create the sidebar UI. Add the app title, a New chat button, and a “My conversations” section.
  2. Generate a dynamic thread ID. Use UUIDs instead of hard-coding a value such as "thread-1".
  3. Store thread IDs in session state. Keep a list of conversations and show them in the sidebar.
  4. Make New chat work. Generate a fresh ID, set it as the active thread, and clear the UI message history.
  5. Make thread buttons clickable. Selecting a thread should fetch its LangGraph state and repopulate the UI.
  6. Polish ordering and verify behavior. Display the most recent thread first and test that switching preserves each thread’s context.
Why this breakdown helps: each task has a clear outcome, so errors are easier to locate. First make the UI visible, then make state correct, then connect the interactions.

5. Step 2 — Generate a dynamic thread ID

A fixed thread ID is not suitable when users can create an unknown number of conversations. If every chat reused the same ID, messages could be associated with the wrong thread. The lesson uses Python’s uuid module to generate unique IDs.

Python · utility functionUUID v4
import uuid

def generate_thread_id():
    """Return a new unique identifier for a conversation."""
    return str(uuid.uuid4())

The thread ID for the active conversation is stored in Streamlit’s st.session_state. Initialize it only if it does not already exist; Streamlit reruns the script during interactions.

if "thread_id" not in st.session_state:
    st.session_state.thread_id = generate_thread_id()

Pass the active ID to LangGraph

When invoking or streaming the graph, pass the ID through the configurable thread field. The exact payload used in the lesson is a configuration dictionary with configurable.thread_id.

config = {
    "configurable": {
        "thread_id": st.session_state.thread_id
    }
}

# Example pattern — adapt to your graph and message format:
# response = chatbot.stream(input_payload, config=config)
Keep the configuration consistent. Use the same thread ID for messages that belong to the same conversation. Use a new ID only when starting a new conversation or deliberately switching to another one.

6. Step 3 — Implement the New chat action

Clicking New chat should do three things: generate a new thread ID, set it as the active ID, and clear the frontend’s current message history. Clearing the UI history makes the chat panel appear empty for the new conversation; it does not delete the older thread’s checkpointed state.

Python · reset the active chatSession state
def reset_chat():
    st.session_state.thread_id = generate_thread_id()
    st.session_state.message_history = []

Initialize the message history before it is used:

if "message_history" not in st.session_state:
    st.session_state.message_history = []

Wire the callback to the sidebar button:

st.sidebar.button("New chat", on_click=reset_chat)

After the click, the app reruns with a fresh active thread and an empty message list. In the next step, the new ID is also added to a list so that the old conversation remains accessible in the sidebar.

7. Step 4 — Keep and display all conversation IDs

Changing the active thread ID alone is not enough: it would replace the only reference to the previous thread. The lesson solves this by maintaining a chat_threads list in session state.

Python · initialize the listSession state
if "chat_threads" not in st.session_state:
    st.session_state.chat_threads = []

Use a small helper to avoid adding the same ID more than once:

def add_thread(thread_id):
    if thread_id not in st.session_state.chat_threads:
        st.session_state.chat_threads.append(thread_id)

Add the initial thread after initialization, and add each new thread when resetting the chat:

if "thread_id" not in st.session_state:
    st.session_state.thread_id = generate_thread_id()

add_thread(st.session_state.thread_id)

def reset_chat():
    st.session_state.thread_id = generate_thread_id()
    st.session_state.message_history = []
    add_thread(st.session_state.thread_id)

Then render a button for each stored thread ID. Converting the ID to a string is useful because the Streamlit button label expects text.

st.sidebar.header("My conversations")

for thread_id in reversed(st.session_state.chat_threads):
    st.sidebar.button(
        str(thread_id),
        key=f"thread-{thread_id}",
        on_click=load_conversation,
        args=(thread_id,)
    )

The reversed() call makes recently created threads appear first because the list is appended to as new conversations are created.

UI improvement opportunity: UUIDs are useful identifiers but poor conversation titles. The lesson leaves a homework task to replace them with meaningful names, such as “Factorial code” or “AI job crisis blog.”

8. Step 5 — Load a previous conversation

To resume a conversation, the app must retrieve the messages associated with the selected thread ID from LangGraph. The lesson uses chatbot.get_state(config); the returned state snapshot exposes the graph values, including the message list.

Python · retrieve messages from LangGraphBackend object
def get_thread_messages(thread_id):
    config = {
        "configurable": {
            "thread_id": thread_id
        }
    }
    snapshot = chatbot.get_state(config)
    return snapshot.values.get("messages", [])

In the source lesson, the graph’s stored messages use message objects (for example, human and AI messages), while the Streamlit frontend renders a list of dictionaries with role and content. Convert between those formats before updating the UI history.

Python · convert message objects for the UIFormat adapter
def load_conversation(thread_id):
    # Mark the selected conversation as active.
    st.session_state.thread_id = thread_id

    # Fetch messages saved by LangGraph for this thread.
    messages = get_thread_messages(thread_id)

    # Convert graph message objects to the UI's role/content format.
    formatted_messages = []
    for msg in messages:
        if isinstance(msg, HumanMessage):
            role = "user"
        else:
            role = "assistant"

        formatted_messages.append({
            "role": role,
            "content": msg.content
        })

    st.session_state.message_history = formatted_messages

Import the message class used by your LangChain/LangGraph version if you use the example above:

from langchain_core.messages import HumanMessage
Adaptation note: this example assumes the graph stores user messages as HumanMessage and assistant responses as other message objects. If your graph also stores tool messages, system messages, or custom message types, map those roles explicitly instead of treating every non-human message as assistant text.

Why update the active thread ID?

When a user selects an older conversation, set st.session_state.thread_id to that selected ID. Otherwise, the UI might display one conversation while subsequent messages are sent to another thread.

Render messages from the frontend history

for message in st.session_state.message_history:
    with st.chat_message(message["role"]):
        st.markdown(message["content"])

Use this same rendering loop after loading history and after new messages arrive. This keeps the display logic in one place.

10. Limitation: why chats disappear after a refresh or restart

The lesson finishes with an important limitation. Its in-memory checkpointer stores graph state in RAM. If the Python process terminates or the app is restarted, that in-memory state is lost. A session list in Streamlit does not turn an in-memory LangGraph checkpointer into durable storage.

The next step in the series is to connect the LangGraph backend to durable database storage.

The planned improvement is to connect the LangGraph backend to a database-backed checkpointer. That is what makes old conversations available after the app process has restarted, rather than only while the current process remains alive.

Do not confuse the two persistence layers: st.session_state is frontend session state; the LangGraph checkpointer stores graph state. Durable conversation recovery requires an appropriate persistent checkpointer and a way to rediscover the saved thread IDs.

11. Testing checklist

  • On first load, a thread ID is created and appears in the sidebar.
  • Sending a message adds it to the active conversation only.
  • Clicking New chat creates a different ID and clears the visible history.
  • The previous thread ID remains in the conversation list.
  • Creating several chats adds each new ID only once.
  • Clicking an older thread loads its previous user and assistant messages.
  • After switching threads, the next user message goes to the selected thread.
  • The most recently created conversation appears at the top.
  • Refreshing/restarting behavior is understood: in-memory state is not durable.

Common problems and fixes

SymptomLikely cause / fix
New chat button does nothingOnly the button UI exists; attach on_click=reset_chat.
Previous thread disappears from sidebarOnly the active ID is stored; maintain a separate chat_threads list.
Wrong conversation receives new messagesSelected thread ID was not written to st.session_state.thread_id before invoking the graph.
Loaded messages do not renderMessage formats differ; convert graph message objects into dictionaries with role and content.
Chats vanish after app restartThe checkpointer is in-memory; use durable database-backed persistence.
Duplicate buttons or key errorsEnsure thread IDs are unique, labels are strings, and each button has a stable unique key.

12. Homework: give conversations meaningful names

The lesson’s proposed exercise is to show a logical conversation title instead of raw UUIDs, similar to a chat application’s conversation list.

  • Start with a simple title derived from the first user message.
  • Keep the thread ID as the internal key; store the title separately.
  • Handle long prompts by shortening the visible title without changing the stored original message.
  • Consider what to show for an empty chat before the first message is sent.

For example, a conversation might display “Python factorial function” while its internal thread ID remains a UUID. This makes the sidebar much easier to scan.

Quick recap

  • Sidebar: title, New chat button, and conversation list.
  • Unique IDs: use uuid.uuid4() instead of a hard-coded thread ID.
  • New chat: generate a new ID, make it active, and reset UI history.
  • Thread list: keep all IDs in session state and render newest first.
  • Resume: call chatbot.get_state(config), extract messages, map them into the UI format, and display them.
  • Persistence: an in-memory checkpointer loses state when the process ends; database-backed persistence is the next improvement.
