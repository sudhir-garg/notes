1. What are we building?

The project in the lesson is a planning-based AI blog-writing agent. A user supplies a topic or a more detailed brief. Instead of immediately writing a long answer, the agent first creates a structured plan, then delegates each planned section to a worker, and finally combines the results into a Markdown blog.

The full demo described in the transcript adds online research for topics that need fresh information, generated images placed into the blog, evidence/citation display, execution logs, an image listing, downloadable output, and access to previously generated blogs.

Core idea: Plan → execute subtasks → combine results. This is especially useful for multi-part tasks where an immediate one-shot response may omit important sections or lack organization.

Input

A topic such as “Self-attention,” or a brief that specifies audience, tone, and desired coverage.

Output

A titled, structured Markdown blog. In later stages, it can include citations and images.

2. Planning agent vs direct execution

A planning agent does not jump straight to the final task. It creates a structured plan of work and then executes that plan step by step.

Direct executionPlanning-based execution
Receives a task and starts answering immediately.Understands the task and breaks it into subtasks first.
Can be sufficient for small, self-contained requests.Useful for complex deliverables with multiple sections or dependencies.
May omit coverage or produce uneven structure.Plan defines section order, goals, and writing requirements before drafting.

Example: asking for a blog about transformer architecture in one step may lead to missing details. A planner can decide on an introduction, mechanism, worked example, applications, limitations, and conclusion before any section is written.

For topics that do not need fresh facts, the router can bypass research and send the topic directly to planning. The graph still uses the same planner → workers → reducer path.

Node responsibilities

  • Router: decides whether online research is needed; in the research-enabled version, it also suggests search queries.
  • Research node: sends queries to Tavily and stores retrieved information for downstream nodes.
  • Orchestrator/planner: creates a structured blog plan: title, audience, tone, and a list of section tasks.
  • Fan-out: checks how many tasks are in the plan and dispatches one worker invocation per task using LangGraph’s `Send` API.
  • Worker: writes only its assigned section, using the topic and overall plan for context.
  • Reducer: joins section outputs in order, forms the Markdown blog, and in the image-enabled stage identifies places where images are useful and inserts them.

5. Stage 1: Basic blog-writing agent

Structured plan schema

The lesson models the planner’s response using Pydantic. The plan contains a blog title and a list of task objects. Each task corresponds to one blog section and includes an ID, title, and brief.

from typing import List
from pydantic import BaseModel, Field

class SectionTask(BaseModel):
    id: int
    title: str
    brief: str = Field(description="What this section should cover")

class BlogPlan(BaseModel):
    title: str
    tasks: List[SectionTask]

This schema makes the planner’s output predictable enough for the graph to dispatch workers without trying to parse an unstructured paragraph.

Graph state

from typing import Annotated, TypedDict
import operator

class BlogState(TypedDict):
    topic: str
    plan: BlogPlan
    sections: Annotated[list[str], operator.add]
    final_blog: str

topic is the user’s input, plan is the planner output, sections collects the outputs from worker runs, and final_blog holds the merged result. The reducer annotation allows multiple worker updates to be accumulated as a list.

Planner → fan-out → worker → reducer

# Illustrative LangGraph pattern; connect node functions in your graph.
def orchestrator(state):
    structured_llm = llm.with_structured_output(BlogPlan)
    plan = structured_llm.invoke([
        ("system", "Create a blog plan with 5–7 useful sections."),
        ("human", state["topic"]),
    ])
    return {"plan": plan}

def fan_out(state):
    # One Send per planned section/task
    return [
        Send("worker", {
            "topic": state["topic"],
            "plan": state["plan"],
            "task": task,
        })
        for task in state["plan"].tasks
    ]

def worker(worker_state):
    task = worker_state["task"]
    result = llm.invoke([
        ("system", "Write one clean Markdown section. Return only that section."),
        ("human", f"""Blog topic: {worker_state['topic']}
Overall plan: {worker_state['plan']}
Section title: {task.title}
Section brief: {task.brief}"""),
    ])
    return {"sections": [result.content]}

def reducer(state):
    title = state["plan"].title
    body = "\\n\\n".join(state["sections"])
    final_blog = f"# {title}\\n\\n{body}"
    with open("blog.md", "w", encoding="utf-8") as f:
        f.write(final_blog)
    return {"final_blog": final_blog}
Implementation note: This is a teaching blueprint illustrating the concepts in the transcript, not a complete copy of the instructor’s project. A working application also needs imports, model configuration, state definitions for worker payloads, graph wiring, compile/invoke code, and compatible LangGraph/LangChain package versions.

Why dynamic fan-out matters

The planner may produce five sections for one topic and seven for another. The program should not hard-code a fixed number of workers. It should create one worker task per item in plan.tasks, allowing sections to be written in parallel.

6. Improve quality with better plans and prompts

The first basic version uses simple prompts. The lesson improves quality by expanding the plan schema and giving the model more explicit instructions.

FieldPurpose
Blog titleTitle of the final article.
AudienceWho the article is written for.
ToneStyle, such as approachable, technical, or formal.
Task ID and titleIdentifies and names each section.
GoalOne sentence describing what the reader should understand or be able to do after the section.
Bullet pointsThree to five concrete, non-overlapping points to cover.
Target wordsApproximate length of each section.
Section typeFor example: introduction, core explanation, example, or checklist.

With this richer plan, each worker receives a clear section goal and non-overlapping coverage points. The transcript reports that this produced more detailed output, including code examples and a summary, compared with the simpler first draft.

Example of a richer task model

class DetailedTask(BaseModel):
    id: int
    title: str
    goal: str
    points: list[str]
    target_words: int
    section_type: str

class DetailedBlogPlan(BaseModel):
    title: str
    audience: str
    tone: str
    tasks: list[DetailedTask]

When improving prompts, describe both the desired output and the constraints: expected format, audience, section purpose, use of examples, and what not to repeat.

7. Stage 2: Add internet research with a router and Tavily

Language models can have gaps in current or rapidly changing information. The router estimates whether a topic needs external research. For example, “What is self-attention?” may not need a search, while “Top AI news this week” or a timeline of recent product releases probably does.

Research flow

  1. The router decides whether research is needed and proposes search queries.
  2. The research node submits each query to Tavily, described in the lesson as a search engine designed for LLM applications.
  3. Search results are stored in graph state as research context, ideally with source URLs and relevant snippets.
  4. The planner uses the topic plus research context to create a more informed outline.
  5. Workers receive the relevant research context when writing sections that need it.
  6. The final application displays citations/evidence so readers can inspect the sources.

Illustrative router output

class ResearchRoute(BaseModel):
    needs_research: bool
    search_queries: list[str]

# Example result for a time-sensitive topic:
{
    "needs_research": True,
    "search_queries": [
        "ChatGPT release timeline and updates",
        "Major new ChatGPT features by year",
        "OpenAI announcements about ChatGPT",
    ],
}
Reliability reminder: Search results are evidence to evaluate, not guaranteed truth. Preserve source URLs, prefer authoritative and recent sources, and make claims traceable to the sources used. The router’s decision is a model judgment, so test it with both timeless and time-sensitive prompts.

8. Stage 3: Add automatic image generation

After the reducer combines the text sections, the image-enabled flow asks a model to identify where an image would help explain the blog. Markdown image syntax uses the form ![alternative text](path-or-URL). In a production app, store generated images with stable filenames or URLs and keep an image manifest that maps each image to its prompt, section, and output path.

  • Generate images only where they add explanatory value; avoid decorative images that do not support the content.
  • Use descriptive prompts tied to the exact section.
  • Keep alternative text for accessibility.
  • Ensure the downloaded blog includes its image files, or package the Markdown and assets together.
  • Show generated images in the app’s image tab, as described in the demo.

9. Stage 4: Build the Streamlit GUI

The final stage converts the workflow from a script into a usable application. The demo includes a topic/brief input, a Generate Blog action, progress updates by graph node, tabs for the plan and blog, evidence/citations, execution logs, generated images, downloads, and a way to reopen previously generated blogs.

Suggested UI components

  • Sidebar: topic/brief input, optional audience and tone, Generate button, previous blogs.
  • Progress area: current graph node (router, research, orchestrator, worker, reducer) and status messages.
  • Plan tab: title, audience, tone, planned sections, target word counts, and each section’s goals.
  • Blog tab: render the final Markdown and embedded images.
  • Evidence tab: source links and citation information for research-backed claims.
  • Logs tab: key decisions and node execution details for debugging.
  • Images tab: gallery/list of generated visuals.
  • Download/history: download Markdown and images, and revisit prior blog runs.

10. End-to-end implementation checklist

  1. Define Pydantic schemas for the plan and each section task.
  2. Define graph state fields for topic, plan, research results, section outputs, final blog, citations, images, and logs as needed.
  3. Configure the LLM and use structured output for planner/router responses.
  4. Implement router and optional research node.
  5. Implement planner/orchestrator.
  6. Implement fan-out with one `Send` per task.
  7. Implement worker prompts so each worker writes one section only.
  8. Implement reducer to merge sections in planned order and create a Markdown file.
  9. Add image generation and insert image references where relevant.
  10. Wire graph edges and conditional routing, compile the graph, and invoke it with a topic.
  11. Build the Streamlit interface and persist run history if the app needs it.

Conceptual graph wiring

START → router
router ── research required ──→ research ──→ planner
router ── no research ────────────────────→ planner
planner → fan-out (Send per task) → workers → reducer → END

In LangGraph, the fan-out function commonly returns a list of Send objects from a conditional edge. Make sure your graph’s state reducers are configured to combine parallel worker updates rather than overwriting them.

11. Testing and troubleshooting checklist

  • Does the planner always return a valid structured plan?
  • Does every task have a unique ID, useful title, and clear goal/brief?
  • Does fan-out create exactly one worker invocation per task?
  • Do parallel worker outputs all reach the reducer?
  • Are sections merged in the intended order, rather than relying on accidental completion order?
  • Does the router skip research for timeless topics and request it for current topics?
  • Are search results and citations preserved with their URLs?
  • Does each research-dependent worker receive the relevant evidence?
  • Are generated image files available when the Markdown is downloaded?
  • Does the UI show useful errors if an API call fails or no topic is entered?
  • Can an old blog run be opened again if history is enabled?

Common failure points

  • Vague output: enrich the plan schema and prompts with audience, goals, coverage bullets, and target length.
  • Repeated sections: ask the planner for non-overlapping points and give each worker the full outline.
  • Missing worker results: verify state reducers and graph fan-in configuration.
  • Stale claims: route current topics to research and check publication dates.
  • Broken images: use stable asset paths and package files for download.
  • Hard-to-debug runs: log node names, decisions, and source metadata without exposing secrets.

12. Key takeaways and project potential

  • Planning is valuable when a task has multiple distinct subtasks or needs a consistent structure.
  • The orchestrator–worker pattern separates planning from execution and supports dynamic parallelism.
  • Structured output gives downstream code a stable schema to work with.
  • Better schemas and precise prompts can noticeably improve writing quality before adding more tools.
  • Research makes the agent more useful for current topics; citations make the resulting claims easier to verify.
  • Image generation can turn a plain article into a richer, illustrated blog.
  • A GUI with progress, plan inspection, evidence, logs, images, downloads, and history makes the project more practical to demonstrate.
Portfolio angle: The lesson presents this as a substantial project with room for refinement. A strong portfolio version could add user-specific writing preferences, editable outlines, human approval before execution, source-quality checks, retry/error handling, and persistent project history.

One-line recap: The agent receives a topic, decides whether to research it, creates a structured plan, writes each section through parallel workers, merges the content, optionally adds images, and presents the result through a user interface.
