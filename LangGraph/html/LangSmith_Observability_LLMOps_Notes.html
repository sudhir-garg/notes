What you will learn

LangSmith is introduced in the source lesson as a unified observability and evaluation platform for AI applications. The central idea is to make a complex LLM workflow inspectable, so developers can understand why a result, delay, cost spike, or failure occurred—not merely observe the final answer.

Observe

Inspect inputs, outputs, intermediate steps, latency, token usage, errors, tags, and metadata.

Debug

Locate which component—retriever, prompt, model, tool, or graph node—is responsible for a problem.

Improve

Evaluate versions, compare prompts, label examples, capture feedback, and monitor trends.

PrerequisitesThe lesson assumes familiarity with LangChain and the LangGraph concepts covered earlier in the course. The examples are educational patterns; adapt package names and APIs to the versions installed in your own project.

1. Why do we need LangSmith?

Traditional application debugging often starts with logs, exceptions, and the final output. An LLM application, however, may be a multi-stage workflow containing retrieval, several model calls, tool calls, parsing, retries, and conditional branches. Seeing only the user's input and the final response hides the reason a system behaved poorly.

Scenario A · Latency

Response time grows

A cover-letter workflow normally takes about two minutes, then suddenly takes seven to ten. Without per-step timing, it is unclear whether document retrieval, profile scanning, matching, generation, or proofreading caused the delay.

Scenario B · Cost

Agent cost spikes

A research agent normally costs roughly ₹0.50 per report, but some reports cost ₹2. A prompt change may cause the agent to repeat its research-and-review loop for certain topics.

Scenario C · Quality

RAG hallucination

An HR policy chatbot gives an incorrect leave-policy answer. The fault may be poor retrieval, insufficient context, a weak prompt, or the generator itself.

The debugging question

For each scenario, the real question is not only “What output did we get?” but also:

  • Which component ran, and in what order?
  • What input did each component receive, and what did it return?
  • How long did each step take? How many tokens and how much cost did it consume?
  • Which documents, prompt, model, tool calls, and intermediate states influenced the final answer?
Conceptual illustration: tracing exposes the sequence of component-level operations that a final answer alone cannot reveal.

2. Observability for LLM applications

Observability is the ability to understand a system's internal state by examining its external outputs, such as logs, metrics, and traces. It helps answer why something happened—even when the exact failure was not anticipated.

Three useful signals

SignalWhat it tells youLLM application example
LogsEvents and details about what happened.Tool failed, request timed out, parser raised an exception.
MetricsNumeric measurements aggregated over time.p95 latency, error rate, token consumption, cost per request.
TracesThe end-to-end path of a single execution, including nested operations.Question → retrieval → prompt construction → model → parser.

LLM systems are often non-deterministic: similar or identical inputs may produce different outputs. They also combine opaque model behavior with multi-step workflows. That makes component-level traces particularly valuable when debugging production behavior.

RememberObservability is not just collecting data. The goal is to connect execution evidence to a diagnosis: for example, “the extra latency came from rebuilding the vector index” or “the wrong answer followed retrieval of irrelevant chunks.”

3. The three core concepts: Project, Trace, Run

A project groups executions; each trace represents one end-to-end execution; each run represents an individual component operation.
ConceptMeaningExample
ProjectA named grouping for traces from an application or workflow.job-assistant, rag-demo, or langgraph-evals.
TraceOne end-to-end execution of the application.One user asks, “What is the capital of Peru?” and receives an answer.
RunOne operation/component inside the trace.Prompt template, model call, parser, retriever, tool, or graph node.

For a simple chain with a prompt template, chat model, and string output parser, one trace typically contains at least those three component runs. In a larger RAG or agent workflow, the trace can contain many more nested runs.

5. Tracing a basic LangChain chain

The lesson starts with a simple question-answer chain. Its components are a prompt template, a chat model, and a string output parser. When tracing is enabled, the execution can be inspected in the LangSmith project UI.

Illustrative code

import os
from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

load_dotenv()  # loads local .env variables

prompt = ChatPromptTemplate.from_template(
    "Answer the question clearly and concisely: {question}"
)
model = ChatOpenAI(model="gpt-4o-mini", temperature=0)
parser = StrOutputParser()

chain = prompt | model | parser

answer = chain.invoke({
    "question": "What is the capital of Peru?"
})
print(answer)

This is a teaching example, not a claim that the original lesson used these exact package versions or model defaults. Install compatible packages and configure your API keys first.

What to inspect in the trace UI

  • Trace overview: top-level input, final output, status/error, start time, duration, and model/token/cost information where available.
  • Run tree: prompt template → chat model → output parser.
  • Run details: component input and output, execution duration, model metadata, and errors.

Change the question and invoke the chain again. A second invocation creates another trace in the same project, allowing you to compare executions.

Sequential chains and metadata

The lesson then expands from a single call to a sequential workflow with multiple prompt/model stages. This is where tracing becomes more useful: you can see which stage generated each intermediate result and attach names, tags, and metadata to make runs easier to filter.

# Illustrative configuration pattern for a named, tagged execution
config = {
    "run_name": "summary-workflow",
    "tags": ["tutorial", "text-summarization"],
    "metadata": {
        "workflow_version": "v1",
        "environment": "development"
    }
}

# Many Runnable-based LangChain components accept config:
# result = chain.invoke({"question": "..."}, config=config)
Do not confuse metadata with model outputTags and metadata help organize and filter traces. They do not improve answer quality by themselves; they make experiments and debugging easier to analyze.

6. Tracing a RAG application

A RAG application retrieves relevant documents for a user's question, combines the question and retrieved context in a prompt, and asks an LLM to answer. A correct-looking final answer is not enough to prove that retrieval and generation both worked correctly.

RAG debugging separates retrieval failures from generation failures by inspecting the evidence passed between stages.

Two major failure areas

1. Retrieval failure

The retriever returns irrelevant or incomplete chunks. Example: a notice-period question retrieves company-history content, or k=1 provides too little context for a multi-document answer.

2. Generation failure

The retriever finds good context, but the model ignores it, misinterprets it, or invents details. Causes may include a weak model, prompt changes, or ambiguous instructions.

RAG tracing checklist

  1. Inspect the user's original question.
  2. Inspect the retrieved documents/chunks and their metadata.
  3. Inspect the exact prompt sent to the model, including the context.
  4. Inspect the model's raw response and parsed answer.
  5. Compare duration and errors for retrieval, prompt construction, model call, and parsing.

Trace preprocessing and indexing too

The lesson highlights a common blind spot: by default, framework tracing may capture the chain's runnable components but not every custom preprocessing operation. PDF loading, chunking, embedding, and index construction may happen outside the traced chain. If those operations are slow or failing, the visible trace can be incomplete.

One approach shown in the lesson is to wrap custom functions with a tracing decorator and give each operation a meaningful run name. The exact import path and decorator options depend on the installed SDK version; treat this as a pattern:

# Pattern only: verify imports/options for your installed LangSmith SDK.
from langsmith import traceable

@traceable(name="load-and-index-pdf")
def load_and_index_pdf(pdf_path: str):
    documents = load_pdf(pdf_path)       # your loader function
    chunks = split_documents(documents)  # your splitter function
    index = build_or_load_index(chunks)  # your vector-store logic
    return index

@traceable(name="rag-question")
def answer_question(question: str):
    retriever = get_retriever()
    docs = retriever.invoke(question)
    return rag_chain.invoke({
        "question": question,
        "context": format_documents(docs)
    })
Index caching mattersThe transcript demonstrates a large latency reduction by reusing an existing vector index instead of reloading the PDF, splitting it, embedding every chunk, and rebuilding the index for every query. Rebuild only when the source documents, chunking strategy, embedding model, or index configuration requires it.

Separate setup from query-time work

OperationTypical timingTrace it?
Load PDF / parse pagesIndex build or refreshYes, especially during ingestion and refreshes
Split into chunks and embedIndex build or refreshYes, to find ingestion bottlenecks
Retrieve top-k chunksEach queryYes, part of query-time latency and answer quality
Generate answer and parse outputEach queryYes, to inspect quality, latency, tokens, and errors

7. Tracing an agent

An agent is given a goal and can decide which actions to take, inspect tool observations, and continue until it determines that the task is complete. This loop makes agent behavior less predictable than a fixed chain.

In the lesson's research-agent example, the agent searches for academic papers, extracts key points, summarizes them into a report, and may then answer questions about that report. If a prompt change encourages it to keep improving the report until it is “perfect,” it may repeat expensive work for some topics while behaving normally for others.

What the trace should reveal

  • Each model decision and the selected tool/action.
  • Tool input (for example, a search query) and tool output/observation.
  • How many times the agent loop repeats.
  • Which calls consume the most latency and tokens.
  • Where errors occur and whether retries or repeated tool calls explain cost growth.
Operational lessonAgent prompts and stopping conditions are production controls. Add explicit iteration limits, timeouts, and budgets where appropriate; monitor token/cost per task and test prompt changes against representative cases.

8. LangGraph + LangSmith integration

LangGraph represents a workflow as nodes and edges. Nodes perform operations; edges define possible transitions. Conditional edges can route execution along different paths, and cycles can support iterative workflows. In a non-trivial graph, a trace helps reveal which path actually ran.

LangSmith tracing can help inspect node-level inputs and outputs, node execution times, and the path taken through the graph. This is particularly useful when conditional branches or loops make the workflow difficult to reason about from source code alone.

Evaluator graph from the lesson

The transcript also describes a graph-based evaluation workflow with separate nodes that score dimensions such as analysis quality and clarity, followed by a final node that combines the dimension-level feedback into an overall evaluation. Structured model output is used to return scores and feedback in a predictable schema.

# Conceptual schema for structured evaluation output
from pydantic import BaseModel, Field

class DimensionScore(BaseModel):
    score: float = Field(ge=0, le=1)
    feedback: str

class EvaluationResult(BaseModel):
    analysis: DimensionScore
    clarity: DimensionScore
    overall_score: float = Field(ge=0, le=1)
    overall_feedback: str

The schema above illustrates the structured-output idea described in the lesson; it is not a verbatim reproduction of the course repository's graph code.

10. Observability vs monitoring

DimensionObservabilityMonitoring
Primary focusUnderstand one execution in detail.Understand system health and trends across many executions.
Typical unitA trace and its component runs.A time window, metric series, dashboard, or alert.
Questions answeredWhy did this request take 10 seconds? Which retrieval result was used?Has p95 latency risen over the last hour? Did error rate cross a threshold?
Useful dataInputs, outputs, intermediate state, run timing, errors.Aggregated latency, cost, tokens, failure rate, user ratings.

They complement each other. Monitoring can alert a team that latency has increased; tracing helps identify the exact stage causing the increase. A single slow request may be an outlier, while a sustained trend can indicate a systemic issue.

11. Evaluation: measure quality repeatably

LLM output varies, so manually checking a handful of examples is not a reliable way to compare versions. Evaluation provides a repeatable procedure for running a dataset through a system and scoring the results against defined criteria.

Common evaluation approaches mentioned

EvaluatorHow it worksGood fitLimitations to consider
Code / rule-basedExact match, schema checks, string rules, deterministic metrics.Structured outputs, format constraints, known answers.May miss semantic correctness or nuanced quality.
Human annotationA person labels or rates model outputs.High-stakes quality judgments, creating trusted labels.Costs time; guidelines and reviewer agreement matter.
LLM-as-a-judgeA separate model scores a response using a rubric.Semantic relevance, helpfulness, faithfulness, style.Can be biased or inconsistent; validate against human judgments.
Similarity / semantic metricCompare output with a reference using lexical or embedding-based similarity.Large-scale approximate comparisons.Similarity alone does not guarantee factual correctness.

Offline and online evaluation

Offline evaluation

Run a fixed dataset before release or during CI. Useful for regression tests, prompt/model comparisons, and release gates.

Online evaluation

Evaluate sampled production traffic or live interactions. Useful for detecting real-world failures, distribution shifts, and quality changes not represented in the test set.

Evaluation dataset

Store representative inputs, expected outputs or labels, and relevant metadata. Keep a stable test set for fair comparisons.

Evaluation workflow

  1. Define the task and success criteria (for example, groundedness, relevance, factuality, or schema validity).
  2. Build a representative dataset, including common cases and difficult edge cases.
  3. Choose an evaluator and specify its rubric or scoring logic.
  4. Run the current version and record scores plus individual examples.
  5. Change one variable—prompt, model, retriever, or graph logic—and rerun.
  6. Inspect regressions and trade-offs before release.
RAG-specific evaluationSeparate retrieval quality from answer quality. A response can be poor because the right evidence was never retrieved, or because the model failed to use evidence that was retrieved. Component-level metrics and trace inspection help distinguish these cases.

12. Prompt experimentation

Prompt wording can change model behavior, token usage, latency, and cost. A seemingly small instruction such as “keep improving the report until it is perfect” may increase agent iterations for only some inputs. Prompt experimentation helps compare alternatives systematically.

Controlled comparison

  1. Create two prompt versions, A and B.
  2. Run both against the same evaluation dataset and, where possible, comparable model settings.
  3. Compare quality scores alongside latency, token usage, and cost.
  4. Inspect examples where the results differ.
  5. Promote the better prompt only after checking both improvements and regressions.
# Example experiment record — keep the dataset and scoring rubric fixed
experiment = {
    "dataset": "support-qa-v1",
    "candidates": ["prompt-A", "prompt-B"],
    "metrics": [
        "groundedness",
        "answer_relevance",
        "latency_ms",
        "total_tokens",
        "estimated_cost"
    ]
}
Fair test principleChange one major factor at a time when diagnosing a regression. If the prompt, model, retriever configuration, and dataset all change together, it becomes difficult to identify what caused the outcome.

13. Datasets and manual annotation

Datasets turn one-off observations into repeatable tests. The lesson describes creating datasets from examples and using manual annotation to label outputs. Traces can be a useful source of realistic examples, especially when users encounter edge cases in production.

A useful evaluation example record

{
  "inputs": {
    "question": "What is the notice period?"
  },
  "reference": {
    "answer": "Use the current company policy document."
  },
  "metadata": {
    "category": "HR-policy",
    "difficulty": "normal",
    "source_version": "policy-2026-09"
  }
}

The JSON above is an illustrative record shape, not a required LangSmith schema. Use the dataset format supported by the SDK/UI version you have installed.

Annotation guidelines

  • Write clear criteria before labeling: factuality, groundedness, relevance, completeness, tone, or format.
  • Distinguish “incorrect answer” from “insufficient context” and “correct refusal.”
  • Record the source policy/document version when facts can change over time.
  • Use representative examples; do not build a dataset only from easy successes.
  • Review disagreement between annotators and refine ambiguous guidelines.

A reusable dataset can be used to compare future prompt or model versions, detect regressions, and measure whether a change improves the system beyond a few cherry-picked examples.

14. User feedback and collaboration

Capture feedback alongside traces

The lesson discusses attaching feedback such as thumbs-up/down ratings or structured feedback to the trace for the corresponding interaction. This makes it possible to study user sentiment alongside the exact prompt, model, and execution state that produced the answer.

  • Capture a rating or a structured feedback label where appropriate.
  • Associate it with the relevant trace or response.
  • Aggregate feedback across traces to identify patterns.
  • Investigate low-rated examples using the trace details and add valuable cases to an evaluation dataset.

Team collaboration

Instead of sending screenshots and manually describing a failure, a developer can share a trace link with a teammate, who can inspect the same execution. The lesson also mentions collaboration around prompt versions and shared dashboards.

Privacy noteTraces can contain user prompts, retrieved documents, tool inputs, and model outputs. Decide what may be logged, redact sensitive fields where needed, restrict access, and set retention policies before enabling production tracing broadly.

15. The bigger picture: LLMOps

The lesson groups observability, monitoring, evaluation, prompt experimentation, dataset creation, annotation, feedback, and collaboration under the broader idea of LLMOps—the practices and tooling required to build, evaluate, deploy, monitor, and continuously improve LLM-powered applications.

Building a model-powered feature is only one part of the work. Operating it reliably requires feedback loops, regression tests, monitoring, debugging tools, and team practices that keep quality and cost under control.

16. Practical production checklist

  • Enable tracing in development and confirm a test invocation appears in the expected project.
  • Give projects, runs, tags, and metadata meaningful names.
  • Verify that custom preprocessing, ingestion, tool calls, and graph nodes are included where needed.
  • Inspect inputs and outputs at component boundaries, especially retrieved context and final prompts.
  • Measure latency, tokens, and cost at both trace and component levels where available.
  • Set explicit agent iteration limits, timeouts, and cost budgets.
  • Cache/reuse vector indexes; avoid rebuilding an index on every query unless necessary.
  • Maintain a representative evaluation dataset and rerun it after prompt, model, retriever, or code changes.
  • Use production monitoring and alerts for sustained changes in latency, errors, cost, or feedback.
  • Protect API keys; exclude secret files from version control and rotate exposed credentials.
  • Review privacy, redaction, access control, and retention for logged prompts/documents.
  • Share trace links and record the context needed for teammates to reproduce and investigate issues.

17. Quick glossary

TermPlain-English meaning
ObservabilityAbility to investigate a system's internal behavior from its emitted evidence.
TraceThe recorded end-to-end path of one application execution.
RunOne operation within a trace, such as a model call or retriever call.
ProjectA named group of related traces.
RAGRetrieval-Augmented Generation: retrieve evidence and supply it to a model before generating an answer.
RetrieverComponent that finds relevant documents/chunks for a query.
GeneratorThe model/prompt stage that produces the answer from the question and context.
AgentA goal-directed system that chooses actions/tools and may repeat a reasoning-action-observation loop.
LangGraphA framework for defining stateful workflows as nodes and edges, including conditional routes and cycles.
LLM-as-a-judgeUsing one model to assess another model's output against a rubric.
Offline evaluationRepeatable testing on a fixed dataset, commonly before release.
Online evaluationEvaluation of live or sampled production interactions.
LLMOpsOperational practices for evaluating, deploying, monitoring, and improving LLM applications.

Final takeaway

Use LangSmith not just to see that an LLM application failed, slowed down, or became expensive, but to understand which step caused the behavior. Start with a traceable baseline, instrument custom steps, keep reusable evaluation datasets, compare changes systematically, and monitor the system after deployment.
