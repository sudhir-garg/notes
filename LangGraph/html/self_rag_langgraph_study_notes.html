1. Why traditional RAG needs improvement

A conventional RAG pipeline commonly retrieves documents for every query, adds them to the prompt, and asks the LLM to generate an answer. Retrieval can help with private or current information, but retrieved text is not automatically relevant, accurate, or sufficient.

Problem 1 — Indiscriminate retrieval

The system retrieves even when retrieval is unnecessary. For “How many seconds are in a minute?”, the model may already know the answer. Extra context can add noise, reduce answer clarity, and consume computation.

Lesson: decide whether retrieval is needed before searching.

Problem 2 — Blind trust in documents

Semantic similarity does not guarantee that a passage answers the question. A document about how diabetes affects blood sugar may be retrieved for “What causes diabetes?” even though it does not explain the cause.

Lesson: judge each retrieved document for relevance.

Problem 3 — No answer verification

A basic RAG chain may pass the generated answer directly to the user without checking whether claims are supported by the retrieved evidence or whether the answer actually answers the question.

Lesson: verify grounding and usefulness after generation.

2. What is Self-RAG?

Self-RAG means Self-Reflective Retrieval-Augmented Generation. Instead of blindly trusting every retrieved passage and every generated answer, the workflow evaluates its own decisions at multiple stages and changes course when necessary.

Core idea: retrieve only when needed, filter irrelevant evidence, check whether claims are supported, revise unsupported answers, and verify that the final response answers the user’s question.

Self-reflection here is an engineering mechanism implemented through model-based evaluators and conditional graph edges—not a claim that the model has human consciousness.

3. The four questions Self-RAG asks

Reflection questionWhere it is checkedWhat it prevents
1. Is retrieval needed?Before retrievalUnnecessary retrieval for general knowledge or simple explanations.
2. Are the retrieved documents relevant?After retrieval, document by documentIrrelevant or merely topic-similar passages contaminating the context.
3. Is the answer grounded in the evidence?After generationUnsupported claims or hallucinations.
4. Does the answer actually answer the question?After grounding checksFactually supported text that still misses the user’s intent.

Grounding verdicts

Fully supported

Every factual claim is supported by the supplied context. The answer can proceed to the usefulness check.

Partially supported

Some claims are supported, but other claims are not present in the evidence. Revise the answer to remove unsupported details.

No support

The answer is not supported by the retrieved context. Treat it as a grounding failure and attempt a strict revision or return no answer.

Example: supported vs. invented details

Suppose the context says: “Clinical trials reported mild dizziness and nausea.” An answer that adds “fatigue and headaches, especially in older patients” contains extra claims not supported by that passage. Even if those claims sound plausible, they should not be presented as evidence-based facts.

Important distinction: “grounded” and “useful” are different. An answer can repeat only true details from the documents yet still fail to answer the actual question.

4. Self-RAG architecture at a glance

The lesson builds the graph incrementally. This diagram summarizes the complete workflow described in the transcript.

Conceptual diagram: the actual graph includes conditional edges and bounded loops. A direct-generation branch may finish without retrieval; the retrieval branch goes through relevance filtering, generation, support checking, and usefulness checking.

Two bounded loops

  • Revision loop: if an answer is partially or not supported, revise it using only the supplied context and run the support check again.
  • Query-rewrite loop: if the answer is grounded but not useful, rewrite the retrieval query, retrieve again, and repeat the pipeline.
Safety valve: both loops need a maximum retry count. The lesson uses examples such as five or ten attempts. If the limit is reached without a satisfactory answer, return “No answer found” rather than looping indefinitely.

5. Building it in LangGraph — step by step

The lesson uses a fictional company called Nexa AI Solutions and three document groups: company profile, company policies, and product/pricing information. Documents are split into chunks (the transcript’s example uses chunk size 600 and overlap 150), embedded in a vector store, and accessed through a retriever.

1Decide whether retrieval is needed

Use an LLM with structured output to return a boolean. Retrieval is appropriate for specific company facts, policy details, source-dependent information, or facts unlikely to be in the model’s general knowledge. General definitions and explanations may be answered directly. If uncertain, the lesson’s prompt prefers retrieval.

from pydantic import BaseModel, Field

class RetrievalDecision(BaseModel):
    should_retrieve: bool = Field(
        description="True when external/company documents are needed"
    )

# Conceptual pattern:
decision_llm = llm.with_structured_output(RetrievalDecision)

def decide_retrieval(state):
    result = decision_llm.invoke([
        ("system", """Decide whether the question needs company-specific
facts or external evidence. Use False for general explanations or
definitions. If unsure, choose True."""),
        ("human", state["question"])
    ])
    return {"need_retrieval": result.should_retrieve}

2Retrieve, then filter relevant documents

First retrieve a candidate set. Then judge each document against the user’s question and keep only documents that contain information useful for answering it. Similar topic does not necessarily mean relevant evidence.

class RelevanceDecision(BaseModel):
    relevant: bool = Field(
        description="Whether this document helps answer the question"
    )

relevance_llm = llm.with_structured_output(RelevanceDecision)

def retrieve_docs(state):
    # In the full workflow, this uses state["retrieval_query"].
    docs = retriever.invoke(state.get("retrieval_query", state["question"]))
    return {"docs": docs}

def filter_relevant_docs(state):
    kept = []
    for doc in state.get("docs", []):
        verdict = relevance_llm.invoke([
            ("system", "Judge whether the document helps answer the question."),
            ("human", f'Question: {state["question"]}\nDocument: {doc.page_content}')
        ])
        if verdict.relevant:
            kept.append(doc)
    return {"relevant_docs": kept}

3Generate from filtered context

Merge relevant document text into a context string and ask the model to answer from that context. If no relevant document remains, do not invent an answer from the absent company information.

def generate_from_context(state):
    docs = state.get("relevant_docs", [])
    if not docs:
        return {"context": "", "answer": "No answer found"}

    context = "\n\n".join(doc.page_content for doc in docs)
    response = llm.invoke([
        ("system", """Answer the question using only the supplied context.
Do not add unsupported facts. If the context is insufficient, say so."""),
        ("human", f'Question: {state["question"]}\n\nContext:\n{context}')
    ])
    return {"context": context, "answer": response.content}

4Check whether the answer is supported

The support evaluator receives the question, answer, and context. It returns a verdict—fully supported, partially supported, or no support—plus evidence snippets. Only a fully supported answer proceeds to usefulness checking.

from typing import Literal
from pydantic import BaseModel, Field

class SupportCheck(BaseModel):
    verdict: Literal["fully_supported", "partially_supported", "no_support"]
    evidence: list[str] = Field(
        description="Context excerpts that support the answer, if any"
    )

support_llm = llm.with_structured_output(SupportCheck)

def check_support(state):
    result = support_llm.invoke([
        ("system", """Compare every factual claim in the answer with the
context. Do not use outside knowledge. Mark fully_supported only if all
claims are supported; partially_supported if some are; no_support if none
are adequately supported. Return evidence excerpts."""),
        ("human", f'Question: {state["question"]}\n'
                  f'Context: {state.get("context", "")}\n'
                  f'Answer: {state.get("answer", "")}')
    ])
    return {"support": result.verdict, "evidence": result.evidence}

5Revise unsupported answers with a retry limit

For partially supported or unsupported answers, instruct the model to remove every claim not directly supported by the context. Count each revision attempt. Re-check the revised answer rather than assuming the revision succeeded.

MAX_REVISION_TRIES = 5

def revise_answer(state):
    revised = llm.invoke([
        ("system", """You are a strict answer reviser. Rewrite the answer
using only facts explicitly supported by the context. Remove unsupported
claims; do not fill gaps using general knowledge. If evidence is insufficient,
return 'No answer found.'"""),
        ("human", f'Question: {state["question"]}\n'
                  f'Context: {state.get("context", "")}\n'
                  f'Current answer: {state.get("answer", "")}')
    ])
    return {
        "answer": revised.content,
        "revision_tries": state.get("revision_tries", 0) + 1
    }

def route_after_support(state):
    if state.get("support") == "fully_supported":
        return "check_usefulness"
    if state.get("revision_tries", 0) >= MAX_REVISION_TRIES:
        return "no_answer"
    return "revise_answer"

6Evaluate usefulness and rewrite the retrieval query

Even a grounded answer may omit the key fact needed to answer the user. A usefulness evaluator judges the question and answer and returns a verdict plus a reason. If useful, finish. If not useful, rewrite the retrieval query to improve the next search, then rerun retrieval and evaluation. Stop after a fixed number of retries.

class UsefulnessCheck(BaseModel):
    useful: bool
    reason: str

usefulness_llm = llm.with_structured_output(UsefulnessCheck)

def check_usefulness(state):
    result = usefulness_llm.invoke([
        ("system", """Decide whether the answer directly and sufficiently
answers the user's question. Judge usefulness, not just factual support.
Return a concise reason."""),
        ("human", f'Question: {state["question"]}\nAnswer: {state["answer"]}')
    ])
    return {"useful": result.useful, "usefulness_reason": result.reason}

class QueryRewrite(BaseModel):
    retrieval_query: str = Field(
        description="Short query optimized for vector retrieval"
    )

rewrite_llm = llm.with_structured_output(QueryRewrite)

def rewrite_query(state):
    result = rewrite_llm.invoke([
        ("system", """Rewrite the user's question as a short query for
searching internal company documents. Preserve key entities and add 2–5
high-signal terms. Do not invent facts."""),
        ("human", f'Question: {state["question"]}\n'
                  f'Previous query: {state.get("retrieval_query", "")}\n'
                  f'Previous answer: {state.get("answer", "")}')
    ])
    return {
        "retrieval_query": result.retrieval_query,
        "rewrite_tries": state.get("rewrite_tries", 0) + 1
    }
Graph integration: these are node-level patterns, not a complete drop-in graph. The final LangGraph must define a shared state schema, register nodes, connect START/END, add conditional routing, initialize counters, and compile the graph. Route names must match registered node names.

6. Testing the workflow

The lesson demonstrates the graph using the fictional Nexa AI Solutions documents. Example test categories include:

QuestionExpected pathWhat to inspect
“What is machine learning?”Direct generationneed_retrieval = False; no company documents should be needed.
“Who is the CEO of Nexa AI?”Retrieve and filterThe CEO passage should survive relevance filtering; the answer should cite/support the company document.
“How many employees does Nexa AI have?”Retrieve → generate → support → usefulnessClaims should be supported by the company profile. The transcript’s example mentions “85+ employees.”
“Does Nexa AI offer a free trial, and for how long?”Retrieve, then possibly no answerIf the documents do not say, the model must not invent a 14-day trial.
“Describe Nexa AI’s company culture.”Retrieve and evaluate; may need revision or rewritten queryCheck whether the answer adds plausible but unsupported culture claims and whether the answer addresses the question.

Practical debugging checklist

  • Print the retrieval decision and current retrieval query.
  • Compare total retrieved documents with the relevant-document count.
  • Inspect the exact context passed to the answer generator.
  • Log support verdicts and evidence excerpts for every answer.
  • Track revision and query-rewrite counters.
  • Check usefulness independently from factual grounding.
  • Ensure empty evidence, failed structured output, or exhausted retries lead to a safe fallback.
  • Keep the original user question separate from the rewritten retrieval query.

7. Traditional RAG vs. Self-RAG

AspectTraditional RAG (as discussed in lesson)Self-RAG workflow
RetrievalTypically retrieves for each queryFirst decides whether retrieval is needed
Document relevanceMay pass retrieved passages straight to generationJudges documents and filters irrelevant ones
GroundingMay accept the first generated answerChecks whether claims are supported by evidence
Answer qualityMay not explicitly verify question coverageChecks usefulness and can search again
Control flowOften a simple retrieve-then-generate chainConditional branches and bounded retry loops
Trade-offSimpler and usually cheaper to runMore LLM calls, latency, and implementation complexity in exchange for stronger checks

8. Key takeaways

  • Self-RAG is built around self-reflection at decision points, not retrieval alone.
  • Semantic similarity is a candidate-finding mechanism—not proof that a passage answers the question.
  • Every factual claim should be supported by the context when the task requires document-grounded answers.
  • Grounding and usefulness are separate checks.
  • Revision removes unsupported details; query rewriting attempts to retrieve better evidence.
  • Use bounded retries and a clear “No answer found” fallback.
  • The lesson builds the graph progressively: retrieval decision → relevance filter → context-based generation → support check → answer revision → usefulness check → query rewrite and re-retrieval.
