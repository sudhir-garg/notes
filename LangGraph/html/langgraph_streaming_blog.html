01 · Overview

What this tutorial builds

The tutorial continues an existing chatbot project and adds streaming so the user can see the assistant's answer as it is generated instead of waiting for the complete answer to appear.

The project is developed incrementally: first a basic LLM chatbot, then short-term conversation memory, then a user interface, and now streaming output. The implementation discussed here uses a LangGraph graph on the backend and Streamlit for the frontend.

Plan of action

  1. Understand the user-experience problem caused by waiting for a complete response.
  2. Define LLM streaming and identify its main benefits.
  3. Replace a one-shot graph call such as graph.invoke(...) with a streaming call such as graph.stream(...) when appropriate.
  4. Read the stream's message chunks and extract their text content.
  5. Use Streamlit's st.write_stream() to display generated text progressively.
  6. Save the completed assistant answer in session state so it remains visible on later reruns.
Core idea: streaming changes how output is delivered to the interface. It does not, by itself, make the model reason better or guarantee that the total generation takes less time.
02 · The problem

Why all-at-once responses feel slow

Imagine asking a chatbot to write a 500-word blog post. In a non-streaming flow, the model generates the answer and the app waits for the completed result before displaying it. During that interval, the chat area can appear blank or frozen.

Without streaming

The user sees little or nothing while the model works. The full answer appears only after generation completes.

With streaming

Partial output appears as it becomes available. The user can start reading while the rest of the answer is still being generated.

There are two practical issues with the all-at-once approach:

  • Perceived delay: a long generation can take several seconds, leaving the user unsure whether the app is working.
  • Readability: a large block of text or code arrives all at once rather than unfolding progressively.
03 · Concept

What is LLM streaming?

LLM streaming means sending parts of a model's response to the application as those parts become available, instead of waiting for the entire response before returning anything.

These parts are often called chunks. A chunk may contain one or more tokens; it is not guaranteed to be exactly one word or one character. Tokenization is a model-level representation and a token may be a word, part of a word, punctuation, or another text unit.

TermMeaning
TokenA unit used by the model to represent input or output text.
ChunkA piece of streamed output delivered to the application; it can contain multiple tokens.
Generator / iteratorA Python object that yields values progressively as it is iterated.
Time to first token (TTFT)The time from sending a request until the first generated content is available. In a UI, transport and rendering also affect when it becomes visible.
Final responseThe assembled answer after all relevant chunks have been received.
Important distinction: a typewriter animation can imitate streaming by revealing already-generated text slowly. True model streaming delivers partial output while generation is still in progress. Streamlit's st.write_stream() can render an iterable or generator progressively; the upstream source must itself yield incrementally for genuine end-to-end streaming.
04 · Benefits

Why streaming matters

1. Faster perceived response

The model may still need time to complete a long answer, but the user sees the first useful content earlier. This reduces the impression that the app has frozen and can help users understand that work is underway.

2. More natural conversation

Progressive output makes the interaction feel more responsive and keeps the user engaged. It resembles the turn-taking rhythm of a live conversation more closely than a long silent pause followed by a complete answer.

3. Better long-form text and code experience

When an answer includes a long explanation or a large code sample, progressive rendering lets the user begin reading earlier. It can make the output easier to follow, although the interface should avoid repeatedly re-rendering expensive components for every tiny chunk.

4. Supports multimodal and voice interfaces

Voice assistants can begin speaking before the entire response is complete. More generally, streaming patterns can deliver incremental text, status events, or other outputs to a responsive interface.

5. Ability to stop work early

If an application supports cancellation and propagates it to the model/provider, the user may stop an unwanted generation before it finishes. This can reduce unnecessary work and potentially token cost. Merely hiding the output in the UI does not guarantee that generation has stopped.

6. Progress updates for agent workflows

An agent may need to search, call tools, inspect results, and then answer. Streaming can communicate intermediate status such as “Searching for sources” or “Processing results.” These status updates are different from the assistant's final answer text.

05 · Architecture

How the pieces fit together

The LangGraph backend is responsible for executing the graph and yielding stream events. The Streamlit frontend consumes the yielded text and renders it in the chat message area.

  1. Collect the user's message.
  2. Pass the correct state and configuration to the graph.
  3. Iterate over the graph's stream events.
  4. Extract only the content intended for the visible answer.
  5. Yield that content to Streamlit's streaming renderer.
  6. Save the completed assistant response in the conversation history.
06 · Backend

Streaming from LangGraph

The central change in the tutorial is to use a streaming API instead of waiting for a single completed result. A normal graph invocation returns the graph's final result; a stream call returns an iterable of events/chunks that can be consumed as they arrive.

Non-streaming patternPython
# Typical one-shot pattern
result = chatbot.invoke(
    {"messages": [HumanMessage(content=user_input)]},
    config=config,
)

# The UI usually waits for result to be ready
answer = result["messages"][-1].content
Streaming pattern — message chunksPython
from langchain_core.messages import HumanMessage

config = {"configurable": {"thread_id": "conversation-1"}}
input_state = {
    "messages": [HumanMessage(content="What is the recipe for pasta?")]
}

for message_chunk, metadata in chatbot.stream(
    input_state,
    config=config,
    stream_mode="messages",
):
    if message_chunk.content:
        print(message_chunk.content, end="", flush=True)

This follows the message-stream pattern demonstrated in the source transcript: supply the initial state, a configuration (including a thread ID where the graph uses checkpointed conversation state), and a stream mode. Iterate through the yielded pair and read the message chunk's content.

Version note: LangGraph/LangChain streaming APIs and event formats can vary by version. In the documented message-stream pattern, stream_mode="messages" yields a message chunk and metadata pair. Check the documentation for the exact version installed in your project, especially when combining multiple stream modes or using async execution.

Why does the loop matter?

Calling chatbot.stream(...) gives the application an iterable stream. The loop requests each next event and handles it. Printing each content fragment with end="" avoids inserting a newline after every chunk; flush=True asks Python to flush the output buffer so terminal output is visible promptly.

What is a Python generator?

A generator is an iterator that produces values as needed, commonly using yield. Rather than building a complete list in memory and returning it all at once, a generator can supply one value, pause, and continue later.

def number_stream():
    yield "First "
    yield "second "
    yield "third."

for part in number_stream():
    print(part, end="", flush=True)

Output: First second third.

Do not assume every stream is a plain generator internally; the important interface property is that it can be iterated incrementally.

07 · Frontend

Render the stream in Streamlit

Streamlit provides st.write_stream() to consume a generator or iterable and display the content progressively with a typewriter-style effect. This keeps the UI code compact: the app prepares an iterator that yields text fragments, and Streamlit handles the progressive rendering.

Minimal text generatorPython
def answer_text_stream():
    for message_chunk, metadata in chatbot.stream(
        input_state,
        config=config,
        stream_mode="messages",
    ):
        if message_chunk.content:
            yield message_chunk.content
Use it inside an assistant chat bubblePython
with st.chat_message("assistant"):
    final_answer = st.write_stream(answer_text_stream())

# Keep the final response for chat history / reruns
st.session_state.messages.append({
    "role": "assistant",
    "content": final_answer,
})

st.write_stream() returns the completed content it has written (for a text-only generator, this is the assembled text). Saving that returned value means the app can render the conversation again after Streamlit reruns the script.

Session state pattern

import streamlit as st

if "messages" not in st.session_state:
    st.session_state.messages = []

for message in st.session_state.messages:
    with st.chat_message(message["role"]):
        st.markdown(message["content"])

user_input = st.chat_input("Ask something")

if user_input:
    st.session_state.messages.append({
        "role": "user",
        "content": user_input,
    })
    with st.chat_message("user"):
        st.markdown(user_input)

    # Generate and display the assistant response here.
    # Append the completed response to session_state afterwards.
Key integration lesson from the transcript: the backend graph does not necessarily need to be redesigned. Much of the UI change happens where the app previously called invoke() and then displayed the completed assistant message. The frontend now consumes a stream and stores the assembled final text.
08 · Put it together

Illustrative end-to-end Streamlit pattern

The following is a reusable pattern, not a drop-in replacement for every project. It assumes chatbot is an already-compiled LangGraph graph that accepts a messages state, and that the graph/provider supports message streaming. Adapt the state schema, model setup, imports, and checkpoint configuration to your existing application.

import streamlit as st
from langchain_core.messages import HumanMessage

# Assumption: `chatbot` is your compiled LangGraph graph.
# Its state schema must accept {"messages": [...]}.

if "messages" not in st.session_state:
    st.session_state.messages = []

# Render previous conversation turns
for item in st.session_state.messages:
    with st.chat_message(item["role"]):
        st.markdown(item["content"])

user_input = st.chat_input("Send a message")

if user_input:
    # Record and display the user message
    st.session_state.messages.append({
        "role": "user",
        "content": user_input,
    })
    with st.chat_message("user"):
        st.markdown(user_input)

    # Use a stable thread ID if the graph uses a checkpointer.
    # In a real multi-user app, scope this ID safely per conversation/user.
    config = {
        "configurable": {
            "thread_id": "streamlit-chat-session"
        }
    }
    input_state = {
        "messages": [HumanMessage(content=user_input)]
    }

    def text_chunks():
        for message_chunk, metadata in chatbot.stream(
            input_state,
            config=config,
            stream_mode="messages",
        ):
            # Some graph streams can include tool/model messages.
            # Add filters here if only a specific node's output should be shown.
            content = message_chunk.content
            if isinstance(content, str) and content:
                yield content
            # Some integrations can return structured content blocks.
            # Handle those explicitly if your model uses multimodal output.

    with st.chat_message("assistant"):
        final_answer = st.write_stream(text_chunks())

    st.session_state.messages.append({
        "role": "assistant",
        "content": final_answer,
    })
Important: this example is intentionally focused on the streaming boundary. If your graph uses a different state schema, a tool-calling flow, multiple model nodes, or a different stream API version, adapt the input and filtering logic. Avoid showing internal tool-call payloads as if they were user-facing prose.

Practical implementation notes

  • Use the user's actual prompt in input_state; do not leave a test prompt hard-coded in production code.
  • Keep a stable conversation/thread ID when checkpointed memory is required. Use an appropriately scoped ID rather than sharing one ID across unrelated users.
  • Choose a stream mode that matches the data you need. Message chunks are useful for incremental LLM text; update events are useful for state/progress changes.
  • Store the completed answer, not the generator object, in chat history.
  • Consider exceptions and display a useful error message if generation fails partway through.
09 · Stream modes

Choosing a LangGraph stream mode

The transcript introduces four modes: updates, values, custom, and messages. They serve different purposes; they are not interchangeable.

ModeUse it forTypical purpose
messagesLLM message chunks plus metadataDisplay generated text progressively as it is produced.
updatesState updates from graph nodesObserve which node updated the graph and inspect incremental state changes.
valuesFull graph state snapshotsObserve the graph's state after steps, useful for debugging or state-aware UIs.
customApplication-defined stream dataEmit custom progress messages or events from graph code.

Exact payload shapes depend on LangGraph version and whether one or multiple stream modes are requested. Inspect and test the actual events before writing production parsing logic.

10 · Debugging

Common mistakes and how to check them

1. The answer is still hard-coded

In the transcript, the first UI test kept returning a pasta recipe even when the user asked about cricket. The reason was that the backend input still contained a hard-coded pasta question. Replace it with the current UI value, such as user_input.

# Incorrect for a real chat UI: fixed prompt
input_state = {
    "messages": [HumanMessage(content="What is the recipe to make pasta?")]
}

# Better: pass the prompt submitted by the user
input_state = {
    "messages": [HumanMessage(content=user_input)]
}

2. The stream appears as one final block

  • Check whether the model/provider supports streaming.
  • Confirm the graph call is a streaming call, not a one-shot invocation.
  • Make sure the frontend consumes the iterator progressively.
  • Check whether an intermediate layer buffers output before forwarding it.

3. The UI displays unexpected messages

Message streams may contain chunks from different graph nodes, including tool-calling or intermediate model steps. Inspect the metadata and filter by the appropriate node/model when only the final assistant response should be visible. Do not assume every yielded message chunk belongs in the chat bubble.

4. Previous answers disappear after a rerun

Streamlit reruns the script after interactions. Store the completed user and assistant messages in st.session_state, and render saved messages at the beginning of the script.

5. Memory seems inconsistent

When using a checkpointer, confirm that the graph receives the intended thread ID and that the graph state schema handles messages correctly. A Streamlit session history and LangGraph checkpointed memory are related but separate mechanisms: saving text in the UI does not automatically persist graph state, and graph checkpoints do not automatically populate the UI history.

6. Errors happen after partial output

Wrap the generation step in error handling and communicate that generation failed. If the user can cancel a response, ensure cancellation is propagated upstream where supported; simply stopping the display may leave model work running.

Pre-run checklist

  • The graph has been compiled and the backend is available to the frontend.
  • The user's prompt is passed dynamically, not hard-coded.
  • The graph input matches its state schema.
  • The selected stream mode matches the expected event structure.
  • The text generator yields only the intended content.
  • st.write_stream() receives an iterable/generator.
  • The final assembled answer is saved to session state.
  • Thread IDs are stable for the intended conversation and safely scoped.
  • Errors and empty chunks are handled gracefully.
11 · Recap

Key takeaways

  1. Streaming delivers partial output incrementally. The UI can show content before the full answer is complete.
  2. Streaming improves perceived responsiveness. It is especially useful for long text, code, voice interfaces, and agent progress updates.
  3. LangGraph: use a streaming API and iterate over the events/chunks it yields. For token-level LLM message output, the transcript demonstrates stream_mode="messages".
  4. Streamlit: pass a text-yielding generator to st.write_stream() to render the answer progressively.
  5. Persist the final text. Store the completed assistant response in st.session_state so it remains in the chat history after reruns.
  6. Debug the whole pipeline. Verify the prompt, graph state, stream event shape, UI renderer, and conversation persistence.

StreamlitA Python framework for building interactive data and AI applications.
