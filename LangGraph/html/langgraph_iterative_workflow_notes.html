1. What is an iterative workflow?

An iterative workflow (also called a looping workflow) repeats one or more steps to improve an output. Instead of accepting the first model response, the system checks it, gives feedback, and tries again when necessary.

Core idea: Generate a draft → evaluate it against explicit criteria → if it needs improvement, revise it using the feedback → evaluate again.

This pattern is useful when a single LLM call may produce mediocre, repetitive, or insufficiently useful content. The evaluation criteria guide the loop, while a maximum-iteration limit prevents endless retries.

Learning objectives

  • Understand iterative/looping workflows in the LangGraph context.
  • Represent workflow data in a typed state.
  • Create generator, evaluator, and optimizer nodes.
  • Use structured output for reliable evaluation decisions.
  • Route execution with a conditional edge and loop back for another evaluation.
  • Track intermediate drafts and feedback for debugging.

2. Recap: four workflow patterns

PatternHow it behavesTypical use
SequentialTasks run one after another in a fixed order.Extract text, then summarize it, then format the summary.
ParallelMultiple tasks run at the same time when they do not depend on each other.Analyze sentiment, keywords, and language independently.
ConditionalA condition chooses which path executes.Send a support request to billing or technical support.
Iterative / loopingA result is checked; execution repeats when improvement is needed.Draft and refine a social post until it meets a quality threshold.
Iterative workflows often combine the other patterns: the nodes may run sequentially, and a conditional edge determines whether the graph ends or loops back.

3. Example use case: generate a funny, original tweet

The example workflow takes a user-provided topic—such as Indian Railways—and creates a short, funny, original tweet. The draft should not be published automatically just because it was generated: it first goes through an evaluator.

Why use a loop?

  • The first LLM response may not be funny or original enough.
  • A separate evaluator can apply consistent criteria.
  • Specific feedback tells the optimizer what to change.
  • The revised tweet is evaluated again rather than being accepted blindly.

In a production system, the approved draft could be shown to a person for final approval (“human in the loop”) before a platform API publishes it. That publishing step is a proposed real-world extension, not required for the basic graph.

5. Design the graph state

LangGraph nodes read the current state and return updates to it. The example state stores the topic, current tweet, evaluation decision, feedback, iteration counters, and (optionally) histories.

FieldType / examplePurpose
topicstrThe subject supplied by the user.
tweetstrThe latest generated or optimized draft.
evaluation"approved" | "needs_improvement"Controls whether the workflow ends or revises.
feedbackstrExplains strengths and weaknesses and gives revision guidance.
iterationintTracks the current attempt / revision count.
max_iterationsintPrevents endless looping.
tweet_historylist[str] (optional)Retains each draft for inspection.
feedback_historylist[str] (optional)Retains feedback from each evaluation.
Important: Keep field names consistent everywhere—state definition, node return dictionaries, routing logic, and initial input. The source walkthrough encountered a naming mismatch around the maximum-iteration field; consistent naming avoids that class of bug.

Example state schema

from typing import Annotated, Literal
import operator
from typing_extensions import TypedDict

class TweetState(TypedDict):
    topic: str
    tweet: str
    evaluation: Literal["approved", "needs_improvement"]
    feedback: str
    iteration: int
    max_iterations: int
    tweet_history: Annotated[list[str], operator.add]
    feedback_history: Annotated[list[str], operator.add]

The history fields are optional. If you include them, initialize them as empty lists or make sure your graph's input/state handling supports omitted values.

6. Build the nodes

The walkthrough uses three LLM roles. It mentions GPT-4o for generation, GPT-4o mini for evaluation, and GPT-4o for optimization as example choices. These are examples from the source, not a claim that they are the best current models for every task.

1 · GeneratePrompt the model to write a short, funny, original tweet on state["topic"].
2 · EvaluateApply a strict rubric and return a decision plus constructive feedback.
3 · OptimizeRewrite the current draft using the evaluator's feedback and update the iteration count.

6.1 Generator prompt checklist

  • Set the role, e.g. “a funny and clever social-media writer.”
  • Specify the topic from the state.
  • Request a short, original, humorous tweet.
  • Avoid question-and-answer format.
  • Keep the tweet within 280 characters.
  • Encourage observational humor, irony, sarcasm, meme logic, punchlines, and relatable everyday language.

6.2 Evaluator rubric

  • Originality: Does it feel fresh rather than familiar or recycled?
  • Humor: Is it actually funny?
  • Punchiness: Is the payoff concise and clear?
  • Viral potential: Is it relatable and shareable?
  • Format: Does it follow the tweet constraints?

Reject automatically if it uses question-and-answer format, exceeds 280 characters, or relies on a conventional/overused joke, according to the example rubric. An evaluator should return only the defined structured fields rather than free-form prose.

6.3 Structured evaluation output

from pydantic import BaseModel, Field
from typing import Literal

class TweetEvaluation(BaseModel):
    evaluation: Literal["approved", "needs_improvement"] = Field(
        description="Whether the tweet meets the quality criteria"
    )
    feedback: str = Field(
        description="Brief, actionable feedback explaining strengths and weaknesses"
    )

Structured output helps make routing dependable: the graph can check a known field and one of two allowed values rather than trying to infer a decision from an unstructured paragraph.

        )),
    ]

            "Return the structured evaluation and actionable feedback."
        )),
    ]
    result = structured_evaluator_llm.invoke(messages)

        SystemMessage(content="Improve tweets using specific feedback."),
        HumanMessage(content=(
            f"Topic: {state['topic']}\\n"

            "Avoid Q&A format."

        "tweet_history": [tweet],
        "iteration": state["iteration"] + 1,
    }

7. Conditional routing and loop termination

The evaluator node does not directly decide graph topology. A routing function reads the updated state and returns the name of the next node. In the example, approval sends execution to the end; a rejected draft sends it to the optimizer.

Routing logic

from langgraph.graph import END

def route_evaluation(state: TweetState):
    if state["evaluation"] == "approved":
        return END
    if state["iteration"] >= state["max_iterations"]:
        return END
    return "optimize"

This template stops when the draft is approved or the iteration limit has been reached. A production workflow should make the “limit reached but not approved” outcome explicit—for example, mark it as exhausted or send it for human review—rather than treating it as approved.

Connect and compile the graph

from langgraph.graph import StateGraph, START, END

builder = StateGraph(TweetState)
builder.add_node("generate", generate_tweet)
builder.add_node("evaluate", evaluate_tweet)
builder.add_node("optimize", optimize_tweet)

builder.add_edge(START, "generate")
builder.add_edge("generate", "evaluate")
builder.add_conditional_edges(
    "evaluate",
    route_evaluation,
    {
        END: END,
        "optimize": "optimize",
    },
)
builder.add_edge("optimize", "evaluate")

graph = builder.compile()

Exact conditional-edge mapping syntax can vary by LangGraph version. Check the API for the version installed in your project.

8. Track draft and feedback history with reducers

When debugging a loop, inspecting only the final tweet hides what happened during earlier attempts. The walkthrough adds two lists:

  • tweet_history — every generated or optimized draft.
  • feedback_history — the evaluator's feedback for each evaluation.

In a LangGraph state, a reducer defines how updates to a field are combined. Using operator.add for list fields appends new list items instead of replacing the existing list.

from typing import Annotated
import operator

class TweetState(TypedDict):
    # Other state fields omitted here
    tweet_history: Annotated[list[str], operator.add]
    feedback_history: Annotated[list[str], operator.add]

# Each node returns a list containing the new item:
return {
    "tweet_history": [new_tweet],
}
Why return a list? The reducer combines the existing list with the new list. Returning the new tweet as a string instead of a list would not match the intended list-append behavior.

Inspect the result

result = graph.invoke({
    "topic": "Indian Railways",
    "iteration": 1,
    "max_iterations": 5,
    "tweet_history": [],
    "feedback_history": [],
})

for number, tweet in enumerate(result.get("tweet_history", []), start=1):
    print(f"Attempt {number}: {tweet}")

for number, feedback in enumerate(result.get("feedback_history", []), start=1):
    print(f"Feedback {number}: {feedback}")

Histories are useful for tracing why a draft was rejected, whether revisions responded to the feedback, and whether the evaluator is too strict or inconsistent.

Initial input

print(result["tweet"])
print(result["evaluation"])
print(result["iteration"])

What to verify

  • Generation creates a tweet for the requested topic.
  • Evaluation returns exactly one allowed decision plus feedback.
  • An approved tweet reaches the end path.
  • A tweet needing improvement is sent to the optimizer.
  • Optimization increments the iteration count and returns to evaluation.
  • The loop stops at the configured maximum.
  • History lists contain the intermediate drafts and feedback.
  • The final result clearly distinguishes “approved” from “stopped because the limit was reached.”
LLM outputs are variable. A model may approve a draft on the first attempt, so repeated runs will not necessarily show multiple iterations. For predictable tests, use mocked node outputs or a controlled test evaluator rather than deliberately feeding meaningless text to the model.

10. Common pitfalls and practical improvements

Potential issueWhy it mattersBetter practice
State key mismatchA node or router may look up a key that was never provided.Use one spelling consistently, such as max_iterations.
Infinite loopThe evaluator may repeatedly reject the draft.Use a maximum-iteration guard and an explicit exhausted outcome.
Unstructured evaluator textRouting becomes fragile if the model changes wording.Use a schema with a constrained decision field.
Vague rubric“Make it good” gives the evaluator little guidance.Define measurable criteria, rejection rules, and actionable feedback.
Model roles not differentiatedOne model may not be equally strong at writing, judging, and revising.Choose and test models by role, quality, latency, and cost.
History gets overwrittenOnly the most recent draft remains visible.Use a list reducer and return each new item as a one-element list.
Iteration limit treated as approvalA low-quality tweet could be mistaken for a successful result.Return a separate status such as max_iterations_reached or route to human review.
Automatic publishing too earlyA generated post can still be incorrect or unsuitable.Use human approval before calling a social-platform publishing API.

11. Quick recap

  1. Iterative workflow: repeats work to improve an output.
  2. Generator: creates the first draft from the topic.
  3. Evaluator: checks quality and returns a constrained decision plus feedback.
  4. Optimizer: rewrites the draft using the feedback.
  5. Conditional edge: decides whether to end or continue the loop.
  6. Maximum iterations: prevents endless retries.
  7. Reducers and histories: preserve intermediate drafts and feedback.
  8. Human in the loop: can provide a final quality check before publication.
Remember the pattern: Generate → Evaluate → (Approved? End : Optimize → Evaluate again). Always include a reliable stop condition.
