The problem

2. Why add tools to an LLM chatbot?

A language model can explain concepts and hold a conversation, but it may not reliably perform calculations, fetch current information, or retrieve live external data by itself. Tools let the model request an operation from a dedicated function or service.

Tool in the lessonPurposeExample request
CalculatorPerform numerical arithmetic.“What is the product of 654 and 713?”
DuckDuckGo searchSearch the web for information that may be recent or absent from the model's knowledge.“Search for today's top news in India.”
Stock-price toolRequest market data from an external API.“What is the current stock price of Apple?”
Important distinction: tool availability does not guarantee correct results. Search results can be weak, APIs can return errors or stale data, and stock prices depend on the provider, ticker, exchange, and market timestamp. The model should report uncertainty rather than invent missing data.
Key vocabulary

3. Core concepts: tool calling, ToolNode, and tools_condition

Tool calling

A tool-enabled model receives a list of available tools and their descriptions. Based on the user's request, it may return a normal assistant response or a structured tool call containing a tool name and arguments. The model generally requests a tool call; the application executes it.

ToolNode

ToolNode is a prebuilt LangGraph node that executes tool calls found in the graph state's messages. It routes each call to the matching registered tool and returns tool results as messages in the state.

tools_condition

tools_condition is a prebuilt conditional-routing helper. In the common setup, it checks the latest assistant message: if the message contains tool calls, the graph routes to the tools node; otherwise, it routes to the end of the graph.

Model / chat node

Chooses whether to answer directly or request one or more tools. It can also interpret tool results and decide what to do next.

Tool node

Executes the requested tool calls. It does not replace the model's job of composing a polished final answer.

Remember: the LLM chooses the tool and arguments; the application executes the tool; then the LLM can interpret the result and respond.

4. Graph architecture: the important loop

The first attempt in the lesson sends the flow from the model to a tool and then directly to the end. That is insufficient for polished responses and multi-step tasks.

Basic chat graph — before adding tools
START
→
Chat / LLM
→
END

Every request goes to the model, which returns a response. There is no execution path for external actions.

Tool-enabled graph — recommended control flow
START
↓
Chat / LLM
↓
No tool call → END
Tool call → ToolNode
ToolNode returns tool messages to Chat / LLM ↺

The model gets another turn after each tool execution. It can use the result, call another tool, or finish with a user-facing answer.

Typical execution sequence

  1. User message: a question enters the graph in the messages state.
  2. Model decision: the model answers directly or emits a tool call.
  3. Conditional route: tools_condition directs tool calls to ToolNode; otherwise the graph ends.
  4. Tool execution: the selected tool runs with the model-provided arguments and returns a tool message.
  5. Model follow-up: the tool result is appended to the conversation state and passed back to the model.
  6. Final response: the model formats the result for the user, or requests another tool if another step is needed.
Tool design

5. Built-in tools vs custom tools

TypeMeaningLesson example
Prebuilt / integration toolA library supplies a ready-made tool wrapper for a common capability.DuckDuckGo search wrapper.
Custom toolYou write a Python function and expose it as a tool, usually with a decorator and a clear schema/description.Calculator and stock-price lookup.

A tool's name, argument schema, and description are part of the interface the model uses to select it. In particular, the description should clearly state when the tool should be used and what it returns.

Docstring rule: give each custom tool a precise description. The model uses the tool's metadata to understand its purpose; vague descriptions make tool selection less reliable.

6.3 Create a custom calculator tool

@tool
def calculator(first_number: float, second_number: float, operation: str) -> str:
    """Perform basic arithmetic on two numbers.

    operation must be one of: add, subtract, multiply, divide.
    """
    if operation == "add":
        result = first_number + second_number
    elif operation == "subtract":
        result = first_number - second_number
    elif operation == "multiply":
        result = first_number * second_number
    elif operation == "divide":
        if second_number == 0:
            return "Error: division by zero is not allowed."
        result = first_number / second_number
    else:
        return "Error: unsupported operation."

    return str(result)

This deliberately uses explicit operations instead of evaluating arbitrary Python expressions. Avoid implementing a calculator with unrestricted eval() on model-generated input.

6.4 Add a web-search tool

6.5 Add a stock-price tool (API pattern)

The video describes using Alpha Vantage and an API key. The sample below illustrates the shape of a custom tool; check the provider's current endpoint, parameters, plan limits, and response format before running it.

@tool
def get_stock_price(symbol: str) -> str:
    """Fetch the latest available quote for a public stock ticker symbol.

    Input should be a ticker such as AAPL or MSFT.
    Returns provider quote data; the caller should check its timestamp.
    """
    api_key = os.getenv("ALPHAVANTAGE_API_KEY")
    if not api_key:
        return "Stock quote unavailable: API key is not configured."

    response = requests.get(
        "https://www.alphavantage.co/query",
        params={
            "function": "GLOBAL_QUOTE",
            "symbol": symbol,
            "apikey": api_key,
        },
        timeout=15,
    )
    response.raise_for_status()
    data = response.json()

    # Avoid pretending an error/rate-limit response is a quote.
    if "Global Quote" not in data:
        return f"Quote unavailable for {symbol}: {data}"

    quote = data["Global Quote"]
    price = quote.get("05. price", "not provided")
    date = quote.get("07. latest trading day", "date not provided")
    return f"{symbol.upper()} price: {price}; latest trading day: {date}"
API note: a provider's “latest quote” may be delayed or unavailable under a free plan. Always check the returned data and display the provider's trading date/time where possible.

6.6 Bind the tools to the model

tools = [search_tool, calculator, get_stock_price]
llm_with_tools = llm.bind_tools(tools)

Binding exposes the available tool definitions to the model. It does not execute them immediately.

6.7 Define the graph state and nodes

from langgraph.graph import MessagesState

def chat_node(state: MessagesState):
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

builder = StateGraph(MessagesState)
builder.add_node("chat", chat_node)
builder.add_node("tools", ToolNode(tools))

builder.add_edge(START, "chat")
builder.add_conditional_edges("chat", tools_condition)
builder.add_edge("tools", "chat")

graph = builder.compile()

The key design choices are the conditional edge after the chat node and the edge from tools back to chat. The graph state retains the conversation messages so the model can interpret tool outputs.

6.8 Invoke a request

result = graph.invoke({
    "messages": [
        {"role": "user", "content": "What is the product of 654 and 713?"}
    ]
})

for message in result["messages"]:
    print(type(message).__name__, ":", message.content)

For a production chatbot, render the final assistant answer in the UI rather than dumping every internal message. Tool messages are useful for debugging but may be noisy or too technical for end users.

Why the loop matters

7. Why tool results must return to the model

The transcript highlights two shortcomings of sending the tool node directly to END.

Problem 1: Raw output

Tools may return JSON, structured records, or implementation details. Showing that output directly is often confusing to users.

Problem 2: Multi-step tasks

A task may require a search or lookup first, followed by a calculation using the result. A direct path to the end prevents the model from orchestrating the second step.

Example: estimate the cost of shares

Two-step tool use
User asks for total cost
↓
Model requests stock quote
↓
Stock tool returns quote
↓
Model reads quote; requests multiplication
↓
Calculator returns total
↓
Model explains result
↓
User-facing answer

The transcript's example asks for a share price and then the cost of buying a number of shares. The correct general workflow is to retrieve a valid price, confirm the currency and quote date, multiply price by share quantity, and clearly state assumptions. The model should not calculate from a missing or malformed quote.

Design principle: tools perform operations; the model coordinates the sequence and turns returned data into a coherent answer. The loop ends when the model returns a message without another tool call.
Frontend integration

8. Stream assistant messages—not raw tool messages

The transcript describes a Streamlit issue: after adding tools, the UI started streaming tool output as though it were assistant prose. The fix is to distinguish AI/assistant messages from tool messages and only display the intended message types.

Conceptual filter

from langchain_core.messages import AIMessage

# Illustrative filtering idea for a streaming loop:
for message_chunk, metadata in graph.stream(
    input_state,
    stream_mode="messages",
):
    if isinstance(message_chunk, AIMessage):
        # Render assistant content in the chat UI.
        # Also check whether this AI message is a tool-call message
        # before displaying its content to the end user.
        pass
Nuance: checking only isinstance(message, AIMessage) may still expose an assistant message whose purpose is to request a tool. For a polished UI, inspect the message's tool-call metadata and stream only user-facing assistant text. The exact event shape depends on the LangGraph stream mode and library version.

Practical UI rules

  • Show final assistant text to the user.
  • Do not display raw tool JSON as normal chat prose unless the user explicitly asks for it.
  • Use a separate status area to show progress such as “Searching the web…” or “Fetching a stock quote…”.
  • Handle tool failures and empty results with a useful message instead of silently pretending success.
  • Keep tool logs available for developers without mixing them into the conversational transcript.

In Streamlit, st.status() can provide a container for progress updates. Keep status labels short and truthful: update them when a tool call actually begins or completes, and avoid implying that a task has finished before the result is available.

import streamlit as st

with st.status("Working on your request…", expanded=True) as status:
    st.write("Searching the web…")
    # Execute the relevant graph/tool work here.
    # Update the status only when the corresponding work happens.
    status.update(
        label="Response ready",
        state="complete",
        expanded=False,
    )

This is a simplified UI pattern, not a complete drop-in replacement for the transcript's frontend. Connect the status updates to actual graph events for accurate per-tool progress.

Observability

10. Trace the graph to understand what happened

The transcript uses LangSmith traces to inspect an execution. A typical tool-using request can be read in three phases:

  1. Chat node: receives the user request and emits a tool call with its arguments.
  2. Tool node: executes the selected tool and returns its result.
  3. Chat node again: sees the conversation history plus the tool result and decides whether to call another tool or produce the final response.

Tracing is particularly useful when the wrong tool is selected, arguments are malformed, the tool returns unexpected data, or the model fails to turn the result into a clear answer.

SymptomWhat to inspect
Wrong tool selectedTool names, descriptions, argument schemas, model prompt, and user request.
Tool receives wrong argumentsAssistant tool-call payload and schema validation.
Raw JSON appears in chatFrontend message filtering and final-answer rendering.
Multi-step task stops earlyGraph edge from tools back to the model and state/message retention.
Search or quote failsNetwork errors, provider response, API limits, environment variables, and timeouts.
Put it into practice

11. Implementation checklist and exercises

Before running the app

  • Define each tool with a clear name, input schema, and docstring.
  • Keep API keys in environment variables.
  • Bind the tools to the chat model.
  • Add a chat node and a ToolNode to the graph.
  • Use conditional routing after the model node.
  • Route the tool node back to the model node.
  • Verify that the frontend does not display internal tool calls as final answers.
  • Handle API failures, rate limits, timeouts, and missing values.
  • Test both normal conversation and tool-required prompts.

Try these exercises

  1. Add a unit-conversion tool. Support a small, explicit set of conversions and return units with every result.
  2. Add a date/time tool. Return timezone-aware values and state the timezone used.
  3. Improve stock responses. Display ticker, currency, provider timestamp, and a note if data may be delayed.
  4. Test multi-tool planning. Ask the chatbot to search for a fact and then calculate something from the result. Verify the trace and final answer.
  5. Test failure paths. Try an invalid ticker, unsupported calculator operation, search with no results, and a missing API key.
Read carefully

12. Accuracy, versioning, and safety notes

  • Examples are representative. The source transcript describes the code flow but does not provide all exact source files in the supplied text. Code here is a teaching scaffold based on those descriptions.
  • Library APIs change. Check the installed versions of LangGraph, LangChain, the search integration, and Streamlit if imports or streaming events differ.
  • Tool output is untrusted input. Treat search results and API responses as data, not instructions. Do not allow retrieved text to override system or application rules.
  • Validate inputs. Use narrow schemas, sensible bounds, timeouts, and explicit error handling. Avoid arbitrary code execution for calculations.
  • Protect credentials. Use your own API key stored in environment configuration. Never commit keys to Git or share them in screenshots.
  • Financial data needs context. A stock quote is not investment advice. Verify the symbol, exchange, currency, quote time, and data-provider limitations before relying on it.
Final takeaway: the essential pattern is LLM → conditional route → ToolNode → LLM. The loop lets the assistant execute actions, interpret the returned results, chain multiple tools, and produce a more helpful final response.
