Lesson overview

1. What are we building?

The lesson extends an existing LangGraph chatbot into a multi-utility chatbot. Users can chat normally, call existing tools, and upload a document—such as a PDF or e-book—to ask questions grounded in that document.

The project is incremental: each new capability teaches a new LangGraph concept. The playlist has already covered the basic chatbot, UI, streaming, persistence/resuming chats, observability, tools, and MCP. This lesson adds Retrieval-Augmented Generation (RAG).

Roadmap

2. Plan of action: three parts

  1. Quick RAG recap. Review why RAG is needed, its core principle, and the high-level architecture. The lesson recommends a separate, more detailed RAG lesson for learners who need deeper theory.
  2. Build a standalone RAG chatbot. Start with a clean notebook and implement document loading, chunking, embeddings, vector storage, retrieval, and a RAG tool. Connect the tool to a LangGraph chat node.
  3. Integrate into the existing project. Add PDF upload to the Streamlit sidebar, implement an ingestion function, register the RAG tool alongside existing tools, and make small frontend/thread-handling changes.

The intermediate standalone implementation is intentional: adding RAG directly to a larger existing codebase could obscure the core idea. Learning the small version first makes integration easier to understand.

Why RAG?

3. Three problems RAG helps address

3.1 Outdated or missing knowledge

A model's built-in knowledge comes from its training. It may not know newer facts or information that was never included in training. A system can fetch relevant external information and pass it to the model as context. The transcript describes web search as one familiar example of this general retrieval pattern.

3.2 Private or organization-specific information

A general model has not automatically seen your personal expense spreadsheet, internal company reports, or private project documents. RAG lets an application retrieve relevant material from a data source you provide and use it to answer questions about that material.

3.3 Hallucinations and unsupported answers

Language models can confidently produce incorrect claims, such as references or links that do not exist. RAG can reduce this risk by grounding the response in retrieved passages and instructing the model to answer from the supplied evidence.

Important limitation: RAG does not guarantee truth, privacy, or zero hallucinations. Retrieval can miss relevant material, documents can contain errors, and the model can still misinterpret context. Use source citations, access controls, and validation when the application requires them.

Core concept

4. RAG's principle: in-context learning

At a high level, RAG uses in-context information: the application sends the user's question together with relevant text, and the model uses that context to form its answer. The model's internal learned knowledge is often called parametric knowledge; retrieved passages provide external context for the current request.

Conceptual illustration: RAG adds relevant retrieved context to the prompt rather than relying only on the model's built-in knowledge.

Why not paste the whole document?

Models have a finite context window, measured in tokens. A short spreadsheet may fit, but dozens of e-books or a codebase containing thousands of files may exceed that limit. Even if the full content fits, irrelevant material can distract from the question.

Instead, split the source into smaller chunks, find the chunks most relevant to the question, and include only those chunks as context. For a question such as “What is machine learning?”, the system should retrieve the sections that discuss machine learning rather than sending every page of a large book.

Architecture

5. RAG architecture at a glance

RAG has two broad phases: indexing (prepare and store the documents) and question answering (retrieve relevant chunks and generate a response).

The vector store retains the chunk text and associated metadata along with its embedding, so retrieved vectors can be mapped back to readable source content.
  1. Load: read the source document (for example, a PDF).
  2. Split: create smaller text chunks, often with some overlap.
  3. Embed: convert each chunk into a numeric vector that represents semantic meaning.
  4. Store: save vectors and their associated text/metadata in a vector store such as FAISS or Chroma.
  5. Retrieve: embed the user's question and search for semantically similar chunks.
  6. Generate: send the question and retrieved context to the LLM and produce an answer.
Build phase 1

6. Preparing documents: loading, chunking, embedding, storing

6.1 Load the PDF

The lesson uses a machine-learning book PDF (called “Intro to ML” in the walkthrough). A PDF loader reads the file and returns document objects. A document object typically includes page text and metadata.

6.2 Split into chunks

A recursive character text splitter divides large documents into manageable chunks. Two key settings are:

  • Chunk size: the approximate maximum size of each text chunk.
  • Chunk overlap: repeated text shared between adjacent chunks to help preserve continuity when a concept crosses a boundary.

Too-small chunks may lose context; too-large chunks can retrieve irrelevant content or consume too much context window. Chunking should be tuned for the document type and questions.

6.3 Generate embeddings

The lesson names OpenAI's text-embedding-3-small as its embedding model. Each chunk is mapped to a vector. Similar meanings tend to be near each other in the embedding space, even if they use different words.

6.4 Save in a vector store

The example uses FAISS. The vector store supports similarity search and associates vectors with the text chunks they represent. The lesson then creates a retriever configured to return the four most similar chunks (top-k = 4).

Remember: the embedding model and the LLM do different jobs. The embedding model maps text to vectors for retrieval; the LLM reads the question and retrieved text to compose the answer.
Build phase 2

7. How a question becomes an answer

  1. User asks a question. Example from the lesson: “What is a decision tree?”
  2. Retriever embeds the question. It creates a query vector using the embedding model.
  3. Similarity search runs. The vector store compares the query with stored vectors and selects the closest matches.
  4. Relevant text is extracted. Each retrieved document may contain an ID, page content, and metadata. The tool gathers the page content and metadata from the top results.
  5. Question + context go to the LLM. The prompt includes the original query and the retrieved passages. The model generates an answer grounded in that material.

What is in a retrieved document object?

FieldPurpose
page_contentThe actual text from the chunk; usually the main evidence for the answer.
metadataAdditional information such as page number, source file, or author, when available.
idAn identifier for the stored document/chunk, depending on the implementation.

The transcript demonstrates questions about finding an ideal value of k in k-nearest neighbors and splitting a node in a decision tree. The sample runs take roughly 8–9 seconds in that demo, illustrating that retrieval and model calls add latency; actual timing depends on the model, provider, document size, and network.

Agentic pattern

8. Integrating RAG as a LangGraph tool

The central implementation choice in the lesson is to wrap the retriever in a tool. This keeps RAG conceptually similar to the search, calculator, and stock-price tools already used in the chatbot.

Simplified control flow. A real graph uses conditional routing to decide whether the assistant's message contains a tool call.

Node responsibilities

  • Chat node: invokes the LLM with the conversation and any tool results. It decides whether to answer directly or request a tool.
  • Tool node: executes the selected tool, including the RAG tool when requested.
  • Conditional edge: routes to the tool node when a tool call is present; otherwise routes to the end.
  • Return edge: after the tool result is added to the conversation, control returns to the chat node so the LLM can write the final response.

The RAG tool's description is important: it should tell the LLM when the tool is appropriate, for example, when a user asks a question about an uploaded document. If the user says “hello,” the model should not need to retrieve document chunks.

9.2 Load a PDF, split it, and create a vector store

import os
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings, ChatOpenAI
from langchain_community.vectorstores import FAISS

# Set OPENAI_API_KEY in your environment before running.
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def build_retriever(pdf_path: str):
    """Index one PDF and return a retriever for relevant chunks."""
    loader = PyPDFLoader(pdf_path)
    pages = loader.load()

    splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000,
        chunk_overlap=150,
    )
    chunks = splitter.split_documents(pages)

    embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
    vector_store = FAISS.from_documents(chunks, embeddings)

    # Return the four most similar chunks for each query.
    return vector_store.as_retriever(
        search_type="similarity",
        search_kwargs={"k": 4},
    )

retriever = build_retriever("intro_to_ml.pdf")
matches = retriever.invoke("What is a decision tree?")
for i, doc in enumerate(matches, start=1):
    print(f"--- Chunk {i} ---")
    print(doc.page_content[:500])
    print(doc.metadata)
Practical note: chunk_size=1000 and chunk_overlap=150 are example settings, not values specified in the transcript. Tune them for your documents. This simple example builds an in-memory FAISS index each time it runs; a real app should decide how to persist, identify, update, and delete indexes.

9.3 Wrap retrieval in a tool

from langchain_core.tools import tool

@tool
def search_uploaded_document(question: str) -> str:
    """Search the user's uploaded document to answer document-specific questions."""
    docs = retriever.invoke(question)
    if not docs:
        return "No relevant passages were found in the uploaded document."

    passages = []
    for i, doc in enumerate(docs, start=1):
        source = doc.metadata.get("source", "uploaded document")
        page = doc.metadata.get("page")
        page_label = f", page {page + 1}" if isinstance(page, int) else ""
        passages.append(
            f"[Passage {i} — {source}{page_label}]\\n{doc.page_content}"
        )
    return "\\n\\n".join(passages)

The tool returns readable text so the LLM can use it. Metadata is included when available. The page number adjustment above assumes the loader reports zero-based page indices; verify the convention for your loader.

9.4 Bind the tool to the LLM

tools = [search_uploaded_document]
llm_with_tools = llm.bind_tools(tools)

# At each chat turn, invoke llm_with_tools with the conversation state.
# If the assistant returns a tool call, execute the requested tool,
# add its result to the message history, and call the LLM again.

In a LangGraph implementation, this pattern is usually represented by a chat node, a tool node, and conditional routing. The lesson describes the same structure and notes that it closely resembles the existing tool-based graph.

Project integration

10. Add RAG to the existing multi-utility chatbot

The lesson says the project receives two new files: one backend file (described as a LangGraph RAG backend) and one Streamlit frontend file. Most existing code remains similar; the major additions are document ingestion, a RAG tool, and a PDF upload control.

10.1 Backend changes

  • Create an ingest_pdf() function to load the uploaded PDF, split it into chunks, create embeddings, build the vector store, and return a retriever.
  • Define the RAG tool around the retriever. Retrieve relevant documents, collect page_content and useful metadata, and return this context to the model.
  • Add the RAG tool to the existing tools list alongside the search, calculator, and stock-price tools.
  • Bind the tools to the LLM and use the existing LangGraph chat/tool flow.
  • Add error handling for invalid files or failures during parsing, embedding, retrieval, or model calls.

10.2 Frontend changes

  • Add a PDF uploader in the Streamlit sidebar.
  • Pass the uploaded file to the ingestion function and associate the resulting retriever with the correct user/session/thread.
  • Keep the existing chat UI and history behavior, with small changes to thread handling as needed.

Observability

11. Inspecting the workflow with tracing

The lesson uses LangSmith tracing (the transcript's speech recognition renders the name approximately as “LangXith/LangSmith”) to inspect the sequence behind a document question. A trace makes it easier to see where a tool was selected, what the retriever returned, and how the final answer was generated.

  1. The user's question enters the chat node.
  2. The LLM decides that RAG is needed and emits a tool call.
  3. The tool node invokes the RAG function, which searches the vector store and returns relevant chunks.
  4. The tool output is added to the message history and sent back to the chat node.
  5. The LLM uses the original question and retrieved context to produce the final answer.
Why tracing matters: it helps debug tool selection, poor retrieval, irrelevant chunks, latency, and unexpected answers. Inspect traces carefully because prompts and retrieved passages may contain sensitive user data.
Revision

12. Implementation checklist and key takeaways

Checklist

  • □ Understand why RAG is useful: knowledge gaps, private documents, and grounding.
  • □ Load the PDF into document objects.
  • □ Split documents into chunks with suitable size and overlap.
  • □ Create embeddings for each chunk.
  • □ Store embeddings with their text and metadata in a vector store.
  • □ Build a retriever and choose a top-k value.
  • □ Wrap retrieval in a clearly described tool.
  • □ Bind the RAG tool to the LLM.
  • □ Build a LangGraph chat node, tool node, and conditional edges.
  • □ Add PDF upload and ingestion to the existing Streamlit UI.
  • □ Test normal chat, document questions, and existing tools independently.
  • □ Trace the workflow and inspect retrieval quality and errors.

Key takeaways

  • RAG is not simply “upload a file to an LLM”; it includes indexing and retrieval so that only relevant content is placed in the model's context.
  • Chunking and embeddings prepare a searchable representation of the source.
  • A retriever returns relevant text; the LLM turns that evidence into a natural-language answer.
  • In this lesson's design, RAG is a tool that the LangGraph agent can choose when needed.
  • Building a standalone example first makes integration into a larger chatbot easier to reason about.
  • RAG can reduce unsupported answers, but answer quality depends on source quality, retrieval quality, prompt design, and model behavior.
