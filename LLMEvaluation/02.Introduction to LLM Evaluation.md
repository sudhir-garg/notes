## 1. Why Do We Need LLM Evaluations?

Traditional software testing is largely deterministic: given the same input and code, we usually expect the same output. LLM-powered systems are different because their outputs can vary and quality is often multidimensional.

For an AI application, asking a handful of questions manually and deciding "looks good" is not enough. We need a systematic way to test representative behavior, edge cases, regressions, safety, groundedness, latency, cost, and other requirements.

## 5. LLM Evals ≠ Just Metrics

A common misconception is that an evaluation is simply a metric such as accuracy, precision, or recall. In LLM applications, the term **evaluation** is broader.

The evaluation setup can include:

* What component or system is being tested?
* What evaluation dataset is used?
* What criteria define acceptable behavior?
* How are outputs judged?
* When and where are evaluations executed?
* Which evaluation tools or frameworks are used?
* How are results compared across versions?

## 9. Why AI Engineers Still Need to Understand Model Evals

An application engineer may not design frontier-model benchmarks from scratch. However, understanding benchmark reports helps when selecting a model for a project.

For example, model selection may involve questions such as:

* Do we need strong coding capability?
* Is long-context performance important?
* Do we require multimodal input?
* Does the model support reliable tool calling?
* What are the latency and cost constraints?
* Do benchmark results actually represent our application's workload?

## 10. Application Evaluations

Application evaluation asks a different question:

> ### *"Does the AI application work correctly for its intended users and use case?"*

An LLM-powered product contains much more than an LLM. Depending on the architecture, it may include:

* System and user prompts
* Tools and external APIs
* Agent or workflow orchestration
* Guardrails and safety controls
* Output parsing and structured-output handling
* Memory and context management
* Retrieval, embeddings, vector stores, and rerankers
* Monitoring, tracing, and feedback loops
* User interface and application logic

## 11. Application Evaluation: Component-Level + System-Level

Application evaluation can happen at different granularities.

| Level | Examples | Questions | 
 | ----- | ----- | ----- | 
| **Component level** | Retriever, reranker, embedding model, prompt, tool | Is this component behaving correctly? | 
| **Workflow level** | RAG pipeline, agent workflow | Does the workflow complete the intended task? | 
| **System level** | Complete chatbot/application | Is the final user experience correct, safe, fast, and useful? | 

## 12. RAG Chatbot Example

Imagine a chatbot for a university's course content. Application evaluation can test questions such as:

| Evaluation area | Example question | 
 | ----- | ----- | 
| **Answer correctness** | Did the chatbot answer the student's question correctly? | 
| **Retrieval quality** | Did the retriever return the relevant course material? | 
| **Groundedness** | Is the answer supported by the retrieved context? | 
| **Hallucination** | Did the system invent information not supported by its sources? | 
| **Clarity** | Is the explanation understandable to the target learner? | 
| **Latency** | Did the user receive the answer within the required response time? | 
| **Safety** | Does the application avoid unsafe or inappropriate responses? |

## 15. A Practical Evaluation Workflow

The concepts in the lecture can be turned into a practical engineering workflow:

1. **Define the task.** Clearly state what the application is supposed to accomplish.
2. **Define quality criteria.** Decide what counts as correct, useful, safe, grounded, and acceptable.
3. **Build an evaluation dataset.** Include normal cases, edge cases, adversarial cases, and representative production examples.
4. **Choose the evaluation target.** Test a component, workflow, or complete system.
5. **Run the baseline.** Capture results for the current implementation.
6. **Change one or more system variables.** For example, prompt, model, retriever, chunking strategy, or orchestration.
7. **Re-run the same evaluation.** Compare against the baseline.
8. **Investigate failures.** Do not rely only on an aggregate score; inspect representative failures.
9. **Promote changes only when they meet the required criteria.**

## 16. Interview Perspective

#### Q: What are LLM evaluations?

> **Answer:** LLM evaluations are systematic, repeatable tests used to judge an LLM or an LLM-powered application against clearly defined criteria. The evaluation setup can include the dataset, target component/system, evaluation criteria, execution method, and tooling—not merely a single metric.

#### Q: What is the difference between model evaluation and application evaluation?

> **Answer:** Model evaluation focuses on the capabilities of the underlying LLM, such as reasoning, coding, mathematical ability, instruction following, long-context handling, and multimodal understanding. Application evaluation focuses on whether the complete AI system works correctly for its intended use case, including retrieval, prompts, tools, orchestration, guardrails, latency, cost, and final response quality.

#### Q: Why isn't a strong model benchmark enough?

> **Answer:** Because an AI application contains many components around the model. A model may perform well on a benchmark while the application's retrieval, prompt, tool orchestration, safety layer, or user experience performs poorly. Application-level evaluation tests the system in the context where it will actually be used.
