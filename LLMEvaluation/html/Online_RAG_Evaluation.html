1. From Offline Evaluation to Online Evaluation

The central transition in this lesson is simple: deployment is not the end of evaluation.

The earlier RAG-evaluation work built an offline evaluation suite with roughly 14–15 metrics and then connected it to regression testing. Offline evaluation answers questions such as: “Does the new version perform better or worse on our known evaluation set?”

Once the application is deployed, however, real users generate inputs that were not known when the golden dataset was created. Online evaluation extends the evaluation process into production by continuously collecting traces, measuring the live system, and looking for quality, safety, and operational degradation.

Core idea Observability tells you what happened; online evaluation adds structured judgments about whether the observed behavior is acceptable.

2. The Reference Constraint: Why Not Every Offline Metric Works Online

The major difference between the two settings is the availability of a reference answer. In offline evaluation, a golden dataset can contain the question, expected answer, and other reference information. For a new production question, that reference normally does not exist beforehand.

MetricReference required?Online?Reason
Contextual RecallYesNoRequires knowing the relevant/correct context.
Contextual PrecisionYesNoRequires reference information for judging retrieved chunks.
CorrectnessYesNoRequires a correct/reference answer.
CompletenessYesNoRequires knowing what a complete answer should contain.
FaithfulnessNoYesCan judge whether the answer is supported by the supplied context.
Answer RelevancyNoYesCan assess whether the answer addresses the question without a gold answer.
Contextual RelevancyNoYesCan assess relevance of retrieved context to the query.
StyleNoPossibleReference-free in the lecture, but omitted from the demo because it was expected to vary less.
Scope / Leakage / ToxicityNoYesSafety properties can be judged without a gold answer.
Latency / Cost / ReliabilityN/AYesOperational telemetry is logged/measured from production runs.
Important distinction “Reference-free” does not mean “free.” An LLM-as-a-judge can still incur model-inference cost and latency when it evaluates a production trace.

5. The Hidden Problem: A RAG Trace May Miss Retrieval

The first trace exposed the prompt, LLM execution, and output parsing, but the instructor noticed that the retrieval stage and reranker were not visible. That is a serious observability gap for a RAG system because retrieval is part of the user-visible behavior and contributes to latency.

Using explicit trace decorators

Illustrative Python pattern

from langsmith import traceable

@traceable(name="rag_pipeline")
def run_rag_pipeline(question: str):
    docs = retriever.invoke(question)
    reranked = reranker.invoke(docs)
    prompt = prompt_template.invoke({
        "question": question,
        "context": reranked
    })
    answer = llm.invoke(prompt)
    return answer

@traceable(name="retriever")
def traced_retrieve(question: str):
    return retriever.invoke(question)

The exact implementation can differ depending on how the RAG pipeline is structured. The lesson's practical principle is more important: when an important component is not captured automatically, explicitly mark it as traceable.

Why this matters for latency If retrieval takes a substantial portion of the request time but is absent from the trace, the observed end-to-end latency is difficult to decompose and optimize.

8. Alerts, Thresholds, and SLOs

The next step after visualization is automation: when a monitored signal crosses an acceptable boundary, notify the team through an operational channel such as Slack.

Why the threshold should come from an SLO

The lesson emphasizes that a “sensitive” threshold is not arbitrary. It should come from the application's Service Level Objective (SLO) and business requirements. A research assistant may reasonably tolerate longer response times than a simple customer-support interaction.

Lecture-specific tooling limitation The demonstrated LangSmith alert configuration supported average latency rather than the desired P95 latency alert in the example. The lesson therefore uses the available average-latency alert mechanism while explaining why P95 is useful for tail-latency analysis.

10. Sampling Rate: The Production-Cost Control

Evaluating every production trace can be expensive when an LLM is used as the evaluator. Sampling reduces evaluation cost while still providing an estimate of production behavior.

If 50,000 traces arrive and sampling is 100%, the evaluator runs on all 50,000. At 30%, only a subset is evaluated. The transcript uses sampling as a practical way to estimate population behavior while controlling evaluation cost.

Production principle Sampling should be treated as a deliberate quality–cost trade-off. Higher-risk applications may justify higher sampling rates, while very high-volume systems may need lower rates or targeted sampling.

11. Online Quality Evals Must Use the Same Evaluator as Offline

This is one of the most important conceptual points in the lesson.

For quality metrics such as contextual relevancy, faithfulness, and answer relevancy, the online evaluator should use the same evaluation methodology that was used offline. The reason is comparability.

ScenarioOffline evaluatorOnline evaluatorCan numbers be compared?
Bad baselineDeepEvalDifferent LangSmith evaluatorNo
Good baselineDeepEvalSame DeepEval evaluatorYes

Why changing the evaluator breaks the comparison

Suppose offline contextual relevancy is 45 and online contextual relevancy is 55. It is tempting to conclude that production improved. But if the offline score was produced by one evaluator and the online score by another, the two numbers may live on different measurement baselines because prompts, judge models, scoring logic, or implementation details differ.

With the same evaluator, a change such as 90 → 85 has a meaningful interpretation: under the same measurement system, the application's observed quality has degraded.

Interview-ready rule For longitudinal quality monitoring, keep the evaluator, scoring definition, and relevant configuration consistent between offline and online evaluation whenever the objective is to compare the scores over time.

12. Implementing the Background Online-Evaluation Service

The lesson then moves from “tool UI configuration” to the architecture behind continuous quality evaluation.

Polling logic

The conceptual loop is:

  1. Trigger a background job periodically.
  2. Fetch the most recent traces from LangSmith.
  3. Optionally sample those traces.
  4. Run the existing offline quality evaluators against the production trace data.
  5. Write the resulting scores back to LangSmith.
  6. Let dashboards and alerts consume the resulting feedback.

Demo vs production The transcript uses an infinite Python loop as a simple demonstration. It explicitly notes that a real deployment should use a persistent background service or scheduled job rather than depending on an open terminal.

Cron-style scheduling

# Example conceptual cron schedule:

This means the background evaluation job is triggered every five minutes. The exact deployment mechanism can instead be a container scheduler, managed job, workflow engine, or another persistent scheduling system.

13. Live Execution: Production Traces Get Scored in the Background

In the demonstration, a new production-style question is submitted while the background evaluation loop is running. The loop periodically checks recent traces and applies the same quality evaluators.

Observed example

For one question, the same DeepEval setup produced example scores such as answer relevancy 0.92, contextual relevancy 0.23, and faithfulness 0.75. These are example results for a particular trace, not universal benchmarks.

Asynchronous behavior

Scores do not necessarily appear immediately when the trace is created. The trace can arrive first, followed by evaluator feedback after the background evaluation completes.

Adding quality charts

The same dashboard pattern can be applied to answer relevancy, contextual relevancy, and faithfulness. Each can be visualized over time and, where supported, associated with alerting rules.

14. Closing the Flywheel: Failed Production Traces → Golden Dataset

This is the final and most valuable architectural idea: online evaluation can continuously improve the offline evaluation dataset.

Why a bad trace is valuable

Suppose a user asks a question and the application produces a poor answer. That production interaction is more than an incident: it is a candidate evaluation example. The trace can be added to a dataset, and an expert can provide the correct/reference answer. The resulting example can then support correctness, completeness, and other reference-based offline evaluations.

Conceptual curation workflow

  1. Identify a production trace with poor quality or safety signals.
  2. Add the trace to an evaluation dataset.
  3. Review the generated answer.
  4. Have an expert create the reference answer when reference-based metrics are needed.
  5. Version the dataset.
  6. Use the expanded dataset in offline regression testing.
  7. Deploy improvements and continue monitoring online.
Single source of truth The lesson recommends managing the golden dataset centrally so that the same dataset can support offline evaluation while new production failures can be added and versioned over time.

15. Final Course Recap

The online-evaluation lesson completes the transition from “evaluate before deployment” to “evaluate continuously after deployment.” The practical stack demonstrated is centered on LangSmith for tracing, monitoring, dashboards, and built-in safety evaluation, while the existing DeepEval quality evaluators are reused for comparable online quality measurements.

Key interview questions

QuestionStrong answer
Why can't every offline metric run online?Many offline metrics require a reference answer or reference context that is unavailable for unknown production queries.
Why trace retrieval explicitly?Without retrieval traces, RAG latency and retrieval behavior are invisible, making diagnosis and optimization incomplete.
Why sample online evaluations?LLM-based evaluators add cost; sampling provides a practical estimate of production behavior without judging every request.
Why use the same evaluator offline and online?To keep scores on the same measurement baseline so changes over time are actually comparable.
What should determine a latency threshold?The application's SLO and business use case, not an arbitrary number.
How can online evaluation improve offline evaluation?Bad or interesting production traces can be curated into the golden dataset with expert reference answers.
Why isn't a terminal-based infinite loop production-ready?The process stops when the terminal/service stops; production needs a persistent scheduler or background service.
One-line mental model Offline evals tell you whether a known test suite passes before release; online evals tell you how the deployed system behaves on real, previously unknown traffic—and continuously turn production failures into better future tests.
