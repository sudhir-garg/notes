1. Why Evaluate an LLM Application?

The lecture distinguishes between model evaluations and application evaluations. The workflow in these notes focuses on the application-evaluation perspective: evaluating the complete LLM-based system that users actually interact with.

Core idea: Building an LLM application is not the same as proving that it works. The application should be evaluated before deployment, improved using evidence from evaluation, and continuously monitored after deployment.

The same general workflow can be applied to simple LLM applications as well as more complex systems such as RAG applications and agents. The lecture presents a simple classification application so the mechanics of evaluation are easy to understand.

2. Running Example: Email Classification

Imagine a large company receiving many customer emails every day. Instead of manually reading each email and routing it to the appropriate team, an LLM application classifies each email into a category.

Email exampleExpected categoryDownstream route
“My card was charged twice.”BillingBilling team
“The app crashes on login.”TechnicalTechnical team
“What are your working hours?”GeneralCustomer support

The application may be technically easy to build, but deployment should come after evaluation. The central question is not merely “Can the LLM produce an answer?” but “Does the application perform its intended task reliably enough for its use case?”

4. Step 1 — Define the Task and Target

Before measuring anything, explicitly state what is being evaluated and what task the application must perform.

QuestionAnswer for the running example
What is the target?The complete email-classification system / workflow.
What is the task?Classify an email into billing, technical, or general.
What must be evaluated?Whether the application performs the classification correctly.
Key lesson: A vague evaluation target produces vague measurements. Define the task before choosing the metric.

5. Step 2 — Define Success Criteria and Metrics

The lecture's classification example uses accuracy as the metric.

If 100 emails are evaluated and 90 are classified correctly:

accuracy = correct_predictions / total_predictions
         = 90 / 100
         = 0.90 = 90%
ConceptMeaning
Success criterionThe behavior you want the application to achieve—for this example, correct classification.
MetricThe quantitative measurement used to assess that criterion—for this example, accuracy.
Important: The lecture uses accuracy for this simple classification example. In a real application, the appropriate metric depends on the task and its failure costs; do not assume accuracy is universally sufficient.

6. Step 3 — Build a Golden Evaluation Dataset

Create a dataset containing representative inputs and their manually established expected outputs. The lecture calls this a golden dataset.

InputExpected output / label
My card was charged twice.Billing
The app crashes on login.Technical
What are your hours?General

How to create it

  1. Prefer real historical application data when appropriate.
  2. For the example, past customer chats/emails can be used as the raw material.
  3. Have people label the examples with the expected category.
  4. Keep the labeled inputs and expected outputs as a reusable evaluation set.

The lecture mentions a rough example of 50–500 examples for the dataset, while emphasizing that the actual size depends on the use case.

Why the golden dataset matters: It provides a stable reference point. When you change a prompt or model, you can run the same dataset again and compare the resulting evaluation.

7. Step 4 — Choose an Evaluation Method

After preparing the expected results, decide who or what will judge the application output.

MethodHow it worksExample fit
AutomatedCode compares generated outputs with expected outputs.Classification labels where exact/structured comparison is possible.
HumanA person reviews the generated output.Cases where quality requires human semantic judgment.
LLM-basedAnother LLM evaluates the generated answer against criteria or a reference.Long-form answers where semantic similarity or qualitative criteria matter.

Why the method changes with the task

For a short classification label such as billing, ordinary code can compare the generated label with the expected label. For long-form responses, literal string comparison is often inadequate because two answers can express the same meaning with different wording.

Decision principle: Match the evaluation method to the type of output and the kind of correctness you need to measure.

9. Step 6 — Evaluate and Analyze Results

Evaluation produces a measurement; analysis explains where and why the application is failing.

For example, suppose the application achieves 80% accuracy on 100 examples. That means 80 examples were classified correctly and 20 were incorrect under the lecture's simple accuracy setup.

Do not stop at the score

The important engineering question is: What patterns exist among the failures?

  • Are billing and technical emails being confused?
  • Are some categories systematically harder?
  • Are there ambiguous examples in the dataset?
  • Does the prompt fail to clearly define category boundaries?
  • Is the selected LLM struggling with the task?
Evaluation tells you how much is working. Error analysis helps you understand what to change.

10. Step 7 — Improve the System

The lecture identifies several possible improvement directions. The key point is that you improve the system, not merely treat the model as an isolated component.

Potential changeReason to investigate it
Prompt improvementThe instructions may not clearly distinguish categories.
Model changeThe selected model may not perform the task sufficiently well.
Other system changesApplication logic, routing, or other components may contribute to errors.

After making a change, do not simply assume it improved the application. Run the evaluation again.

11. Step 8 — Iterate Until the System Is Ready

This is the central feedback loop in the lecture.

IterationSystem changeExample result
BaselineInitial prompt + model80% accuracy
Iteration 1Prompt improved90% accuracy
Iteration 2Model changed95% accuracy

These numbers are illustrative examples from the lecture's explanation of iteration, not a universal threshold for deployment.

Repeatable evaluation is what makes iteration useful. Because the same golden dataset can be reused, changes to the system can be evaluated consistently.

Eventually, the team reaches a point where the application meets the requirements for deployment.

12. Step 9 — Deploy and Monitor in Production

Deployment is not the end of evaluation. Production introduces real inputs that may differ from the evaluation dataset.

A system can perform well on its test dataset and still make mistakes on new production inputs. Therefore, production failures should be captured, reviewed, and—when appropriate—added to the evaluation dataset.

13. Production Failures → Dataset Expansion

The lecture gives a concrete feedback mechanism: when a customer case is incorrectly routed, the responsible downstream team can flag the error. That case can then be added to the golden dataset.

  1. A production email is incorrectly classified.
  2. The downstream team identifies the incorrect routing.
  3. The case is flagged as a failure.
  4. The email and correct label are added to the evaluation dataset.
  5. The system is improved.
  6. The expanded dataset is used for re-evaluation.
  7. The improved system is deployed again when appropriate.
Golden dataset as a living asset: Over time, the dataset can become richer because it incorporates real failure cases discovered in production.

14. Why One LLM Application Can Need Multiple Evaluations

A particularly important point from the lecture is that one LLM-based application may have several evaluations. A single application-level score does not necessarily describe every component or quality dimension.

For a RAG application, the lecture gives examples of separate evaluations for:

Evaluation focusWhat it can investigate
RetrieverWhether the retrieval component is performing as intended.
Embedding modelWhether the embedding component is performing adequately.
Full RAG workflowWhether the end-to-end application works correctly.
LatencyHow quickly the system responds.
Important mental model: Think of evaluation as a set of tests around an application—not necessarily one universal “LLM score.”

The same principle can extend to agentic systems, where different evaluations can examine individual tools/components as well as the complete workflow.

15. Practical Python Example

For the simple classification example, the lecture explains that an automated evaluation can be implemented with ordinary Python because the expected and generated labels are directly comparable.

Minimal accuracy evaluator

def accuracy(expected, predicted):
    if len(expected) != len(predicted):
        raise ValueError("Both lists must have the same length")

    correct = sum(
        exp == pred
        for exp, pred in zip(expected, predicted)
    )

    return correct / len(expected)


expected = [
    "billing",
    "technical",
    "general",
    "billing",
    "general",
]

predicted = [
    "billing",
    "general",
    "general",
    "billing",
    "technical",
]

score = accuracy(expected, predicted)

print(f"Accuracy: {score:.0%}")

Expected output:

Accuracy: 60%

Adding failure analysis

def find_failures(expected, predicted, inputs):
    failures = []

    for item, exp, pred in zip(inputs, expected, predicted):
        if exp != pred:
            failures.append({
                "input": item,
                "expected": exp,
                "predicted": pred,
            })

    return failures


inputs = [
    "My card was charged twice.",
    "The app crashes on login.",
    "What are your hours?",
    "Please refund my duplicate charge.",
    "Where is your nearest store?",
]

failures = find_failures(expected, predicted, inputs)

for failure in failures:
    print(failure)

This second step is important because a single accuracy number does not reveal which examples failed. Failure records provide the raw material for error analysis and system improvement.

Scope note: This Python example mirrors the lecture's simple classification setup. It is not a complete production evaluation framework and does not implement an LLM, prompt management, experiment tracking, or production monitoring.

One-line memory trick

DEFINE → MEASURE → BUILD GOLDEN DATA → CHOOSE EVAL
→ RUN → SCORE → ANALYZE → IMPROVE → REPEAT
→ DEPLOY → MONITOR → ADD FAILURES → RE-EVALUATE

Key distinctions to remember

  • Task = what the application must do.
  • Success criterion = what acceptable behavior looks like.
  • Metric = how that behavior is measured.
  • Golden dataset = labeled reference examples used for repeatable evaluation.
  • Evaluation method = automated code, human judgment, or an LLM-based judge, depending on the task.
  • Evaluation = measure performance.
  • Error analysis = understand failure patterns.
  • Iteration = change the system and evaluate again.
  • Production monitoring = observe real-world behavior after deployment.
  • Dataset expansion = turn validated production failures into new evaluation cases.
  • Multiple evaluations = one application may need separate evaluations for components and quality dimensions.
Big picture: Reliable LLM applications are built through an evaluation loop, not through a one-time test. The reusable golden dataset provides the reference point; evaluation provides evidence; error analysis identifies improvement opportunities; and production monitoring supplies new failure cases that can make the evaluation set increasingly representative.
