1. The Big Picture: What Are Operational Evals?

Quality evaluations answer “Is my RAG application producing good answers?” Operational evaluations answer a different question: “Can this application run reliably, quickly, and economically?”

Application Quality — correctness, faithfulness, relevance, completeness
Pipeline / Component Quality — retriever, generator, etc.
Operational Health — latency, cost, reliability
Production Reality — users, load, failures, telemetry

The lecture frames operational evals as primarily software- and telemetry-driven. Unlike many quality evaluations, they generally do not require a golden dataset or an LLM acting as a judge. fileciteturn1file0L1-L20

Latency
How long?
How quickly does a request receive an answer?
Cost
How much?
How much money is spent per query / over a period?
Reliability
How often?
How often does the pipeline successfully serve requests?
Scope note from the lecture: throughput is also an operational metric, but it was left out of the detailed implementation because proper throughput evaluation generally needs load/stress testing.

2. Why Run Operational Evals Before Deployment?

Operational metrics sound like production metrics, but the lecture makes an important point: they are also valuable in the offline evaluation suite.

Differential benchmarking

Absolute offline latency on a laptop is not necessarily the same as production latency. However, the change between two controlled experiments is still informative.

MetricBefore changeAfter changeDirection
Average latency2.3 s4.1 s⚠️ Worse
P95 latency4.8 s6.2 s⚠️ Worse
Cost/query₹0.72₹1.08⚠️ Worse

The example shows why quality alone can hide a regression: answer quality improved, but latency and cost became worse. The lecture therefore recommends keeping operational measurements in the offline suite and using them to detect directional changes. fileciteturn1file0L145-L169

Rule: Keep the experimental setup consistent. If you change multiple unrelated parts of the benchmark setup, the resulting delta becomes difficult to interpret.

3. Core Metric #1 — Latency

Latency is the amount of time a system takes to respond to a request. For a RAG application, an end-to-end request may involve retrieval, reranking, generation, and response delivery.

User Query
→
Embedding
→
Retriever
→
Reranker
→
LLM Generator
→
Answer
End-to-End Latency = response_end_time − request_start_time

Why the average is not enough

A single average can hide slow requests. A production-like latency view should preserve the distribution and expose tail behavior.

Illustrative distribution: most requests cluster around a normal latency, while a smaller tail can be substantially slower.

4. P50, P95 and P99 — Tail Latency

PercentileMeaningWhat it tells you
P5050% of requests complete at or below this latency.Typical / median experience.
P9595% of requests complete at or below this latency.Important tail-user experience.
P9999% of requests complete at or below this latency.Very slow tail / worst-user experience.
Example: If P95 = 5 seconds, approximately 95% of measured requests finished within 5 seconds, while the slowest ~5% took longer.

The lecture recommends looking at P50/P95/P99 rather than reporting only the mean, because the tail tells you how badly some users are experiencing the system. fileciteturn1file0L318-L399

5. TTFT — Time to First Token

TTFT measures how long it takes before the user sees the first generated token.

Query sent
→
Retrieval + prompt processing
→
LLM starts generation
→
🎯 First token
→
Remaining stream

Streaming improves perceived responsiveness because users see progress before the complete answer has been generated. Therefore, an evaluation should measure both:

  • End-to-end latency — when the full answer is complete.
  • TTFT — when the first token becomes visible.

The lecture added streaming specifically so TTFT could be measured. fileciteturn1file0L426-L461

6. How to Build a Good Latency Evaluation

6.1 Warm up first

Cold starts can occur when models, containers, caches, vector-database connections, or network connections are initialized. The lecture recommends discarding the initial warm-up runs and measuring subsequent runs. fileciteturn1file0L464-L504

6.2 Record output and context size

Latency depends partly on how much work the model must process. Longer answers generally require more generation time; larger contexts require more input processing. Therefore, record token counts/context size alongside latency.

6.3 Separate component latency

E2E = 4.5 s
≈
Retriever = 1.5 s
+
Generator = 3.0 s

Break down the total into embedding, retrieval, reranking, generation, and other stages where possible. This identifies the optimization target rather than merely telling you that the whole system is slow. fileciteturn1file0L404-L424

6.4 Distinguish latency from throughput

LatencyThroughput
Time required to process one request.How many requests the system can handle in a given time.
Example: “This query took 3 seconds.”Example: “The service can handle 10,000 concurrent requests.”

The lecture uses a restaurant analogy: latency is how long one customer waits for food; throughput is how many customers the kitchen can serve in a given time. Under load, queues can form and latency can increase. fileciteturn1file0L518-L567

6.5 Repeat experiments

External APIs are noisy. A single request is not a strong estimate. The lecture demonstrates repeating each question multiple times and averaging the resulting measurements; for production-quality benchmarking, substantially more samples may be appropriate. fileciteturn1file0L567-L591

6.6 Track failures separately

A lower latency can be misleading if many requests failed or timed out. For example, an experiment can show a better P95 simply because failed requests were excluded. Always inspect latency together with timeout/error rates.

6.7 Define latency budgets / SLOs

Example from the lecture:

  • RAG P95 end-to-end latency ≤ 3 seconds.
  • Retriever latency ≤ 1 second.
  • TTFT P95 ≤ 1.2 seconds.

These values are examples from the lecture’s evaluation setup, not universal industry limits. Budgets should be chosen for the application, users, and business requirements. fileciteturn1file0L633-L654

6.8 Use representative workloads

A benchmark made only from easy questions can produce unrealistically good results. The lecture suggests mixing simple, medium, complex, long-context, long-answer, and edge-case queries. fileciteturn1file0L655-L680

Latency optimization levers discussed

  • Reduce unnecessary retrieval/context.
  • Review reranking overhead.
  • Choose an appropriate model rather than automatically using a larger model.
  • Keep geographically interacting services closer when possible.
  • Use streaming to improve perceived responsiveness.
  • Analyze which component dominates latency before optimizing.

What should a cost evaluation measure?

MetricPurpose

The lecture emphasizes that cost should be examined as a distribution as well. Some queries may be dramatically more expensive than the normal case, so those tail queries deserve investigation. fileciteturn1file0L1074-L1099

Cost budget

A business-level monthly budget can be translated into a rough per-query budget. This gives the evaluation a concrete pass/fail threshold.

Example: If the business says a certain workload cannot exceed ₹X/month, convert that requirement into a target cost/query using the expected request volume and query mix.

Prompt caching consideration

The lecture notes that repeated identical questions can cause provider-side caching effects. Therefore, a synthetic benchmark that repeatedly sends exactly the same input may not represent production traffic where questions vary. fileciteturn1file0L1240-L1267

8. Core Metric #3 — System Reliability

Reliability is the ability of the RAG system to successfully serve requests without errors, timeouts, crashes, or broken pipeline stages.

100 requests
→
Successful = 80
+
Failed = 20
Success Rate = successful requests / total requests × 100
Error Rate = failed requests / total requests × 100

The lecture gives the simple example of 8 successful responses out of 10 requests, describing that as 80% reliability for that measurement. fileciteturn1file0L1268-L1290

Track more than one number

MetricDefinition / interpretation
Success ratePercentage of requests successfully served.
Error ratePercentage of requests that failed.
Timeout ratePercentage of requests exceeding the allowed time.
Retry ratePercentage of requests requiring at least one retry.

Do not use one generic error bucket

If the system has a 20% failure rate, investigate why. Useful categories include:

  • LLM/API failure
  • Retriever failure
  • Reranker failure
  • Vector database failure
  • Timeout
  • Rate-limit error
  • Parser/formatting error
  • Internal application exception

Breaking failures down makes the metric actionable: instead of merely knowing that the system is failing, you can identify which component or failure mode needs attention. fileciteturn1file0L1370-L1396

Reliability under load

A system can appear highly reliable when tested from one laptop with a small number of sequential requests and still fail under real concurrency. The lecture therefore highlights load/concurrency as an important production consideration and recommends using enough samples to expose rare failures.

Representative reliability workloads

  • Simple queries
  • Long-context queries
  • Complex queries
  • Queries producing long answers
  • Known edge cases

This segmentation helps reveal cases where, for example, simple queries succeed reliably but complex or long-context queries fail more often.

9. Practical Python Evaluation Scripts

The lecture demonstrates eval_latency.py, eval_cost.py, and eval_reliability.py. The following are compact study implementations of the same measurement ideas—not copies of the lecture's full scripts.

9.1 Latency + P50/P95/P99 + TTFT

from time import perf_counter
from statistics import mean
from typing import Callable
import numpy as np

def percentile(values, p):
    return float(np.percentile(values, p))

def benchmark(call_rag: Callable[[str], dict], questions, repeats=5, warmups=2):
    rows = []

    # Warm-up: avoid measuring cold-start effects.
    for _ in range(warmups):
        call_rag(questions[0])

    for question in questions:
        for run in range(repeats):
            start = perf_counter()

            # Example contract:
            # {
            #   "answer": "...",
            #   "ttft": 1.2,
            #   "retrieval_ms": 700,
            #   "generation_ms": 2900,
            #   "input_tokens": 800,
            #   "output_tokens": 250
            # }
            result = call_rag(question)

            end = perf_counter()

            rows.append({
                "question": question,
                "latency_s": end - start,
                "ttft_s": result["ttft"],
                "retrieval_ms": result["retrieval_ms"],
                "generation_ms": result["generation_ms"],
                "input_tokens": result["input_tokens"],
                "output_tokens": result["output_tokens"],
            })

    latencies = [r["latency_s"] for r in rows]
    ttfts = [r["ttft_s"] for r in rows]

    return {
        "mean_latency_s": mean(latencies),
        "p50_latency_s": percentile(latencies, 50),
        "p95_latency_s": percentile(latencies, 95),
        "p99_latency_s": percentile(latencies, 99),
        "p95_ttft_s": percentile(ttfts, 95),
        "samples": rows,
    }

9.2 Cost per query

def llm_cost(input_tokens, output_tokens,
             input_price_per_million,
             output_price_per_million):

    input_cost = (
        input_tokens / 1_000_000
    ) * input_price_per_million

    output_cost = (
        output_tokens / 1_000_000
    ) * output_price_per_million

    return {
        "input_cost": input_cost,
        "output_cost": output_cost,
        "total_cost": input_cost + output_cost,
    }

9.3 Reliability + failure categorization

from collections import Counter

def evaluate_reliability(call_rag, questions, repeats=5, max_retries=2):
    total = 0
    success = 0
    retries_used = 0
    failures = Counter()

    for question in questions:
        for _ in range(repeats):
            total += 1

            for attempt in range(max_retries + 1):
                try:
                    call_rag(question)
                    success += 1

                    if attempt > 0:
                        retries_used += 1
                    break

                except TimeoutError:
                    if attempt == max_retries:
                        failures["timeout"] += 1

                except RateLimitError:
                    if attempt == max_retries:
                        failures["rate_limit"] += 1

                except RetrieverError:
                    if attempt == max_retries:
                        failures["retriever"] += 1

                except Exception:
                    if attempt == max_retries:
                        failures["internal_error"] += 1

    failed = total - success

    return {
        "success_rate": success / total,
        "error_rate": failed / total,
        "retry_rate": retries_used / total,
        "failure_categories": dict(failures),
    }

9.4 A simple pass/fail gate

def evaluate_slos(report):
    checks = {
        "latency_p95": report["p95_latency_s"] <= 3.0,
        "ttft_p95": report["p95_ttft_s"] <= 1.2,
        "success_rate": report["success_rate"] >= 0.99,
        "cost_per_query": report["cost_per_query"] <= 0.50,
    }

    return {
        "passed": all(checks.values()),
        "checks": checks,
    }
Important: The thresholds above mirror the lecture's example setup where applicable. They are not universal requirements. Replace them with application-specific SLOs and current provider pricing.

11. Interview & Revision Cheat Sheet

QuestionAnswer
What are operational evals?Measurements of whether an application runs reliably, quickly, and economically.
Quality eval vs operational eval?Quality asks whether the answer is good; operational eval asks whether the system can deliver it effectively in operation.
Why run ops evals offline?To detect regressions before deployment, especially changes in latency, cost, and reliability.
Why P95/P99 instead of only mean?They expose slow tail requests that an average can hide.
What is TTFT?Time from request initiation until the first generated token is available.
Why warm up?To avoid cold-start initialization contaminating benchmark measurements.
Why repeat runs?External APIs have noise; repeated runs make estimates more stable.
Why track failures separately?A lower latency can be fake improvement if more requests are timing out/failing.
What is latency vs throughput?Latency is time per request; throughput is requests handled per unit time.
What is cost/query?Input token cost + output token cost, plus other billable components when applicable.
What is reliability?Ability to successfully serve requests without errors, timeouts, crashes, or broken stages.
Why categorize failures?To turn an aggregate failure rate into actionable root-cause information.
What is the role of representative workloads?Prevent easy-only benchmarks from producing misleadingly optimistic results.
