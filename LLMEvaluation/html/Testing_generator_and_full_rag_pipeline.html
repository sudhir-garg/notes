Building a RAG Evaluation Suite

Generator-level evaluation, faithfulness, answer relevancy, the RAG Triad, contextual relevancy, and pipeline-level diagnosis — presented as a practical engineering guide.

These notes are based on the supplied lecture transcript. Demo scores are reported as examples from that session, not universal benchmarks.

1. Session Overview

The session continues the construction of a reusable RAG evaluation suite. The evaluation is deliberately built in layers rather than waiting until the entire application is finished.

The transcript's immediate objective is to complete two pieces: evaluate the generator and then evaluate the complete RAG pipeline. The retriever had already been evaluated using recall and precision. fileciteturn0file0L5-L29

2. What Is a RAG Evaluation Suite?

A RAG evaluation suite is a collection of tests that can be executed together to assess different parts of a RAG system. The session organizes it into three levels:

LevelWhat is evaluated?Metrics emphasized in this session
ComponentRetriever and generator independentlyRetriever: Recall, Precision
Generator: Faithfulness, Answer Relevancy
PipelineRetriever + generator as one RAG pipelineRAG Triad: Faithfulness, Answer Relevancy, Contextual Relevancy
ApplicationEnd-user quality and operational behaviorCorrectness, completeness, style, safety, ops, etc.
Engineering principleBuild and test component-by-component. The lecture explicitly compares this to normal software engineering: build a component, test it, then connect it to the next component.

3. Building the Generator

In a RAG system, the generator receives two inputs:

Input 1 — User question

The query that the user wants answered.

Input 2 — Retrieved context

The relevant documents/chunks supplied to the generator by the retrieval stage.

The generator's output is the final natural-language answer.

Generator prompt design

The transcript's initial generator used an LLM with temperature set to zero and a system prompt that emphasized:

  • Answer only from the provided context.
  • Do not add outside knowledge.
  • If the context does not contain enough information, explicitly say that the material is insufficient.
  • Do not hallucinate.
  • Keep the answer clear and concise.

The lecture used GPT-4o-mini for the demonstrated generator. fileciteturn0file0L79-L113

# Representative implementation based on the lecture's generator design
from langchain_openai import ChatOpenAI
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

prompt = ChatPromptTemplate.from_messages([
    ("system", """You are a helpful teaching assistant.
Answer the student's question only from the context provided.

Rules:
1. Use only information present in the context.
2. Do not add outside knowledge.
3. Do not strengthen or invent claims.
4. If the context is insufficient, say so explicitly.
5. Keep the answer clear and concise.

Context:
{context}"""),
    ("human", "{query}")
])

generator_chain = prompt | llm | StrOutputParser()

def generate(query: str, context: str) -> str:
    return generator_chain.invoke({
        "query": query,
        "context": context
    })
ImportantCreating a working generator only proves that the code executes. It does not prove that the generator is good. Quality requires evaluation.

4. The Two Core Generator Failure Modes

The transcript uses a first-principles evaluation strategy: before choosing metrics, ask how can this component fail?

Failure mode 1 — Unfaithful answer

The model uses the context but adds unsupported information from its own knowledge or reasoning.

RiskHallucinated claims can be especially dangerous in production RAG applications.

Failure mode 2 — Irrelevant answer

The answer may be faithful to the supplied context, yet fail to answer the user's actual question.

RiskThe user receives context-derived information, but not the information they asked for.

Example: faithful does not mean correct

Suppose the retrieved context itself is wrong. A generator that strictly answers from that context can still be faithful while producing an incorrect answer.

Key distinctionFaithfulness asks “Did the answer stay grounded in the supplied context?” It does not ask “Is the context itself correct?”

5. Faithfulness

Faithfulness measures how much of the generated answer can be supported by the supplied context.

Faithfulness for one answer = supported claims ÷ total claims

Claim-level evaluation

The session describes an LLM-as-a-judge process:

  1. Generate an answer from a question and golden context.
  2. Break the generated answer into atomic claims.
  3. Check each claim against the golden context.
  4. Count how many claims are supported.
  5. Compute the ratio.
  6. Average the per-question scores across the dataset.

The transcript gives a similar 3/5 example and explains that the final dataset-level score is the average across questions. fileciteturn0file0L361-L411

6. Answer Relevancy

Answer Relevancy asks whether the generated answer actually helps answer the user's question.

Answer Relevancy for one answer = relevant claims ÷ total claims

The important contrast is:

MetricQuestion being asked
FaithfulnessIs the generated claim supported by the supplied context?
Answer RelevancyDoes the generated claim help answer the user's question?
CorrectnessIs the answer actually correct?
Do not conflate themAn answer can be relevant but incorrect, or faithful but irrelevant. Correctness is a separate metric that the transcript says will be addressed at the application level.

For answer relevancy, the judge can work without a reference answer. The answer is decomposed into claims, and each claim is judged for its contribution to answering the question. fileciteturn0file0L452-L520

7. LLM-as-a-Judge: Why Use It?

The evaluation relies heavily on an LLM judge because claim support and relevance are semantic judgments rather than simple string comparisons.

1
Generate

Produce the candidate answer.

2
Decompose

Break the answer/context into claims.

3
Judge

Assess each claim against the required criterion.

Judge limitationAn LLM judge can make mistakes, including false positives and false negatives. The transcript recommends using a strong judge and keeping evaluation conditions consistent when comparing runs.

A useful practical point from the lecture is that the same judge model can perform the claim extraction and claim analysis through separate API calls. The important thing is that each call receives the appropriate task inputs.

Why generator evaluation is isolated

When evaluating the generator as a component, the retriever is intentionally disconnected. The generator receives the golden context directly from the dataset. This isolates generator quality from retrieval quality.

9. Implementing the Generator Evaluation

The lecture's evaluation script follows a repeatable pattern:

  1. Load the faithfulness golden dataset.
  2. Choose a judge model and threshold.
  3. For every dataset row, call the generator using the question + golden context.
  4. Create an evaluation test case containing the question, generated answer, and retrieval context.
  5. Attach faithfulness and answer-relevancy metrics.
  6. Run the evaluation and inspect aggregate scores and reasons for failures.
# Representative DeepEval-style implementation
import json

from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import FaithfulnessMetric, AnswerRelevancyMetric

with open("golden/faithfulness_dataset.json", "r", encoding="utf-8") as f:
    dataset = json.load(f)

test_cases = []

for row in dataset:
    question = row["question"]
    golden_context = row["golden_context"]

    answer = generate(
        query=question,
        context=golden_context
    )

    test_cases.append(
        LLMTestCase(
            input=question,
            actual_output=answer,
            retrieval_context=[golden_context]
        )
    )

faithfulness = FaithfulnessMetric(
    threshold=0.70,
    include_reason=True
)

answer_relevancy = AnswerRelevancyMetric(
    threshold=0.70,
    include_reason=True
)

evaluate(
    test_cases,
    [faithfulness, answer_relevancy]
)

The code above is a teaching-oriented representation of the flow described in the transcript. Adapt imports/API details to the DeepEval version installed in your environment.

The transcript reports a baseline run of approximately 91% faithfulness and 73% answer relevancy. fileciteturn0file0L735-L803

10. Improving the Generator: Prompt Engineering

Once the baseline is measured, evaluation becomes an optimization loop:

The session identifies two major levers for the generator: use a better model and improve the system prompt. The demonstrated improvement came primarily from iterative prompt refinement based on failed test cases.

The final prompt added rules such as not strengthening or overstating claims, not upgrading two different statements into separate stronger methods, and recognizing that the source material is an informal lecture transcript that may need synthesis and rephrasing rather than exact wording.

Practical lessonDo not tune prompts blindly. Use failed evaluation cases as evidence. Group failure patterns, update the prompt, and rerun the complete evaluation suite.

After several iterations, the transcript reports approximately 96% faithfulness and 92% answer relevancy. fileciteturn0file0L868-L890

11. Assemble the Full RAG Pipeline

After independently evaluating the retriever and generator, the next step is to connect them.

At this stage, the retrieved context is no longer supplied directly from the golden dataset. It comes from the real retriever. That difference is the key transition from isolated generator evaluation to pipeline evaluation. fileciteturn0file0L1050-L1087

12. The RAG Triad

The pipeline-level evaluation focuses on three relationships:

Question ↔ Context

Contextual Relevancy

Is the retrieved context actually relevant to answering the question?

Context ↔ Answer

Faithfulness

Is the generated answer grounded in the retrieved context?

Question ↔ Answer

Answer Relevancy

Does the generated answer address the user's question?

The lecture calls these three metrics together the RAG Triad. If all three relationships are strong, the pipeline is behaving well from the retrieval-to-answer perspective. fileciteturn0file0L1138-L1200

13. Contextual Relevancy

Contextual Relevancy evaluates the quality of retrieved context at a finer granularity than chunk-level precision.

How it is calculated

  1. Give the question to the real retriever.
  2. Collect the retrieved chunks.
  3. Break the retrieved context into claims using an LLM judge.
  4. For every claim, ask whether it is relevant to answering the question.
  5. Compute relevant claims ÷ total claims.
  6. Average the score over the evaluation questions.
Contextual Relevancy = claims relevant to the question ÷ all claims in retrieved context

The metric is reference-free in the sense described by the lecture: it does not require a golden context to judge whether the retrieved material itself is relevant to the query.

15. The Curious Case: High Recall & Precision, Low Contextual Relevancy

This is one of the most useful conceptual sections of the lecture.

MetricWhat it catchesGranularity
RecallHow much of the needed relevant context was retrieved?Retrieved chunks vs expected relevant chunks
PrecisionHow many retrieved chunks are useful/relevant?Chunk level
Contextual RelevancyHow much of the content inside retrieved chunks is actually relevant?Claim/content level

Why can all three disagree?

Imagine K = 5. Four of five retrieved chunks contain something useful, so precision can be high. But each chunk may contain a lot of unrelated material around the useful sentence.

That explains the apparent contradiction: precision can be high because a chunk contains at least one useful piece of information, while contextual relevancy can be low because most of that chunk is irrelevant noise. fileciteturn0file0L1380-L1470

Likely tuning lever

The transcript points to chunking as the first parameter to investigate. Smaller or better-targeted chunks may reduce irrelevant material inside each retrieved context. Chunk overlap and other retrieval parameters can also be experimented with, but improvements may involve trade-offs.

Key mental modelRecall asks “Did I find the needed chunks?” Precision asks “Are the chunks I found useful?” Contextual relevancy asks “How much of the content inside those chunks is actually useful for this question?”

16. Experiment Tracking

The session also demonstrates saving evaluation runs to a dashboard such as Confident AI. This enables experiment tracking similar to MLflow-style workflows.

  • View aggregate test results.
  • Inspect individual failed test cases.
  • Store configuration associated with a run.
  • Track system-prompt versions.
  • Store chunk-size and other parameters.
  • Compare experiments instead of relying on memory.
For serious evaluation work, the score alone is not enough. Store the prompt, model, retrieval configuration, dataset version, thresholds, and evaluation results together so a later regression can be explained.

18. Interview & Revision Cheat Sheet

QuestionShort answer
Why isolate the generator?To evaluate generation quality without letting retrieval quality contaminate the result.
What is faithfulness?Whether generated claims are supported by the supplied context.
Does faithfulness mean correctness?No. A model can faithfully reproduce an incorrect retrieved context.
What is answer relevancy?Whether the generated answer contributes to answering the user's question.
What is contextual relevancy?Whether the retrieved context content is relevant to the question.
What is the RAG Triad?Faithfulness + Answer Relevancy + Contextual Relevancy.
Why can precision be high while contextual relevancy is low?A retrieved chunk can contain one useful sentence and a large amount of irrelevant material.
How can generator quality be improved?Use a stronger model and, importantly, refine the system prompt using failed evaluation cases.

One-page mental model

Final takeaway A RAG system should not be judged by one score. Evaluate the retriever, evaluate the generator, connect them, then evaluate the complete pipeline. The most valuable failures are often diagnostic: a low score should tell you which relationship in the RAG system is breaking.
