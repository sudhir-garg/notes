The outline marks a transition from evaluation concepts into a hands-on model-selection exercise. The practical focus is not simply “which model is best?” but which candidate model best satisfies a defined application requirement under operational constraints.

Core idea: A leaderboard can help create a shortlist, but a production decision should be validated against the application's own task, data, correctness definition, latency target, context requirements, and cost ceiling.

5. Step 1 — Gathering Requirements & Defining the Task

Before comparing models, specify the task and its acceptance criteria. For Text-to-SQL, correctness is more meaningful when defined in terms of the executed result, not merely whether generated SQL text resembles a reference query.

TaskGenerate executable SQL from a natural-language question.
CorrectnessDoes the query produce the expected table/result?
LatencyHow quickly can the system return a usable answer?
CostCan expected token usage fit the application's budget?
ContextCan the model handle schema, instructions, examples, and question?

6. Calculating Operational Costs: Token Math & Budget Ceilings

Model selection should account for both input tokens and output tokens. A simple planning model is:

cost_per_request =
    (input_tokens  / 1_000_000) * input_price_per_million
  + (output_tokens / 1_000_000) * output_price_per_million

monthly_cost =
    requests_per_month * cost_per_request

A budget ceiling turns pricing into a hard engineering constraint. For example, if a model is highly accurate but consistently exceeds the permitted per-request or monthly cost, it may not be a viable production candidate.

7. Deep Dive: Prompt Caching & KV Cache Optimization

The outline specifically calls out prompt caching and KV cache optimization. Conceptually, these techniques target repeated computation in workloads where a large prefix of the prompt is reused across requests.

ConceptWhat is reused?Why it matters
Prompt cachingA reusable prompt/prefix portion, when supported by the serving provider.Can reduce repeated processing and/or effective input cost/latency.
KV cacheTransformer attention key/value states for tokens already processed.Reduces recomputation during generation and can improve serving efficiency.
Practical interpretation: Cache behavior is provider/model dependent. Treat it as an optimization to measure, not an assumption to bake into an evaluation result.

10. Normalizing Leaderboard Scores: Accuracy vs. Speed

When multiple leaderboard dimensions use different scales, normalize them before combining them. A generic min-max normalization is:

normalized(x) = (x - min_value) / (max_value - min_value)

A weighted score can then be constructed:

final_score =
    accuracy_weight * normalized_accuracy
  + speed_weight    * normalized_speed

The weights should reflect the actual product requirement. If correctness is safety-critical, accuracy should dominate. If the workload is highly interactive, latency may receive greater weight.

12. Step 3 — Custom Eval Workflow Architecture

The key design choice is to evaluate the observable application outcome. For Text-to-SQL, that often means executing the candidate SQL and comparing its result with the expected result.

13. Creating & Validating the Golden Dataset

The source names the dataset golden_hard.csv. A golden dataset should contain representative questions and an authoritative expected answer or expected result representation.

An illustrative structure is:

question,expected_result
"Which player scored the most runs in 2024?","player=..."
"List matches won by India in 2023","..."
Validation checklist: remove ambiguous questions, verify expected results independently, include difficult edge cases, keep schema assumptions explicit, and avoid accidental leakage of the answer into the prompt.

15. Writing the Evaluator: Why String Comparison Fails for SQL

The outline explicitly highlights a central evaluation problem: SQL string equality is not equivalent to semantic correctness.

Two different SQL queries can produce the same result. They may differ in whitespace, capitalization, aliases, join order, equivalent predicates, or other syntactic details while remaining semantically equivalent.

-- Query A
SELECT name FROM players ORDER BY name;

-- Query B
select p.name
from players AS p
order by p.name;

A literal string comparison can mark these as different even when their result tables are identical.

16. Table Comparison Logic: Rows, Normalization & Sorting

A stronger evaluator compares structured results. A practical pipeline is:

  1. Execute candidate SQL.
  2. Capture the result table.
  3. Normalize values and representations.
  4. Apply deterministic ordering where row order is not semantically meaningful.
  5. Compare expected and actual columns/rows.
  6. Record pass/fail plus diagnostics.
def normalize_table(rows):
    normalized = []
    for row in rows:
        normalized.append(tuple(
            None if value is None else str(value).strip()
            for value in row
        ))
    return sorted(normalized)

def tables_equal(expected, actual):
    return normalize_table(expected) == normalize_table(actual)
Do not sort blindly. If ordering is part of the question's semantics (for example, “top 5 in descending order”), the evaluator must preserve and test that ordering rather than treating all permutations as equivalent.

17. Orchestrating the Eval Loop with main.py

The orchestration layer should make each model go through the same dataset and evaluation procedure so the comparison is controlled.

# main.py — simplified architecture
for model in candidate_models:
    for case in golden_dataset:
        sql = generate_sql(model, case["question"])

        try:
            actual = execute_sql(sql)
            passed = tables_equal(
                case["expected_result"],
                actual
            )
        except Exception as exc:
            passed = False
            error = str(exc)

        record_result(
            model=model,
            passed=passed,
            latency=...,
            error=error if not passed else None,
        )

Useful aggregate metrics include pass rate, execution-error rate, generation latency, total evaluation cost, and failure categories.

19. Final Results Comparison & Selecting the Winner

The final decision should be based on a consistent evaluation matrix rather than a single metric.

DimensionExample decision question
Task correctnessWhich model produces the highest valid-result rate?
Syntax reliabilityHow often does generated SQL fail before execution?
LatencyDoes the model meet the application SLA?
CostDoes expected usage stay below the budget ceiling?
Context capabilityCan it handle the full schema + instructions + question?

A useful final score can be a weighted composite, but the winner should also satisfy any hard constraints. A model that fails a mandatory correctness or latency threshold should not be rescued by a high score on another dimension.
