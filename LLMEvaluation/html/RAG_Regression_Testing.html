2. What Is Regression Testing?

Regression means that a system returns to a previous, less-advanced or worse state. Regression testing checks whether a change intended to improve one part of a system accidentally makes another part worse.

RAG example

Suppose retrieval recall is 85%. Increasing k and adding a reranker may raise recall to 90%, but precision, contextual relevance, latency or cost may worsen. If only recall is measured, the team can deploy a system that is worse overall.

Core principle: never evaluate a RAG change using only the metric you intended to improve. Re-run the complete evaluation suite.

3. The Danger of Single-Metric Tuning

ChangeIntended benefitPossible regression
Increase retrieval kImprove recallLower precision, more irrelevant context, higher latency/cost
Add rerankerImprove retrieval qualityAdditional latency and compute cost
Reduce chunk sizePotentially improve contextual relevanceDifferent retrieval behavior and indexing cost
Change modelImprove answer qualityCost, latency, safety or behavior changes
Change system promptImprove generation behaviorUnexpected quality/safety changes

The lesson's central warning is that RAG quality is multidimensional. A positive change in one metric can coexist with negative changes elsewhere. Regression testing makes those trade-offs visible before deployment.

5. Baseline → Candidate → Delta

  1. Build the runner: one Python entry point calls the evaluation modules.
  2. Create the baseline: run the suite and save all metric results, preferably as JSON.
  3. Change the RAG system: modify retrieval, chunking, model, prompt or another component.
  4. Create the candidate: run the same suite against the changed system.
  5. Compare: calculate per-metric deltas and determine whether meaningful regression occurred.

This baseline/candidate comparison is the core regression workflow described in the transcript. 

def run_suite():
    quality = run_quality_evals()
    safety = run_safety_evals()
    operations = run_operational_evals()
    return {**quality, **safety, **operations}

baseline = run_suite()
save_json("baseline.json", baseline)

# ...make a RAG change...

candidate = run_suite()
save_json("candidate.json", candidate)

compare("baseline.json", "candidate.json", "metric_registry.py")
Implementation note: the lesson intentionally uses a bare-shell conceptual implementation. Production teams may use dedicated evaluation/regression tools, but the underlying concepts remain the same.

6. Two Core Challenges

Challenge 1 — Metrics have different directions

DirectionExamplesMeaning
Higher is betterFaithfulness, recall, precisionAn increase is generally an improvement.
Lower is betterLatency, cost, toxicityA decrease is generally an improvement.

The comparison engine therefore needs metadata describing the direction of each metric.

Challenge 2 — LLM-as-a-Judge introduces noise

Most quality and safety evaluations in this setup use an LLM as a judge. Because LLMs are probabilistic, the same application and evaluation configuration can produce slightly different scores across runs.

Example: precision can be 85.6 in one run and 84.8 in another without any application change. A naive comparison would incorrectly call that a regression.

7. Noise Thresholds with Standard Deviation

The lesson's solution is to measure natural evaluation variability before using the suite for regression decisions.

→

≈ 2 × σ

For each metric, repeatedly run the suite without changing the application. Calculate the standard deviation of that metric's scores. The lesson uses approximately two standard deviations as a practical noise threshold. A change inside the threshold is treated as evaluator noise rather than a meaningful regression. 

import statistics

scores = [90.0, 90.8, 89.7, 90.2, 89.9, 90.4, 90.1, 89.8, 90.5, 90.0]

sigma = statistics.stdev(scores)
noise_threshold = 2 * sigma

print("standard deviation:", sigma)
print("noise threshold:", noise_threshold)

If baseline recall is 90 and the tolerance is ±1, a candidate value of 89.5 is treated as noise. A candidate of 87.5 lies outside the tolerance and is treated as regression.

Metric Registry

Every metric needs two important pieces of metadata:

  1. Direction: higher or lower is better.
  2. Noise threshold: expected evaluator variation.

The transcript describes storing this information in a separate metric registry so the comparison logic can determine both whether movement is desirable and whether it exceeds normal noise.

8. Small Golden Datasets: An Important Limitation

The example golden datasets are explicitly described as very small—sometimes only around 5, 10 or 15 entries. This can produce substantial run-to-run variability. The transcript notes that increasing dataset size generally makes the system appear more stable.

Practical lesson: do not interpret a noisy score from a tiny evaluation set as a highly precise measurement. Dataset size is itself an important factor in evaluation stability.

9. Refactoring the Evaluation Codebase

Before automation, the evaluation modules are reorganized so they can be called consistently.

Operational and safety consolidation

The three operational evaluations—reliability, cost and latency—are combined into one operational module. Likewise, leakage, toxicity and scope evaluations are consolidated into one safety module.

Quality evaluation modules

The retriever, generator, pipeline and application evaluations remain separate. Each is refactored to expose a callable run() function and an if __name__ == "__main__" entry point. This allows the module to run directly or be invoked from another script. 

def run():
    return {
        "recall": 0.96,
        "precision": 0.90
    }

if __name__ == "__main__":
    print(run())

Test harness

A harness.py-style layer standardizes how the quality evaluations receive input and how their output is extracted. Its purpose is consistency, not implementing the evaluation logic itself.

11. Live Experiment: Retriever Chunk Size

The demonstrated experiment changes the retriever configuration from a chunk size of 1500 to 500, with overlap set to 100. The motivation is to try to improve contextual relevance. Because chunking changed, the vector database is rebuilt so the documents are re-embedded using the new chunks. 

chunk_size = 500
chunk_overlap = 100

# Rebuild index because chunking changed
vector_store.delete_all()

documents = load_documents()
chunks = split_documents(
    documents,
    chunk_size=chunk_size,
    chunk_overlap=chunk_overlap
)
vector_store.add(chunks)

The updated configuration is logged with the evaluation run. The full suite then executes automatically and writes the new results to candidate.json. The transcript notes that the run can take several minutes because many evaluations are being executed and the vector store may need to be rebuilt.

12. Comparing Baseline vs Candidate

The comparison step consumes three inputs:

baseline.jsonMetrics before the change.
candidate.jsonMetrics after the change.
metric_registry.pyDirection and noise tolerance.
def compare_metric(baseline, candidate, direction, threshold):
    delta = candidate - baseline

    if abs(delta) <= threshold:
        return "flat", delta

    if direction == "higher":
        return ("improved" if delta > 0 else "regressed"), delta

    if direction == "lower":
        return ("improved" if delta < 0 else "regressed"), delta

def compare(baseline, candidate, registry):
    report = {}
    for metric, config in registry.items():
        status, delta = compare_metric(
            baseline[metric],
            candidate[metric],
            config["direction"],
            config["noise_threshold"]
        )
        report[metric] = {
            "baseline": baseline[metric],
            "candidate": candidate[metric],
            "delta": delta,
            "status": status
        }
    return report
StatusMeaning
ImprovedMovement is desirable and exceeds the noise threshold.
RegressedMovement is undesirable and exceeds the noise threshold.
FlatDifference is within expected evaluator noise.

The live comparison produced many flat metrics because their variation was within the configured noise tolerance, while several metrics improved. The value of the report is that it exposes all dimensions rather than hiding trade-offs behind a single number.

Using metric groups for diagnosis

If retrieval metrics such as recall, precision and contextual relevance remain healthy but answer quality deteriorates, generation becomes a stronger suspect. If retrieval metrics deteriorate, the retriever or retrieval configuration becomes a stronger suspect. The metrics therefore serve not only as gates but also as diagnostic signals.

14. Evaluation Cost & the Single-Score Temptation

Evaluation itself has a cost. The transcript notes that even the small example suite can consume meaningful money because many LLM-based evaluations are executed. Larger golden datasets would increase that cost.

Should all metrics become one score?

A weighted composite score is technically possible:

overall_score =
    0.30 * faithfulness +
    0.20 * answer_relevance +
    0.20 * contextual_relevance +
    0.15 * safety_score +
    0.15 * reliability_score

However, the lesson cautions that merging all metrics into a single dimension can hide important differences between aspects of the application. Individual metrics exist because they reveal different failure modes. A composite score may be useful in a domain-specific system, but it should not replace the underlying metric-level report.

15. Key Takeaways

1. Full-suite evaluationImproving one metric is not sufficient evidence that a RAG change is good.
2. Baseline mattersThe previous known state is the reference for candidate changes.
3. Direction mattersSome metrics should increase; others should decrease.
4. Noise mattersLLM-as-a-judge is probabilistic, so small changes may be evaluator noise.
5. Registry mattersStore metric direction and tolerance centrally.
6. Dataset size mattersSmall golden sets can produce large variability.
7. Automation mattersOne suite runner eliminates repetitive manual commands.
8. Diagnostics matterMetric groups can help identify retrieval vs generation problems.
9. Cost mattersEvaluation can become expensive as datasets and judge calls grow.
10. CI mattersRegression tests can become a pre-deployment quality gate.
