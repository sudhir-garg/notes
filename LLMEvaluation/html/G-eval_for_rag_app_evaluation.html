2. Count-Based vs Judgment-Based Evaluation

Earlier RAG evaluation used metrics such as recall, precision, faithfulness, answer relevance and context relevance. The lesson groups these earlier techniques around a common pattern: decompose something into checkable units, count favorable vs unfavorable units, and derive a ratio.

Why style cannot be reduced to claim counting

Suppose the desired teaching style is defined at the answer level—e.g., explain the “why, what and how” naturally. A single sentence does not necessarily contain every characteristic of the overall style. Therefore, checking each sentence independently and computing a ratio does not represent the holistic property reliably.

Why correctness can also defeat claim counting

An answer may use an analogy. The analogy can look unrelated to the reference answer when isolated, yet make perfect sense in the context of the complete explanation. Treating the analogy as an independent claim can incorrectly penalize a correct answer.

Core distinction: count-based metrics ask “how many individual units satisfy a rule?” Judgment-based metrics ask “how well does the complete answer satisfy a criterion?”

3. Why a Naive LLM-as-a-Judge Is Not Reliable Enough

The straightforward approach is tempting:

  1. Create a golden dataset containing a question and expected answer.
  2. Run the RAG application to obtain the actual answer.
  3. Give question + expected answer + actual answer to an LLM judge.
  4. Ask for a score from 0–10.
  5. Average the scores across the dataset.

Two causes of variance highlighted in the lesson

CauseWhat happensWhy it matters
Loose criterionThe judge receives a high-level instruction such as “decide how factually correct it is.”Different calls may interpret “correctness” differently.
Integer score selectionThe model must choose one discrete token such as 6, 7, 8, 9 or 10.Small probability changes can flip the selected token and create large score jumps.
Reliability requirement: if nothing in the evaluation setup changes, repeated runs should have low variance. The lesson uses this as the key reason to move beyond naive direct LLM judging.

5. G-Eval Innovation #1 — Convert Criteria into Evaluation Steps

Instead of asking a judge to interpret a vague criterion independently on every call, G-Eval first turns the criterion into a more explicit rule set. The lesson describes this as converting the high-level criterion into roughly four or five evaluation steps, creating a “constitution” or “rule book” for evaluation.

Step 1 — Select metric: e.g., correctness.
Step 2 — Define criterion: e.g., compare the actual answer with the expected answer based on factual correctness.
Step 3 — Derive evaluation steps: make the criterion operational and explicit.
Step 4 — Build judge prompt: supply question, expected answer, actual answer and evaluation steps.
Step 5 — Score: evaluate according to the defined rubric.

Example evaluation rule set for correctness

Evaluation criterion:
Compare the actual answer against the expected answer
and judge factual correctness.

Evaluation steps:
1. Compare factual claims in the actual answer with the expected answer.
2. Penalize claims that contradict the expected answer.
3. Penalize claims that are factually false.
4. Do not penalize an answer merely because it is shorter.
5. Do not lower the score for correct additional information.

The important design change is that the evaluator is no longer given only a single broad sentence. It receives a repeatable evaluation procedure.

6. G-Eval Innovation #2 — Probability-Weighted Scoring

The second innovation addresses the instability of asking the judge to output one integer directly. The lesson explains the idea using the model’s token probabilities.

From “pick 8” to “how likely were 7, 8 and 9?”

Suppose the judge considers these numeric output tokens:

TokenIllustrative probability
80.70
70.20
90.05
Non-numeric alternatives0.05 combined

After retaining the relevant numeric candidates, their probabilities are normalized. The weighted score is then conceptually:

Weighted score = Σ(scorei × normalized probabilityi)

Using the lesson’s illustrative numbers:

8 × 0.73 + 7 × 0.21 + 9 × 0.05 ≈ 7.84

Instead of taking the single most probable token, the evaluator uses the probability mass around plausible numeric scores. This produces a smoother score than simply switching between integer outputs.

Why this helps: a small change from “8 is most likely” to “7 is most likely” does not necessarily turn the final score from 8 to 7. The weighted score can move gradually.

Normalization

If only the top-k relevant numeric tokens are retained, their probabilities may not sum to 1. The lesson therefore normalizes them before computing the weighted average.

p′i = pi / Σ pj

The resulting score can then be mapped to the desired range. The transcript describes dividing a 0–10 score by 10 to obtain a 0–1 metric, followed by thresholding.

7. End-to-End G-Eval Pipeline

Per-test-case flow

  1. Take a question from the golden dataset.
  2. Run the RAG application.
  3. Capture its actual answer.
  4. Provide question, expected answer, actual answer and evaluation criteria/steps to the G-Eval judge.
  5. Extract the relevant score-token probabilities.
  6. Normalize and calculate the weighted score.
  7. Compare the normalized score against a threshold.
  8. Aggregate results across the test set.

9. Metric 2 — Completeness

Completeness asks whether the generated answer addresses all the parts of the user's question. This is especially important for multi-part questions.

Example

Question: “Explain X and also compare it with Y.”

Partial answer: explains X but never compares it with Y.

Complete answer: addresses both requested components.

Same G-Eval machinery, different criterion

The dataset structure remains similar: question + ideal answer + actual generated answer. The main change is the metric definition and evaluation rubric. The judge is instructed to check whether the answer covers the multiple components of the question rather than stopping after addressing only the first component.

Lesson example: after a prompt refinement that explicitly told the generator not to miss any part of a multi-component question, the reported completeness score improved from roughly 50% to 75%, with failed test cases dropping from 10 to 1 in the shown run.

Practical rule

Completeness criterion:
- Identify every distinct requirement in the question.
- Check whether the answer addresses each requirement.
- Do not stop evaluation after finding one answered component.
- Do not reward invented information simply to fill missing components.

10. Metric 3 — Tone & Style

Style is a particularly useful judgment-based metric because there is no single “golden answer” that the generated response must match word-for-word.

Reference-free evaluation: the lesson evaluates style using a clearly defined rubric plus the generated answer, without requiring an ideal answer.

Example style rubric used in the lesson

  • Reward an intuitive explanatory tone.
  • Prefer plain language.
  • Explain the idea before introducing formulas or jargon.
  • Briefly unpack technical terms when they are used.
  • Prefer a direct, conversational teacher-to-student register over a dry textbook tone.
  • Use concrete examples or analogies when they genuinely help.

11. Prompt Engineering and Rubric Tuning

The lesson demonstrates an important evaluation-development loop: evaluate → inspect failures → refine the generator prompt or evaluator rubric → rerun.

Example: improving completeness

The generator was explicitly instructed to consider all parts of a multi-component question instead of stopping after the first component. The reported score improved substantially in the demonstrated run.

Example: improving style

The initial style score was reported around 54. The generator prompt was then made more explicit about the desired conversational teaching style. The evaluator rubric was also refined.

A subtle evaluator failure: over-correction

The original style rubric rewarded examples and analogies. The evaluator began penalizing answers that did not contain an analogy—even when the question did not need one. This is a classic rubric-design problem: a desirable behavior was accidentally turned into a mandatory requirement.

Rubric correction: an analogy or concrete example should be a bonus when the concept is abstract; a clear, direct explanation should remain fully acceptable without one.

After the two refinements—generator prompt tuning and rubric tuning—the demonstrated style score rose to around 74.

Key lesson: evaluation is not only measurement. The metric results reveal where the application or evaluator needs refinement.

What the framework does conceptually

Interview question: Why not just use an LLM as a judge?

Answer: You can, but a direct “give me a 0–10 score” setup can be highly variable. The lesson attributes this to two main issues: the evaluation criterion is under-specified, and discrete score-token selection can change between runs. G-Eval reduces this variability by making evaluation steps explicit and using probability-weighted scoring.

Interview question: What are the two core innovations of G-Eval?

Answer: First, convert a high-level evaluation criterion into explicit evaluation steps. Second, derive the final score from probability-weighted candidate score tokens rather than simply taking one generated integer.

Interview question: Does G-Eval replace LLM-as-a-judge?

Answer: No. In the lesson's framing, G-Eval is an improved way to perform LLM-as-a-judge evaluation. The judge is still an LLM; G-Eval makes the judging procedure more structured and the score more stable.

Interview question: How do you evaluate style when there is no golden answer?

Answer: Define a precise style rubric describing the desired characteristics and score the generated answer against that rubric. This is reference-free judgment-based evaluation.
