1. Previous-Session Recap

Before understanding multiple evaluation pipelines, remember the three core ideas from the previous session.

Why LLM Evals?

Deploying an LLM application without systematic evaluation can lead to incorrect answers, hallucinations, unsafe outputs, poor retrieval, high cost, and unacceptable latency.

What are LLM Evals?

LLM evaluations are systematic and reliable ways of evaluating LLMs or LLM-based applications against clearly defined criteria.

Two broad types

Model evaluation: evaluates the model itself, often with benchmarks.
Application evaluation: evaluates the application you built around one or more models.

Course focus: In an AI-engineering context, application evaluation is especially important because the application combines multiple components and workflows.

2. Why Do We Need Multiple Eval Pipelines?

There are two major reasons:

1

Multiple failure points

An LLM application contains several components. Any individual component—or the interaction between components—can fail.

2

Multiple risk categories

Even if a component performs its intended job, it may still be too slow, expensive, unsafe, incomplete, or unreliable.

Core principle: One application usually needs several evaluation pipelines because “correct” is only one dimension of production quality.

Failure Point #1 — Retriever

The retriever may return irrelevant documents. If the correct document is missing or ranked too low, the generator receives poor evidence.

Failure Point #2 — Generator

Even with useful context, the generator can produce an unsupported or incorrect answer. This is where faithfulness / groundedness becomes important.

4. The “8-Week ML Course” Trap

Consider the query:

“What is the duration of the Machine Learning course?”

Suppose K = 5, meaning the retriever returns five documents:

RankDocumentRelevant?
D1Unrelated information❌
D2Unrelated information❌
D3Unrelated information❌
D4Information about another course❌
D5“Machine Learning course duration = 8 weeks”✅
Important: The correct document exists inside the retrieved top-K set. Therefore, the retriever can satisfy a recall@5-style criterion even though the ranking is not ideal.

Where can the system still fail?

The generator receives all five documents. If the prompt or ranking causes it to prioritize D1–D4, it may use an incorrect fact such as another course’s duration and answer incorrectly.

Key insight: The retriever can be acceptable by one metric, and the generator can independently follow its instructions, yet the combined RAG workflow can still produce a wrong final answer.

Solution: Evaluate the workflow

The workflow-level evaluation tests the interaction between retrieval and generation. If the right document is present but badly ranked, a reranker may improve the final context order.

Reranker: a second-stage ranking component that reorders retrieved candidates using a more targeted relevance model.

5. The Three Levels of Evaluation

Level 1 — Component Evaluation

Evaluate individual building blocks independently.

  • Retriever
  • Reranker
  • Query rewriter
  • Embedding model
  • Vector database
  • Prompt/system prompt
  • Output parser
  • Agent tool selector
  • Memory
  • Guardrails

Level 2 — Workflow Evaluation

Evaluate whether components work correctly together.

  • RAG: retrieval → reranking → generation
  • Agent: reasoning → tool selection → tool execution → recovery
  • Multi-turn chatbot: conversation state → response generation

Level 3 — Application Evaluation

Evaluate the complete user-facing system against production requirements.

  • End-to-end latency
  • Cost per request
  • Time to first token (TTFT)
  • Reliability / error rate
  • Safety and privacy
  • Overall user-task success
Important: Passing component and workflow evaluations does not automatically mean the application is production-ready. For example, a correct response that takes 10 seconds may violate the application's latency requirement.

6. Multiple Risk Categories

The second reason for multiple evaluations is that each failure point can have several dimensions of risk.

1. Application Quality

Does the system actually do the requested job well?

  • Correctness
  • Relevance
  • Completeness
  • Instruction following
  • Groundedness

2. Safety

Does the system avoid harmful, unsafe, unauthorized, or privacy-violating behavior?

  • Toxicity
  • Harmful content
  • Bias
  • PII/data leakage
  • Prompt injection
  • Jailbreak resistance

3. Operations

Can the application run reliably and economically in production?

  • Latency
  • Cost/request
  • Token efficiency
  • Error rate
  • Latency under load
  • Reliability

8. Practical Code Examples

8.1 A Simple Evaluation Record

from dataclasses import dataclass
from typing import Optional

@dataclass
class EvalResult:
    name: str
    score: float
    passed: bool
    details: Optional[str] = None

def threshold_eval(name: str, score: float, threshold: float) -> EvalResult:
    return EvalResult(
        name=name,
        score=score,
        passed=score >= threshold,
        details=f"threshold={threshold}"
    )

result = threshold_eval(
    name="retriever_recall_at_5",
    score=0.92,
    threshold=0.90
)

print(result)

8.2 Retriever Recall@K

A simplified version: the test passes if the expected relevant document appears in the retrieved top-K results.

def recall_at_k(retrieved_ids, relevant_ids, k):
    retrieved = set(retrieved_ids[:k])
    relevant = set(relevant_ids)

    if not relevant:
        return 0.0

    return len(retrieved & relevant) / len(relevant)


retrieved = ["doc_17", "doc_04", "doc_21", "doc_08", "doc_99"]
relevant = ["doc_99"]

score = recall_at_k(retrieved, relevant, k=5)

print(f"Recall@5 = {score:.2f}")
# Recall@5 = 1.00
Important distinction: Recall@5 = 1 does not mean the best document was ranked first. It only tells us that the relevant document exists somewhere in the top five.

8.3 A Basic Groundedness Check

For production systems, use a robust evaluator or model-based judge rather than the toy word-overlap example below. This example only illustrates the concept.

def simple_groundedness(answer: str, context: str) -> float:
    # Educational toy metric only.
    # Real systems should use claim-level evaluation,
    # an LLM judge, NLI-style evaluation, or a specialized
    # groundedness evaluator.
    answer_words = set(answer.lower().split())
    context_words = set(context.lower().split())

    if not answer_words:
        return 0.0

    return len(answer_words & context_words) / len(answer_words)


context = "The Machine Learning course duration is 8 weeks."
answer = "The Machine Learning course duration is 8 weeks."

print(simple_groundedness(answer, context))

8.4 Application-Level Latency Evaluation

import time

def evaluate_latency(app, query, threshold_seconds=2.0):
    start = time.perf_counter()

    response = app(query)

    elapsed = time.perf_counter() - start

    return {
        "response": response,
        "latency_seconds": round(elapsed, 3),
        "passed": elapsed <= threshold_seconds
    }

8.5 Combine Multiple Evaluations

def production_gate(results):
    # Every required evaluation must pass.
    failed = [r for r in results if not r["passed"]]

    return {
        "ready": len(failed) == 0,
        "failed_checks": failed
    }


checks = [
    {"name": "retrieval_recall", "passed": True},
    {"name": "groundedness", "passed": True},
    {"name": "latency", "passed": False},
    {"name": "safety", "passed": True},
]

print(production_gate(checks))

9. Production Evaluation Checklist

  • ☐ Identify every major component and define its job.
  • ☐ Create component-level evaluations.
  • ☐ Create workflow-level tests for component interactions.
  • ☐ Define application-level success criteria.
  • ☐ Separate quality, safety, and operational evaluations.
  • ☐ Test normal and adversarial inputs.
  • ☐ Test retrieval quality separately from final-answer quality.
  • ☐ Measure latency and TTFT separately where relevant.
  • ☐ Track cost per request and token usage.
  • ☐ Add privacy/PII leakage tests.
  • ☐ Add prompt-injection and jailbreak tests.
  • ☐ Run evaluations on a representative evaluation dataset.
  • ☐ Establish thresholds before production release.
  • ☐ Re-run evaluations whenever prompts, models, retrieval, tools, or data change.

10. Interview & Revision Cheat Sheet

Q1. Why do we need multiple eval pipelines?

Answer: Because an LLM application has multiple failure points and multiple risk dimensions. We need separate evaluations for components, their interactions, the overall application, and dimensions such as quality, safety, and operations.

Q2. If the retriever and generator both pass their individual evaluations, is the RAG application guaranteed to be correct?

Answer: No. The interaction between them can still fail. For example, the correct document may be retrieved but ranked too low, causing the generator to use less relevant context.

Q3. What are the three evaluation levels?

Component → Workflow → Application.

Q4. What are the three broad risk categories?

Application Quality → Safety → Operations.

Q5. What does faithfulness / groundedness measure?

Whether the generated answer is supported by the supplied context rather than introducing unsupported facts.

Q6. What does Recall@K tell us?

Whether the relevant evidence appears within the top K retrieved results. It does not, by itself, tell us that the relevant document is ranked first.

Q7. Give examples of application-level operational evaluations.

End-to-end latency, time to first token, cost per request, token efficiency, error rate, reliability, and latency under load.

One-line mental model:
“Did each component work?” → “Did the components work together?” → “Did the whole application satisfy user and production requirements?”
