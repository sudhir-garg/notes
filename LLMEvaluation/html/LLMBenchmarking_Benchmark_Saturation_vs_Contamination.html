1. Course Recap: From Application Evals to Model Evals

The course started with a broad question: why do we need LLM evaluations? From there, the discussion moved toward understanding what exactly should be evaluated and how evaluation fits into the lifecycle of an AI application.

Two major categories of LLM evaluation were introduced:

Model Evaluations

Evaluations designed to directly measure the capabilities, behavior, reliability, safety, and other characteristics of an underlying LLM.

Application Evaluations

Evaluations designed to measure an LLM-powered application such as a RAG system, chatbot, classifier, or agent.

LLM Model
→
Model Evaluation
→
Application Evaluation
→
Production Monitoring
Course direction The earlier part of the course focused primarily on application evaluations—RAG evaluators, retriever evaluation, generator evaluation, application-level evaluation, offline evaluation, and online evaluation. The course now moves down one level and focuses on the model itself.

The transition

Suppose we build a RAG application. We may evaluate:

  • Whether the retriever finds the correct documents.
  • Whether the generator produces a grounded answer.
  • Whether the complete RAG pipeline performs correctly.

But there is another fundamental question:

What about the brain of the application? Which LLM should power the RAG system in the first place, and how do we know that it is the right model?

That is where model evaluations become essential.

2. What Is a Model Evaluation?

A model evaluation is a systematic process for measuring an underlying language model's capabilities, behavior, reliability, and operational characteristics under controlled conditions.

In simpler terms:

Model Eval = A controlled test used to measure what an LLM can and cannot do.

The important word here is systematic. A model evaluation is not simply asking an LLM a few questions and deciding whether the responses look good.

A meaningful evaluation requires:

  • A clearly defined capability.
  • A test designed to measure that capability.
  • Controlled execution conditions.
  • A scoring and interpretation mechanism.

3. Why Do AI Engineers Need Model Evaluations?

A frontier AI laboratory needs model evaluations to improve and train its models. But an AI engineer has a different problem.

An AI engineer usually needs to build a reliable application using one or more available models.

The central principle

If you cannot measure it, you cannot reliably improve or compare it.

Model evaluations turn vague statements such as "Model A feels better" into measurable evidence.

Reason 1 — Compare multiple models

Imagine your company wants to build a RAG application. You have several candidate models:

  • A proprietary API model.
  • Another proprietary model.
  • An open-source model hosted internally.

The question in a professional engineering environment is not:

"Which one feels better?"

Instead, the question should be:

"Which model performs best against the capabilities and constraints that matter to our application?"

Model evaluations provide the evidence needed to answer this question.

Reason 2 — Evaluate whether a new model is actually better

New models are released continuously. If your application currently uses Model A and Model B is released, you need evidence before migrating.

Existing Model
→
New Model
→
Run Same Evaluation
→
Compare Results

A model evaluation gives you a repeatable basis for deciding whether the new model represents a genuine improvement.

Reason 3 — Evaluate safety and reliability

Model selection is not only about intelligence. You also need to understand:

  • Hallucination behavior.
  • Safety behavior.
  • Resistance to jailbreaks.
  • Truthfulness.
  • Instruction-following reliability.
  • Potentially dangerous or undesirable behaviors.

Reason 4 — Decide between proprietary APIs and self-hosting

One of the most important architectural decisions is whether to:

Use a Proprietary API

Pay a model provider and consume the model through an API.

Self-Host an Open Model

Deploy an open-weight model on your own infrastructure and operate your own inference stack.

This decision involves multiple dimensions:

Dimension Question
Quality Which model performs better on our required capabilities?
Cost Which model is economically sustainable at our scale?
Latency Which model can satisfy our response-time requirements?
Privacy Does the workload require internal deployment?
Control How much control do we need over infrastructure and inference?
Safety Which model satisfies our safety requirements?
Without evaluation, model selection becomes guesswork. Model evaluations provide the empirical evidence needed to make this architecture decision.

5. The Four Structural Steps of Model Evaluation

Every model evaluation can be understood as a four-step process.

1
Define Capability
→
2
Design / Select Test
→
3
Run Under Fixed Protocol
→
4
Score & Interpret

Step 1 — Decide what capability to test

LLMs are general-purpose models. They do not have a single universal "intelligence score" that completely describes their usefulness.

You may want to measure:

  • Reasoning
  • Coding
  • Mathematics
  • Safety
  • Long-context understanding
  • Vision
  • Tool use
  • Instruction following

Step 2 — Bring a test

Once the capability is defined, you need a test that can measure it.

The test could be:

  • A standardized benchmark.
  • A custom dataset.
  • A collection of real-world tasks.
  • A simulated environment.
  • A programmatic test suite.

Step 3 — Run the model under a fixed protocol

The models should receive comparable conditions.

You may need to control:

  • Dataset version.
  • Prompt format.
  • Sampling parameters.
  • Number of evaluation examples.
  • Tool availability.
  • Execution environment.
  • Scoring procedure.
Why controlled conditions matter If Model A receives an easier test or different execution conditions than Model B, their scores cannot be interpreted as a fair comparison.

Step 4 — Score and interpret

The final stage is not merely producing a number. The score must be interpreted in context.

For example: 

Model A
Accuracy: 94%
Cost:     $6 / 1,000 requests
Latency:  4.1 seconds

Model B
Accuracy: 91%
Cost:     $0.21 / 1,000 requests
Latency:  0.9 seconds

A higher accuracy score does not automatically make Model A the better engineering choice.

6. Standardized Benchmarks vs Custom Evaluation Datasets

The second step of model evaluation—choosing the test—is where two major approaches appear.

Benchmark Evaluation Custom Evaluation
Standardized test Designed around your application
Shared across models Built from your own workload
Excellent for general comparison Excellent for application-specific decisions
Usually measures broad capabilities Measures what your business actually cares about
Useful for industry-wide comparisons Useful for engineering and deployment decisions

What is a benchmark?

A benchmark is a standardized, shared test used to evaluate models against a common set of tasks.

The major advantage is comparability.

Model A
Model B
Model C
Same Benchmark
↓
Comparable Scores

Because the models are evaluated using the same standardized test, benchmark scores provide a common ground for comparison.

What is a custom evaluation?

A custom evaluation is created around the actual workload for which the model will be used.

For example, a company building an email-routing system may construct a dataset containing real historical emails labelled as:

  • Billing
  • Technical
  • Refund

The company can then evaluate candidate models directly on this task.

Key distinction Benchmarks answer: "How capable is this model generally?"

Custom evaluations answer: "How useful is this model for our particular workload?"

Consider an application that automatically routes incoming customer emails to the correct department.

If we only look at public benchmarks, Model A appears to be the obvious choice.

But this ignores the actual application.

Build a golden dataset

Suppose the team collects 200–500 historical emails and manually labels each one.

Historical Emails
→

→

→
Evaluate Both Models

Application-specific results

Metric Model A Model B
Classification accuracy 94% 91%
Urgency accuracy 88% 87%
Cost / 1,000 emails ~$6 <$0.21
Latency ~4.1 sec ~0.9 sec

The engineering decision

Model A is technically more capable.

But Model B is only a few percentage points behind for the actual workload, while providing major advantages in cost and latency.

Result: Model B can be the better production choice. The goal is not to select the model with the highest benchmark score. The goal is to select the model that provides the best value for the application's requirements.

Why benchmarks alone would fail here

Suppose Model A beats Model B on every public benchmark.

That still would not prove that Model A is the economically optimal choice for the email-classification application.

The custom evaluation exposes a crucial engineering insight:

Best general-purpose model ≠ Best model for every application.

A useful decision framework

Dimension Question
Quality Does it meet the required accuracy?
Cost Can we afford it at production scale?
Latency Can it meet our response-time SLA?
Safety Does it behave safely for the workload?
Reliability Does performance remain stable across representative inputs?

8. The Eight Core Capabilities of Modern LLMs

Before studying individual benchmarks, we need to understand what exactly those benchmarks are trying to measure.

Modern LLMs are general-purpose systems. A model can perform many different types of tasks, so there cannot be one universal test that completely describes the model.

The course organizes the major capabilities into eight broad categories:

1Knowledge & Reasoning

Factual knowledge, multi-step reasoning, and connecting information.

2Coding & Software Engineering

Code generation, debugging, repository-level work, and engineering tasks.

3Mathematics

Numerical, symbolic, competition-level, and advanced mathematical reasoning.

4Long Context

Using and retrieving information effectively from very large inputs.

5Vision & Multimodality

Understanding images, video, documents, and other modalities.

6Agentic & Tool Use

Using tools, APIs, browsers, computers, and external systems.

7Safety & Alignment

Responsible behavior, robustness, truthfulness, and resistance to attacks.

8Instruction Following

Following explicit user requirements accurately and consistently.

9. Capability #1 — Knowledge & Reasoning

Knowledge and reasoning are closely related but distinct capabilities.

Knowledge

Knowledge asks:

  • What factual information does the model know?
  • Can it recall facts across different domains?
  • Can it answer questions about science, history, biology, physics, etc.?

Reasoning

Reasoning asks whether the model can connect multiple facts and perform multi-step inference to reach a conclusion.

+
Fact B
+
Fact C
→
Reasoned Conclusion

What can be tested?

Area Example Evaluation Question
Factual recall Can the model correctly answer factual questions?
Cross-domain knowledge Can it answer questions across many academic subjects?
Multi-step reasoning Can it connect several pieces of information?
Inference Can it derive a conclusion that is not explicitly stated?

Example benchmark category

MMLU-style evaluations are designed to test knowledge across a broad range of subjects.

Real-world applications

  • Research assistants.
  • Professional knowledge assistants.
  • Technical document analysis.
  • Scientific research workflows.
  • Legal or educational assistants.
Why frontier labs care Strong knowledge plus strong reasoning is often used as an indicator of a model's general intellectual capability.

10. Capability #2 — Coding & Software Engineering

Coding has become one of the most economically important capabilities of modern LLMs because software development represents a huge amount of enterprise work.

What is evaluated?

  • Functional code generation.
  • Test generation.
  • Bug fixing.
  • Code modification.
  • Repository-level reasoning.
  • Multi-file changes.
  • Refactoring.
  • Command-line interaction.
  • Environment setup.
  • API and function calling.

Simple code-generation evaluation

Prompt:
"Write a Python function that determines whether
a given string is a palindrome."

Model Output:

def is_palindrome(text):
    normalized = text.lower().replace(" ", "")
    return normalized == normalized[::-1]

A useful coding evaluation should not stop at checking whether the code looks correct. The generated code can actually be executed against test cases. 

def test_is_palindrome():
    assert is_palindrome("level") is True
    assert is_palindrome("racecar") is True
    assert is_palindrome("hello") is False

This moves the evaluation from subjective inspection toward measurable functional correctness.

Advanced software-engineering evaluation

More sophisticated evaluations may provide the model with an existing repository and ask it to:

  • Find a bug.
  • Implement a missing feature.
  • Refactor multiple files.
  • Run tests.
  • Interpret failures.
  • Modify the implementation.
  • Run the tests again.
Important shift Coding evaluation is moving from "Can the model write code?" toward "Can the model successfully complete real software-engineering tasks?"

11. Capability #3 — Mathematics

Mathematics can be considered a structured form of reasoning because the model must follow a sequence of logical and symbolic operations to reach a solution.

Typical evaluation levels

Level What is tested?
Grade-school mathematics Arithmetic and basic word problems.
Competition mathematics Creative problem solving and non-trivial reasoning.
Undergraduate mathematics Higher-level mathematical concepts and symbolic reasoning.
Research-level reasoning Advanced or open-ended mathematical problems.

Why does mathematical capability matter?

Mathematical reasoning becomes particularly important in:

  • Scientific computing.
  • Financial modeling.
  • Engineering simulations.
  • Data analysis.
  • Scientific research.

12. Capability #4 — Long Context Management

A model's context window tells us how much information it can theoretically accept. But context-window size alone does not tell us how effectively the model can use that information.

Context window size ≠ Context utilization quality A model may technically accept a very large context while still struggling to retrieve or reason over information buried inside it.

What is evaluated?

  • Retrieving a small fact from a huge document.
  • Finding a specific person or entity in a large context.
  • Summarizing very long documents.
  • Maintaining consistency across long conversations.
  • Understanding large codebases.
  • Preserving relevant information across long inputs.
100K+ Token Input
→
Find Relevant Information
→
Reason Over It
→
Correct Answer

This capability matters particularly for:

  • Large document analysis.
  • Legal document processing.
  • Research assistants.
  • Long-running coding agents.
  • Large repository understanding.
  • Long conversations.

13. Capability #5 — Vision & Multimodality

LLMs increasingly operate in a multimodal environment rather than a text-only environment.

A multimodal model may need to understand:

  • Images.
  • Videos.
  • Charts.
  • Documents.
  • Screenshots.
  • Visual interfaces.

Example

Imagine giving an AI assistant an image of the contents of a refrigerator and asking:

"What meals could I prepare using these ingredients?"

The model must first understand the visual information and then reason about it.

Multimodal evaluation therefore asks:

  • Can the model correctly identify objects?
  • Can it understand visual relationships?
  • Can it read information from documents or charts?
  • Can it reason over visual information?
  • Can it understand video or temporal information?

Examples of tool-use capabilities

  • Structured tool calling.
  • API interaction.
  • Database interaction.
  • Computer interaction.
  • Command-line operations.
  • Multi-step tool orchestration.

Example

"What is the current USD to INR exchange rate

Agent:

1. Understand request
2. Select currency/exchange-rate tool
3. Call tool
4. Read result

The important evaluation question is not simply whether the model can generate a correct tool-call schema. It is whether the model can reliably use tools to accomplish a real task.

15. Capability #7 — Safety & Alignment

A highly capable model is not automatically a safe model.

Safety and alignment evaluations examine whether a model can be trusted to behave responsibly under normal and adversarial conditions.

Areas commonly evaluated

  • Harmful content generation.
  • Jailbreak resistance.
  • Adversarial robustness.
  • Truthfulness.
  • Deceptive or misleading behavior.
  • Cybersecurity-related capabilities.
  • Resistance to manipulation.
Capability creates responsibility As models become more capable, safety evaluation becomes increasingly important because a more capable system can potentially produce more consequential failures.

Truthfulness vs agreeableness

A useful model should not simply agree with everything a user says.

For example:

User: "I think this architecture is perfect. What do you think?"

A trustworthy model should identify genuine strengths and weaknesses rather than automatically responding with praise.

Security-related evaluation

Modern model evaluations can also test whether models possess capabilities related to:

  • Cybersecurity.
  • Cryptography.
  • Vulnerability discovery.
  • Reverse engineering.
  • Digital forensics.

The same capabilities that make a model useful can also create new risks, which is why safety evaluation must accompany capability evaluation.

16. Capability #8 — Instruction Following

Instruction following measures whether a model actually does what the user asked it to do.

Example

Suppose the user says: 

Answer in a bullet list.
Use fewer than 200 words.
Use a friendly tone.
Do not include a conclusion.

A strong instruction-following model should satisfy all applicable requirements.

What can be evaluated?

Instruction Evaluation
Format Did the model use the requested format?
Length Did it stay within the requested limit?
Tone Did it maintain the requested style?
Constraints Did it obey explicit restrictions?
Ambiguity Did it ask a clarifying question when necessary?

Why this matters in production

Instruction following directly influences user experience.

→

→

If the model repeatedly ignores user requirements, users may perceive the application as unreliable and eventually stop using it.

18. Practical AI-Engineering Takeaways

1. Don't select models based only on reputation

A model being famous, expensive, or ranked highly does not automatically make it the best choice for your application.

2. Use benchmarks for general capability comparison

Benchmarks provide a standardized language for comparing models.

3. Use custom evaluations for production decisions

When the decision affects your application, evaluate models using representative workloads.

4. Include operational metrics

Accuracy is only one dimension. Also consider:

Quality
Accuracy, correctness, task success
Cost
Token cost and infrastructure cost
Latency
Time required to produce the response
Safety
Risk, robustness, and responsible behavior

5. Build a golden dataset for important applications

A representative golden dataset allows you to compare candidate models against the same real-world requirements.

6. Re-run evaluations when models change

Model selection should not be a one-time activity. New model versions, prompt changes, infrastructure changes, and application changes can all alter performance.

7. Separate general intelligence from application fitness

This is perhaps the most important lesson.

General capability and application suitability are different questions.

A model can dominate public benchmarks while another model provides a better cost-quality-latency trade-off for your specific application.

Benchmark

Question: How capable is this model in a standardized setting?

Best for industry-wide comparison and general capability analysis.

Custom Evaluation

Question: How suitable is this model for our actual application?

Best for model selection, production decisions, cost optimization, and application-specific validation.

Big picture The previous part of the course focused primarily on evaluating the application built around an LLM. This part shifts the lens toward the underlying model itself. The next natural step is to study how standardized benchmarks work, how benchmark scores should be interpreted, and how engineers can build and run custom model evaluations.

Why the theory matters

The reason for spending time on this conceptual foundation is simple: practical evaluation becomes much easier once the evaluation dimensions are clear.

If you understand the distinction between:

  • Model vs application evaluation,
  • Benchmark vs custom evaluation,
  • Capability vs operational metric,
  • General model quality vs application fitness,
  • Quality vs cost vs latency vs safety,

then the practical process of creating datasets, running tests, calculating metrics, comparing models, and making deployment decisions becomes much more meaningful.

Core lesson to remember Model evaluation is not about finding the model with the biggest leaderboard score. It is about generating reliable evidence that helps you understand what a model can do and whether it is the right model for the job.
