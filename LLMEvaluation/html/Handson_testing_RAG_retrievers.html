Building a RAG Evaluation Suite: From Retriever Construction to Benchmarking

A practical learning guide based on the supplied lecture transcript. The lesson builds a retriever, defines robust golden data, evaluates contextual recall and contextual precision with an LLM-as-a-judge approach, and iteratively improves the retrieval stack.

2. RAG Evaluation Architecture

A RAG system has two particularly important components in this lesson:

  • Retriever: takes a query and fetches relevant context from the vector database.
  • Generator: receives the query plus retrieved context and produces the answer.
The lesson evaluates the retriever first, then moves toward generator and higher-level evaluation.

4. Build the Retriever

The retriever implementation in the lesson follows this sequence:

Load transcripts. Read the lecture transcript files from data/.
Clean the transcripts. Remove timestamp lines so timestamps do not pollute semantic retrieval.
Create Documents. Store the cleaned text as LangChain document objects and preserve the session number as metadata.
Chunk. Split documents with an initial chunk size of 750 and overlap of 100.
Embed. Use an OpenAI embedding model and persist vectors in ChromaDB.
Create retriever. Configure top-K retrieval, initially K = 5.

Conceptual implementation

from pathlib import Path
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma
from langchain_text_splitters import RecursiveCharacterTextSplitter

load_dotenv()

DATA_DIR = Path("data")
CHROMA_DIR = "chroma_store"

def load_transcripts():
    # Read transcript files, remove timestamp-only lines,
    # and attach session metadata.
    ...

def build_retriever():
    embeddings = OpenAIEmbeddings(model="text-embedding-3-small")

    if not Path(CHROMA_DIR).exists():
        documents = load_transcripts()

        splitter = RecursiveCharacterTextSplitter(
            chunk_size=750,
            chunk_overlap=100
        )
        chunks = splitter.split_documents(documents)

        Chroma.from_documents(
            documents=chunks,
            embedding=embeddings,
            persist_directory=CHROMA_DIR
        )

    store = Chroma(
        persist_directory=CHROMA_DIR,
        embedding_function=embeddings
    )

    return store.as_retriever(search_kwargs={"k": 5})

if __name__ == "__main__":
    retriever = build_retriever()
    results = retriever.invoke("What is regression testing?")

    for doc in results:
        print(doc.metadata)
        print(doc.page_content[:500])
        print("-" * 60)
The transcript deliberately keeps this implementation simple because the lesson's focus is evaluation rather than production-grade ingestion architecture.

Important data-ingestion observation

The lecture points out that, in this simplified implementation, adding a new transcript requires rebuilding the vector store. In a production design, data ingestion and retrieval should ideally be decoupled so that document updates do not require unnecessary reconstruction of the entire retrieval layer.

5. The Two Core Retriever Failure Modes

A retriever can fail in two fundamental ways.

Failure 1 — Miss

The retriever fails to bring back context that is actually needed to answer the query.

low recall

Failure 2 — Noise

The retriever brings some useful context but also returns irrelevant chunks. That noise is passed to the generator and can hurt answer quality.

low precision

6. Recall vs Precision

MetricQuestion it answersSimple interpretation
RecallOf all correct/relevant context available, how much did the retriever bring back?“Did I miss information I needed?”
PrecisionOf everything the retriever brought back, how much is actually useful?“How much noise did I retrieve?”
Recall = relevant retrieved context ÷ all relevant context
Precision = relevant retrieved context ÷ all retrieved context

Example from the lesson: if five correct contexts exist and the retriever finds three, recall is 3/5. If the retriever returns five contexts and only two are useful, precision is 2/5.

The K trade-off

Increasing K can help recall because more candidates are retrieved. But increasing K can simultaneously introduce more irrelevant chunks, reducing precision. Therefore K creates a practical recall–precision trade-off.

Engineering implication: “increase K” is not a universal fix. It can recover missed context while also increasing noise.

7. Why Chunk-ID Golden Datasets Fail

The first intuitive strategy is to create a golden dataset like:

[
  {"question": "What is regression testing?", "relevant_chunk_ids": [72, 89, 100]},
  {"question": "What is RAG triad?", "relevant_chunk_ids": [111, 120]}
]

Then run the retriever and compare the retrieved IDs against the golden IDs.

This can work in some tightly controlled situations, but the lesson identifies a major weakness for the current application: chunk IDs are coupled to the chunking configuration.

For the lecture dataset, the transcript information can be spread across different chunks. Changing chunk size or overlap changes chunk boundaries and therefore changes which IDs contain the information. Rebuilding the golden dataset after every chunking experiment would make iterative retrieval optimization unnecessarily expensive.

Core lesson: evaluate against the meaning/content you want retrieved, not a brittle identifier tied to a particular chunking implementation.

8. The Robust Golden Dataset: Question + Ideal Answer

The lesson replaces the chunk-ID dataset with a semantic reference:

[
  {
    "question": "What is regression testing?",
    "ideal_answer": "The explanation of regression testing taught in the course..."
  },
  {
    "question": "What is the RAG triad?",
    "ideal_answer": "The course explanation of the RAG triad..."
  }
]

The important detail is that the ideal answer is grounded in the application's own knowledge base. It is not simply an answer copied from a web search. The transcript explains that the answer is constructed from the relevant material taught in the course.

Why this survives chunking changes: chunk boundaries may change, but the semantic ideal answer does not. Therefore the same golden dataset can be reused while experimenting with chunk size, overlap, embeddings, retrieval K, and reranking.

9. Contextual Recall: LLM-as-a-Judge

The lesson calls the DeepEval-style metric contextual recall. The core idea is to turn the ideal answer into a set of claims and check whether the retrieved context contains evidence for those claims.

Example from the transcript:

  • The ideal answer contains three claims.
  • The five retrieved chunks collectively contain evidence for all three.
  • Therefore contextual recall for that testcase is 3/3 = 1.0.

For another question, if the ideal answer contains two claims and the retrieved context supports only one, contextual recall is 1/2 = 0.5.

Contextual Recall = supported claims from the ideal answer ÷ total claims in the ideal answer

10. Contextual Precision: Useful Context + Ranking

Contextual precision asks whether each retrieved chunk is useful for producing the expected answer. The LLM judge receives the question, ideal answer, and one retrieved chunk, and returns a usefulness judgment with a reason.

Question: What is regression testing?

Ideal answer:
The expected explanation of regression testing.

Retrieved chunk:
<chunk text>

Judge:
Is this chunk relevant?
Does it contain information that helps produce the expected answer?

Return:
YES / NO
Reason: ...

If three of five retrieved chunks are useful, ordinary precision is 3/5. But the lesson emphasizes that DeepEval's contextual precision also considers rank: useful chunks appearing earlier are better than useful chunks appearing near the bottom.

Rank-aware intuition

Case A

Useful, useful, noise, noise, noise

Better — useful evidence appears early.

Case B

Noise, noise, noise, useful, useful

Worse — useful evidence appears late.

Both cases contain two useful chunks out of five, so simple precision is identical. A rank-aware contextual precision metric differentiates them by rewarding useful context near the top of the retrieval ranking.

At each rank k: precision@k = useful chunks in top-k ÷ k
Contextual precision = average of these rank-aware precision values
This makes contextual precision particularly relevant to RAG because the generator sees a ranked list of retrieved context, and higher-ranked context generally receives greater practical importance.

The transcript discusses several ways to create goldens:

Production feedbackUse successful production interactions, such as positive user signals, as candidates for golden examples.Useful after deployment, but not enough to bootstrap the initial set.

The lesson's practical dataset contains 15 questions, with questions designed to resemble realistic student questions and answers grounded in the supplied transcripts.

Quality matters more than quantity alone. A golden dataset is an evaluation instrument. Poorly designed questions or weak reference answers can produce misleading evaluation scores.

12. DeepEval Fundamentals

The lecture introduces a simple mental model for DeepEval: three core building blocks.

1. LLMTestCase

Represents one row/example from the golden dataset, containing fields such as the input question and expected/actual context or output depending on the metric.

2. Metric

Defines what quality dimension is being evaluated, such as contextual recall or contextual precision.

3. evaluate()

Runs the selected metrics against the test cases and produces scores and pass/fail results.

Metrics can be configured with a judge model and a threshold. The lecture also enables reasons so that failed or borderline cases can be inspected rather than treated as unexplained numbers.

13. Evaluation Script

The lesson's evaluation script imports the retriever, loads the golden dataset, configures an LLM judge, selects contextual recall and contextual precision, and evaluates the test cases.

import json

from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import (
    ContextualRecallMetric,
    ContextualPrecisionMetric,
)

from src.retriever import build_retriever

GOLDEN_PATH = "goldens/retriever_goldens.json"

def load_goldens():
    with open(GOLDEN_PATH, "r", encoding="utf-8") as f:
        return json.load(f)

def build_test_cases(retriever):
    test_cases = []

    for row in load_goldens():
        question = row["question"]
        ideal_answer = row["ideal_answer"]

        docs = retriever.invoke(question)
        retrieved_context = [doc.page_content for doc in docs]

        test_cases.append(
            LLMTestCase(
                input=question,
                actual_output="",
                expected_output=ideal_answer,
                retrieval_context=retrieved_context,
            )
        )

    return test_cases

retriever = build_retriever()
test_cases = build_test_cases(retriever)

recall = ContextualRecallMetric(
    threshold=0.7,
    include_reason=True,
)

precision = ContextualPrecisionMetric(
    threshold=0.7,
    include_reason=True,
)

evaluate(
    test_cases=test_cases,
    metrics=[recall, precision],
)
The exact package APIs can vary by installed DeepEval version. Treat the code above as a learning-oriented implementation of the structure taught in the transcript rather than a claim about a version-specific API.

14. Benchmark, Diagnose, Improve, Repeat

The lesson does not stop after computing a score. It uses evaluation as an engineering feedback loop.

Experiment 1 — Baseline

The first baseline run uses the initial configuration of approximately 750 chunk size, 100 overlap, K=5. The transcript reports a baseline of roughly 80 contextual recall and 80 contextual precision, with 10 of 15 test cases passing and five failing.

Experiment 2 — Larger chunks

The chunk configuration is increased to 1000 chunk size and 150 overlap. The transcript reports a major improvement: contextual recall rises to roughly 97 and contextual precision to roughly 83, with three failed cases.

Scores are reproduced as reported in the supplied transcript; they are lesson-run results, not universal benchmarks.

Experiment 3 — Add a reranker

A sentence-transformer reranker is added after initial retrieval. Its job is to reorder retrieved chunks so more meaningful context moves toward the top. The transcript reports precision improving from about 83 to 85 and failed cases dropping from three to two, while recall decreases somewhat.

Experiment 4 — Upgrade the embedding model

The embedding model is upgraded from text-embedding-3-small to text-embedding-3-large. The transcript reports recall rising to approximately 99 while precision remains around 85. The speaker notes the cost trade-off of using a larger embedding model.

Experiment 5 — Lower K

Reducing K from 5 to 3 is tried as another way to reduce noise. The transcript reports little useful improvement and notes that some variation is expected because only 15 golden test cases are being used.

Final lesson conclusion: the retriever reaches roughly 95%+ recall and ~85% precision in the reported experiments, giving enough confidence to move forward to generator construction and evaluation.

15. Key Lessons to Remember

1. Evaluate incrementally

Do not wait until the whole RAG application is complete. Build a component, evaluate it, improve it, then continue.

2. Retriever quality has two sides

Recall protects against missing useful information. Precision protects against flooding the generator with irrelevant information.

3. Golden data should be stable under implementation changes

Chunk IDs are implementation-dependent. A question + ideal answer is more robust because the semantic target survives changes in chunk boundaries.

4. Contextual recall is claim-oriented

Break the ideal answer into claims and check whether retrieved context collectively supports those claims.

5. Contextual precision is rank-aware

It is not enough to retrieve useful context. Useful chunks should appear early enough to be valuable to downstream generation.

6. Scores are only the starting point

Inspect failed test cases and judge reasons. The purpose of an eval suite is to tell you what to change in the system.

7. Retrieval optimization is empirical

Chunk size, overlap, embedding model, K, and reranking can all affect retrieval quality. Benchmark changes rather than assuming one configuration is universally best.
