## Introduction and Playlist Recap

After covering the **Why**, **What**, and **How** of MCP—including building **local MCP servers** and **remote MCP servers**—the final core component of the MCP ecosystem is learning how to build **custom MCP clients**.

### Goal

Instead of depending on Claude Desktop, you can build your own chatbot interface that connects to multiple MCP servers simultaneously.

For example, your custom client could connect to:

- a **local Math server**
- a **remote Expense Tracker server**
- a **third-party Manim animation server**

This gives you complete control over the user experience, orchestration logic, and server integrations.

---

## Choosing the Right Library: langchain-mcp-adapters

Although you can build an MCP client directly with the official MCP SDK, this tutorial uses **`langchain-mcp-adapters`**.

### Why use it?

Because it provides a lightweight wrapper that makes MCP tools compatible with the **LangChain** and **LangGraph** ecosystems.

### Key advantage

It is one of the easiest ways to bind MCP tools directly to an LLM, allowing the model to:

- discover tools from MCP servers
- choose when to call them
- integrate tool results into final responses

This makes it an excellent choice for building custom AI applications on top of MCP.

## Building the MCP Client (Step-by-Step)

In this section, we create an asynchronous Python client that:

1. connects to multiple MCP servers
2. fetches available tools
3. binds those tools to an LLM
4. executes tool calls when requested by the model

---

## Step 4.1: Server Configuration

The first step is to define how the client connects to each MCP server.

### Local server connection

For a local MCP server using **STDIO**, provide the command used to launch the server.

### Remote server connection

For a remote MCP server using **HTTP/SSE**, provide the deployed server URL.

```python
import asyncio
from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, ToolMessage
from dotenv import load_dotenv

load_dotenv()

# Define connections to multiple servers (Local and Remote)
servers_config = {
    "math_server": {
        "command": "uv",
        "args": ["run", "fastmcp", "run", "/path/to/math/server/main.py"],
        "transport": "stdio"
    },
    "expense_server": {
        "url": "https://your-deployed-expense-tracker.fastmcp.cloud",
        "transport": "sse"
    }
}
```

This configuration allows one client to orchestrate tools across multiple servers.

---

## Step 4.2: Connecting and Fetching Tools

Once the server configuration is defined, initialize the `MultiServerMCPClient` and fetch all tools exposed by the connected servers.

```python
async def main():
    # 1. Initialize the client
    async with MultiServerMCPClient(servers_config) as client:
        # 2. Fetch all tools from all connected servers
        tools = await client.get_tools()

        # 3. Create a dictionary mapping tool names to tool objects
        name_to_tool = {tool.name: tool for tool in tools}

        # 4. Initialize LLM and bind tools
        llm = ChatOpenAI(model="gpt-4o")
        llm_with_tools = llm.bind_tools(tools)

        # Start the chat logic...
```

### Why the tool dictionary matters

The `name_to_tool` mapping makes it easy to:

- look up a tool by name
- execute the correct tool when the LLM requests it
- support multiple tool calls in the same interaction

---

## Step 4.3: The LLM Tool-Calling Loop

When a user sends a prompt to the LLM, the model can respond in two ways:

1. answer directly
2. request one or more tool calls

If tool calls are requested, the client must:

1. execute the selected tools
2. capture the results
3. send the tool outputs back to the LLM
4. ask the LLM for the final user-facing answer

```python
        user_prompt = "What is the remainder of 2314 divided by 7?"
        messages = [HumanMessage(content=user_prompt)]

        # Get initial response from LLM
        response = await llm_with_tools.ainvoke(messages)
        messages.append(response)

        # Check if the LLM decided to call any tools
        if not response.tool_calls:
            print("LLM Answer:", response.content)
            return

        # Handle one or multiple tool calls
        for tool_call in response.tool_calls:
            selected_tool_name = tool_call["name"]
            selected_tool_args = tool_call["args"]
            tool_call_id = tool_call["id"]

            # Retrieve the tool from our dictionary
            selected_tool = name_to_tool[selected_tool_name]

            # Execute the tool asynchronously
            tool_result = await selected_tool.ainvoke(selected_tool_args)

            # Create a ToolMessage with the result
            tool_message = ToolMessage(
                content=str(tool_result),
                tool_call_id=tool_call_id,
                name=selected_tool_name
            )
            messages.append(tool_message)

        # Send the full history back to the LLM
        final_response = await llm_with_tools.ainvoke(messages)
        print("Final Answer:", final_response.content)

if __name__ == "__main__":
    asyncio.run(main())
```

### Flow summary

The loop works like this:

- user sends a question
- LLM inspects available tools
- LLM requests a tool call if needed
- client executes the tool
- client returns the result to the LLM
- LLM produces a final answer

This is the core execution model for building MCP-powered chatbot clients.

## Adding Third-Party Servers

One of the biggest advantages of a custom MCP client is extensibility.

You are not limited to your own servers. You can also connect third-party MCP servers built by other developers.

### Example: Manim MCP Server

By simply adding a **Manim MCP server** configuration to `servers_config`, your chatbot gains the ability to:

- generate Python animation code
- render visual animations
- return generated media such as `.mp4` files

This makes the client far more powerful than a single-purpose app, because it can coordinate across many specialized MCP tools.

## Wrapping It in a Streamlit GUI

Running the client from the terminal works, but in most real applications you will want a graphical user interface.

A common approach is to wrap the asynchronous LangChain logic inside a **Streamlit** application.

### Why Streamlit?

Streamlit makes it easy to build a lightweight chat interface where users can:

- enter prompts
- view responses
- display tool-generated outputs
- interact with multiple MCP-backed capabilities from a single UI

### Result

By moving the logic into a script such as `client2.py` and running:

```bash
streamlit run client2.py
```

you get a user-friendly chatbot interface that silently routes requests to the appropriate MCP server based on the user’s natural language input.

For example:

- math questions route to the **local Math server**
- expense queries route to the **remote Expense Tracker server**
- animation requests route to the **Manim server**
