## Introduction

In the previous stages of learning LangChain, we explored its fundamental building blocks, such as models, prompts, chains, Runnables, and document loaders.

Now, we are moving towards building practical Retrieval-Augmented Generation (RAG) applications. To build a RAG system effectively, we need to understand how to prepare and organize documents before passing them to embedding models and language models.

One of the most important components in this process is the **Text Splitter**.

Imagine that you have a PDF containing thousands of pages. You want to use its contents for semantic search, question answering, or summarization. Processing the entire document as one large piece of text can create problems with context limits, retrieval precision, and computational efficiency.

A common solution is to divide the document into smaller, manageable pieces called **chunks**.

This process is known as **text splitting**, and the LangChain components that perform this operation are called **text splitters**.

## 1. What Is Text Splitting?

Text splitting is the process of breaking a large piece of text, such as an article, PDF, HTML page, or book, into smaller, manageable pieces that can be processed more effectively by language models and other components.

Each smaller piece is called a **chunk**.

For example, suppose you have a document containing 1,000 paragraphs. Instead of processing the entire document at once, you might divide it into chunks containing a few paragraphs each.

### Conceptual workflow

<img width="718" height="521" alt="image" src="https://github.com/user-attachments/assets/de814859-84b0-4195-811e-d609dddab0d9" />


The resulting chunks can then be used for embedding generation, vector storage, retrieval, summarization, and other downstream tasks.

### Important terminology

| Term | Meaning |
|---|---|
| **Text splitting** | The overall process of dividing text into smaller pieces. |
| **Text splitter** | The component or algorithm that performs the splitting. |
| **Chunk** | One individual piece of the resulting text. |
| **Chunk size** | The target or maximum size used to determine chunk boundaries. |
| **Chunk overlap** | The amount of text shared between adjacent chunks. |

## 2. Why Is Text Splitting Important?

Text splitting is an important preprocessing step in many LLM-powered applications. There are several reasons for using it.

### 2.1 Overcoming model input limitations

Language models have a maximum context window. This determines how much input the model can process in a single request, taking into account the applicable token limits.

Suppose a hypothetical model has a context window of 50,000 tokens, while your document contains 100,000 tokens.

Sending the entire document in one request would exceed the assumed limit. Instead, you can divide the document into smaller chunks and process those chunks separately.

<img width="727" height="391" alt="image" src="https://github.com/user-attachments/assets/8fbe3d82-e82c-458c-88cd-9399e20ad945" />


These are illustrative chunk sizes without overlap. Each chunk is below the assumed 50,000-token limit.

This allows large documents to be processed in multiple requests rather than requiring them to fit into one input.

### 2.2 Improving embedding quality

An embedding model converts text into a numerical vector that represents aspects of its semantic content.

Consider a document containing three paragraphs:

- Paragraph 1: Information about Chennai Super Kings (CSK).
- Paragraph 2: Information about Mumbai Indians (MI).
- Paragraph 3: Information about Royal Challengers Bengaluru (RCB).

If all three paragraphs are combined into one large embedding input, the resulting vector may represent several different topics together.

If the paragraphs are embedded separately, each vector can focus more specifically on its corresponding topic.

<img width="928" height="783" alt="image" src="https://github.com/user-attachments/assets/7cfdd650-5481-4290-bf18-8155ad530801" />

This can make the vectors more useful for topic-specific retrieval. However, chunking alone does not guarantee better embeddings; the result depends on the embedding model, the content, and the chunking strategy.

### 2.3 Improving semantic search

In a typical vector-search workflow:

1. Documents are split into chunks.
2. Each chunk is converted into an embedding.
3. The embeddings and associated chunk data are stored in a vector database.
4. A user's query is embedded.
5. The query embedding is compared with stored embeddings.
6. Relevant chunks are retrieved and supplied to the LLM.

For example, suppose the user asks:

> Which IPL team does Virat Kohli play for?

If the document has been divided into topic-specific chunks, the retrieval system can search for the chunk containing information about Virat Kohli rather than relying on one embedding for an entire large document.

This can improve retrieval precision, although actual performance depends on the chunk boundaries, embedding model, indexing strategy, and retrieval method.

### 2.4 Improving summarization and other downstream tasks

Large inputs can make it more difficult for a model to consistently preserve all relevant details. Depending on the model and task, this can contribute to omissions, loss of focus, or unsupported statements.

Chunking allows an application to process portions of the document individually and then combine the results.

For example, a long-document summarization pipeline could:

- Summarize each chunk separately.
- Combine the chunk summaries.
- Generate a final summary from those intermediate summaries.

This is one example of a **hierarchical summarization** approach.

### 2.5 Optimizing computational resources

Processing smaller chunks can also offer practical engineering advantages:

- Smaller individual requests may require less peak memory.
- Independent chunks can sometimes be processed in parallel.
- Failed chunks can potentially be retried without reprocessing the entire document.
- Applications can control request sizes and batch processing.

However, chunking also introduces overhead, such as additional requests, metadata, and embedding operations. More chunks do not automatically mean lower total computational cost.

## 4. Length-Based Text Splitting

Length-based splitting is one of the simplest approaches to text chunking.

The basic idea is to decide in advance how large each chunk should be and split the text according to that size.

The size can be measured in different units, including:

- Characters.
- Tokens.
- Other units supported by the splitter implementation.

For example, if the chunk size is 100 characters, a basic character-based splitter can divide a long string into segments of approximately 100 characters each.

### 4.1 How it works

Imagine the following text:

```text
LangChain helps developers build applications
using language models and external data sources.
```

If we split this text at a fixed character count, a chunk boundary could occur in the middle of a word or sentence.
<img width="717" height="234" alt="image" src="https://github.com/user-attachments/assets/76b3c883-88fa-46cc-ac15-5f3c7a71c284" />


The exact boundaries depend on the splitter's configuration and whether it includes separators in the resulting chunks.

### 4.2 LangChain's `CharacterTextSplitter`

LangChain provides `CharacterTextSplitter` for character-based splitting.

```python
from langchain_text_splitters import CharacterTextSplitter

text = """
LangChain helps developers build applications
using language models and external data sources.
"""

splitter = CharacterTextSplitter(
    separator=" ",
    chunk_size=100,
    chunk_overlap=0,
    strip_whitespace=True,
)

chunks = splitter.split_text(text)

print(chunks)
```

#### Parameters

| Parameter | Purpose |
|---|---|
| `separator` | Specifies the text separator used by the splitter. |
| `chunk_size` | Specifies the target chunk size. |
| `chunk_overlap` | Specifies how much text adjacent chunks should share. |
| `strip_whitespace` | Controls the removal of leading and trailing whitespace from chunks. |

> **Important distinction:** `CharacterTextSplitter` splits using a specified separator. It does not necessarily cut a string at an exact character count. For strict character-count splitting, consider a splitter configured with character-level separators, such as `RecursiveCharacterTextSplitter` with a character fallback. For token-oriented sizing, use an appropriate token-aware length function or encoder integration.

### 4.3 Advantages

- Easy to understand and configure.
- Fast and relatively straightforward to implement.
- Gives the developer direct control over chunk sizing.
- Useful when input data is already divided into suitable units.

### 4.4 Disadvantages

- It may split sentences or paragraphs at inconvenient locations.
- A chunk can lose important context that appears in a neighboring chunk.
- A chunk containing unrelated parts of different topics may produce less focused embeddings.
- The separator-based implementation may produce chunks smaller or larger than expected, depending on how it handles individual segments.

### 4.5 When should you use it?

Consider length-based splitting when simplicity and predictable processing are important, or when the source has already been divided into meaningful units.

For general-purpose RAG over natural-language documents, a structure-aware splitter is often a useful starting point.

## 5. Chunk Size and Chunk Overlap

Two important parameters in text splitting are `chunk_size` and `chunk_overlap`.

### 5.1 What is chunk size?

Chunk size specifies how much text a chunk should contain.

For example:

```python
chunk_size=500
```

This configures a target size of 500 units according to the splitter's length-measurement configuration. In common character-based configurations, that means 500 characters.

Increasing chunk size generally produces fewer, larger chunks. Decreasing it generally produces more, smaller chunks.

<img width="720" height="164" alt="image" src="https://github.com/user-attachments/assets/daa56c7b-dea8-42c7-82d6-bda8a4b030b6" />


- **Smaller chunks:** more granular retrieval, but potentially less context per chunk.
- **Larger chunks:** more context per chunk, but potentially less granular retrieval.

### 5.2 What is chunk overlap?

Chunk overlap specifies how much text is shared between consecutive chunks.

Suppose we have a string divided into chunks with a size of 100 characters and an overlap of 20 characters. 

The second chunk begins 20 characters before the end of the first chunk.

<img width="713" height="265" alt="image" src="https://github.com/user-attachments/assets/6005f9b1-fb1f-43ea-9ea4-a6905a33445a" />

Overlap helps preserve context around chunk boundaries. If a sentence or explanation is divided between chunks, some of its preceding text may remain available in the next chunk.

### 5.3 Why use chunk overlap?

Consider this example.

**Chunk 1**

> The company introduced a new embedding model designed to improve semantic search performance. The model was trained on...

**Chunk 2 without overlap**

> ...a large collection of domain-specific documents and evaluated on several retrieval benchmarks.

The second chunk begins in the middle of a sentence. Without the preceding context, it may be harder to interpret independently.

With overlap, part of the preceding text is included in the second chunk, which can make the relevant context easier to retain.

### 5.4 Trade-offs of chunk overlap

| More overlap | Less overlap |
|---|---|
| Preserves more boundary context. | Reduces repeated text. |
| Can help retrieval when answers span boundaries. | Usually produces fewer redundant tokens. |
| Increases the number of tokens stored and processed. | Can leave important context separated across chunks. |

There is no universally optimal overlap value. The appropriate value depends on the document type, chunk size, retrieval requirements, and computational budget.

For example, 10–20% overlap can be a reasonable initial experiment for some RAG workloads, but it should be evaluated rather than treated as a universal rule.

## 6. Text-Structure-Based Splitting

Length-based splitting focuses on size. However, natural-language text has an inherent structure.

A document is often organized into:

- Paragraphs.
- Sentences.
- Words.
- Characters.

A structure-aware splitter attempts to preserve these natural boundaries whenever possible.

The main technique covered here is `RecursiveCharacterTextSplitter`.

### 6.1 What is `RecursiveCharacterTextSplitter`?

`RecursiveCharacterTextSplitter` is a LangChain text splitter that tries a sequence of separators in priority order.

It attempts to split the text using larger structural boundaries first. If the resulting pieces are still too large, it moves to smaller boundaries.

A typical default separator hierarchy is:

```python
["\\n\\n", "\\n", " ", ""]
```

These separators roughly correspond to:

| Separator | Intended boundary |
|---|---|
| `"\n\n"` | Paragraph breaks |
| `"\n"` | Line breaks |
| `" "` | Word boundaries |
| `""` | Character-level fallback |

The exact behavior depends on the input, configuration, and size-measurement function.

<img width="1266" height="1304" alt="image" src="https://github.com/user-attachments/assets/ccd07acf-7708-490f-a619-be16fe12ecb6" />

### 6.2 How the recursive strategy works

Suppose we have this text:

```text
My name is Nitish. I am 35 years old.

I live in Gurgaon. How are you?
```

Assume that we configure a relatively small chunk size.

The splitter first attempts to divide the text at paragraph boundaries. If a paragraph is too large, it tries line breaks. If the resulting segments are still too large, it tries spaces and finally character-level splitting.

After splitting, the implementation can combine smaller pieces into larger chunks when doing so respects the configured size.

This means that the splitter attempts to produce useful chunks without unnecessarily fragmenting the text.

### 6.3 LangChain code example

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text = """
My name is Nitish. I am 35 years old.

I live in Gurgaon. How are you?
"""

splitter = RecursiveCharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=10,
    length_function=len,
    separators=["\n\n", "\n", " ", ""],
)

chunks = splitter.split_text(text)

print(f"Total chunks: {len(chunks)}")

for i, chunk in enumerate(chunks):
    print(f"Chunk {i + 1}: {chunk}")
```

### 6.4 Understanding the parameters

| Parameter | Explanation |
|---|---|
| `chunk_size` | Target maximum size for each chunk according to the configured length function. |
| `chunk_overlap` | Target amount of shared text between consecutive chunks. |
| `length_function` | Function used to measure the size of text segments. |
| `separators` | Ordered list of boundaries the splitter attempts. |

### 6.5 Why is it widely useful?

The recursive approach offers a practical balance between chunk size and text structure.

For example:

- If paragraphs fit within the size limit, they may remain intact.
- If a paragraph is too large, the splitter can divide it into smaller units.
- If a sentence is too large, it can fall back to word or character boundaries.

This makes it useful for many natural-language RAG applications.

However, it is **not a semantic understanding algorithm**. It uses separator hierarchy and size constraints rather than reasoning about the meaning of every sentence.

## 7. Document-Structure-Based Splitting

Not all documents are ordinary prose.

Consider these examples:

- Python or JavaScript source code.
- Markdown documentation.
- HTML pages.
- Other structured formats.

Such documents have their own organization. A Python program contains classes, functions, loops, and conditional statements. A Markdown document contains headings, lists, and code blocks.

Applying generic paragraph-based splitting to these documents may break useful structures.

### 7.1 Splitting code using language-specific separators

LangChain provides `RecursiveCharacterTextSplitter.from_language()` to configure recursive splitting with separators appropriate for a supported programming language.

For Python, the splitter can prioritize boundaries associated with constructs such as classes and functions before falling back to more general text separators.

```python
from langchain_text_splitters import (
    RecursiveCharacterTextSplitter,
    Language,
)

code = """
class DocumentProcessor:
    def load(self, path):
        print(f"Loading {path}")

    def split(self, text):
        return text.split()

def main():
    processor = DocumentProcessor()
    processor.load("notes.txt")
    print(processor.split("LangChain text splitters"))

if __name__ == "__main__":
    main()
"""

splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=120,
    chunk_overlap=20,
)

chunks = splitter.split_text(code)

for index, chunk in enumerate(chunks, start=1):
    print(f"--- Chunk {index} ---")
    print(chunk)
```

The language-specific configuration gives the splitter a separator hierarchy designed for Python source code. It can try boundaries around class and function definitions before falling back to more general separators.

This is a structural heuristic, not a full Python parser. A chunk may still contain an incomplete construct, especially when a function or class is larger than the configured size.

### 7.2 Supported languages

LangChain includes language presets for a range of programming languages and document formats. The available `Language` enum members can vary by installed package version, so consult the API reference for the version in your environment.

Example pattern:

```python
from langchain_text_splitters import (
    Language,
    RecursiveCharacterTextSplitter,
)

splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.JS,
    chunk_size=200,
    chunk_overlap=30,
)
```

Replace `Language.JS` with the appropriate language member for the code you are splitting.

### 7.3 Splitting Markdown documents


Markdown has its own structural elements, including headings, paragraphs, lists, and fenced code blocks. A Markdown-aware strategy can prioritize boundaries associated with these elements.

```
# Introduction

This is an introductory paragraph.

## Installation

Install the required packages.

## Usage

Here is how to use the application.
```

One option is to use `RecursiveCharacterTextSplitter` with the Markdown language preset:

```python
from langchain_text_splitters import (
    Language,
    RecursiveCharacterTextSplitter,
)

markdown_text = """
# Introduction

LangChain is a framework for building applications with language models.

## Text Splitters

Text splitters divide long documents into smaller chunks.

### Recursive Splitting

This method tries larger structural boundaries before smaller ones.
"""

splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.MARKDOWN,
    chunk_size=250,
    chunk_overlap=30,
)

chunks = splitter.split_text(markdown_text)
```

For workflows where headings should become metadata, consider `MarkdownHeaderTextSplitter` instead:

```python
from langchain_text_splitters import MarkdownHeaderTextSplitter

headers_to_split_on = [
    ("#", "Header 1"),
    ("##", "Header 2"),
    ("###", "Header 3"),
]

markdown_splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers_to_split_on
)

documents = markdown_splitter.split_text(markdown_text)

for document in documents:
    print(document.page_content)
    print(document.metadata)
```

`MarkdownHeaderTextSplitter` divides content according to heading levels and can place the heading hierarchy in each resulting document's metadata. It is not the same as a size-limited recursive splitter; a second splitting step may be useful if any section is still too large.

### 7.4 Splitting HTML documents

HTML is structured using elements such as headings, paragraphs, lists, and other tags.

LangChain provides language-specific separator configurations for HTML as well.

``` python
from langchain_text_splitters import (
    RecursiveCharacterTextSplitter,
    Language,
)

html_text = """
<html>
  <body>
    <h1>Introduction</h1>
    <p>This is an introductory paragraph.</p>
    <h2>Features</h2>
    <p>This section describes the features.</p>
  </body>
</html>
"""

html_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.HTML,
    chunk_size=200,
    chunk_overlap=20,
)

chunks = html_splitter.split_text(html_text)

for chunk in chunks:
    print(chunk)
```


### 7.4 Why document-aware splitting matters

Document-structure-based splitting extends the recursive splitting approach.

Instead of relying only on generic paragraph, line, and word separators, it uses separators associated with the document's format.

This is especially useful when processing code repositories, technical documentation, and structured text

## 8. Semantic Meaning-Based Splitting

The previous techniques primarily use text length or structural boundaries to determine where chunks should begin and end.

But consider this example:

```
Farmers use modern irrigation systems to improve crop yields.

The Indian Premier League features several professional
cricket teams.

Terrorism can involve politically motivated violence
against civilians.
```

These are three different topics:

1. Agriculture.
2. Cricket.
3. Terrorism.

A paragraph-based splitter might preserve the first paragraph as one chunk, the second as another, and the third as a third chunk. But what if a single paragraph contains multiple unrelated topics?

In that situation, paragraph boundaries alone may not be sufficient.
**Semantic splitting** instead attempts to identify changes in meaning. The underlying intuition is that sentences discussing the same topic should often remain together, while a significant topic change may indicate a useful place to start a new chunk.

### 8.1 Basic idea

<img width="1100" height="647" alt="image" src="https://github.com/user-attachments/assets/1d4380a1-51ec-4163-be75-82e247d230bf" />


A semantic chunking pipeline commonly works as follows:

1. Divide the document into smaller units, often sentences.
2. Generate an embedding for each unit.
3. Compare embeddings for neighboring units.
4. Identify substantial changes in semantic similarity.
5. Create chunk boundaries around those changes, subject to the implementation's settings.

```text
Document
   ↓
Sentence-sized units
   ↓
Embedding model
   ↓
Compare neighboring meanings
   ↓
Detect topic shifts
   ↓
Semantic chunks
```

Unlike a fixed character count, semantic chunking uses an embedding-based signal to help decide where the content changes topic.


### 8.2 Understanding the similarity approach

Suppose a document contains four sentences:

- S1: A sentence about farming.
- S2: Another sentence about farming.
- S3: A sentence about cricket.
- S4: Another sentence about cricket.

An embedding model generates vectors for the sentences:

```math
E_1,\ E_2,\ E_3,\ E_4
```

We can compare consecutive vectors using a similarity measure such as cosine similarity.

```sim(Ei​,Ei+1​)```

If S1 and S2 are about the same topic, their embeddings may be relatively similar. If S2 is about farming and S3 is about cricket, the similarity may be lower.

A sufficiently large change can indicate a possible topic boundary.

Important: Embedding similarity is an imperfect proxy for meaning. Similarity scores depend on the embedding model and the content, so they do not guarantee that a topic change has been detected correctly.


### 8.3 Illustrative example

Consider these sentences:

- “A vector database stores embeddings and supports similarity search.”
- “A retriever uses a search strategy to find relevant documents.”
- “The Himalayas contain some of the world's highest mountain peaks.”

The first two sentences are related to information retrieval. The third introduces a different topic. A semantic strategy may place a boundary before the third sentence.

This is an illustration of the intuition, not a guaranteed output. The actual grouping depends on the embedding model, distance metric, threshold or breakpoint strategy, and input text.

### 8.4 Conceptual Python example to compare sentence embeddings

The following illustrates the core idea of comparing adjacent sentence embeddings. It is a conceptual example rather than a complete implementation of a semantic chunker.

```
from sklearn.metrics.pairwise import cosine_similarity

# Assume these embeddings were generated by an embedding model.
sentence_embeddings = [
    embedding_1,
    embedding_2,
    embedding_3,
    embedding_4,
]

for i in range(len(sentence_embeddings) - 1):
    similarity = cosine_similarity(
        [sentence_embeddings[i]],
        [sentence_embeddings[i + 1]],
    )[0][0]

    print(f"S{i + 1} vs S{i + 2}: {similarity:.3f}")
```

In a complete chunking algorithm, the similarity or distance measurements would be combined with a thresholding strategy to select boundaries.


### 8.5 Semantic chunking in LangChain


LangChain has provided semantic chunking functionality through experimental components, including SemanticChunker in langchain_experimental

A typical pattern is:

```python
from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings()

splitter = SemanticChunker(embeddings)

documents = splitter.create_documents([
    """
    LangChain helps developers build applications powered by language models.
    Text splitters divide long documents into smaller chunks.

    The Pacific Ocean is the largest ocean on Earth.
    It covers a vast area between Asia, Australia, and the Americas.
    """
])

for document in documents:
    print(document.page_content)
```

This example requires the relevant LangChain packages and valid embedding-provider configuration. The experimental package and constructor options can change, so verify them against the installed version.

### 8.6 Understanding breakpoint thresholds

A semantic chunker needs a rule for deciding when a change is significant enough to create a boundary.

Possible threshold strategies include:

- Standard deviation.
- Percentile-based thresholds.
- Interquartile-range-based thresholds.
- Gradient-based approaches.

For a standard-deviation-based method, the algorithm uses the distribution of semantic distances or related measurements to help identify unusually large changes.

The precise threshold interpretation depends on the implementation. A larger or smaller configured threshold can change the number of chunks produced, so it is important to evaluate the resulting chunks rather than assuming that a particular value is universally correct.

### 8.7 Advantages and limitations

| Advantages | Limitations |
|---|---|
| Can identify topic changes within paragraphs. | Requires embedding computation. |
| May produce more topic-coherent chunks. | More computationally expensive than simple splitting. |
| Can be useful when structural boundaries do not align with meaning. | Threshold selection and embedding quality affect results. |
| Can adapt chunk boundaries to the content. | Semantic boundaries are not guaranteed to be correct. |

**Note:** Semantic chunking can be useful when topic coherence is especially important, but it should be tested against simpler strategies on the target dataset.

## 9. Comparison of Text Splitting Techniques

| Feature | Length-based | Text-structure-based | Document-structure-based | Semantic-based |
|---|---|---|---|---|
| **Main principle** | Fixed size | Natural text boundaries | Format-specific boundaries | Meaning and topic changes |
| **Typical boundaries** | Characters or tokens | Paragraphs, sentences, words | Classes, functions, headings, tags | Semantic discontinuities |
| **Computational cost** | Generally low | Generally low | Generally low to moderate | Higher due to embeddings |
| **Preserves structure** | Limited | Often preserves natural-language structure | Attempts to preserve format-specific structure | Depends on semantic boundaries |
| **Main limitation** | Can split text awkwardly | May not detect topic changes within a paragraph | Does not guarantee complete code or document structures | Depends on embeddings and thresholds |
| **Example use** | Simple text processing | General-purpose RAG | Code and Markdown retrieval | Topic-sensitive chunking |

### Which splitter should you start with?

For many general-purpose RAG applications, `RecursiveCharacterTextSplitter` is a practical starting point because it balances size constraints with natural text boundaries.

For code, Markdown, and other structured documents, consider the relevant language-specific separators.

Semantic chunking is worth evaluating when topic boundaries matter more than simple structural boundaries and the additional embedding cost is justified.

These are implementation guidelines, not universal performance guarantees. The appropriate strategy should be evaluated using the documents, queries, and retrieval metrics relevant to your application.

### 10.1 Connecting a PDF loader and text splitter

Here is a practical example using LangChain's `PyPDFLoader` and `RecursiveCharacterTextSplitter`.

```
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

# Step 1: Load the PDF
loader = PyPDFLoader("document.pdf")
documents = loader.load()

# Step 2: Create the text splitter
splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=200,
)

# Step 3: Split the loaded documents
chunks = splitter.split_documents(documents)

# Step 4: Inspect the results
print("Total chunks:", len(chunks))

print("\nFirst chunk:")
print(chunks[0].page_content)

print("\nFirst chunk metadata:")
print(chunks[0].metadata)
```

### 10.3 Practical checks before indexing

Before generating embeddings and storing chunks, verify that:

- Chunks are within the intended size budget, using the same unit the application expects.
- Important headings, source identifiers, and page information are retained in metadata.
- Chunks do not contain excessive repeated text from overlap.
- Code examples, tables, and other special structures have not been damaged in ways that matter to the use case.
- The chunks can be understood when retrieved individually, or include sufficient context to support interpretation.

Chunking is an engineering choice that should be tested with the actual documents and questions the application will handle.

## 11. Important Takeaways

1. **Text splitting** divides large documents into smaller chunks that can be embedded, retrieved, and processed.
2. **Chunk size** controls the target size of a chunk; the unit depends on the configured length function.
3. **Chunk overlap** repeats some content across adjacent chunks to help preserve boundary context, at the cost of additional storage and processing.
4. **`CharacterTextSplitter`** uses a specified separator and should not be mistaken for an unconditional exact-width character slicer.
5. **`RecursiveCharacterTextSplitter`** tries a hierarchy of separators, moving from larger boundaries to smaller ones when necessary.
6. **Language-specific splitting** can use separators appropriate for code or formats such as Markdown, but it is not a full syntax parser.
7. **Markdown header splitting** can preserve heading context as metadata; very large sections may still need another size-limited split.
8. **Semantic chunking** uses embedding-based signals to help locate topic changes, but adds computation and depends on the embedding and breakpoint configuration.
9. No single strategy is ideal for every dataset. The source structure, retrieval task, context budget, and evaluation results should guide the choice.
10. A RAG pipeline should be evaluated end to end: useful chunk boundaries matter because they affect what the retriever can return to the language model.


### Final conclusion

Text splitting is not simply about making documents smaller. It is about preparing text in a way that supports the downstream task.

For a RAG application, the chunking strategy can influence what information is retrieved, how much context reaches the language model, and how efficiently documents are processed.

A sensible workflow is to begin with a structure-aware splitter, choose an appropriate chunk size and overlap, and evaluate the results using representative queries. More specialized approaches, including document-aware or semantic chunking, can then be introduced when the application requires them.

The key principle is to create chunks that are small enough to process efficiently but retain enough relevant context to remain useful.
