## Introduction

LangChain provides building blocks for developing applications powered by large language models (LLMs). These applications can include chatbots, PDF question-answering systems, retrieval-augmented generation (RAG) pipelines, and AI agents.

One of the central concepts behind connecting these building blocks is the **Runnable**.

In this guide, we’ll build an understanding of Runnables from the ground up:

- Why LangChain introduced a common interface for its components.
- What a Runnable is and how it processes data.
- How Runnables can be connected to form workflows.
- How this relates to LangChain chains.
- How to understand the concepts through Python code and practical examples.

The notes follow the concepts and teaching sequence in the supplied transcript, with code examples and visual explanations to make the material easier to study.

# 2. Why Do Runnables Exist?

To understand why Runnables matter, we need to understand the problem they were designed to address.

## 2.1 The rise of LLM applications

The transcript begins with the emergence of publicly accessible LLM APIs and the growing demand for applications built around language models.

As developers began building more sophisticated applications, they needed to work with different model providers and many other components besides the LLM itself.

For example, a PDF question-answering application may require:

1. Loading a document.
2. Splitting the document into smaller chunks.
3. Generating embeddings for those chunks.
4. Storing the embeddings in a vector database.
5. Retrieving relevant chunks for a user query.
6. Sending the retrieved information and query to an LLM.
7. Returning the generated answer.

This is a pipeline of multiple operations, not simply a call to a language model.

## 2.2 The first problem: different model APIs

Different model providers expose different APIs and interfaces. LangChain’s components help developers interact with these providers through a more consistent framework.

The goal is to reduce the amount of provider-specific code developers need to write when working with different models.

## 2.3 The second problem: components were difficult to connect uniformly

The transcript explains that LangChain had components for models, prompts, retrievers, parsers, and other tasks. However, these components did not originally share a standardized interface.

| Component | Method described in the transcript |
|---|---|
| LLM | `predict()` |
| Prompt template | `format()` |
| Retriever | `get_relevant_documents()` |
| Parser | `parse()` |

Because these components had different interfaces, developers needed custom code to connect them.

LangChain introduced chains to automate common combinations of components. But creating many specialized chains introduced another challenge.

## 2.4 The problem with too many chains

The transcript identifies two major disadvantages:

- **A larger codebase:** many specialized chains require more code to maintain.
- **A steeper learning curve:** developers must learn which chain is appropriate for which use case.

The intended goal was to make components behave like interchangeable building blocks. The difficulty was that the components did not originally follow a common contract.

This leads to the central idea of Runnables: give components a shared interface so they can be connected more consistently.

# 3. What Is a Runnable?

A **Runnable** can be understood as a unit of work that accepts input, performs an operation, and produces output.

The transcript emphasizes four fundamental characteristics:

1. **A unit of work** — each Runnable has a purpose. It processes some input and returns an output.
2. **A common interface** — Runnables expose a consistent set of methods, such as `invoke()`, `batch()`, and `stream()`.
3. **Composability** — Runnables can be connected so that the output of one operation becomes the input of another.
4. **Composed workflows are also Runnables** — a workflow assembled from Runnables can itself be treated as a Runnable, allowing further composition.

## 3.1 The LEGO-block analogy

Think of each Runnable as a LEGO block:

- Each block performs a particular function.
- Blocks share compatible connection points.
- Multiple blocks can be connected to form a larger structure.
- The resulting structure can be connected to other structures.

This analogy captures the core design goal: build complex workflows from smaller, reusable units.

# 4. The Common Runnable Interface

The most important interface introduced in the transcript is `invoke()`.

Instead of requiring every component to have a different method for processing input, we can standardize the interaction.

## 4.1 `invoke()`

`invoke()` runs a Runnable with a single input and returns its output.

```python
result = runnable.invoke(input_data)
```

For example:

- A prompt Runnable can accept a dictionary and produce a formatted prompt.
- An LLM Runnable can accept a prompt and produce a model response.
- A parser Runnable can accept a model response and extract the desired output.

The exact input and output types depend on the particular Runnable.

## 4.2 `batch()`

`batch()` allows a Runnable to process multiple inputs in one operation.

```python
results = runnable.batch([
    input_one,
    input_two,
    input_three,
])
```

This is useful when you need to apply the same operation to several independent inputs.

## 4.3 `stream()`

`stream()` allows output to be consumed incrementally rather than waiting for the complete result.

```python
for chunk in runnable.stream(input_data):
    print(chunk)
```

Streaming is especially useful for applications where showing partial model output improves responsiveness.

### Runnable methods at a glance

| Method | Purpose |
|---|---|
| `invoke()` | Process one input and return one result. |
| `batch()` | Process a collection of inputs. |
| `stream()` | Yield output incrementally. |

These are conceptual examples of the interface. Actual behavior, supported input types, and streaming capabilities depend on the Runnable implementation.

# 5. Building Runnables From Scratch

The transcript demonstrates the underlying idea by creating simplified Python classes rather than relying immediately on the full LangChain implementation.

The approach is:

1. Create a dummy LLM component.
2. Create a dummy prompt-template component.
3. Give both components a common abstract base class.
4. Implement a connector that invokes them in sequence.
5. Add a parser and compose larger workflows.

## 5.1 Create a dummy LLM

The example LLM does not call a real model. Instead, it returns a randomly selected response from a predefined list.

```python
import random

class FakeLLM:
    def __init__(self):
        self.responses = [
            "Delhi is the capital of India.",
            "IPL is a cricket league.",
            "AI stands for Artificial Intelligence."
        ]

    def predict(self, prompt):
        return random.choice(self.responses)
```

This dummy component lets us study the mechanics of a workflow without needing a model API.

## 5.2 Create a prompt-template component

A prompt template stores a format string and fills its placeholders using a dictionary of input values.

```python
class FakePromptTemplate:
    def __init__(self, template, input_variables):
        self.template = template
        self.input_variables = input_variables

    def format(self, input_dict):
        return self.template.format(**input_dict)
```

Example:

```python
prompt = FakePromptTemplate(
    template="Write a {length} poem about {topic}.",
    input_variables=["length", "topic"]
)

formatted_prompt = prompt.format({
    "length": "short",
    "topic": "India"
})

print(formatted_prompt)
```

Output:

```text
Write a short poem about India.
```

## 5.3 The manual workflow

Without a common interface, the developer must know which method belongs to each component.

```python
prompt = FakePromptTemplate(
    "Write a {length} poem about {topic}.",
    ["length", "topic"]
)

llm = FakeLLM()

formatted_prompt = prompt.format({
    "length": "short",
    "topic": "India"
})

response = llm.predict(formatted_prompt)

print(response)
```

Notice the manual coordination:

- Call `format()` on the prompt template.
- Pass its output into `predict()` on the LLM.
- Handle the result.

This is the sort of component interaction that the transcript uses to motivate a common interface.

## 5.4 Standardize the components with an abstract base class

The next step is to introduce a common `Runnable` base class.

The transcript uses Python’s `ABC` and `abstractmethod` to illustrate how a component can be required to implement a particular method.

```python
from abc import ABC, abstractmethod

class Runnable(ABC):

    @abstractmethod
    def invoke(self, input_data):
        pass
```

Because `invoke()` is abstract, a concrete subclass must implement it before it can be instantiated.

### Convert the LLM into a Runnable

```python
class FakeLLM(Runnable):

    def __init__(self):
        self.responses = [
            "Delhi is the capital of India.",
            "IPL is a cricket league.",
            "AI stands for Artificial Intelligence."
        ]

    def invoke(self, prompt):
        return random.choice(self.responses)

    def predict(self, prompt):
        # Compatibility with older code
        return self.invoke(prompt)
```

The example retains `predict()` as a compatibility method while making `invoke()` the standardized entry point.

### Convert the prompt template into a Runnable

```python
class FakePromptTemplate(Runnable):

    def __init__(self, template, input_variables):
        self.template = template
        self.input_variables = input_variables

    def invoke(self, input_dict):
        return self.template.format(**input_dict)

    def format(self, input_dict):
        # Compatibility with older code
        return self.invoke(input_dict)
```

Now both components expose the same method name:

```python
prompt.invoke(input_dict)
llm.invoke(formatted_prompt)
```

The implementations still perform different tasks, but their interaction follows a common contract.

> **Key insight:** A common interface does not mean that every component performs the same operation. It means that components can be called through a consistent interaction pattern, making composition easier.

## 5.5 Create a Runnable connector

The transcript next introduces a connector that accepts a list of Runnables and passes data through them in order.

```python
class RunnableConnector(Runnable):

    def __init__(self, runnable_list):
        self.runnable_list = runnable_list

    def invoke(self, input_data):
        for runnable in self.runnable_list:
            input_data = runnable.invoke(input_data)

        return input_data
```

The important operation is:

```python
input_data = runnable.invoke(input_data)
```

After each step, the output replaces the current input. The next Runnable receives that output.

### Use the connector

```python
prompt = FakePromptTemplate(
    "Write a {length} poem about {topic}.",
    ["length", "topic"]
)

llm = FakeLLM()

chain = RunnableConnector([prompt, llm])

result = chain.invoke({
    "length": "short",
    "topic": "India"
})

print(result)
```

## 5.6 Add a parser as another Runnable

The transcript then adds a string output parser that extracts the response from a dictionary-like model result.

A simplified version of that operation is:

```python
class FakeStrOutputParser(Runnable):

    def invoke(self, input_data):
        return input_data["response"]
```

The exact shape of the input must match what the preceding component returns. For this illustrative parser, the input is expected to contain a `"response"` key.

A parser can be added to the connector’s list:

```python
chain = RunnableConnector([
    prompt,
    llm,
    parser
])
```

This demonstrates that a workflow can be extended by adding another component, provided the output of each step is compatible with the next step’s input.

# 6. Composing Runnables Into Larger Workflows

One of the transcript’s central points is that a composed workflow can itself be treated as a Runnable.

This means we can connect smaller workflows to create larger ones without having to redesign the entire application.

## 6.1 Sequential composition: generate a joke, then explain it

Suppose an application needs to:

1. Generate a joke about a topic.
2. Explain the generated joke.

These are two separate operations. Each can be represented as a chain, and the two chains can then be composed sequentially.

<img width="710" height="197" alt="image" src="https://github.com/user-attachments/assets/db1fca2e-8045-402e-9a83-58587971a887" />


The following is a simplified composition example using the connector created earlier:

```python
joke_prompt = FakePromptTemplate(
    "Write a joke about {topic}.",
    ["topic"]
)

explanation_prompt = FakePromptTemplate(
    "Explain this joke: {response}",
    ["response"]
)

joke_chain = RunnableConnector([joke_prompt, llm])

explanation_chain = RunnableConnector([
    explanation_prompt,
    llm
])
```

The transcript’s broader lesson is that a chain can be connected to another chain because the chain itself exposes the Runnable interface.

This is an illustration of the composition pattern, not a complete production-ready joke application. In a real implementation, the intermediate output may need to be mapped into the input key expected by the next chain.

## 6.2 Why composition matters

Without composition, the developer has to manually coordinate every component and every intermediate result.

With a common interface:

- Components can be assembled into reusable workflows.
- A workflow can become a building block for another workflow.
- More complex applications can be constructed from smaller operations.

This is the same LEGO-block analogy introduced earlier, applied to complete workflows rather than individual components.

## 8.1 The document preparation stage

A typical preparation workflow described in the transcript involves:

- Loading a document.
- Splitting it into smaller chunks.
- Generating embeddings.
- Storing those embeddings in a vector database.

```text
Load → Split → Embed → Store
```

## 8.2 The question-answering stage

When a user asks a question:

- A retriever searches for relevant document chunks.
- The relevant text is combined with the user’s question.
- An LLM generates an answer.
- The application returns the answer to the user.

```text
Question → Retrieve → Build prompt → Generate answer
```

The two stages serve different purposes: preparing searchable document representations and using retrieved context to answer a query.

The transcript uses this example to show how multiple components cooperate in an LLM application. The key connection to Runnables is the ability to represent processing steps using compatible interfaces and combine them into larger workflows.
