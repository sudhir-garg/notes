# 2. What is a retriever?

A retriever is a component in LangChain that fetches relevant documents
from a data source in response to a user's query.

Think of it as a search interface between a question and a collection of
information.

Suppose a user asks:

> What are the major causes of climate change?

The retriever searches an available data source, identifies documents
relevant to the question, and returns those documents for further
processing.

## 2.1 Input and output

Conceptually, a retriever behaves like a function:

<img width="649" height="53" alt="image" src="https://github.com/user-attachments/assets/584854b7-2f0b-45bb-8846-9a19b7bb597a" />


-   **Input:** A user's query, typically represented as a string.
-   **Processing:** Searches a data source using a particular retrieval
    strategy.
-   **Output:** A list of LangChain `Document` objects.

A `Document` generally contains:

-   `page_content` --- the text content of the document.
-   `metadata` --- additional information such as a source, title, page
    number, or other attributes.

## 2.2 How a retriever works

<img width="649" height="349" alt="image" src="https://github.com/user-attachments/assets/edb87419-e97d-4b8f-8aed-172755b607c3" />


A retriever is not necessarily limited to vector databases. It can
retrieve information from different kinds of data sources, depending on
its implementation.

## 2.3 Retrievers are Runnables

An important concept in LangChain is that retrievers can be used as
Runnables.

This means they can participate in Runnable-based workflows and can be
invoked using a standardized interface.

For example:

``` python
documents = retriever.invoke("What is photosynthesis?")
```

The returned value is typically a list of `Document` objects.

This standard interface makes retrievers easier to integrate into chains
and other LangChain workflows.

> **Important distinction:** A retriever is not the same thing as a
> language model. Its primary responsibility is to find relevant
> information, not to generate the final natural-language answer.

# 3. Types of retrievers

LangChain supports different retrievers because different applications
have different retrieval requirements.

For example:

-   One application may need to search Wikipedia.
-   Another may need to search a private vector database.
-   Another may need diverse results instead of several nearly identical
    documents.
-   Another may need to rewrite an ambiguous query or remove irrelevant
    text from retrieved documents.

We can understand retrievers using two complementary classification
dimensions.

# 4. Wikipedia Retriever

## 4.1 What is a Wikipedia Retriever?

A Wikipedia Retriever searches Wikipedia for articles relevant to a
user's query and returns the selected content as LangChain `Document`
objects.

For example, a user might ask:

> Explain the geopolitical history of India and Pakistan.

The retriever can query Wikipedia, identify relevant articles, and
return their content.

<img width="680" height="264" alt="image" src="https://github.com/user-attachments/assets/e6395b19-5b47-4047-8bb1-b80ec97e856b" />


The key distinction is that a retriever performs a search to select
relevant information. It does not simply load every article from
Wikipedia.

## 4.2 How does it work?

The general process is:

1.  The user supplies a query.
2.  The retriever sends a search request to the Wikipedia integration.
3.  The search mechanism identifies potentially relevant articles.
4.  The retriever returns the selected content as documents.

The precise ranking and search behavior depends on the implementation
and its underlying integration. The important concept is that retrieval
involves selecting results in response to a query.

## 4.3 Code demonstration

The following example illustrates the interface used in the lesson. It
uses the community Wikipedia integration.

> **Environment note:** LangChain integrations and import paths can
> change between releases. Install the matching integration packages and
> check their documentation if an import is unavailable in your
> environment.

``` python
# Install the required packages in your notebook:
# %pip install -U langchain-community wikipedia

from langchain_community.retrievers import WikipediaRetriever

# Create the retriever
retriever = WikipediaRetriever(
    top_k_results=2,
    lang="en"
)

# Define the query
query = (
    "The geopolitical history of India and Pakistan "
    "from the perspective of a Chinese"
)

# Retrieve relevant documents
results = retriever.invoke(query)

# Display the retrieved documents
for i, doc in enumerate(results, start=1):
    print(f"\\n--- Document {i} ---")
    print("Metadata:", doc.metadata)
    print("Content:", doc.page_content[:1000])
```

## 4.4 Retriever versus document loader

A document loader is generally responsible for loading content from a
specified source or set of resources. A retriever selects content in
response to a query.

A Wikipedia retriever therefore serves a different purpose from a
workflow that loads a predetermined set of Wikipedia pages.

# 5. Vector Store Retriever

## 5.1 What is a Vector Store Retriever?

A Vector Store Retriever retrieves relevant documents from a vector
store using a supported search mechanism.

This is one of the central retrieval patterns used in
semantic-search-based RAG applications.

Common vector stores include:

<img width="597" height="172" alt="image" src="https://github.com/user-attachments/assets/58ee5c24-f621-45e8-8778-16f18b361d55" />


Other vector-store integrations can be used as well.

## 5.2 How does vector retrieval work?

Before retrieval, documents are embedded and stored in a vector index.

At query time:

1.  The user's query is converted into a vector using the embedding
    model.
2.  The vector store compares the query representation with stored
    representations.
3.  A search method identifies relevant candidates.
4.  The selected documents are returned to the caller.

<img width="662" height="265" alt="image" src="https://github.com/user-attachments/assets/161e3e21-2879-499d-87c4-dfbe42aabb24" />


### What is semantic similarity?

Semantic similarity attempts to identify content related in meaning,
even when the wording differs.

For example:

-   **Query:** "How can I improve my sleep?"
-   **Document:** "Maintaining a consistent bedtime can support healthy
    sleep habits."

These texts do not use exactly the same words, but their meanings are
related. An embedding-based search can help identify this relationship.

The actual results depend on the embedding model, indexed data, distance
metric, and retrieval configuration.

## 5.3 Creating a Vector Store Retriever

The following example uses Chroma and OpenAI embeddings.

``` python
# %pip install -U langchain-chroma langchain-openai

from langchain_core.documents import Document
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

# Example documents
documents = [
    Document(
        page_content=(
            "LangChain helps developers build applications "
            "powered by language models."
        ),
        metadata={"topic": "LangChain"}
    ),
    Document(
        page_content=(
            "Chroma is a vector database used to store and "
            "retrieve embedding representations."
        ),
        metadata={"topic": "Chroma"}
    ),
    Document(
        page_content=(
            "Embeddings represent text as numerical vectors "
            "that can be compared for similarity."
        ),
        metadata={"topic": "Embeddings"}
    ),
]

# Create the embedding model
embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

# Create the vector store and index the documents
vector_store = Chroma.from_documents(
    documents=documents,
    embedding=embeddings,
    collection_name="langchain_notes"
)

# Create a retriever
retriever = vector_store.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 2}
)

# Run a query
query = "What is Chroma used for?"
results = retriever.invoke(query)

for doc in results:
    print(doc.page_content)
    print(doc.metadata)
```

This example requires valid OpenAI API credentials in the environment.
It creates a sample collection; production applications should also
consider persistence, collection management, and index lifecycle.

## 5.4 Understanding `as_retriever()`

The `as_retriever()` method exposes a vector store through the retriever
interface.

``` python
retriever = vector_store.as_retriever(
    search_type="similarity",
    search_kwargs={"k": 2}
)
```

-   `search_type="similarity"` selects similarity-based retrieval.
-   `search_kwargs={"k": 2}` requests two results.

This is useful because the resulting retriever can be plugged into
Runnable-based workflows.

## 5.5 Why use a retriever if the vector store already supports search?

A vector store may expose direct search methods, such as:

``` python
results = vector_store.similarity_search(
    "What is Chroma used for?",
    k=2
)
```

This can retrieve documents without explicitly creating a retriever.

So why create one?

The main advantages are:

1.  **Standardized interface:** The retriever can be invoked using
    `invoke()`.
2.  **Workflow integration:** It can be incorporated into Runnable-based
    chains.
3.  **Strategy flexibility:** Retriever abstractions can expose
    different retrieval approaches, including MMR and other advanced
    strategies.
4.  **Separation of responsibilities:** The vector store handles storage
    and search capabilities, while the retriever provides a retrieval
    interface that can be composed into an application.

A basic similarity retriever may return results similar to a direct
similarity-search call. The retriever abstraction becomes particularly
useful when building reusable or more sophisticated retrieval workflows.

# 6. Maximum Marginal Relevance (MMR)

## 6.1 The problem: relevant but repetitive results

Imagine that a vector store contains the following documents about
climate change:
<img width="536" height="185" alt="image" src="https://github.com/user-attachments/assets/1be10f01-9310-4257-9637-80f748cb7bce" />

The user asks:

> What are the adverse effects of climate change?

A basic similarity search might return D1, D2, and D3.

Although all three documents are relevant, D1 and D2 cover almost the
same information. The results may therefore lack diversity.

Ideally, we would like to retrieve relevant documents that also cover
different aspects of the topic.

## 6.2 What is MMR?

Maximum Marginal Relevance (MMR) is a retrieval strategy that balances
two objectives:

-   Relevance to the user's query.
-   Diversity among the selected documents.

Instead of simply selecting the documents most similar to the query, MMR
also considers how similar each candidate is to documents that have
already been selected.

This helps reduce redundancy while retaining useful information.

## 6.3 How MMR works

A simplified description of the process is:

1.  Retrieve a candidate set of documents.
2.  Select an initial document with high relevance to the query.
3.  Evaluate the remaining candidates based on both query relevance and
    their difference from already selected documents.
4.  Select the next document with a favorable relevance-diversity
    trade-off.
5.  Repeat until the required number of documents has been selected or
    the candidates are exhausted.

## 6.5 Implementing MMR in LangChain

The vector store retriever can be configured to use MMR.

``` python
# Assuming vector_store has already been created

mmr_retriever = vector_store.as_retriever(
    search_type="mmr",
    search_kwargs={
        "k": 3,
        "fetch_k": 10,
        "lambda_mult": 0.5
    }
)

query = "What are the adverse effects of climate change?"
results = mmr_retriever.invoke(query)

for i, doc in enumerate(results, start=1):
    print(f"\\n--- Result {i} ---")
    print(doc.page_content)
```

### Parameters

-   `k`: The number of final documents requested.
-   `fetch_k`: The number of candidate documents considered before
    selecting the final results.
-   `lambda_mult`: Controls the relevance-diversity trade-off in the
    vector-store integration.

In the example, MMR considers a candidate pool of up to 10 documents and
requests three final results.

> **When should you consider MMR?** Use MMR when ordinary similarity
> search tends to return near-duplicate documents and you need multiple
> relevant perspectives, topics, or evidence sources.

# 7. Multi-Query Retriever

## 7.1 The problem: ambiguous or underspecified queries

A user may ask:

> How can I stay healthy?

This question is broad. The user might be interested in:

-   Nutrition and food choices.
-   Exercise frequency and physical activity.
-   Stress management and mental well-being.
-   Sleep and lifestyle habits.

A single query may not retrieve documents covering all these
interpretations.

The Multi-Query Retriever addresses this problem by generating
alternative formulations of the original query and using them to
retrieve information.

## 7.2 What is a Multi-Query Retriever?

A Multi-Query Retriever uses a language model to generate multiple
related queries from a user's original question. It then retrieves
documents for those queries and combines the results.

The goal is to improve retrieval coverage by exploring different ways of
expressing the information need.

## 7.3 How does it work?

<img width="643" height="444" alt="image" src="https://github.com/user-attachments/assets/cddb1699-ced9-434d-8070-23de2c37009d" />


The generated queries should preserve the original information need
while exploring useful alternative phrasings or subtopics.

## 7.4 Why can multiple queries improve retrieval?

Suppose the indexed documents use different terminology:

-   One document discusses "physical activity."
-   Another discusses "cardiovascular exercise."
-   Another discusses "stress reduction."
-   Another discusses "nutritional balance."

A single broad query may not match all these topics effectively.

Generating alternative queries can help the retrieval system discover
relevant documents that would otherwise be missed.

However, query generation does not guarantee better results. Poorly
generated queries may introduce irrelevant topics, and retrieving more
documents can increase cost and latency.

## 7.5 Code demonstration

This example uses the Multi-Query Retriever with a vector store
retriever.

``` python
# %pip install -U langchain-classic langchain-openai

from langchain_classic.retrievers.multi_query import MultiQueryRetriever
from langchain_openai import ChatOpenAI

# Assume vector_store has already been created

base_retriever = vector_store.as_retriever(
    search_kwargs={"k": 5}
)

# LLM used to generate alternative queries
llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0
)

# Create the Multi-Query Retriever
multi_query_retriever = MultiQueryRetriever.from_llm(
    retriever=base_retriever,
    llm=llm
)

query = "How can I improve energy levels and maintain balance?"
results = multi_query_retriever.invoke(query)

for i, doc in enumerate(results, start=1):
    print(f"\\n--- Result {i} ---")
    print(doc.page_content)
```

The Multi-Query Retriever import path is version-sensitive. In some
LangChain releases it is provided through `langchain.retrievers`; in
newer package layouts, legacy chain and retriever utilities may be
available through `langchain-classic`. Check the installed version's
documentation.

### Understanding the code

1.  `base_retriever` is the underlying retriever responsible for
    searching the vector store.
2.  `ChatOpenAI` provides the LLM used to generate alternative queries.
3.  `MultiQueryRetriever.from_llm()` combines the query-generation model
    with the base retriever.
4.  `invoke()` runs the retrieval workflow for the original question.

The underlying retriever can be configured with a different supported
retrieval strategy, depending on the integration.

## 7.6 Multi-Query versus MMR

These two strategies solve different problems.

# 8. Contextual Compression Retriever

## 8.1 The problem: retrieved documents contain irrelevant content

Imagine that a vector store contains the following paragraph:

> The Grand Canyon is a famous natural landmark in the United States.
> Photosynthesis is the process through which plants convert light
> energy into chemical energy. Many tourists visit the Grand Canyon
> every year.

The user asks:

> What is photosynthesis?

The paragraph contains the required information, but it also contains
unrelated material about the Grand Canyon.

If the whole paragraph is passed to the LLM, part of the context may be
unnecessary.

This is where contextual compression can help.

## 8.2 What is contextual compression?

A Contextual Compression Retriever combines a base retriever with a
document compressor.

The base retriever first finds relevant documents. The compressor then
filters or transforms the retrieved content based on the user's query.

Depending on the compressor, this may involve:

-   Extracting relevant passages.
-   Filtering out irrelevant documents.
-   Reducing the amount of text passed downstream.
-   Reformatting or otherwise transforming the retrieved content.

The result is a more focused context for the next stage of the
application.

## 8.3 How does it work?

<img width="726" height="384" alt="image" src="https://github.com/user-attachments/assets/d1c88949-c6fb-4f40-b14a-1e696ea1fda2" />


## 8.4 Why might a document contain mixed information?

Large documents may discuss multiple topics. When a text splitter
divides them into chunks, the resulting chunks may still contain
information from more than one subject.

This can happen when:

-   A paragraph contains multiple topics.
-   A chunk boundary falls between related sentences.
-   A document uses long sections with several subtopics.
-   The chunking configuration prioritizes size over semantic
    boundaries.

Contextual compression can help address this issue after retrieval.

## 8.5 Code demonstration

This example uses a base vector-store retriever and an LLM-based
extraction chain as the compressor.

``` python
# %pip install -U langchain-classic langchain-openai

from langchain_classic.retrievers import ContextualCompressionRetriever
from langchain_classic.retrievers.document_compressors import LLMChainExtractor
from langchain_openai import ChatOpenAI

# Assume vector_store has already been created

# 1. Create the base retriever
base_retriever = vector_store.as_retriever(
    search_kwargs={"k": 4}
)

# 2. Create the LLM-based compressor
llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0
)
compressor = LLMChainExtractor.from_llm(llm)

# 3. Combine the retriever and compressor
compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)

# 4. Retrieve compressed documents
query = "What is photosynthesis?"
results = compression_retriever.invoke(query)

for i, doc in enumerate(results, start=1):
    print(f"\\n--- Compressed result {i} ---")
    print(doc.page_content)
```

As with Multi-Query, the package location may vary by LangChain version.
Confirm the installed package's API before running the example.

## 8.6 Understanding the components

<img width="723" height="140" alt="image" src="https://github.com/user-attachments/assets/d2ed55cc-b5de-4f02-9b83-164e600811af" />


The compressor does not necessarily have to be an LLM. LangChain
supports different kinds of document compressors, including filtering
and transformation approaches.

## 8.7 When should contextual compression be used?

Consider contextual compression when:

-   Retrieved chunks contain substantial irrelevant text.
-   Documents are long or cover multiple topics.
-   You want to reduce the amount of context sent to the LLM.
-   You need to focus downstream generation on query-relevant evidence.

### Important limitation

Compression can discard useful information if the compressor
misunderstands the query or removes context that is indirectly
necessary. It can also add model latency and cost.

Compression should therefore be evaluated as part of the overall RAG
pipeline, rather than assumed to improve every application
automatically.

# 9. Other retrievers in LangChain

The four retriever examples discussed in detail are not the only

## 9.1 Parent Document Retriever

A common challenge in RAG is choosing the right chunk size.

-   Small chunks can provide precise matches but may lack surrounding
    context.
-   Large chunks can preserve context but may contain irrelevant
    information.

A Parent Document Retriever addresses this by retrieving based on
smaller child chunks and returning their associated parent documents.

<img width="716" height="294" alt="image" src="https://github.com/user-attachments/assets/10aa9894-be26-4f19-86a4-f720be75a6c6" />


## 9.2 Self-Query Retriever

A Self-Query Retriever can help when the data contains useful metadata.

For example, a user might ask:

> Find science articles published after 2022.

The retriever may use an LLM to interpret the request and construct a
search that includes both semantic content and metadata constraints.

This can be useful when a collection contains fields such as publication
date, author, category, or document type.

## 9.3 Ensemble Retriever

An Ensemble Retriever combines multiple retrievers. For example, an
application might combine:

-   A keyword-based retriever, which can match exact terms.
-   A vector-based retriever, which can identify semantic similarity.

Combining retrieval methods can provide complementary coverage, although
the result depends on the chosen retrievers, fusion method, and
configuration.

# 10. Why are there so many retrievers?

There is no single retrieval strategy that works equally well for every
dataset, query, and application.

A basic similarity retriever may be sufficient for straightforward
semantic search. More specialized retrievers address limitations that
appear in particular use cases.

<img width="696" height="251" alt="image" src="https://github.com/user-attachments/assets/0cbcccca-af7c-4497-913c-a8d8213be4b1" />


The choice should be guided by retrieval quality, latency, cost,
complexity, and the requirements of the application.

## 10.1 Retriever selection is part of RAG optimization

A RAG system's performance depends on several stages:

1.  How the source data is loaded.
2.  How documents are split into chunks.
3.  How the chunks are embedded and indexed.
4.  How relevant information is retrieved.
5.  How the retrieved context is assembled.
6.  How the language model uses that context to generate an answer.

Changing the retriever can improve one part of this pipeline, but it
does not automatically fix problems caused by poor source data,
unsuitable chunking, or incorrect answers generated from the supplied
context.

# 11. Comparison of retrieval strategies

The following table summarizes the key concepts from this lesson.

| **Feature** | **Similarity Search** | **MMR** | **Multi-Query** | **Contextual Compression** |
|---|---|---|---|---|
| **Main objective** | Find documents similar to the query. | Balance relevance and diversity. | Expand retrieval through alternative queries. | Focus retrieved context on relevant content. |
| **Uses an LLM as a core part of the strategy?** | Not necessarily. | Not necessarily; commonly uses vector similarity calculations. | Yes, for query generation in the described implementation. | In the LLM-based example, yes, for extraction. |
| **Main stage affected** | Candidate retrieval and ranking. | Candidate selection. | Query formulation and retrieval. | Post-retrieval processing. |
| **Helps with redundancy?** | Not specifically. | Yes, by considering similarity among selected documents. | May retrieve more coverage, but does not inherently guarantee deduplication or diversity. | Can remove irrelevant content, but does not inherently guarantee document diversity. |
| **Potential trade-off** | May return overlapping results. | Diversity may come at the expense of some relevance. | Additional model calls, latency, and potentially more retrieved content. | Additional processing cost and possible loss of useful context. |


# 12. Key takeaways

1.  A **retriever** is a LangChain component that takes a query and returns
    relevant `Document` objects.
2.  Retrievers can search different data sources, including vector
    stores and external information sources.
3.  Retrievers are Runnables, allowing them to participate in
    standardized Runnable-based workflows.
4.  A **Vector Store Retriever** provides a convenient interface for
    retrieving documents from a vector store.
5.  **MMR** balances query relevance with diversity among selected
    documents.
6.  **Multi-Query** uses alternative query formulations to help broaden
    retrieval coverage.
7.  **Contextual Compression** processes retrieved documents to focus the
    context on information relevant to the query.
8.  Parent Document, Self-Query, Ensemble, and other retrievers address
    additional retrieval requirements.
9.  More advanced retrieval is not automatically better. The strategy
    should be evaluated against the actual application's needs.

## Final perspective

Retrieval is not simply about returning the documents with the highest
similarity score. It is about supplying the right evidence for the task.

A useful RAG system must consider what the user is asking, how the
information is stored, which retrieval strategy is appropriate, and how
much context the language model actually needs.

Understanding these retriever patterns provides a foundation for
building and evaluating more sophisticated RAG applications in
LangChain.
