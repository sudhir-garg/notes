## 1. Introduction and Learning Objectives

In earlier lessons, prompts were used to provide input to an LLM. This lesson focuses on processing the **output** produced by an LLM.

The goal is to make model responses predictable enough to pass to other software systems, such as databases, APIs, and agent tools.

By the end of this topic, you should understand:

- The difference between structured and unstructured output.
- Why structured output is useful in software applications.
- How to define an output schema using `TypedDict`, Pydantic, or JSON Schema.
- How to use LangChain's `with_structured_output()` method.
- How schema descriptions and validation help guide and check model responses.
- Which schema format may fit different project requirements.

## 2. What Is Structured Output?

### Unstructured output

LLMs commonly return ordinary text. For example:

**Prompt:** “What is the capital of India?”

**Response:** “New Delhi is the capital of India.”

This is understandable to a person, but the response does not follow a specific data structure. Such a response is referred to as **unstructured output** in the lesson.

### Structured output

Structured output means asking the model to return information in a **well-defined data format**, such as JSON, with known fields and value types.

For example, a one-day Paris itinerary could be represented as:

```json
{
  "itinerary": [
    {"time": "morning", "activity": "Visit the Eiffel Tower"},
    {"time": "afternoon", "activity": "Visit a museum"},
    {"time": "evening", "activity": "Have dinner"}
  ]
}
```

Here, the data follows a defined shape: an `itinerary` list containing objects with `time` and `activity` fields.

## 3. Why Do We Need Structured Output?

The lesson highlights three major use cases.

### 3.1 Data extraction

Suppose a job portal accepts resumes and needs to store candidate information in a database.

A typical flow is:

1. A candidate uploads a resume.
2. The application extracts the resume text.
3. The text is sent to an LLM.
4. The LLM returns fields such as candidate name, previous company, and academic marks in a structured format.
5. Application code inserts the extracted information into the database.

A predictable structure makes it easier to map extracted values to database columns.

### 3.2 Building APIs

Product reviews are often long, free-form text. An application could use an LLM to extract:

- Topics discussed, such as battery, display, or processor.
- Pros mentioned by the reviewer.
- Cons mentioned by the reviewer.
- Overall sentiment.

The application could then expose the extracted data through an API built with a framework such as Flask or FastAPI.

### 3.3 Building agents and using tools

An agent may need to pass information to a tool. For example, a calculator expects numbers and an operation, not a natural-language request such as “Find the square root of two.”

Structured extraction can identify the required values and provide them in a form the tool can use. The tool then performs its operation and returns a result.

**Main idea:** Structured output helps bridge the gap between human-oriented language and machine-oriented data.

## 4. Ways to Get Structured Output

The lesson distinguishes two broad situations:

1. **Models that support structured output:** LangChain provides `with_structured_output()` to specify the desired schema.
2. **Models that do not support the required structured-output capabilities:** LangChain output parsers can be used to parse or structure ordinary model text.

This lesson focuses on `with_structured_output()`. Output parsers are reserved for the following lesson in the source material.

## 5. `TypedDict`

`TypedDict` lets you describe the expected keys and value types of a Python dictionary. It is useful for communicating the intended dictionary structure to type checkers and code editors.

### 5.1 Basic `TypedDict` Example

```python
from typing import TypedDict

class Person(TypedDict):
    name: str
    age: int

new_person: Person = {
    "name": "Nitish",
    "age": 32
}

print(new_person)
```

In this example:

- `name` is expected to be a string.
- `age` is expected to be an integer.
- `Person` describes the intended dictionary structure.

**Important limitation:** `TypedDict` is primarily a typing aid. It does not, by itself, perform runtime validation. A value with the wrong type may still be created at runtime unless separate validation is used.

### 5.2 Using `Annotated` for Descriptions

Descriptions can provide additional guidance about the meaning of fields. The lesson uses `Annotated` for this purpose.

```python
from typing import Annotated, TypedDict

class Review(TypedDict):
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[
        str,
        "The overall sentiment: positive, negative, or neutral"
    ]
```

A more constrained sentiment field can use `Literal`:

```python
from typing import Annotated, Literal, TypedDict

class Review(TypedDict):
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[
        Literal["pos", "neg", "neutral"],
        "The overall sentiment of the review"
    ]
```

Descriptions help clarify what the model should put in each field. For optional information, a schema can specify that a field may be absent or `None`, depending on the schema form and framework behavior.

### 5.3 Structured Output with `TypedDict`

A review-extraction schema can include themes, summary, sentiment, pros, cons, and a product name.

```python
from typing import Annotated, Literal, Optional, TypedDict

class Review(TypedDict):
    key_themes: Annotated[list[str], "Main topics discussed in the review"]
    summary: Annotated[str, "A concise summary of the review"]
    sentiment: Annotated[
        Literal["pos", "neg", "neutral"],
        "Overall sentiment of the review"
    ]
    pros: Annotated[Optional[list[str]], "Advantages explicitly mentioned"]
    cons: Annotated[Optional[list[str]], "Disadvantages explicitly mentioned"]
    name: Annotated[Optional[str], "Name of the product, if stated"]
```

The precise optional-field syntax can depend on the Python and typing approach used. In particular, `Optional[T]` means `T | None`; it does not alone mean a dictionary key may be omitted.

Marking a field optional does not automatically guarantee that the LLM will omit it when information is absent.

For example, if a review does not explicitly mention disadvantages, the model might still infer some disadvantages.

A more explicit description can help:

``` python
cons: Annotated[
    Optional[list[str]],
    "Include only disadvantages explicitly mentioned "
    "in the review. If none are mentioned, return null."
]
```

## 6. The `with_structured_output()` Function

The core workflow is:

1. Define a schema.
2. Bind the schema to a supported chat model using `with_structured_output()`.
3. Invoke the resulting runnable with the input.
4. Use the structured result in application code.

### Example

```python
from typing import Literal, TypedDict
from langchain_openai import ChatOpenAI
from dotenv import load_dotenv

load_dotenv()

class Review(TypedDict):
    summary: str
    sentiment: Literal["pos", "neg", "neutral"]

model = ChatOpenAI()

structured_model = model.with_structured_output(Review)

review_text = """
The phone has a bright display and excellent battery life,
but the camera struggles in low light.
"""

result = structured_model.invoke(review_text)

print(result)
print(result["summary"])
print(result["sentiment"])
```

The lesson demonstrates that the structured model returns a dictionary-like result for a `TypedDict` schema, allowing fields to be accessed by key.

### What happens behind the scenes?

The schema communicates the desired fields and their meaning. LangChain and the model use that information to guide the response into the requested structure. The returned data can then be processed by ordinary Python code.

The exact underlying mechanism depends on the model integration and selected method; the lesson's conceptual point is that the schema informs the model of the desired response shape.

## 7. Pydantic

Pydantic is a Python library for defining data models and validating/parsing data. It supports richer validation behavior than `TypedDict`.

### 7.1 Basic Pydantic Model

```python
from pydantic import BaseModel

class Student(BaseModel):
    name: str
    age: int

student = Student(name="Aman", age=20)

print(student)
print(student.name)
```

Pydantic models can validate input according to their declared fields and types. Features such as defaults, optional fields, field constraints, and custom validators can be added as needed.

For example, Pydantic v2 provides `model_dump()` to convert a model to a dictionary and `model_dump_json()` to serialize it as JSON.

### 7.2 Review Extraction with Pydantic

```python
from typing import Literal, Optional
from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class Review(BaseModel):
    key_themes: list[str] = Field(
        description="Main topics discussed in the review"
    )
    summary: str = Field(
        description="A concise summary of the review"
    )
    sentiment: Literal["pos", "neg", "neutral"] = Field(
        description="Overall sentiment of the review"
    )
    pros: Optional[list[str]] = Field(
        default=None,
        description="Advantages explicitly mentioned in the review"
    )
    cons: Optional[list[str]] = Field(
        default=None,
        description="Disadvantages explicitly mentioned in the review"
    )
    name: Optional[str] = Field(
        default=None,
        description="Product name, if it is stated"
    )

model = ChatOpenAI()
structured_model = model.with_structured_output(Review)

review_text = """
The phone has a bright display and excellent battery life,
but the camera struggles in low light.
"""

result = structured_model.invoke(review_text)

print(result)
```

`Field` can hold descriptions and constraints. Pydantic also supports default values and validation rules; the exact available features depend on the Pydantic version and field configuration.

### 7.3 Accessing the Result

With a Pydantic schema, the result is a Pydantic model instance rather than a plain dictionary in the pattern shown in the lesson.

```python
print(result.summary)
print(result.sentiment)

# Convert to a dictionary in Pydantic v2:
result_dict = result.model_dump()
print(result_dict)
```

Use attribute access (such as `result.summary`) for the model instance. Convert it to a dictionary first if dictionary-style access is needed.

## 8. JSON Schema

JSON Schema describes the structure and constraints of JSON data. Because it is a language-independent data contract, it can be useful when different parts of a project use different programming languages.

### 8.1 Basic Student Schema

```python
student_schema = {
    "title": "Student",
    "description": "Schema about students",
    "type": "object",
    "properties": {
        "name": {
            "type": "string",
            "description": "The student's name"
        },
        "age": {
            "type": "integer",
            "description": "The student's age"
        }
    },
    "required": ["name"]
}
```

Important schema elements:

- `title`: a name for the schema.
- `description`: an explanation of the schema or a field.
- `type`: the data type, such as `"object"`, `"string"`, or `"integer"`.
- `properties`: the fields and their definitions.
- `required`: the fields that must be present.

In this example, `name` is required while `age` is not listed as required.

### 8.2 Review Schema

```python
review_schema = {
    "title": "Review",
    "description": "Structured information extracted from a product review",
    "type": "object",
    "properties": {
        "key_themes": {
            "type": "array",
            "items": {"type": "string"},
            "description": "Main topics discussed in the review"
        },
        "summary": {
            "type": "string",
            "description": "A concise summary of the review"
        },
        "sentiment": {
            "type": "string",
            "enum": ["pos", "neg", "neutral"],
            "description": "Overall sentiment of the review"
        },
        "pros": {
            "anyOf": [
                {"type": "array", "items": {"type": "string"}},
                {"type": "null"}
            ],
            "description": "Advantages explicitly mentioned"
        },
        "cons": {
            "anyOf": [
                {"type": "array", "items": {"type": "string"}},
                {"type": "null"}
            ],
            "description": "Disadvantages explicitly mentioned"
        },
        "name": {
            "anyOf": [
                {"type": "string"},
                {"type": "null"}
            ],
            "description": "Product name, if stated"
        }
    },
    "required": ["key_themes", "summary", "sentiment"]
}

structured_model = model.with_structured_output(review_schema)
result = structured_model.invoke(review_text)

print(result)
print(result["summary"])
```

The lesson's JSON Schema example returns a dictionary-like result. JSON Schema syntax and supported keywords can vary with the API/provider's structured-output implementation, so check the specific integration's requirements when applying this pattern.

## 11. Important Takeaways

- LLMs commonly produce free-form text, which can be difficult for applications to consume reliably.
- Structured output asks the model to return data in a defined shape.
- Structured data can be used to populate databases, power APIs, and pass values to agent tools.
- LangChain's `with_structured_output()` binds a schema to a compatible model.
- The lesson covers three schema choices: `TypedDict`, Pydantic, and JSON Schema.
- `TypedDict` mainly supplies typing information; it does not itself enforce runtime validation.
- Pydantic provides validation and richer data-model features.
- JSON Schema is useful for language-independent contracts.
- JSON mode and function calling serve different use cases, and model support varies.
- Output parsers are an alternative for models that cannot natively produce the required structured output.

## 12. Quick Self-Test

1. **What is structured output?**  
   A model response that follows a defined data format or schema.

2. **Does `TypedDict` automatically validate values at runtime?**  
   No. It primarily describes expected types for static type checking and editor assistance.

3. **What is a key benefit of Pydantic?**  
   It supports data parsing and validation, along with defaults and additional model features.

4. **When is JSON Schema especially useful?**  
   When a schema needs to be shared across components or services written in different programming languages.

5. **What does `with_structured_output()` do?**  
   It configures a compatible model/runnable to return data according to a supplied schema.

6. **When is function calling useful?**  
   When structured model output is intended to provide arguments for a function or tool, such as in an agent workflow.

---

**Summary:** Structured output makes LLM responses easier for software to consume by giving them a predictable schema. Choosing an appropriate schema format and a supported model method helps connect language models to databases, APIs, and tools.
