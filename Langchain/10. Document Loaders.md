## Introduction

In the previous stages of learning LangChain, we explored its fundamental building blocks, including models, prompts, chains, and Runnables.

Now, we are moving from learning individual components to building practical Retrieval-Augmented Generation (RAG) applications.

The first component we will study is the **Document Loader**.

Document loaders help us bring data from different sources into LangChain in a standardized format. This is important because an LLM application may need to work with PDFs, text files, web pages, CSV datasets, cloud storage, and many other sources.

By the end of these notes, you will understand how to load these sources, inspect their contents and metadata, and choose between eager and lazy loading.

# 1. Introduction to RAG

## 1.1 What is RAG?

**Retrieval-Augmented Generation (RAG)** is a technique that combines information retrieval with language generation.

Instead of relying exclusively on the information learned during training, an LLM application can retrieve relevant information from an external knowledge source and use it as context when generating an answer.

This is particularly useful when the required information is:

- Not included in the model's training data.
- More recent than the model's training cutoff.
- Private or specific to an organization.
- Stored in documents that the model has not previously seen.
- Too large to include in a single prompt.

## 1.2 Why do we need RAG?

A general-purpose LLM may answer many questions correctly, but it cannot automatically know the contents of every private document or newly updated database.

| Scenario | Why a standalone LLM may be insufficient |
|---|---|
| Current company policies | It may not know the latest internal policy. |
| Personal emails | It cannot answer from emails it has not been given access to. |
| Internal documentation | It may not have been trained on your company's documents. |
| Large PDF collections | The entire collection may not fit into the model's context window. |

RAG addresses these situations by connecting the application to a relevant external knowledge source.

A typical RAG application follows this conceptual flow:

### Example

Suppose a user asks:

> What is our company's current work-from-home policy?

A RAG application can:

1. Receive the user's question.
2. Search the company's policy documents.
3. Retrieve the relevant policy passages.
4. Provide those passages to the LLM as context.
5. Generate an answer based on the retrieved information.

The model can now answer using information supplied by the knowledge source, rather than having to rely only on its pretrained knowledge.

## 1.4 Benefits of RAG

- **Access to external information:** Applications can retrieve information that was not part of the model's original training.
- **More up-to-date answers:** The knowledge base can be updated independently of the model.
- **Document-based question answering:** Users can ask questions about PDFs, company documentation, reports, and other supported sources.
- **Efficient handling of large collections:** Documents can be divided into smaller chunks and relevant portions retrieved as needed, instead of putting an entire collection into every prompt.
- **Potentially improved data control:** An organization can design a system that retrieves information from its own infrastructure without sending its entire document collection to a third-party chatbot. Actual privacy depends on the deployment, access controls, and model provider.

**Important:** RAG can reduce the impact of missing knowledge, but it does not guarantee that every answer will be correct. Retrieval quality, document quality, permissions, and the LLM's response all matter.

# 3. Understanding Document Loaders

## 3.1 What is a Document Loader?

A **Document Loader** is a LangChain component used to load data from various sources and convert it into a standardized format, usually a list of `Document` objects.

The data may come from:

- Text files (`.txt`)
- PDF files (`.pdf`)
- CSV files (`.csv`)
- Web pages
- Databases
- Cloud storage
- Other applications and data sources

Different sources have different formats. A PDF contains pages, a CSV contains rows and columns, and a web page contains HTML.

Document loaders provide a common interface for bringing these different data sources into a LangChain application.

## 3.2 The basic workflow

<img width="724" height="411" alt="image" src="https://github.com/user-attachments/assets/a30c6c73-0981-4ee4-820c-0dbd8e4cf42b" />


The key idea is that downstream components can work with a consistent representation instead of needing to understand every original file format.

# 4. The LangChain Document Object

A LangChain `Document` is a data structure that stores text content together with associated metadata.

It has two important fields:

| Field | Description |
|---|---|
| `page_content` | The actual textual content extracted from the source. |
| `metadata` | Additional information describing the content, such as its source, page number, or other attributes. |

For example:

```python
from langchain_core.documents import Document

doc = Document(
    page_content="LangChain helps developers build LLM applications.",
    metadata={
        "source": "notes.txt",
        "topic": "LangChain"
    }
)

print(doc.page_content)
print(doc.metadata)
```

Output:

```text
LangChain helps developers build LLM applications.

{'source': 'notes.txt', 'topic': 'LangChain'}
```

## 4.1 Why is metadata important?

Metadata helps us understand where a piece of content came from and provides information that can be useful during retrieval and application processing.

For example, metadata can help an application:

- Identify the original source of a passage.
- Associate extracted text with a PDF page.
- Filter documents using attributes such as document type or category.
- Preserve provenance so that retrieved content can be traced back to its source.

Metadata fields vary by loader and source. Inspect the actual metadata produced by your loader instead of assuming every loader returns identical fields.

## 4.2 A crucial rule: loaders commonly return a list

The standard `load()` interface returns a list of documents.

```python
docs = loader.load()

print(type(docs))
print(len(docs))
print(type(docs[0]))
```

Conceptually, the output structure looks like this:

```text
docs
 ├── Document(page_content=..., metadata=...)
 ├── Document(page_content=..., metadata=...)
 └── Document(page_content=..., metadata=...)
```

The number of documents depends on the loader's behavior:

- A text file may produce one document.
- A PDF loader configured for page-level extraction may produce one document per page.
- A CSV loader may produce one document per row.
- A directory loader may produce documents from multiple files.

**Remember:** One source file does not necessarily mean one `Document` object.

# 5. TextLoader

## 5.1 What is TextLoader?

`TextLoader` is a straightforward loader for reading text files and converting their contents into LangChain `Document` objects.

It is useful for sources such as:

- Log files
- Plain-text notes
- Text-based transcripts
- Code snippets stored in text files
- Other textual data saved on disk

A typical text file produces one document containing its text, along with metadata identifying its source.

## 5.2 Installing the required packages

In a typical LangChain community setup:

```bash
pip install -U langchain-community
```

## 5.3 Loading a text file

Suppose we have a file called `cricket.txt`.

```python
from langchain_community.document_loaders import TextLoader

loader = TextLoader(
    file_path="cricket.txt",
    encoding="utf-8"
)

docs = loader.load()

print(docs)
```

Here:

- `file_path` specifies the file to read.
- `encoding` specifies how the text should be decoded. UTF-8 is a common choice, but the correct encoding depends on the file.
- `load()` reads the file and returns the resulting documents.

## 5.4 Inspecting the output

```python
print(type(docs))
print(len(docs))

doc = docs[0]

print(type(doc))
print(doc.page_content)
print(doc.metadata)
```

For a simple text file, the list will commonly contain one `Document`.

You can access the content and metadata separately:

```python
text = docs[0].page_content
metadata = docs[0].metadata

print(text)
print(metadata)
```

## 5.5 Sending the loaded text to an LLM

Once the content is loaded, you can use it in a LangChain chain.

The following illustrates a prompt → model → parser workflow using a chat model integration.

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = ChatOpenAI(model="gpt-4o-mini")

prompt = PromptTemplate.from_template(
    "Write a concise summary of the following text:\n\n{text}"
)

parser = StrOutputParser()

chain = prompt | model | parser

result = chain.invoke({
    "text": docs[0].page_content
})

print(result)
```

This example assumes your OpenAI credentials and required packages are configured.

Notice that the loader and the LLM chain have separate responsibilities:

1. `TextLoader` reads the source file.
2. `page_content` extracts the text from the resulting document.
3. The prompt places the text into the requested task.
4. The model generates a response.
5. `StrOutputParser` converts the model output into a string.

# 6. PyPDFLoader

## 6.1 What is PyPDFLoader?

`PyPDFLoader` is a LangChain community document loader for extracting content from PDF files.

It is particularly useful when a PDF contains selectable, text-based content.

A key behavior is page-level extraction: a PDF with 23 pages can produce 23 `Document` objects.

For example, a three-page PDF may be represented as:

<img width="713" height="187" alt="image" src="https://github.com/user-attachments/assets/035547a4-14b1-4515-b285-2d97eb2e6140" />


Each page is represented as a separate document in page-level loading. This separation is useful because an application can work with individual pages rather than treating the entire PDF as a single large text block.

## 6.2 Installation

```bash
pip install -U langchain-community pypdf
```

## 6.3 Loading a PDF

```python
from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("dl_curriculum.pdf")

docs = loader.load()

print(f"Number of documents: {len(docs)}")
```

If the PDF contains 23 extractable pages and the loader returns one document per page, the result will contain 23 documents.

## 6.4 Accessing a particular page

```python
# First page: Python index 0
first_page = docs[0]

print(first_page.page_content)
print(first_page.metadata)
```

You can also inspect another page:

```python
# Second page
second_page = docs[1]

print(second_page.page_content)
```

Python list indexing starts at zero, so `docs[0]` represents the first document.

## 6.5 Understanding PDF metadata

A page-level PDF document may contain metadata such as:

- The source file path.
- The page index.
- PDF-level information, when available.

For example:

```python
print(docs[0].metadata)
```

The exact fields depend on the loader and the PDF. A page index of `0` typically refers to the first page in zero-based indexing; do not confuse it with a human-readable page number.

## 6.6 Limitations of PyPDFLoader

`PyPDFLoader` is not a complete solution for every type of PDF.

| PDF type | Consideration |
|---|---|
| Text-based PDF | Often suitable for ordinary text extraction. |
| Scanned PDF | May require OCR because the page content is stored as images. |
| Complex layouts | Multi-column text, tables, and unusual reading order may not extract as desired. |
| Image-heavy PDF | Text extraction alone may not capture information contained in images. |

If the PDF contains scanned pages, tables, or complex visual structures, consider a loader or extraction pipeline designed for those requirements.

# 7. Other PDF Loaders and Their Use Cases

LangChain's ecosystem includes multiple PDF-loading and document-extraction integrations. The appropriate choice depends on the content you need to preserve.

| Loader or integration | When to investigate it |
|---|---|
| `PyPDFLoader` | General text extraction from PDFs. |
| `PDFPlumberLoader` | PDFs where tables and layout-aware text extraction are important. |
| `PyMuPDFLoader` | PDF processing using PyMuPDF, including use cases involving layout or richer page extraction. |
| `UnstructuredPDFLoader` | Documents that need structural or element-oriented extraction. |
| Amazon Textract integrations | Document extraction workflows involving OCR and supported document-analysis capabilities. |

These are starting points rather than guarantees. Their behavior depends on the installed integration, configuration, and document structure.

For example, OCR may be needed for a scanned PDF, while a table-heavy document may require a table-aware extraction strategy. Evaluate the extracted output before using it in a RAG pipeline.

# 8. DirectoryLoader

## 8.1 What is DirectoryLoader?

`DirectoryLoader` is used to load files from a directory instead of manually creating a loader for each file.

It is useful when a project contains a collection of documents, such as:

- A folder containing multiple PDFs.
- A directory of text files.
- A collection of files organized into subdirectories.

A directory loader can work with a specified underlying loader class. This separates directory traversal from the logic used to read each file.

## 8.2 Example: Loading multiple PDFs

Suppose a folder named `books` contains several PDF books:

```text
project/
└── books/
    ├── book1.pdf
    ├── book2.pdf
    └── book3.pdf
```

We can use `DirectoryLoader` with `PyPDFLoader`:

```python
from langchain_community.document_loaders import (
    DirectoryLoader,
    PyPDFLoader
)

loader = DirectoryLoader(
    path="books/",
    glob="*.pdf",
    loader_cls=PyPDFLoader
)

docs = loader.load()

print(f"Total documents: {len(docs)}")
```

### Understanding the parameters

| Parameter | Purpose |
|---|---|
| `path` | Directory to search. |
| `glob` | Pattern used to select files. |
| `loader_cls` | Loader class used to process each matching file. |

Because `PyPDFLoader` extracts pages, the number of resulting documents can be much larger than the number of files.

For instance, if three PDFs contain 326, 392, and 468 pages, respectively, the total number of page-level documents would be:

```text
326 + 392 + 468 = 1186
```

This assumes all pages are successfully loaded and each page produces one document.

## 8.3 Understanding glob patterns

Glob patterns help select files based on their names and locations.

| Pattern | Typical purpose |
|---|---|
| `*.pdf` | PDF files directly inside the specified directory. |
| `*.txt` | Text files directly inside the specified directory. |
| `**/*.pdf` | PDF files in the directory tree, including nested folders, when supported by the loader's glob handling. |
| `**/*.txt` | Text files in nested directories, when supported. |
| `data/*.csv` | CSV files inside the `data` subdirectory relative to the search path. |

Glob behavior can depend on the underlying file-matching implementation and loader configuration. Check the documentation for recursive matching and hidden-file handling if those details matter.

## 8.4 Inspecting documents from a directory

```python
print(len(docs))

print(docs[0].page_content)
print(docs[0].metadata)
```

Metadata can help identify which source file a particular page came from.

For large collections, loading everything at once may consume significant memory. That leads us to lazy loading.

# 9. Eager Loading vs. Lazy Loading

When processing a large collection of documents, the way you load them can affect memory consumption and when processing begins.

LangChain document loaders commonly provide two relevant interfaces:

- `load()` — loads the documents eagerly and returns a list.
- `lazy_load()` — provides a lazy iterator over documents, allowing them to be processed incrementally.

## 9.1 Eager loading with `load()`

```python
docs = loader.load()

for doc in docs:
    print(doc.metadata)
```

With eager loading, the loader returns the collection before the loop begins processing it.

For a large collection, this can mean:

- More documents are held in memory simultaneously.
- The application may wait for the loading operation to complete before processing the returned list.
- It is convenient when the entire collection is small enough to handle comfortably.

## 9.2 Lazy loading with `lazy_load()`

```python
for doc in loader.lazy_load():
    print(doc.metadata)
```

Lazy loading allows documents to be yielded incrementally rather than requiring the entire result list to be created first.

This can help with:

- Processing large collections.
- Reducing the need to hold all loaded documents in memory simultaneously.
- Starting downstream processing as documents become available.

The exact loading behavior depends on the loader implementation. Lazy loading does not guarantee that every underlying operation is performed one physical page at a time, nor does it automatically make all processing faster.

## 9.3 Comparison table

| Feature | `load()` | `lazy_load()` |
|---|---|---|
| Loading strategy | Eager | Lazy or incremental |
| Typical return | List of documents | Iterator yielding documents |
| Memory considerations | May retain the entire result list | Can avoid retaining the entire collection |
| Processing style | Process the returned collection | Process documents as they are yielded |
| Suitable for | Small or manageable collections | Large collections and streaming-style workflows |

## 9.4 Processing documents incrementally

For example, you might process each document immediately rather than collecting every document first:

```python
for doc in loader.lazy_load():
    text = doc.page_content

    # Perform an operation on the current document.
    print(text[:100])
```

This example processes each yielded document and prints only its first 100 characters.

If your downstream workflow stores all results in another list, you may lose some of the memory benefits of incremental processing. The overall pipeline must also be designed to avoid unnecessary accumulation.

## 9.5 An important implementation detail

The synchronous `lazy_load()` interface is not universally supported by every loader in every configuration. Some integrations provide asynchronous interfaces such as `alazy_load()` as well.

Check the loader's documentation and supported methods before relying on lazy or asynchronous processing.

# 10. WebBaseLoader

## 10.1 What is WebBaseLoader?

`WebBaseLoader` is a document loader that fetches web pages and extracts their textual content.

It is useful for many relatively static HTML pages, such as:

- Blog articles.
- Public documentation.
- News articles.
- Informational web pages.

The extracted text can then be used in a LangChain pipeline.

## 10.2 How does it work?

At a high level, the workflow is:

1. Fetch the page using an HTTP request.
2. Parse the returned HTML.
3. Extract textual content from the page.
4. Represent the extracted content as a LangChain `Document`.

The extracted result depends on the page's HTML structure and the loader's parsing configuration.

## 10.3 Installation

```bash
pip install -U langchain-community beautifulsoup4
```

## 10.4 Loading a web page

```python
from langchain_community.document_loaders import WebBaseLoader

loader = WebBaseLoader(
    web_path="https://example.com/"
)

docs = loader.load()

print(f"Documents: {len(docs)}")
print(docs[0].page_content)
print(docs[0].metadata)
```

For a single URL, this commonly produces one document containing the extracted page text.

## 10.5 Loading multiple URLs

You can also supply multiple URLs where supported by the loader's `web_path` parameter.

```python
loader = WebBaseLoader(
    web_path=[
        "https://example.com/page1",
        "https://example.com/page2"
    ]
)

docs = loader.load()

for doc in docs:
    print(doc.metadata)
    print(doc.page_content[:200])
```

The loader can produce a document for each successfully processed page.

## 10.6 Asking questions about the page

After loading the page, you can pass its content into a prompt.

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = ChatOpenAI(model="gpt-4o-mini")

prompt = PromptTemplate.from_template(
    """Answer the question using only the supplied text.

Text:
{text}

Question:
{question}

If the answer is not present in the text, say that the text
does not provide the information."""
)

chain = prompt | model | StrOutputParser()

answer = chain.invoke({
    "text": docs[0].page_content,
    "question": "What is the main topic of this page?"
})

print(answer)
```

This is a simple context-passing example. For large pages or collections of pages, a full RAG pipeline with splitting and retrieval is generally more suitable than placing all the text directly into a prompt.

## 10.7 Limitations of WebBaseLoader

| Limitation | Explanation |
|---|---|
| JavaScript-rendered content | Content that appears only after browser-side JavaScript execution may not be present in the fetched HTML. |
| Dynamic websites | Pages that depend on user interactions or client-side rendering may require a browser-based approach. |
| Authentication | Protected pages may require authentication and an appropriate integration. |
| Website restrictions | Requests must respect applicable access rules, terms, and rate limits. |
| HTML extraction quality | Navigation, advertisements, or unrelated text may appear in the extracted content. |

For JavaScript-heavy sites, a browser automation integration, such as a Selenium-based loader, may be more appropriate. The correct choice depends on the website and the extraction requirements.

## 11.6 Using CSV content with an LLM

You can pass a row or selected rows to an LLM for tasks such as summarization or natural-language explanations.

However, an LLM is not a substitute for a reliable numerical computation engine.

For questions such as “What is the maximum salary in this dataset?”, deterministic code or a database query is usually more appropriate than asking a language model to calculate from a large collection of rows.

For example, use Python for the calculation:

```python
import csv

with open(
    "social_network_ads.csv",
    newline="",
    encoding="utf-8"
) as file:
    reader = csv.DictReader(file)

    salaries = [
        int(row["EstimatedSalary"])
        for row in reader
    ]

print(max(salaries))
```

This computes the maximum salary directly from the CSV values.

You can then provide the computed result to an LLM if you need a natural-language explanation.

## 11.7 When is CSVLoader useful?

CSVLoader is useful when each record can reasonably be treated as a text document.

For more complex analytical tasks, consider using tools designed for structured data processing, such as:

- Python with pandas.
- SQL databases.
- Data analysis tools that support filtering, grouping, aggregation, and joins.

The best approach depends on whether the task is primarily semantic retrieval, numerical analysis, or a combination of both.

# 13. Building a Custom Document Loader

## 13.1 Why would we need a custom loader?

Sometimes your data source does not have an existing LangChain integration.

For example, your organization might store information in:

- A proprietary document format.
- An internal service with a custom API.
- A specialized file structure.
- A data source that requires custom authentication or extraction logic.

In such cases, you can implement your own loader.

The central responsibility remains the same: retrieve the source data and convert it into LangChain `Document` objects.

## 13.2 A simple custom loader

The following example demonstrates a custom loader that reads a text file and returns one document.

```python
from pathlib import Path

from langchain_core.documents import Document
from langchain_core.document_loaders import BaseLoader


class CustomTextLoader(BaseLoader):
    def __init__(self, file_path: str):
        self.file_path = file_path

    def lazy_load(self):
        path = Path(self.file_path)

        text = path.read_text(encoding="utf-8")

        yield Document(
            page_content=text,
            metadata={"source": str(path)}
        )


loader = CustomTextLoader("notes.txt")

docs = loader.load()

print(docs[0].page_content)
print(docs[0].metadata)
```

This example illustrates the core pattern:

1. Define a class that inherits from `BaseLoader`.
2. Store the information needed to access the data source.
3. Implement `lazy_load()` to yield `Document` objects.
4. Include the extracted content in `page_content`.
5. Include useful source information in `metadata`.

The base class provides the standard loader interface, including the eager `load()` method that can consume the lazy results.

## 13.3 Custom loader design considerations

When creating a loader for a real application, consider:

- **Error handling:** What happens when a file is missing or an API request fails?
- **Metadata:** Which source identifiers, timestamps, or other attributes should be preserved?
- **Memory usage:** Can the loader yield documents incrementally?
- **Authentication:** How should credentials and access permissions be handled?
- **Data quality:** How will malformed or empty records be treated?
- **Testing:** Can the loader be tested against representative files and edge cases?

A well-designed custom loader makes a new data source usable by the rest of the LangChain pipeline.

# 14. Key Takeaways and Revision

## 14.1 The most important concepts

- **Document loaders standardize data ingestion.** They bring content from different sources into a common representation that downstream LangChain components can consume.
- **A `Document` contains `page_content` and `metadata`.** The content stores the extracted text; metadata preserves useful information about its source and context.
- **The number of documents depends on the loader.** A PDF can produce one document per page, while a CSV loader commonly produces one document per row.
- **DirectoryLoader combines directory traversal with a file loader.** Use file-matching patterns to select files and `loader_cls` to specify how those files should be processed.
- **Lazy loading supports incremental processing.** It can reduce the need to retain a large document collection in memory, provided the rest of the pipeline is also designed appropriately.
- **Choose loaders according to the data source and extraction requirements.** A simple text extractor may not be suitable for scanned PDFs, complex layouts, or JavaScript-rendered web pages.
