## 1. The Big Picture

[↑ Back to Contents](#table-of-contents)

An LLM is very good at understanding a request and generating language, but language generation alone does not give it access to your database, APIs, shell, files, or external systems.

## 3. Tool Creation

[↑ Back to Contents](#table-of-contents)

A LangChain tool is essentially a callable operation plus metadata that makes the operation understandable to a model.


```python
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two integers and return their product."""
    return a * b

result = multiply.invoke({"a": 3, "b": 4})
print(result)  # 12

print(multiply.name)
print(multiply.description)
print(multiply.args)
```
The tool metadata helps the LLM understand:
- What the tool is called.
- What the tool does.
- Which arguments it expects.
- Which data types should be used.

<img width="915" height="176" alt="image" src="https://github.com/user-attachments/assets/7f9c541c-4713-467d-94b4-a3dd1bdfb4d9" />


**Why descriptions matter ?**
- The model uses the tool name, description, and argument schema as part of its decision process. Poor descriptions make correct tool selection harder.

## 4. Tool Binding

[↑ Back to Contents](#table-of-contents)

Tool binding connects the model to one or more tool definitions. In current LangChain APIs, the common pattern is `llm.bind_tools([...])`.
```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

llm_with_tools = llm.bind_tools([multiply])

ai_msg = llm_with_tools.invoke("Can you multiply 8 by 7?")
print(ai_msg.tool_calls)
```
You would typically get something similar to:

``` json
[
    {
        'name': 'multiply',
        'args': {
            'a': 8,
            'b': 7
        },
        'id': 'call_xxxxxxxxxxxxx',
        'type': 'tool_call'
    }
]
```
The exact id will be different on every request.
<img width="1008" height="276" alt="image" src="https://github.com/user-attachments/assets/37ec3d7c-c8be-409e-906c-465b192b1752" />

> Binding does not execute the tool. It only makes the tool available to the model and communicates its schema.

> **Compatibility:** Not every model/provider supports tool calling. Check the selected model's tool-calling capability before designing around `bind_tools()`.

## 5. Tool Calling

[↑ Back to Contents](#table-of-contents)

Tool calling is the model-side decision: “For this request, I want this tool, with these arguments.”

<img width="1001" height="378" alt="image" src="https://github.com/user-attachments/assets/f2713281-39d6-48cc-aafc-c3f669300d90" />

A typical tool call contains:
``` json
{
    "name": "multiply",
    "args": {
        "a": 3,
        "b": 10
    },
    "id": "unique-tool-call-id",
    "type": "tool_call"
}
```
> **Critical distinction:** *tool calling ≠ tool execution*. The model produces the request. Your program decides whether to execute that request and actually runs the function.

## 6. Tool Execution

[↑ Back to Contents](#table-of-contents)

The application reads the tool call, selects the corresponding tool, supplies the arguments, and invokes the tool.

tool_map = {
    "multiply": multiply,

for tool_call in ai_msg.tool_calls:

    tool_result = selected_tool.invoke(tool_call["args"])

## 7. The Message History

[↑ Back to Contents](#table-of-contents)

The cleanest mental model is a conversation trace. You start with a human message, receive an AI message containing the tool request, execute the tool, append a tool message, then call the model again.

| Message | Purpose |
| --- | --- |
| **HumanMessage** | User's original request. |
| **AIMessage** | Model response; may contain `tool_calls`. |
| **ToolMessage** | Execution result associated with a tool call ID. |
```python
from langchain_core.messages import HumanMessage, ToolMessage

messages = [HumanMessage(content="Multiply 3 by 10")]

ai_msg = llm_with_tools.invoke(messages)
messages.append(ai_msg)

for tool_call in ai_msg.tool_calls:
    tool = {"multiply": multiply}[tool_call["name"]]
    result = tool.invoke(tool_call["args"])
    messages.append(
        ToolMessage(
            content=str(result),
            tool_call_id=tool_call["id"],
        )
    )

final_msg = llm_with_tools.invoke(messages)
print(final_msg.content)
```

**Why send the ToolMessage back?** The model needs the actual tool result in its context so it can ground the final response in what the external system returned.

The content of messages variable would be something like below
``` json
[
    HumanMessage("Multiply 3 by 10"),

    AIMessage(
        tool_calls=[
            {
                "name": "multiply",
                "args": {"a": 3, "b": 10},
                "id": "call_xxxxx"
            }
        ]
    ),

    ToolMessage(
        content="30",
        tool_call_id="call_xxxxx"
    )
]
```
When `llm_with_tools.invoke(messages)` is called the second time, the LLM reads the entire message history. It sees the initial request, recognizes it called a tool, and reads the `ToolMessage` containing the result `"30"`.

The LLM will then synthesize this raw data into a natural language response. The printed output of `final_msg.content` will look something like this:

> "The result of 3 multiplied by 10 is 30."

## 9. Injected Tool Arguments

[↑ Back to Contents](#table-of-contents)

For a request such as “Convert 10 USD to INR,” the second tool depends on the output of the first:
- Fetch the USD-to-INR conversion rate.
- Use that live rate to convert 10 USD.

If both tools are requested in one model response, the LLM may try to fill the second tool’s conversion_rate argument using its own outdated knowledge. That can produce an incorrect result.


`InjectedToolArg` marks an argument that should be supplied by your application at execution time rather than generated by the model.
```python
from typing import Annotated
from langchain_core.tools import tool, InjectedToolArg

@tool
def convert_amount(
    amount: float,
    conversion_rate: Annotated[float, InjectedToolArg],
) -> float:
    """Convert an amount using a developer-supplied exchange rate."""
    return amount * conversion_rate
```

| Argument | Who supplies it? | Reason |
| --- | --- | --- |
| `amount` | Model | Can be inferred from the user's request. |
| `conversion_rate` | Application | Can be produced by an earlier tool and should not be invented by the model. |

With this annotation, the LLM supplies only the user-facing amount. The program injects the live conversion rate.

## 10. Worked Example: Currency Conversion

[↑ Back to Contents](#table-of-contents)

<img width="1013" height="356" alt="image" src="https://github.com/user-attachments/assets/ad104b75-6608-4c8a-8982-e5ee6f3856ed" />


The meaningful example replaces toy multiplication with a real external-data workflow: fetch an exchange rate, then calculate the converted amount.

### Tool 1 — Fetch the conversion rate
```python
import os
import requests
from langchain_core.tools import tool

@tool
def get_conversion_factor(base_currency: str, target_currency: str) -> float:
    """Fetch the current conversion rate between two currency codes."""
    api_key = os.environ["EXCHANGE_RATE_API_KEY"]
    url = (
        "https://v6.exchangerate-api.com/v6/"
        f"{api_key}/pair/{base_currency}/{target_currency}"
    )

    response = requests.get(url, timeout=10)
    response.raise_for_status()
    data = response.json()

    if data.get("result") != "success":
        raise RuntimeError(data.get("error-type", "currency API error"))

    return float(data["conversion_rate"])
```

The Pair endpoint accepts a base and target ISO 4217 currency code and returns a conversion rate. Keep credentials in environment variables rather than hard-coding them. API freshness depends on the provider/plan; “real-time” should not be assumed merely because an API is external.

### Tool 2 — Perform the conversion
```python
from typing import Annotated
from langchain_core.tools import tool, InjectedToolArg

@tool
def convert_amount(
    amount: float,
    conversion_rate: Annotated[float, InjectedToolArg],
) -> float:
    """Calculate the target-currency value from an amount and exchange rate."""
    return amount * conversion_rate
```

### Bind both tools
```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools([
    get_conversion_factor,
    convert_amount,
])
```
### Sequential Execution Pattern
``` python
import json

messages = [HumanMessage(
    content="What is the conversion rate from USD to INR, and convert 10 USD to INR."
)]

ai_message = llm_with_tools.invoke(messages)
messages.append(ai_message)

conversion_rate = None

for tool_call in ai_message.tool_calls:
    tool_name = tool_call["name"]

    if tool_name == "get_conversion_factor":
        tool_message = get_conversion_factor.invoke(tool_call)
        messages.append(tool_message)

        conversion_rate = json.loads(
            tool_message.content
        )["conversion_rate"]

    elif tool_name == "convert":
        tool_args = dict(tool_call["args"])
        tool_args["conversion_rate"] = conversion_rate

        updated_tool_call = {
            **tool_call,
            "args": tool_args
        }

        tool_message = convert.invoke(updated_tool_call)
        messages.append(tool_message)

final_message = llm_with_tools.invoke(messages)
print(final_message.content)
```

> **Important:** The manual orchestration loop teaches the mechanics. In a production agent, an agent runtime/orchestrator can perform the repeated model → tool → model cycle while still applying your application's tool permissions and policies.

> **Design principle**: Let the model decide which capability is needed, but let the application control sensitive values, execution order, validation, and permissions.

API documentation: [ExchangeRate-API Pair Conversion](https://www.exchangerate-api.com/docs/pair-conversion-requests) · [ExchangeRate-API Authentication](https://www.exchangerate-api.com/docs/authentication).

## 11. Is the Currency Converter an AI Agent?

[↑ Back to Contents](#table-of-contents)

The currency-conversion application uses tools and tool calling, but it is not fully autonomous. Much of the decision-making and execution order is written manually by the programmer.

**Not by itself.** The workflow uses tools and tool calling, but the implementation still hard-codes substantial orchestration and dependency handling.

<img width="944" height="292" alt="image" src="https://github.com/user-attachments/assets/eb2fb7b3-8d66-4189-9278-7c745fe6f896" />

A true agent would independently reason:
- The conversion rate is required.
- Call the live-rate tool.
- Inspect the returned rate.
- Call the conversion tool with the live rate.
- Present the final answer.

<img width="999" height="323" alt="image" src="https://github.com/user-attachments/assets/49ae7bb2-7663-4e60-8d79-59d8a4f0e984" />


> **Exam/interview definition:** A tool is an action capability. Tool calling is the model producing a structured request for that capability. An agent adds an autonomous control loop that can repeatedly reason about the current state, choose tools, observe results, and continue until a goal is reached or a stopping condition is met.

## 12. Interview Perspective

[↑ Back to Contents](#table-of-contents)

### Q1. What is tool binding?

Tool binding is the step where tool definitions are made available to a chat model so the model can see the tool names, descriptions, and argument schemas and can generate compatible tool calls.

### Q2. What is tool calling?

Tool calling is the model generating a structured request identifying a tool and its arguments. It is a request/decision, not the actual execution.

### Q3. Who executes the tool?

The application, orchestration layer, or agent runtime executes the tool. This separation gives the application an opportunity to validate permissions, arguments, side effects, and policy before execution.

### Q4. Why do we need ToolMessage?

It records the result of a tool execution and associates that result with the corresponding tool call so the model can use it as context for its next response.

### Q5. Why use InjectedToolArg?

Use it when an argument should be controlled by the application rather than generated by the model—for example, a value produced by an earlier tool or a trusted runtime context.

### Q6. Is every tool-calling application an agent?

No. Tool calling is a mechanism. An agent requires an autonomous loop or runtime capable of selecting and sequencing actions toward a goal rather than relying entirely on hard-coded orchestration.

## 13. Best Practices

[↑ Back to Contents](#table-of-contents)

- Write precise tool descriptions. The model uses them for tool selection.
- Use strict type annotations for every argument.
- Validate model-generated arguments before execution.
- Keep API keys and secrets outside source code.
- Set network timeouts and handle API errors.
- Do not allow unrestricted tools such as shell or database tools without safeguards.
- Log tool calls, results, failures, and execution time.
- Use injected arguments for values that must come from trusted program state.
- Require confirmation for destructive or irreversible actions.
- Return structured tool results whenever possible.
