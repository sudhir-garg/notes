## 1. What Is LangChain?

LangChain is an open-source framework designed for developing applications powered by Large Language Models (LLMs).

LLMs such as GPT-4 and Gemini are powerful on their own, but real-world applications often need to connect them to external data sources, databases, APIs, documents, and business systems. LangChain provides the scaffolding and reusable components needed to build these applications.

It helps developers create systems that combine:

- LLMs
- Prompts
- External data sources
- Document loaders
- Text splitters
- Embedding models
- Vector databases
- Retrieval systems
- Conversation memory
- Tools and APIs

---

## 2. Why Do We Need LangChain?

To understand why LangChain exists, consider a classic use case: building a **Chat with PDF** application.

Imagine that a user uploads a large textbook, such as a machine learning book, and wants to ask questions about it. The user might ask:

- Explain page 5 to me like I am a 5-year-old.
- Generate True/False questions based on the Linear Regression chapter.
- Summarize the assumptions of Linear Regression.

To build this application, the system must read the PDF, find the information relevant to the user's question, and generate a conversational answer.

Passing the entire book to the AI for every question is inefficient. A better approach is to retrieve only the most relevant sections and provide those sections to the LLM as context.

LangChain helps coordinate all of these steps.

---

## 3. High-Level System Design

When a user asks a question such as:

> What are the assumptions of linear regression?

The complete 1,000-page book should not be passed to the AI. Doing so would be computationally expensive and could exceed the model's context window. Instead, the application searches for the most relevant pages or text chunks first.

### Keyword Search vs. Semantic Search

#### Keyword Search

Keyword search looks for exact word matches. For example, it might search for the word `assumptions` throughout the book.

This approach can be inefficient because:

- The word may appear on many irrelevant pages.
- It does not understand the user's intent.
- It may miss relevant passages that use different terminology.
- It relies heavily on exact wording.

#### Semantic Search

Semantic search looks for meaning rather than exact word matches. It can understand that a question about the assumptions of linear regression is related to concepts such as:

- Linearity
- Independence
- Homoscedasticity
- Normality of residuals
- Absence of multicollinearity

The system can retrieve relevant content even when the query and the document use different words.

### How Semantic Search Is Implemented

Semantic search is commonly implemented using **vector embeddings**.

An embedding model converts text into an array of numbers called a vector. Texts with similar meanings produce vectors that are mathematically close to one another.

The process works as follows:

1. The PDF text is divided into smaller chunks.
2. Each chunk is converted into an embedding vector.
3. The user's query is also converted into an embedding vector.
4. The system compares the query vector with the document vectors.
5. The closest vectors are returned as the most relevant results.

The similarity calculation may use a metric such as cosine similarity or Euclidean distance.

## 4. The RAG Architecture

The process of retrieving relevant documents and passing them to an LLM to generate an answer is called **Retrieval-Augmented Generation (RAG)**.

RAG combines two capabilities:

- **Retrieval:** Find relevant information from an external knowledge source.
- **Generation:** Use an LLM to generate a response based on the retrieved information.

### RAG Pipeline

```text
User uploads a PDF
        ↓
PDF is stored, for example in AWS S3
        ↓
Document loader extracts the text
        ↓
Text splitter creates smaller chunks
        ↓
Embedding model converts chunks into vectors
        ↓
Vector database stores the vectors
        ↓
User asks a question
        ↓
The question is converted into a vector
        ↓
Vector database retrieves the most relevant chunks
        ↓
Question and retrieved context are sent to the LLM
        ↓
LLM generates the answer
```

### Main Components

#### 1. Storage

The uploaded PDF can be stored in a service such as AWS S3, Google Cloud Storage, or another object-storage system.

#### 2. Document Loader

A document loader extracts text and metadata from the PDF. Metadata may include information such as the file name, page number, or document identifier.

#### 3. Text Splitter

Large documents are divided into smaller chunks. Chunking makes the content easier to embed, retrieve, and pass to the LLM.

Typical chunking parameters include:

- Chunk size: approximately 1,000 characters
- Chunk overlap: approximately 100 characters

Overlap helps preserve context between adjacent chunks.

#### 4. Embedding Model

An embedding model converts each text chunk into a vector representation. Examples include OpenAI embedding models, Google embedding models, and open-source models.

#### 5. Vector Database

A vector database stores embeddings and supports similarity searches. Common options include:

- Chroma
- Pinecone
- FAISS
- Weaviate
- Milvus
- Qdrant

#### 6. Retriever

The retriever accepts a user query and returns the most relevant document chunks from the vector database.

#### 7. LLM

The LLM receives the user's question along with the retrieved context and generates the final answer.

---

## 5. The Role of the Brain: The LLM

The LLM is the reasoning and language-generation component of the system. It needs at least two important capabilities.

### Natural Language Understanding

The model should understand the user's intent even when the question is written in different languages, uses informal wording, or contains grammatical mistakes.

For example, the following questions may express a similar intent:

- What are the assumptions of linear regression?
- Tell me the conditions required for linear regression.
- Explain linear regression assumptions in simple words.

### Context-Aware Text Generation

The LLM must read the retrieved pages or chunks, identify the relevant information, and generate a clear response based on that context.

For example, it might retrieve two or three pages about linear regression and summarize the assumptions in a conversational format.

A well-designed RAG system should instruct the LLM to use the retrieved context and avoid inventing unsupported facts.

---

## 6. Where LangChain Comes In

Building this system from scratch requires connecting many moving parts:

- AWS or another storage provider
- PDF loaders
- Chunking algorithms
- Embedding models
- Vector databases
- Prompt templates
- LLM APIs
- Retrieval logic
- Conversation memory
- Error handling

LangChain acts as the glue between these components. It provides abstractions and integrations for assembling the complete workflow.

For example, LangChain can help developers:

- Load documents from files, websites, and cloud storage.
- Split documents into useful chunks.
- Generate embeddings.
- Store and retrieve vectors.
- Construct prompts.
- Connect to different LLM providers.
- Build retrieval chains and agents.
- Maintain conversational context.

One benefit is that switching providers can be simpler. For example, an application may be able to switch from OpenAI to Google Gemini or from Chroma to Pinecone by replacing the corresponding integration while keeping the rest of the application architecture largely unchanged.

## 7. Building a RAG Pipeline with LangChain

The following example demonstrates the core pipeline using Python. Package names and APIs can change between LangChain releases, so consult the current LangChain documentation when implementing this in a production application.

### Step 1: Load the PDF

```python
from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("machine_learning_book.pdf")
documents = loader.load()
```

### Step 2: Split the Text into Chunks

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=1000,
    chunk_overlap=100,
)

chunks = text_splitter.split_documents(documents)
```

### Step 3: Create Embeddings and Store Them in a Vector Database

```python
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

embeddings = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

vector_db = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    collection_name="machine-learning-book",
)
```

### Step 4: Set Up the LLM

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0,
)
```

### Step 5: Create a Retrieval Chain

```python
from langchain.chains import create_retrieval_chain
from langchain.chains.combine_documents import (
    create_stuff_documents_chain,
)
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages(
    [
        (
            "system",
            "Answer the question using only the following context:\n\n{context}",
        ),
        ("human", "{input}"),
    ]
)

document_chain = create_stuff_documents_chain(
    llm,
    prompt,
)

retriever = vector_db.as_retriever(
    search_kwargs={"k": 3}
)

retrieval_chain = create_retrieval_chain(
    retriever,
    document_chain,
)
```

### Step 6: Ask a Question

```python
query = "What are the assumptions of linear regression?"

response = retrieval_chain.invoke(
    {"input": query}
)

print(response["answer"])
```

### How the Example Works

1. `PyPDFLoader` reads the PDF and creates document objects.
2. `RecursiveCharacterTextSplitter` divides the documents into overlapping chunks.
3. `OpenAIEmbeddings` converts the chunks into vectors.
4. `Chroma` stores the vectors and provides similarity-based retrieval.
5. `ChatOpenAI` provides the language model.
6. The retriever finds the top three relevant chunks.
7. The retrieval chain passes the chunks and the question to the LLM.
8. The LLM generates the final answer.

## 8. Summary

LangChain simplifies the process of building applications around Large Language Models.

A typical document-question-answering application needs to:

1. Load a document.
2. Split the document into manageable chunks.
3. Convert the chunks into vector embeddings.
4. Store the embeddings in a vector database.
5. Retrieve the most relevant chunks for a user query.
6. Pass the query and retrieved context to an LLM.
7. Generate a useful, context-aware answer.

This architecture is known as **Retrieval-Augmented Generation**, or **RAG**.

LangChain provides the components and integrations needed to orchestrate this workflow, including:

- Document management
- Prompts
- Embeddings
- Vector stores
- Retrievers
- LLM calls
- Conversation memory
- Tool integrations

In short, LangChain acts as an orchestration framework that connects language models to external knowledge and application logic.
