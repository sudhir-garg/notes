# 1. Introduction to Vector Stores

In the previous stages of learning LangChain, we explored components such as document loaders and text splitters. These components help us bring data into our application and prepare it for further processing.

Now, we are moving toward building practical Retrieval-Augmented Generation (RAG) applications.

One of the most important components in this process is the vector store.

A vector store is a system designed to store and retrieve data represented as numerical vectors. It allows us to search for information based on semantic similarity rather than relying exclusively on exact keyword matches.

For example, consider the following two sentences:

- "The player is an excellent fast bowler."
- "He is a talented pace attack specialist."

Although these sentences use different words, their meanings are closely related. A semantic search system can identify this relationship by representing the text as embeddings and comparing their vectors.

Vector stores make it practical to store these embeddings and retrieve relevant information efficiently.

# 2. Why Do We Need Vector Stores?

To understand why vector stores are necessary, let's consider a practical example: building a movie recommendation website similar to IMDb.

| Director     | Name of the director                 |
| Actors       | Main actors in the movie             |
| Genre        | Drama, comedy, thriller, etc.        |
| Release date | Date or year of release              |
| Outcome      | Information such as hit or flop      |
| Plot         | Description of the movie's storyline |

The data could be collected through public APIs, web scraping, or other data sources.

This architecture works well for ordinary operations such as looking up a movie by its title, director, or ID.

However, suppose we want to recommend movies based on the meaning of their stories. That requirement introduces a new challenge.

## 2.2 The first approach: keyword matching

A simple recommendation system could compare movies using their metadata.

For example, it could compare:

- Director
- Actors
- Genre
- Release date

If two movies share several of these attributes, the system could consider them similar and recommend one when a user views the other.

This approach is easy to implement, but it has an important limitation: matching metadata does not necessarily mean that two movies have similar stories.

### Example 1: Similar metadata, different stories

**_Consider My Name Is Khan and Kabhi Alvida Naa Kehna._**

A keyword-based system might identify similarities such as a shared director, a shared lead actor, and overlapping genre labels.

It might therefore recommend one movie when a user watches the other, even though their central storylines differ.

### Example 2: Different metadata, similar themes

**_Consider Taare Zameen Par and A Beautiful Mind._**

These movies have different directors, casts, and release dates. A keyword-based system may therefore fail to recognize meaningful similarities between their stories.

Yet both feature central characters dealing with significant personal or cognitive challenges and explore their experiences and abilities.

We therefore need a method that compares the meaning of the movie plots, rather than simply matching their metadata.

# 3. Embeddings and Semantic Similarity

To compare movie plots based on their meaning, we need to convert text into a numerical representation.

This is where embeddings become useful.

## 3.1 What is an embedding?

An embedding is a numerical vector that represents information such as text, an image, or another type of input in a mathematical space.

For text, an embedding model processes the input and produces a vector intended to capture useful semantic and contextual information.

<img width="646" height="344" alt="image" src="https://github.com/user-attachments/assets/8d290055-b885-4213-8240-f48f39c2a265" />


The numbers are not ordinary keywords or a human-readable summary. They are learned numerical features whose relationships can be used to compare inputs.

For instance, a model might produce vectors with 512, 768, or 1,536 dimensions, depending on the embedding model. The actual dimensionality is model-dependent.

## 3.2 Comparing embeddings

Suppose we have four movie plots:

<img width="720" height="105" alt="image" src="https://github.com/user-attachments/assets/d0f52031-9ea2-4346-afbd-fab6f507c29e" />


We convert every plot into an embedding vector.

We can then compare the vectors using a similarity or distance measure.
<img width="600" height="512" alt="image" src="https://github.com/user-attachments/assets/ae3a91e4-5df5-44f9-8840-7afb064c4a75" />


If two vectors point in similar directions, their cosine similarity is high. This can indicate that the corresponding texts are semantically related.

For example, if the embedding of a movie plot is most similar to the embedding of another movie plot, the system can consider that second movie as a candidate recommendation.

## 3.3 Cosine similarity

Cosine similarity measures the cosine of the angle between two vectors.

<img width="689" height="69" alt="image" src="https://github.com/user-attachments/assets/16a7fdc4-faf6-4237-9d18-6de88c4bc9f2" />


For nonzero vectors, the result is between -1 and 1 mathematically:

- A value near 1 indicates that the vectors point in similar directions.
- A value near 0 indicates little directional similarity.
- A value near -1 indicates opposing directions.

The interpretation of these values depends on the embedding model and the data. In many practical text embedding applications, similarities are commonly nonnegative, but this is not a universal requirement.

Important: Cosine similarity and cosine distance are not the same thing. A common definition of cosine distance is \\(1-\text{cosine similarity}\\). Higher similarity indicates a closer match, while lower distance indicates a closer match.

A vector store provides the functionality needed to address these requirements through vector storage, similarity search, indexing, and associated data-management operations.

# 5. Four Core Features of Vector Stores

## 5.1 Storage

A vector store stores embeddings and can associate them with metadata and document content.

For example, a movie record might contain:

| Property  | Example                                  |
| --------- | ---------------------------------------- |
| ID        | `movie_101`                              |
| Text      | Plot of the movie                        |
| Embedding | Numerical vector generated from the plot |
| Metadata  | Title, director, genre, release year     |

The metadata helps us identify the source of a retrieved vector and apply additional constraints during search.

### In-memory versus persistent storage

| In-memory storage                                     | Persistent storage                                                                 |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Data is held in memory, such as RAM.                  | Data is saved to durable storage.                                                  |
| Often useful for experiments and temporary workloads. | Useful when data must survive application restarts.                                |
| Data may be lost when the process ends.               | Data can be loaded again after restarting, depending on the storage configuration. |

These are general storage concepts. The exact persistence behavior depends on the particular vector store and how it is configured.

## 5.2 Similarity search

A vector store can retrieve vectors that are similar to a query vector.

For example, a user searches for:

> Movies about a brilliant individual overcoming personal challenges.

The embedding model converts the query into a vector. The vector store then retrieves relevant movie records based on their vector similarity.

This is useful even when the query wording does not exactly match the wording in the movie plots.

## 5.3 Indexing

Indexing organizes vectors in a way that can make similarity search more efficient.

Without an index, a straightforward nearest-neighbor search may compare the query against every vector in the dataset.

With a suitable index, the system can narrow the search to a smaller set of candidate vectors.

We will examine this process in the next section.

## 5.4 CRUD operations

Vector stores commonly support data-management operations:

| Operation       | Meaning                                      |
| --------------- | -------------------------------------------- |
| Create / Add    | Insert new vectors and associated records    |
| Read / Retrieve | Fetch stored documents, vectors, or metadata |
| Update          | Modify existing records                      |
| Delete          | Remove records from the collection           |

The precise methods and capabilities vary by implementation, but these operations are central to maintaining a vector collection.

# 6. Indexing and Approximate Nearest Neighbor Search

Let's understand why indexing matters.

Suppose a vector store contains:

- 1,000,000 vectors
- 784 dimensions per vector
- One incoming query vector with 784 dimensions

A brute-force search compares the query vector against every stored vector.

That requires one million vector comparisons, with each comparison involving operations across 784 dimensions. This can become expensive as the dataset and query volume grow.

## 6.1 A simple clustering-based illustration

One way to understand indexing is to imagine dividing the million vectors into 10 clusters.

<img width="1044" height="590" alt="image" src="https://github.com/user-attachments/assets/27675cc9-7389-4015-97ae-70af71128583" />


If the system selects one cluster containing approximately 100,000 vectors, it could compare the query with those 100,000 vectors rather than all one million.

In this simplified illustration, that is approximately 100,010 comparisons: 10 centroid comparisons plus 100,000 comparisons within the selected cluster.

This example demonstrates the potential benefit of narrowing the candidate search space.

Important qualification: This is an illustrative indexing strategy, not a guarantee that the exact nearest neighbor will always be found. A query's nearest vector may be in another cluster. Practical systems may search multiple clusters or use other indexing algorithms to balance speed, memory use, and recall.

## 6.2 Approximate Nearest Neighbor (ANN) search

Approximate Nearest Neighbor search is a family of methods designed to find vectors that are very close to a query without necessarily evaluating every stored vector.

ANN methods can reduce query latency substantially for large datasets, often by trading some search accuracy or recall for speed.

Examples of indexing approaches used in vector search systems include:

- Graph-based indexes, such as HNSW.
- Inverted-file indexes, such as IVF.
- Quantization-based methods, such as product quantization.

The appropriate method depends on the dataset size, available memory, latency requirements, and accuracy requirements.

# 8. Vector Store vs. Vector Database

The terms vector store and vector database are sometimes used interchangeably. However, a useful conceptual distinction can be made between them.

## 8.1 Vector store

A vector store is a system or component focused on storing vectors and retrieving them through similarity search.

It may be a lightweight library, an embedded storage system, or a service. It does not necessarily provide every feature associated with a full database management system.

## 8.2 Vector database

A vector database is a database system designed to store, index, and query vector data. Depending on the product, it may also provide capabilities such as:

- Persistent storage and durability.
- Distributed architecture and horizontal scaling.
- Backup and restore.
- Concurrent access and transaction-related guarantees.
- Metadata filtering and richer query functionality.
- Authentication, authorization, and access control.

These capabilities are implementation-dependent; not every vector database provides all of them.

## 8.3 Comparison

| Feature                     | Vector store (general concept)                                | Vector database (general concept)                            |
| --------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------ |
| Vector storage              | Core functionality                                            | Core functionality                                           |
| Similarity search           | Core functionality                                            | Core functionality                                           |
| Indexing                    | Common                                                        | Common                                                       |
| Metadata handling           | Often supported                                               | Commonly supported, sometimes with richer query capabilities |
| Persistence                 | Depends on implementation                                     | Typically a central capability                               |
| Distributed scaling         | Not necessarily available                                     | May be available                                             |
| Security and access control | Depends on implementation                                     | Often provided in production-oriented systems                |
| Typical use                 | Lightweight applications, prototypes, or retrieval components | Persistent, managed, or larger-scale vector workloads        |

The distinction is useful, but it is not a universal industry standard. Some products described as vector stores also have database features, and some vector databases expose lightweight library interfaces.

# 14. Performing Similarity Search

Now comes the most important operation: retrieving documents based on semantic similarity.

LangChain provides the `similarity_search()` method.

## 14.1 Basic similarity search

Suppose we want to find which players are bowlers.

``` python
query = "Who among these players is a bowler?"

results = vector_store.similarity_search(
    query=query,
    k=1,
)

for doc in results:
    print(doc.page_content)
    print(doc.metadata)
```

### Understanding the parameters

| Parameter | Meaning                                        |
| --------- | ---------------------------------------------- |
| `query`   | The text query used to find relevant documents |
| `k`       | The maximum number of documents to return      |

The vector store embeds the query using the configured embedding model and searches for similar stored vectors.

With `k=1`, it requests one result. With `k=2`, it requests up to two results.

For our sample data, Jasprit Bumrah is a plausible top result for the bowler query, while Ravindra Jadeja may also be retrieved because his description mentions spin bowling.

The exact ranking depends on the embedding model, stored content, and search implementation. Semantic search does not guarantee that the result will always match a particular human interpretation.

## 14.2 Retrieve the top two results

``` python
results = vector_store.similarity_search(
    query="Who among these players is a bowler?",
    k=2,
)

for doc in results:
    print(doc.page_content)
```

The `k` parameter controls the number of requested matches, not a minimum similarity threshold.

# 15. Similarity Search with Scores

Sometimes, retrieving documents is not enough. We may also want to inspect the score associated with each result.

LangChain provides `similarity_search_with_score()`.

``` python
results = vector_store.similarity_search_with_score(
    query="Who among these players is a bowler?",
    k=2,
)

for doc, score in results:
    print("Document:", doc.page_content)
    print("Score:", score)
```

## 15.1 Interpreting the score

For the standard Chroma distance-based scoring returned by this method, the score represents a distance, not a similarity value.

- Lower distance generally indicates a closer match.
- Higher distance generally indicates a less close match.

The exact interpretation depends on the configured distance metric. Do not assume that all vector stores return scores on the same scale or use the same direction.

# 16. Metadata Filtering

Vector stores can also filter records using metadata.

Suppose we want to retrieve only players belonging to Chennai Super Kings.

We can use the `filter` argument in a similarity search:

```
results = vector_store.similarity_search(
    query="Who is a cricket player?",
    k=5,
    filter={"team": "Chennai Super Kings"},
)

for doc in results:
    print(doc.page_content)
    print(doc.metadata)
```

This constrains the search to documents whose metadata matches the specified team.

In our sample dataset, the matching records are MS Dhoni and Ravindra Jadeja.

## 16.1 Filtering versus semantic search

These two mechanisms serve different purposes:

| Semantic search                                 | Metadata filtering                                        |
| ----------------------------------------------- | --------------------------------------------------------- |
| Finds records based on vector similarity.       | Restricts records using structured attributes.            |
| Uses the embedding representation of the query. | Uses metadata conditions such as team, category, or date. |
| Helps find conceptually relevant content.       | Helps enforce explicit constraints.                       |

They can be combined to retrieve semantically relevant documents from a subset of the collection.

For example, an application could search for bowling-related documents while restricting the results to a particular team.

# 17. Updating Existing Documents

Suppose we want to update Virat Kohli's description.

We can create a replacement document and use the existing record ID.

``` python
updated_doc = Document(
    page_content=(
        "Virat Kohli, the former captain of Royal "
        "Challengers Bengaluru, is known for his "
        "aggressive leadership and consistency."
    ),
    metadata={"team": "Royal Challengers Bengaluru"},
)
```

If the original ID is stored in `virat_id`, we can update the record:

``` python
vector_store.update_document(
    document_id=virat_id,
    document=updated_doc,
)
```

The `update_document()` method is available in the LangChain vector store interface for integrations that support it.

When the document content changes, the vector store generally needs an embedding corresponding to the updated text. The integration's update implementation handles this according to its supported behavior.

You should preserve the correct record ID so that you update the intended document rather than accidentally creating a separate record.

# 18. Deleting Documents

To delete a document, use its ID.

``` python
vector_store.delete(
    ids=[virat_id]
)
```

The ID must refer to the record you want to remove.

You can delete multiple records by supplying multiple IDs:

``` python
vector_store.delete(
    ids=["player_001", "player_002"]
)
```

The exact deletion semantics depend on the backend, but the intended operation is to remove the specified records from the vector store.

### Verify the remaining records

``` python
result = vector_store._collection.get(
    include=["documents", "metadatas"]
)

print(result)
```

This allows you to inspect the records that remain in the collection. As with the earlier inspection example, `_collection` is an integration-specific internal attribute.

## 19.4 Final takeaway

Vector stores are an essential building block for applications that need semantic retrieval. Embedding models represent data as vectors, while vector stores organize those representations and provide mechanisms to search and retrieve relevant records.

LangChain makes it easier to work with different vector store integrations through a common interface. Chroma provides a practical environment for learning these concepts and implementing the fundamental operations.

With document loading, text splitting, embeddings, and vector storage understood, we have established the core data-retrieval foundation needed to move toward building a complete RAG application.
