2. Structured Streaming Fundamentals

What is streaming?

Streaming is the continuous or incremental processing of data as it becomes available rather than waiting for a complete bounded dataset. A utility meter may produce thousands or millions of readings while the pipeline remains active.

Batch vs streaming

DimensionBatchStreaming
InputBounded datasetUnbounded/incrementally arriving dataset
ExecutionRun → finishLong-running or repeatedly triggered
LatencyMinutes/hours/daysSeconds/minutes depending on SLA
StateOften recomputed per jobMay be retained between triggers
Failure recoveryRerun jobCheckpointed offsets/state allow continuation

Micro-batch processing

Structured Streaming is primarily executed as incremental micro-batches: the engine identifies new source data, processes it as a batch, commits progress, and repeats. This gives a streaming programming model while retaining Spark SQL/DataFrame semantics.

Continuous processing

Apache Spark also has a continuous-processing execution mode with lower-latency goals but different operator/support semantics. Do not treat it as synonymous with “a stream.” On current Databricks, operational low-latency deployment choices are also affected by the compute and pipeline mode you choose; for example, Databricks documents a distinct real-time mode and does not support the OSS continuous trigger on serverless compute.

Structured Streaming vs legacy Spark Streaming

Legacy Spark Streaming (DStreams)Structured Streaming
RDD/DStream-oriented APIDataFrame/SQL-oriented API
Lower-level programming modelDeclarative query model
Older architectureModern Spark streaming API
Less natural integration with SQL optimizationsUses Spark SQL engine and Catalyst/Tungsten execution foundations

Streaming DataFrame

A streaming DataFrame has the same relational abstraction as a batch DataFrame, but represents data that will arrive over time. spark.readStream creates a streaming input; transformations remain lazy until a writeStream query is started.

Source → transformation → sink

The core mental model is simple: Source supplies records; transformations parse, filter, join, aggregate and enrich them; sink persists or forwards the result. A streaming query is the running execution of that plan.

4. Kafka as the Streaming Source

Kafka is a distributed, partitioned commit log. Spark integrates with Kafka as a Structured Streaming source using the kafka format. Spark's current Kafka integration requires Kafka 0.10 or higher.

Topic

Logical stream name, e.g. meter_usage.

Partition

Ordered append-only log within a topic. Partitioning provides parallelism.

Offset

Monotonic position within a partition. Spark uses offsets to define progress.

Producer

Application that publishes usage events.

Consumer group

Kafka-side mechanism for distributing partitions among consumers. Spark's source maintains its own streaming progress through checkpoints.

Key / value

Key can drive partitioning; value carries the event payload. Preserve useful metadata for troubleshooting.

Kafka partitions, offsets and Spark micro-batches

Kafka source options

OptionPurposeImportant behavior
subscribeRead one or more named topicsUse when the topic set is explicitly known.
subscribePatternSubscribe using a topic-name regexUseful for controlled topic families; ensure new topics are intentionally included.
startingOffsetsStarting position for a new queryearliest, latest, or explicit offsets. On restart, the checkpoint takes precedence.
endingOffsetsBatch/incremental bounded endpointRelevant to bounded reads; not the normal way to cap a continuously running query.
failOnDataLossControls behavior when Spark detects possible lost/out-of-range Kafka dataDefault is true in the documented Kafka integration. Disabling it can hide real data-loss conditions.
maxOffsetsPerTriggerRate-limit input per triggerUseful for backpressure/cost control and catch-up management.
kafka_df = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", kafka_bootstrap)
    .option("subscribe", "meter_usage")
    .option("startingOffsets", "latest")
    .option("failOnDataLoss", "true")
    .load())

raw = kafka_df.selectExpr(
    "CAST(key AS STRING) AS kafka_key",
    "CAST(value AS STRING) AS raw_json",
    "topic",
    "partition",
    "offset",
    "timestamp AS kafka_timestamp"
)

Current Spark documentation notes that startingOffsets applies when a new streaming query is started; a resumed query uses its checkpointed progress. Newly discovered Kafka partitions start from the earliest available offset in the documented behavior.

Do not confuse Kafka offset progress with business-event deduplication. Structured Streaming can process source offsets exactly once at the query level under supported sink/query semantics, but it does not magically remove duplicate business events already present in Kafka. Use an event identifier and explicit deduplication.

5. Designing the Meter Usage Event

Example Kafka JSON

{
  "event_id": "MU-20260926-000001",
  "meter_id": "MTR-100045",
  "account_id": "ACC-700145",
  "service_location_id": "SL-90122",
  "meter_timestamp": "2026-09-26T10:05:00Z",
  "usage_kwh": 2.731,
  "reading_type": "INTERVAL",
  "ingestion_timestamp": "2026-09-26T10:05:02Z"
}

Explicit Spark schema

from pyspark.sql.types import (
    StructType, StructField, StringType, DoubleType, TimestampType
)

meter_schema = StructType([
    StructField("event_id", StringType(), False),
    StructField("meter_id", StringType(), False),
    StructField("account_id", StringType(), False),
    StructField("service_location_id", StringType(), False),
    StructField("meter_timestamp", TimestampType(), False),
    StructField("usage_kwh", DoubleType(), False),
    StructField("reading_type", StringType(), True),
    StructField("ingestion_timestamp", TimestampType(), True),
])

parsed = (raw
    .withColumn("payload", from_json("raw_json", meter_schema))
    .select("*", "payload.*")
    .drop("payload"))

Why explicit schemas?

  • Streaming schema inference can be brittle when producers evolve payloads.
  • Types become deterministic across batches.
  • Timestamp and numeric handling is explicit.
  • Unexpected fields can be detected and routed rather than silently becoming a new interpretation.
  • Schema review becomes part of deployment/change management.

Malformed records

from_json returns null for malformed JSON when used in its standard permissive pattern. Production pipelines should identify records where the parsed struct is null and quarantine the raw payload together with Kafka metadata.

from pyspark.sql.functions import col, from_json, current_timestamp

parsed = raw.withColumn("payload", from_json("raw_json", meter_schema))

bad = (parsed
    .filter(col("payload").isNull())
    .select("raw_json", "topic", "partition", "offset", "kafka_timestamp")
    .withColumn("quarantine_ts", current_timestamp()))

good = parsed.filter(col("payload").isNotNull()).select("*", "payload.*").drop("payload")

Relationships

account_dim = spark.read.table("utility_ref.account")
billing_dim = spark.read.table("utility_ref.billing")
location_dim = spark.read.table("utility_ref.service_location")
Freshness matters. A stream-static join uses the current static snapshot available to the query. If a dimension is corrected after a fact has already been processed, the old enriched Silver row is not automatically rewritten by a normal stream-static join. If historical re-enrichment is required, design a replay/backfill or a point-in-time dimension strategy.

7. The Critical Pattern: Kafka Facts + S3/Delta Dimensions

Stream-static enrichment of meter usage with current dimension snapshots

Stream-static join

A stream-static join combines an incremental streaming DataFrame with a batch/static DataFrame. Databricks describes this as a stateless join: each micro-batch's new records are joined with the current static table version. No watermark is required merely because the join is stream-static.

enriched = (meter_stream
    .join(account_dim, "account_id", "left")
    .join(billing_dim, "account_id", "left")
    .join(location_dim, "service_location_id", "left"))

Why LEFT JOIN is often safer

An inner join drops usage events when a dimension record is missing. That can silently reduce operational totals. A left join preserves the fact and makes the missing enrichment observable through null dimension attributes or a quality flag.

from pyspark.sql.functions import when, col

silver = (enriched
    .withColumn(
        "dimension_status",
        when(col("account_id").isNull(), "INVALID_ACCOUNT")
        .when(col("billing_id").isNull(), "MISSING_BILLING")
        .when(col("service_location_id").isNull(), "MISSING_LOCATION")
        .otherwise("ENRICHED")
    ))

Broadcast joins

Broadcasting can be effective when a dimension is small enough to replicate to executors. It avoids a full shuffle of the streaming side. Do not broadcast a “dimension” merely because its business role is a dimension; a dimension can still be tens or hundreds of gigabytes.

from pyspark.sql.functions import broadcast

small_account_dim = broadcast(account_dim)
enriched = meter_stream.join(small_account_dim, "account_id", "left")
Production rule: choose broadcast based on measured executor memory, dimension size, join cardinality and cluster configuration—not on a hard-coded “dimensions are always broadcast” rule.

Late-arriving dimension data

Suppose a meter event references ACC-900, but the Account dimension extract does not contain that account until 10 minutes later. A normal stream-static join processes the event against the snapshot available at that time. It does not automatically revisit the event. Strategies include: dimension refresh before stream processing, reprocessing/backfill, maintaining a Delta dimension with a reliable update process, or designing a separate reconciliation job.

8. Event Time, Processing Time and Watermarks

Event-time watermarking for late meter readings
Time conceptMeaningMeter example
Event timeWhen the business event actually occurredMeter reading timestamp = 10:05
Ingestion timeWhen your ingestion system accepted/recorded itKafka ingestion metadata = 10:05:02
Processing timeWhen Spark processed the recordExecutor processes it at 10:12

If the event occurred at 10:05 but arrives at 10:12, using processing time would place it in the wrong business interval. Event-time windows preserve the meaning of the measurement.

meter_stream = meter_stream.withWatermark("meter_timestamp", "10 minutes")

A watermark establishes a lateness threshold for stateful processing. Spark tracks progress in event time and can evict old state. A watermark that is too short can cause valid late data to be excluded from stateful results; one that is too long retains more state and can increase latency/resource usage. Databricks explicitly recommends tuning watermarks to the late-data behavior your workload must support.

Watermark is not a timer that delays every record. It is a progress/cleanup boundary used by stateful operations. Do not explain it as “Spark waits exactly 10 minutes and then processes the record.”

9. Windowing

Windowing converts an unbounded event stream into bounded time buckets for analytics.

WindowDefinitionMeter use case
TumblingFixed, non-overlapping intervalsHourly consumption
SlidingFixed duration with a smaller slide15-minute rolling usage every 5 minutes
SessionActivity-based periods separated by inactivity gapsLess common for interval meters; useful for user/device activity patterns.

Tumbling: hourly consumption

from pyspark.sql.functions import window, sum as _sum

hourly = (meter_stream
    .withWatermark("meter_timestamp", "30 minutes")
    .groupBy(
        window("meter_timestamp", "1 hour"),
        "meter_id",
        "account_id"
    )
    .agg(_sum("usage_kwh").alias("usage_kwh")))

Sliding: 15-minute window every 5 minutes

rolling = (meter_stream
    .withWatermark("meter_timestamp", "30 minutes")
    .groupBy(
        window("meter_timestamp", "15 minutes", "5 minutes"),
        "meter_id"
    )
    .agg(_sum("usage_kwh").alias("usage_kwh")))

State implications

Every active group/window can require state. More dimensions in the grouping key, longer windows and longer watermarks generally increase the amount of state that must be retained.

10. Stateful Streaming

Stateful operators remember information across micro-batches. Stateless operators can process a record independently of prior records.

StatelessStateful
select, cast, filter, simple withColumnwindowed aggregation, deduplication, stream-stream joins, stateful custom logic
Limited cross-batch memoryRequires state store and checkpointed state
Usually simpler recoveryState size and cleanup must be managed

Hourly total consumption

hourly_usage = (meter_stream
    .withWatermark("meter_timestamp", "30 minutes")
    .groupBy(
        window("meter_timestamp", "1 hour"),
        "meter_id",
        "account_id"
    )
    .agg(_sum("usage_kwh").alias("total_usage_kwh")))

The state store keeps partial aggregates so Spark can update the result as more events arrive. Watermarks provide a mechanism to eventually clean up old state. Databricks documents watermarks as a key technique for preventing unbounded state growth in aggregations, deduplication and other stateful operations. citeturn1search0

11. Delivery Semantics and “Exactly Once”

SemanticMeaningRisk
At-most-onceRecords may be lost, but are not intentionally retried into duplicatesData loss
At-least-onceRecords are retried until acknowledged; duplicates may occurDuplicates
Exactly-onceUnder a defined source/query/sink contract, each input effect is reflected once in the transactional resultRequires end-to-end conditions; not a blanket guarantee across arbitrary external side effects

Structured Streaming checkpointing records source progress and committed micro-batches; with a compatible transactional sink such as Delta Lake, this supports exactly-once processing semantics for the query. Databricks documents checkpoints as tracking offsets, commits and state, while Delta provides transactional table semantics.

Exactly-once does not mean “Kafka can never contain duplicate business events.” If a producer publishes the same event twice with different Kafka offsets, Spark sees two source records. Business-level deduplication is still your responsibility.

Also be careful with arbitrary external sinks or side effects in foreachBatch: the application must make its writes idempotent or transactionally coordinated if it needs equivalent end-to-end semantics.

12. Checkpointing

Checkpoint-based recovery

Databricks documents checkpoint directories as containing source offsets, commit information and state metadata/state for stateful queries. A restarted query can use that information to continue from recorded progress. Deleting the checkpoint or changing to a new checkpoint path causes the next run to start a new query history.

Typical checkpoint path

checkpoint_path = "s3://<governed-bucket>/checkpoints/meter_usage_silver/"

query = (silver_stream.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .toTable("utility.silver.meter_usage"))

With Unity Catalog, Databricks states that Structured Streaming checkpoints must use paths in Unity Catalog-managed external locations. citeturn0search0

Never share one checkpoint across unrelated queries. The checkpoint belongs to a specific streaming query definition and source/sink history. Use a stable, dedicated checkpoint directory per logical query.

Default / 0-second processing timeContinuously process available data with minimal scheduling delayUseful on supported classic compute for low-latency micro-batches, but increases checking/storage overhead.
processingTime="10 seconds"Bound latency and reduce trigger overheadGood general-purpose tuning knob.

# Always-on classic-compute style
query = (silver_stream.writeStream
    .format("delta")
    .outputMode("append")
    .trigger(processingTime="10 seconds")
    .option("checkpointLocation", checkpoint_path)
    .toTable("utility.silver.meter_usage"))

# Bounded incremental processing
query = (silver_stream.writeStream
    .format("delta")
    .outputMode("append")
    .trigger(availableNow=True)
    .option("checkpointLocation", checkpoint_path)
    .toTable("utility.silver.meter_usage"))

Current Databricks documentation recommends AvailableNow for incremental batch-style processing and documents trigger differences by compute mode. Serverless Structured Streaming currently supports AvailableNow and the deprecated Once, but not the default/time-based triggers.

15. Delta Lake as the Streaming Sink

Delta Lake is a natural sink for Databricks Structured Streaming because it provides transactional table semantics, schema controls and lakehouse integration. Databricks documents Delta as a streaming source and sink and highlights reliability and performance benefits for streaming workloads.

query = (enriched_stream.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "s3://<bucket>/checkpoints/silver_meter_usage")
    .toTable("utility.silver.meter_usage"))

Schema enforcement vs schema evolution

Schema enforcement protects a table from incompatible writes. Schema evolution is an explicit decision that allows compatible changes under supported configurations. Do not enable evolution blindly; treat producer schema changes as contract changes.

MERGE

MERGE is useful for batch-style upserts and CDC patterns. A streaming query should not automatically use a per-row MERGE pattern simply because a table is transactional. If you need custom micro-batch upserts, foreachBatch plus a carefully designed idempotent MERGE is a common pattern, but it increases operational complexity.

OPTIMIZE, file sizes and liquid clustering

Low-latency streaming can generate many small files. Databricks provides table optimization capabilities to improve file layout. Liquid clustering can be useful for tables where access patterns and data distribution make traditional partitioning less effective. Choose layout based on workload characteristics rather than applying every optimization by default.

Do not confuse streaming partitioning with Delta table partitioning. Kafka partitions determine source parallelism. Spark partitions determine execution parallelism. Delta partitioning/clustering determines storage layout. They solve different problems.

18. Deduplication

Duplicate Kafka records can arise from producer retries, upstream replay, application bugs, connector behavior or at-least-once delivery patterns. Use a stable business identifier such as event_id.

# For events whose duplicate arrival is bounded by the watermark horizon
clean = (meter_stream
    .withWatermark("meter_timestamp", "2 hours")
    .dropDuplicates(["event_id"]))

For cases where duplicate records can have different timestamps/arrival metadata, Databricks Runtime 13.3 LTS+ provides dropDuplicatesWithinWatermark. It requires a watermark and guarantees deduplication within the configured watermark horizon.

clean = (meter_stream
    .withWatermark("meter_timestamp", "2 hours")
    .dropDuplicatesWithinWatermark(["event_id"]))
Deduplication horizon is a business decision. If duplicates can appear 12 hours after the original event, a 2-hour watermark cannot guarantee removal of that late duplicate.

  • Missing-dimension rate spikes.
  • Query is not active when it should be.

23. End-to-End Databricks Implementation

End-to-end utility meter data product

Step 1 — Configuration

from pyspark.sql import functions as F
from pyspark.sql.types import *

KAFKA_BOOTSTRAP = "broker1:9092,broker2:9092"
KAFKA_TOPIC = "meter_usage"
CHECKPOINT_BRONZE = "s3://<bucket>/checkpoints/bronze/meter_usage"
CHECKPOINT_SILVER = "s3://<bucket>/checkpoints/silver/meter_usage"
CHECKPOINT_GOLD = "s3://<bucket>/checkpoints/gold/hourly_usage"
SecretsDo not hard-code Kafka passwords, IAM secrets or tokens. Use Databricks secret-backed configuration, Unity Catalog governed access, workload identity/roles and the appropriate Kafka authentication mechanism.

Step 2 — Kafka Bronze

kafka_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", KAFKA_BOOTSTRAP)
    .option("subscribe", KAFKA_TOPIC)
    .option("startingOffsets", "latest")
    .option("failOnDataLoss", "true")
    .option("maxOffsetsPerTrigger", 200000)
    .load())

bronze = (kafka_raw
    .select(
        F.col("key").cast("string").alias("kafka_key"),
        F.col("value").cast("string").alias("raw_json"),
        "topic", "partition", "offset",
        F.col("timestamp").alias("kafka_timestamp")
    )
    .withColumn("ingested_at", F.current_timestamp()))

bronze_query = (bronze.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", CHECKPOINT_BRONZE)
    .toTable("utility.bronze.meter_usage_raw"))

Expected behavior: every accepted Kafka record is landed with raw payload and Kafka metadata. This layer is intentionally close to source so that downstream parsing rules can be changed without needing the producer to replay immediately.

Step 3 — Parse and validate

meter_schema = StructType([
    StructField("event_id", StringType(), False),
    StructField("meter_id", StringType(), False),
    StructField("account_id", StringType(), False),
    StructField("service_location_id", StringType(), False),
    StructField("meter_timestamp", TimestampType(), False),
    StructField("usage_kwh", DoubleType(), False),
    StructField("reading_type", StringType(), True),
    StructField("ingestion_timestamp", TimestampType(), True),
])

parsed = (bronze
    .withColumn("payload", F.from_json("raw_json", meter_schema)))

valid = (parsed
    .filter(F.col("payload").isNotNull())
    .select("*", "payload.*")
    .drop("payload")
    .filter(F.col("event_id").isNotNull())
    .filter(F.col("meter_id").isNotNull())
    .filter(F.col("account_id").isNotNull())
    .filter(F.col("service_location_id").isNotNull())
    .filter(F.col("meter_timestamp").isNotNull())
    .filter(F.col("usage_kwh") >= 0))

Step 4 — Deduplicate with event time

deduped = (valid
    .withWatermark("meter_timestamp", "2 hours")
    .dropDuplicatesWithinWatermark(["event_id"]))

Step 5 — Read dimensions

account_dim = spark.read.table("utility_ref.account")
billing_dim = spark.read.table("utility_ref.billing")
location_dim = spark.read.table("utility_ref.service_location")

Step 6 — Enrich

silver = (deduped
    .join(account_dim, "account_id", "left")
    .join(billing_dim, "account_id", "left")
    .join(location_dim, "service_location_id", "left")
    .withColumn(
        "dimension_status",
        F.when(F.col("billing_id").isNull(), "MISSING_BILLING")
         .when(F.col("region").isNull(), "MISSING_LOCATION")
         .otherwise("ENRICHED")
    ))

Step 7 — Write Silver

silver_query = (silver.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", CHECKPOINT_SILVER)
    .toTable("utility.silver.meter_usage"))

Step 8 — Hourly Gold aggregation

hourly = (silver
    .withWatermark("meter_timestamp", "30 minutes")
    .groupBy(
        F.window("meter_timestamp", "1 hour"),
        "account_id",
        "meter_id",
        "region"
    )
    .agg(
        F.sum("usage_kwh").alias("total_usage_kwh"),
        F.count("event_id").alias("reading_count")
    )
    .select(
        "account_id", "meter_id", "region",
        F.col("window.start").alias("window_start"),
        F.col("window.end").alias("window_end"),
        "total_usage_kwh", "reading_count"
    ))

gold_query = (hourly.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", CHECKPOINT_GOLD)
    .toTable("utility.gold.hourly_meter_usage"))
Production patternKeep the Bronze, Silver and Gold checkpoints separate. Treat each layer as a separately observable query so failures and reprocessing boundaries are explicit.

Important caveat: dimension history

The code above joins to the current dimension snapshot. If billing tariff must reflect the tariff effective at meter_timestamp, use effective-date logic or a point-in-time dimension model. For example, the conceptual condition is effective_from <= meter_timestamp AND (effective_to IS NULL OR meter_timestamp < effective_to). This becomes a data-modeling requirement, not merely a Spark syntax issue.

25. Common Spark Structured Streaming Mistakes

MistakeWhy it is a problemSafer pattern
No checkpointRestart loses query progress/state.Use a durable, dedicated checkpoint.
Deleting checkpoints to “fix” a streamCreates a new query history and may replay or skip data depending on source configuration.Understand the failure first; repair/replay deliberately.
Watermark too shortLate valid events can be excluded and state can be cleaned too early.Base lateness on measured source behavior and SLA.
Watermark too longRetains state longer and can increase resource use.Use the minimum safe horizon.
Broadcasting a huge dimensionExecutor memory pressure/OOM.Measure size; use optimized join strategy.
Ignoring Kafka partitionsLimits source parallelism or creates unnecessary overhead.Design partitions around throughput and ordering keys.
Using processing time for business windowsLate/out-of-order events land in wrong intervals.Use event time for event-time business metrics.
Unbounded stateState store grows indefinitely.Use watermarks, bounded windows and controlled cardinality.
Small-file explosionSlow reads and metadata overhead.Control trigger/file size and optimize table layout.
Collecting streaming data to driverDriver memory bottleneck; breaks distributed design.Aggregate/filter distributed and persist results.
Blind schema inferenceProducer drift can change interpretation.Explicit schemas and contract management.
Assuming stream-static join is point-in-timeCurrent dimension values may not represent historical state.Use SCD/effective-date logic where required.

26. Spark Streaming Interview Preparation

Beginner

  1. What is Structured Streaming? A Spark SQL/DataFrame-based streaming engine for incremental processing of continuously arriving data.
  2. What is a streaming DataFrame? A DataFrame representing an unbounded/incremental input rather than a finite batch.
  3. What is a micro-batch? A bounded set of newly available records processed as one trigger execution.
  4. What is a checkpoint? Durable query-progress and state information used for recovery.
  5. What is a watermark? An event-time progress threshold used to control late-data handling and state cleanup in supported stateful operations.

Intermediate

  1. How does Spark read Kafka? It discovers topic partitions and offsets, processes new offsets incrementally, and records progress in the streaming checkpoint.
  2. What is a stream-static join? A streaming DataFrame joined to a batch/static DataFrame, typically without stateful stream-stream join semantics.
  3. Why use event time? Because business events can arrive late/out of order; event time preserves when the measurement actually happened.
  4. Why use watermarking? To bound how long state is retained and define lateness behavior.
  5. Append vs Update? Append emits newly finalized rows; Update emits changed result rows; exact support depends on query semantics.
  6. What does maxOffsetsPerTrigger do? It caps the amount of Kafka offset work taken in one trigger, helping control processing rate.

Advanced

  1. Does exactly-once mean duplicates cannot exist? No. Query/sink exactly-once semantics are not business-event deduplication. Duplicate source events still require deduplication.
  2. What happens if a dimension changes after a stream has processed a fact? A normal stream-static join does not automatically rewrite the historical enriched result. Reprocessing or point-in-time modeling may be required.
  3. How do you control state growth? Watermarks, bounded windows, bounded deduplication horizons, appropriate grouping cardinality and monitoring.
  4. Why can Kafka lag increase even when executors are busy? Processing may be bottlenecked by shuffle, joins, state, skew, sink I/O, or too-small trigger capacity rather than raw CPU.
  5. How would you troubleshoot increasing batch duration? Compare input rate vs processed rate, inspect query progress, identify slow stages/shuffles, check state growth, Kafka lag, dimension join cost and Delta write/file behavior.
  6. When would you use foreachBatch? When each micro-batch needs custom batch logic or a sink operation such as an idempotent MERGE that is not directly expressible as a normal streaming sink.
  7. What is the difference between Kafka partitions and Spark partitions? Kafka partitions are source-log partitions and the unit of Kafka ordering/parallelism; Spark partitions are distributed execution partitions and can change through transformations.

27. Architecture Decisions: Problem → Options → Trade-offs

Decision 1: Where should raw Kafka events land?

OptionTrade-off
Directly parse into SilverFewer layers, but weaker replay/audit boundary.
Kafka → Bronze → SilverMore storage and jobs, but stronger replayability, auditability and schema-change isolation.

Pattern for this guide: Bronze first for important utility facts.

Decision 2: S3 files vs Delta tables for dimensions

OptionTrade-off
Raw CSV/JSON on S3Simple source integration; weaker transactional semantics and potentially expensive scans.
ParquetEfficient analytical reads; still requires external process for transactional updates.
DeltaACID, versioning, schema enforcement and table-level integration.

Pattern for production: keep source extracts if required, but curate dimensions into governed Delta tables when the platform supports it.

Decision 3: Inner vs left dimension join

Inner join enforces “only fully enriched records are valid,” but can silently lose facts. Left join preserves facts and exposes missing-dimension conditions. For operational metering, preserving the fact plus explicit enrichment status is often easier to reconcile.

Decision 4: Trigger strategy

Choose from business SLA first. If the pipeline is a continuously running operational workload on supported classic compute, a processing-time trigger may be appropriate. If the requirement is “process whatever arrived since the last scheduled run and stop,” use AvailableNow. Current Databricks documentation distinguishes these modes and their compute support.

Decision 5: Current dimension vs point-in-time dimension

If analysts ask “what tariff was applicable when the meter reading occurred?”, a current snapshot join is insufficient. Use effective dates/SCD2 or another temporal lookup strategy. If the question is “what is the account's current status for this newly arriving event?”, current-snapshot enrichment may be sufficient.

28. Final End-to-End Mental Model

End-to-end utility meter data product

The six-step mental model

  1. Kafka provides facts. Meter usage arrives as events with topic/partition/offset metadata.
  2. Spark processes continuously. Structured Streaming turns the unbounded source into incremental micro-batches and applies DataFrame/SQL transformations.
  3. Event time gives business meaning. Watermarks and windows manage late/out-of-order events and bounded state.
  4. Dimensions add context. Account, Billing and Service Location attributes enrich each fact; point-in-time rules are required when historical dimension correctness matters.
  5. Delta provides durable data products. Bronze preserves raw facts; Silver creates trusted enriched events; Gold creates business aggregates.
  6. Databricks operationalizes the system. Unity Catalog, jobs/pipelines, monitoring, quality expectations and governed storage turn the Spark application into a production data product.

Production checklist

  • ☐ Kafka topic partition count matches expected throughput and ordering needs.
  • ☐ Kafka authentication/networking is governed and secrets are not hard-coded.
  • ☐ Bronze preserves raw payload and source metadata.
  • ☐ Explicit event schema and schema-change process exist.
  • ☐ Event time is defined and timestamp timezone semantics are clear.
  • ☐ Watermark is based on observed late-data behavior.
  • ☐ Deduplication key and deduplication horizon are documented.
  • ☐ Dimension freshness and point-in-time requirements are documented.
  • ☐ Stream-static joins are sized and optimized appropriately.
  • ☐ Checkpoints are durable, unique and governed.
  • ☐ Output mode and trigger match the query semantics and SLA.
  • ☐ Delta schema policy is explicit.
  • ☐ Small-file behavior and table optimization are monitored.
  • ☐ State size and Kafka lag are monitored.
  • ☐ Quarantine/dead-letter path exists for malformed or invalid events.
  • ☐ Recovery from driver/cluster failure has been tested.
  • ☐ Replay/backfill procedure is documented.
  • ☐ Data-quality metrics and alerts exist.
  • ☐ CI/CD and environment-specific configuration are separated from code.
  • ☐ Security/governance uses Unity Catalog and appropriate cloud-storage controls.
