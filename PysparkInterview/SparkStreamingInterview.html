Architecture & Execution

Questions designed to test reasoning, mechanisms and production trade-offs.

01

What is the difference between Spark Streaming and Structured Streaming?

Answer

Spark Streaming is the older DStream-based API. Structured Streaming models an unbounded stream as a continuously growing table and applies DataFrame/Spark SQL semantics. It provides event-time processing, watermarks, checkpoint-based recovery and broad integration with modern sources and sinks.

Architecture
Senior-level point: Do not describe Structured Streaming as merely a faster DStream API.
02

What does a micro-batch actually do?

Answer

A trigger identifies new input, creates a bounded increment, executes the physical plan, updates state when required, writes to the sink and records progress in the checkpoint. The next trigger repeats the process.

Execution
Senior-level point: If processing takes longer than the trigger interval, latency grows even though the query is still healthy.
03

Event time vs ingestion time vs processing time?

Answer

Event time is when the business event occurred; ingestion time is when the platform received it; processing time is when Spark processed it. Meter usage normally needs event time because network delay should not change the business interval.

Correctness
Senior-level point: Keep the event-time column explicit and typed as a timestamp.
04

How does watermarking work?

Answer

Spark tracks event-time progress and applies the configured delay to establish a threshold. Stateful operators can use that threshold to finalize results and evict old state. It bounds state at the cost of tolerance for very late records.

Watermarks
Senior-level point: A watermark is an event-time progress mechanism, not a wall-clock timer.

Event Time, Watermarks & State

Questions designed to test reasoning, mechanisms and production trade-offs.

05

Does a watermark mean late records are always discarded?

Answer

No. The effect is operator-dependent. Watermarks primarily bound state and enable finalization of stateful results. Records older than the watermark can be too late for particular stateful operations and may be dropped, but a watermark does not make every transformation discard old rows.

Watermarks
Senior-level point: Explain the operator semantics instead of saying watermark equals delete.
06

Why can a watermark move slowly?

Answer

Event-time progress is tracked across the relevant partitions or input streams. A partition that stops advancing event time can hold back global progress. For multiple inputs, the default global watermark policy is conservative and follows the slowest input.

Advanced
Senior-level point: Choosing a faster multiple-watermark policy can reduce latency but can sacrifice data from slower inputs.
07

How would you choose a watermark for meter usage?

Answer

Measure real arrival-delay distributions. If valid events normally arrive within about 10 minutes, start with a threshold that covers the required percentile plus operational margin, then tune using latency, state size and late-data metrics.

Production
Senior-level point: Watermark selection is a correctness-versus-latency/state decision.
08

What is a stateful streaming operation?

Answer

A stateful operator needs information from previous micro-batches. Examples include aggregations, deduplication, stream-stream joins and custom stateful processing. Stateless operations such as select and filter only process the current input plus source progress.

State
Senior-level point: State growth is a major operational risk in long-running streams.
09

Why does state become a performance bottleneck?

Answer

High-cardinality keys, long watermarks, skew and slow eviction can make state grow. More state increases memory/IO, checkpoint work, batch duration and latency.

State
Senior-level point: Monitor state size and batch duration together.
10

How do you calculate hourly meter consumption correctly?

Answer

Parse event time, apply an appropriate watermark, group by the event-time hour plus meter/account identifiers, and aggregate usage. This keeps business time independent from arrival time.

Windowing
Senior-level point: Explain why event-time windows are preferable to processing-time windows for telemetry.
11

Tumbling vs sliding vs session windows?

Answer

Tumbling windows are fixed and non-overlapping. Sliding windows overlap and use duration plus slide. Session windows group activity separated by inactivity gaps. Hourly utility consumption commonly uses tumbling windows; rolling demand metrics can use sliding windows.

Windowing
Senior-level point: Always give a business example.

Joins & Dimension Enrichment

Questions designed to test reasoning, mechanisms and production trade-offs.

12

What is a stream-static join?

Answer

A streaming DataFrame is joined with a bounded/static DataFrame. Kafka meter events can be enriched with a current Account, Billing or Service Location snapshot.

Joins
Senior-level point: A static snapshot does not automatically provide historical point-in-time semantics.
13

What is the hidden issue with a static dimension join?

Answer

The dimension represents a snapshot. If an account or location relationship changes, an older event processed later may be enriched with the newer relationship. Historical correctness requires effective-dated or temporal enrichment when that matters.

Joins
Senior-level point: Separate current enrichment from point-in-time enrichment.
14

When should you broadcast a dimension?

Answer

Broadcast when the dimension is small enough to replicate safely to executors and the memory overhead is acceptable. It can avoid a large shuffle. Broadcasting a large table can cause executor memory pressure or failure.

Performance
Senior-level point: Measure dimension size and executor memory instead of blindly broadcasting.
15

How do you handle missing dimension records?

Answer

Decide business semantics. A left join preserves the fact and yields null dimension attributes; an inner join drops the event. Auditable pipelines often preserve the fact, mark enrichment failure and route unresolved records to quarantine/reprocessing.

Production
Senior-level point: Do not silently discard unmatched facts.
16

How do you handle late-arriving dimension data?

Answer

Options include retry/reprocessing, effective-dated dimensions, periodic backfill and downstream reconciliation. The choice depends on whether the Silver layer must be immediately correct or eventually correct.

Architecture
Senior-level point: Streaming latency and historical dimensional correctness are different requirements.
17

At-least-once vs exactly-once?

Answer

At-least-once allows retries and possible duplicate processing. Exactly-once means the supported source/sink protocol prevents duplicate committed effects under its defined failure model. It does not make arbitrary external side effects exactly-once.

Semantics
Senior-level point: Always qualify exactly-once by source, sink, checkpoint and external side-effect behavior.

Reliability & Exactly-Once

Questions designed to test reasoning, mechanisms and production trade-offs.

18

Why are checkpoints essential?

Answer

A checkpoint stores query progress and, for stateful queries, the state information needed for recovery. It includes source offsets, commit information, state metadata/data where applicable and query metadata.

Recovery
Senior-level point: Each independent streaming query needs its own durable checkpoint location.
19

What happens if you delete a checkpoint?

Answer

You discard the stored progress/state identity. A restart with a new checkpoint behaves like a new query, so source offsets and state recovery no longer follow the previous execution history. Depending on source configuration, data can be replayed or skipped.

Recovery
Senior-level point: Checkpoint deletion is a migration/reprocessing decision, not routine cleanup.
20

Can you change stateful query logic and reuse the same checkpoint?

Answer

Not safely in general. Stateful operators depend on compatible state schemas and query structure. Changes to grouping keys, aggregates, deduplication keys or join state can make existing state incompatible.

State migration
Senior-level point: A code deployment is not automatically a state migration.
21

Append vs Update vs Complete output modes?

Answer

Append emits finalized rows, Update emits rows changed by the current trigger, and Complete emits the full result table for supported aggregations. Stateful operators and sinks have compatibility constraints.

Output modes
Senior-level point: Current Databricks guidance notes that Delta sinks support append and complete directly, not update.
22

Why can Complete mode become expensive?

Answer

Complete mode outputs the full aggregate result on every trigger. As the number of groups grows, output volume can become large even when only a small portion changed.

Performance
Senior-level point: Do not choose Complete mode merely because it is easy.
23

How do you deduplicate Kafka events?

Answer

Use a stable event_id and retain one logical event. For an unbounded stream, pair deduplication with an event-time watermark so old keys can eventually be evicted.

Deduplication
Senior-level point: Correctness depends on event_id uniqueness and producer behavior.
24

Why can deduplication consume a lot of state?

Answer

Spark must remember previously seen keys. Without bounded state, the set grows throughout the stream lifetime. Watermark-aware deduplication lets old keys become eligible for eviction.

State
Senior-level point: High-cardinality event IDs can create substantial state.
25

How does Kafka partitioning affect Spark performance?

Answer

Kafka partitions provide source parallelism. Too few partitions limit concurrency regardless of Spark cores. Skewed partitions create stragglers. Partitioning must consider throughput, key distribution, ordering and consumer parallelism.

Kafka
Senior-level point: More Spark cores cannot compensate for a severely under-partitioned topic.

Kafka, Performance & Triggers

Questions designed to test reasoning, mechanisms and production trade-offs.

26

What is maxOffsetsPerTrigger?

Answer

It caps how much Kafka data a micro-batch attempts to process. It can smooth catch-up, protect downstream systems and control batch size, but overly restrictive limits increase backlog and latency.

Kafka
Senior-level point: It is a throughput-control mechanism, not a replacement for adequate capacity.
27

How do you diagnose growing Kafka lag?

Answer

Determine whether input rate exceeds processing capacity. Inspect partition skew, batch duration, state growth, shuffle-heavy joins, sink latency and executor pressure. Compare input rows/sec with processed rows/sec and inspect per-batch progress.

Troubleshooting
Senior-level point: First identify whether the bottleneck is source, Spark processing or sink.
28

What causes a stream to fall behind its trigger interval?

Answer

Large input batches, expensive shuffles, state growth, skew, slow dimension joins, small-file-heavy sinks, GC pressure, insufficient capacity or downstream throttling. Trigger interval is not a guaranteed completion deadline.

Troubleshooting
Senior-level point: Tune the dominant stage, not the trigger blindly.
29

When should you use AvailableNow?

Answer

AvailableNow is useful for incremental workloads where the query should process all currently available data and then stop, such as scheduled ingestion. It differs from an always-running low-latency stream.

Databricks
Senior-level point: Do not confuse Databricks Jobs Continuous scheduling with Spark Continuous trigger.
30

What is Continuous Processing?

Answer

It is a distinct low-latency execution mode with different support and semantics from normal micro-batch execution. Micro-batch remains the common model for broad stateful and sink compatibility.

Triggers
Senior-level point: It is not simply micro-batch with a tiny trigger interval.
31

How do you make foreachBatch idempotent?

Answer

Use the batch identifier and deterministic business keys so retries do not create duplicate effects. Use transactional operations such as Delta MERGE where suitable, or maintain an application-level idempotency record in the target.

Sink design
Senior-level point: Exactly-once source processing does not automatically make an arbitrary external API exactly-once.

Delta, Quality & Schema

Questions designed to test reasoning, mechanisms and production trade-offs.

32

How would you design Kafka → Delta ingestion?

Answer

Keep raw Kafka payload and Kafka metadata in Bronze, parse into typed columns, validate and deduplicate in Silver, enrich deliberately, and write curated data to Delta. Preserve source metadata for replay and audit.

Architecture
Senior-level point: Raw ingestion and enrichment separation simplifies recovery.
33

Why is Delta Lake a strong streaming sink?

Answer

Delta integrates with Structured Streaming and provides transactional commits, consistent table versions and reliable concurrent reads/writes. Databricks documents exactly-once guarantees for supported Delta streaming writes.

Delta
Senior-level point: Exactly-once at Delta does not automatically cover arbitrary downstream consumers.
34

What is the small-file problem?

Answer

Frequent low-volume micro-batches can create many small files, increasing metadata overhead and degrading scans. Use sensible trigger/batch sizing, compaction and current Delta optimization/clustering capabilities where appropriate.

Delta performance
Senior-level point: Do not sacrifice latency solely to hide small files.
35

Why is data skew dangerous?

Answer

A few hot keys can receive disproportionate traffic. Their partitions/tasks do much more work, creating stragglers and concentrated state.

Performance
Senior-level point: Look for long-tail task durations and uneven key distributions.
36

How do you handle malformed Kafka JSON?

Answer

Parse using an explicit schema and retain the raw payload. Invalid records go to a quarantine/dead-letter path with an error reason and source metadata such as topic, partition and offset.

Data quality
Senior-level point: Preserve raw evidence for investigation and replay.
37

How should Kafka schema evolution be handled?

Answer

Treat schemas as producer/consumer contracts. Adding an optional field is generally easier than changing/removing fields or changing types. Schema Registry with Avro/Protobuf can enforce compatibility policies more explicitly.

Schema
Senior-level point: Schema evolution is as much a data-contract problem as a Spark problem.
38

What is a stream-stream join and why is it harder?

Answer

Both sides are unbounded, so Spark must retain state from each side to match future records. Without time bounds, state can grow indefinitely. Watermarks and time-range constraints are therefore central.

Joins
Senior-level point: Explain state bounding, not just join syntax.

Advanced Scenarios & Troubleshooting

Questions designed to test reasoning, mechanisms and production trade-offs.

39

Processing-time vs event-time windowing?

Answer

Processing-time groups by when Spark processes records; event-time groups by when the business event occurred. Telemetry normally requires event time because retries and network delay should not redefine the business interval.

Time semantics
Senior-level point: A reading generated at 10:05 and processed at 10:12 still belongs to the 10:00–11:00 event-time window.
40

How do you recover after a driver restart?

Answer

Restart the query with the same code/configuration and durable checkpoint. Spark restores source progress and state according to the source and sink semantics.

Recovery
Senior-level point: Changing the checkpoint location turns recovery into a new-query problem.
41

What if S3 is temporarily unavailable?

Answer

The affected read/write may fail the batch or query. Durable checkpoints let a restarted query resume from the last committed progress. Production design also needs orchestration retries, alerts and correct cloud permissions/networking.

Failure
Senior-level point: Recovery only works if checkpoints and source data remain available.
42

What should you monitor?

Answer

Track input rows/sec, processed rows/sec, batch duration, trigger interval, Kafka lag, state size, watermark progression, failed batches, sink throughput, data-quality rejects and executor/resource utilization.

Observability
Senior-level point: Ask whether the stream is keeping up while preserving correctness, not merely whether it is running.
43

How do you troubleshoot increasing batch duration?

Answer

Use query progress and Spark UI to find whether time is spent in source ingestion, parsing, shuffle, state store, joins or sink commits. Inspect skew, state growth, input volume, partitions, file sizes and resource pressure.

Troubleshooting
Senior-level point: Change one bottleneck at a time and measure.
44

How would you design replay?

Answer

Retain raw Bronze data and source metadata long enough for replay, keep transformations deterministic, isolate checkpoints, and provide a controlled backfill path. Replay should be tested operationally.

Senior design
Senior-level point: A replay strategy is essential for billing and telemetry pipelines.
45

What is the most common exactly-once misconception?

Answer

Exactly-once does not mean a record can never be read or processed twice. Retries can happen. The guarantee is about the committed effect under the supported source/sink protocol. External APIs and poorly designed foreachBatch logic can still duplicate effects.

Must know
Senior-level point: Use the phrase: exactly-once effect under defined source/sink and failure semantics.

Final Senior-Level Mental Model

Think in this order during an interview:
  1. Source: partitions, ordering, offsets and replay.
  2. Time: business event time and valid late-arrival tolerance.
  3. State: what survives across batches and how it is bounded.
  4. Correctness: duplicates, missing records, retries and commit semantics.
  5. Join: static, streaming, historical or point-in-time enrichment.
  6. Sink: transactional and idempotent guarantees.
  7. Performance: Kafka, shuffle, state, compute, files and sink throughput.
  8. Recovery: driver/executor/source/sink failure behavior.
  9. Operations: lag, latency, state growth, data quality and alerts.
