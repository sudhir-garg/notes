01. Explain your end-to-end data pipeline experience (from ingestion to reporting).

01

Interview-ready answer

Answer the question as an architecture story rather than a tool list. Start with the business SLA and source systems, then cover ingestion, raw retention, transformation, quality, modeling, serving, reporting, security, monitoring and recovery. A representative enterprise pipeline is: operational systems/APIs/files → Kafka or batch ingestion → cloud object storage/Bronze → Spark transformations/Silver → dimensional and business aggregates/Gold → warehouse or Delta serving layer → BI/reporting. In a utility example, meter-usage events arrive through Kafka while Account, Billing and Service Location dimensions arrive from S3. Spark validates, deduplicates and enriches the events, Delta stores curated data, and Gold aggregates feed Databricks SQL or BI.

Key points to mention
  • Mention: business requirement and SLA
  • source ingestion
  • Bronze/raw retention
  • transformation
  • data quality
  • Silver/Gold modeling
  • serving
  • orchestration
  • security
  • monitoring
  • recovery.
from pyspark.sql.functions import from_json, col

# Representative streaming source
events = (spark.readStream
    .format("kafka")
    .option("subscribe", "meter_usage")
    .option("startingOffsets", "latest")
    .load())

# Typical sequence: parse -> validate -> deduplicate -> enrich -> aggregate -> Delta

02. How do you design a data lake vs a data warehouse, and when would you use each?

02

Interview-ready answer

A data lake is designed for large volumes of diverse data and flexible processing. A data warehouse is optimized for governed analytical consumption, predictable SQL performance and business reporting. Modern lakehouse architectures often combine these capabilities. The important interview point is that the decision should be workload-driven: raw retention, data variety, governance, latency, concurrency, cost and consumer needs determine where each dataset belongs.

Key points to mention
  • Compare: lake for raw/varied data and data science
  • warehouse for governed BI
  • lakehouse for unified analytics
  • consider storage cost, compute model, governance, SQL performance and workload isolation.
Likely follow-up: Follow-up: Why not put everything in a warehouse? Explain raw-data retention, semi/unstructured data, large-scale transformations, cost and multiple downstream workloads.

03. What are different data partitioning strategies in Big Data systems, and why are they important?

03

Interview-ready answer

Partitioning controls how data is distributed so systems can parallelize work and avoid scanning irrelevant data. Common strategies are hash partitioning, range partitioning, time partitioning, composite partitioning and bucketing. In Spark, execution-level shuffle partitions are also important. For meter usage, date/hour partitions can enable pruning for time-range queries, while high-cardinality meter IDs are usually better handled through clustering or execution partitioning rather than creating millions of storage partitions.

Key points to mention
  • Discuss: partition pruning, parallelism, shuffle reduction, skew, cardinality and file size. Time partitions are common for event data, but partition explosion and tiny files must be avoided.
Likely follow-up: Interview trap: “partition by the most queried column” is incomplete. Explain volume, cardinality, temporal locality, skew, query patterns and file size.

04. How do you handle schema evolution in data pipelines (like Avro, Parquet, or JSON)?

04

Interview-ready answer

Treat schema evolution as a data-contract problem. Avro works well with explicit schemas and schema registries with compatibility rules. Parquet embeds schema in files and is efficient for analytics, but readers must handle compatible field changes. JSON is flexible but has weaker contracts, so production consumers should parse against an explicit schema, validate records and version producer contracts. Additive nullable fields are usually easier than type changes, renames or semantic changes.

Key points to mention
  • Mention: backward/forward compatibility, additive fields, breaking changes, schema registry, contract testing, explicit Spark schemas, quarantine of invalid records.
from pyspark.sql.types import *

schema = StructType([
    StructField("event_id", StringType(), False),
    StructField("meter_id", StringType(), True),
    StructField("usage_kwh", DoubleType(), True),
    StructField("event_time", TimestampType(), True),
])

parsed = raw.select(from_json(col("json_payload"), schema).alias("data")).select("data.*")
Likely follow-up: Follow-up: What if integer becomes string? Treat it as a breaking contract unless the consumer explicitly supports and validates conversion. Never silently coerce business-critical fields.

05. What are the differences between batch and streaming pipelines? Give real-life examples.

05

Interview-ready answer

Batch processes bounded data on a schedule or on demand. Streaming processes continuously arriving or incrementally available data, commonly using micro-batches. Batch fits daily financial reconciliation, historical backfills and scheduled master-data loads. Streaming fits fraud alerts, IoT telemetry, clickstreams and real-time meter readings. Streaming also introduces event-time semantics, state, watermarks, checkpointing and replay concerns.

Key points to mention
  • Compare bounded vs unbounded input, latency, state, failure recovery, cost and operational complexity. Emphasize that the correct architecture is the simplest one that meets the business SLA.
Likely follow-up: Follow-up: Should every Kafka source be processed continuously? No. Kafka can also support scheduled incremental/AvailableNow-style processing when continuous low latency is unnecessary.

06. How do you optimize Spark jobs for performance (partitioning, caching, joins)?

06

Interview-ready answer

Start with measurement. Inspect the Spark UI, physical plan, stage/task duration, shuffle read/write, spill, skew, executor memory and GC. Then reduce unnecessary shuffles, select appropriate join strategies, use predicate/projection pushdown, size partitions appropriately, handle skew, manage file sizes and cache only expensive datasets that are reused. In streaming, also inspect Kafka partitions, batch duration, state growth and sink throughput.

Key points to mention
  • Mention: explain plans
  • shuffle reduction
  • AQE
  • broadcast joins for genuinely small dimensions
  • partition sizing
  • skew handling
  • small-file management
  • selective caching
  • avoiding driver-heavy operations.

enriched = events.join(broadcast(account_dim), "account_id", "left")
Likely follow-up: Follow-up: Should you cache everything? No. Cache has memory/storage overhead and is useful only when reuse offsets recomputation enough to justify it.

07. What are the different join strategies in Spark and when do you use each?

07

Interview-ready answer

Important physical strategies include broadcast hash join, sort-merge join and shuffled hash join, plus nested-loop variants for special cases. Broadcast is effective when one side is small enough to replicate. Sort-merge is common for large equi-joins because both sides can be distributed and sorted. Nested-loop or Cartesian approaches can become extremely expensive and require strong justification. AQE can change execution decisions at runtime.

Key points to mention
  • Explain: data size, join type, equi-join condition, statistics, broadcast threshold, shuffle and skew.
Likely follow-up: Interview trap: never say Spark always uses sort-merge joins. The optimizer and AQE can select another strategy.

08. How do you handle late-arriving data or out-of-order events in streaming?

08

Interview-ready answer

Use event time as the business clock. A meter event generated at 10:05 may arrive at 10:12. Processing-time windows can therefore misclassify it. Watermarks bound state and allow stateful operators to finalize/clean up old event-time information. Choose the watermark from observed arrival distributions and business tolerance. Data beyond the accepted lateness policy should be dropped, quarantined, reconciled or corrected through backfill depending on business requirements.

Key points to mention
  • Mention: event time, processing time, ingestion time, watermark, state cleanup, late-data policy and reconciliation.
watermarked = (events
    .withWatermark("event_time", "15 minutes")
    .groupBy(window("event_time", "1 hour"), "meter_id")
    .sum("usage_kwh"))
Likely follow-up: Follow-up: Does a watermark mean every record older than it is physically deleted? No. Explain that watermark behavior is operator-dependent and primarily bounds state/finalization.

09. What is the difference between OLAP and OLTP databases, and where does data engineering fit?

09

Interview-ready answer

OLTP systems optimize concurrent business transactions, point lookups and updates. OLAP systems optimize large scans, joins and aggregations. Data engineering connects them: CDC or extraction captures operational changes, pipelines land and transform them, models them into facts/dimensions or analytical tables, applies quality/governance, and publishes them without placing heavy BI workloads on the transactional system.

Key points to mention
  • Mention: CDC, workload isolation, normalization vs dimensional modeling, incremental loads and analytical serving.
Likely follow-up: Follow-up: Why not run BI directly on OLTP? Large analytical queries can contend with customer-facing transactions and degrade operational SLAs.

10. How do you implement slowly changing dimensions (SCD) in ETL pipelines?

10

Interview-ready answer

SCD techniques control how dimension changes are represented. Type 1 overwrites the old value. Type 2 preserves history by creating a new version with effective dates and usually a current flag. Type 3 stores limited previous-state information. Type 2 is common when reports must answer what was true at a historical point in time.

Key points to mention
  • Explain: business key, surrogate key, change detection/hash, effective_from, effective_to, is_current and MERGE/upsert patterns. For fact enrichment, join on business key plus effective-time range for point-in-time correctness.
-- Typical SCD2 attributes
account_id
customer_id
account_status
effective_from
effective_to
is_current
record_hash
Likely follow-up: Follow-up: How do you join a fact to SCD2? Use the business key and a temporal predicate such as fact_time >= effective_from AND fact_time < effective_to.

11. What are common data quality checks you implement in pipelines?

11

Interview-ready answer

Quality should be layered: schema validity, completeness, uniqueness, validity/range, referential integrity, consistency, timeliness and anomaly/volume checks. For meter usage, check non-null event_id and meter_id, valid timestamps, non-negative usage where the domain requires it, unique event IDs, valid account references and abnormal volume changes. Invalid data should be observable and recoverable rather than silently discarded.

Key points to mention
  • Mention: prevention, detection, quarantine, alerting and reconciliation. Explain what happens after a failed check, not just the check itself.
Likely follow-up: Senior point: data quality is a contract plus an operational action policy. A check with no alert, quarantine or remediation path is not a complete production control.

12. How do you decide between using Kafka, Kinesis, or Pub/Sub for streaming ingestion?

12

Interview-ready answer

Choose based on cloud ecosystem, throughput, partitioning/order requirements, retention and replay, operational ownership, integrations and team expertise. Kafka provides a broad ecosystem and explicit topic/partition/offset model. Kinesis is deeply integrated with AWS and uses streams/shards. Pub/Sub is strongly integrated with GCP and uses topics/subscriptions. There is no universal winner; architecture constraints determine the choice.

Key points to mention
  • Ask first: cloud? throughput? ordering? retention? replay? delivery semantics? multi-region? managed-service preference? operational expertise?
Likely follow-up: Follow-up: For an AWS-native team, why might Kinesis be attractive? Lower integration/operational friction. Why might Kafka still win? Existing Kafka ecosystem, portability, tooling or platform standards.

13. What is the difference between Hive external and managed tables?

13

Interview-ready answer

Historically, a managed table meant the metastore/table system had stronger ownership of the table data lifecycle, while an external table referenced data whose location/lifecycle was managed outside the table. The key interview concept is ownership of the data location and lifecycle. Modern catalogs and lakehouse platforms add governance semantics, so explain the exact engine/version rather than assuming old Hive behavior applies unchanged.

Key points to mention
  • Mention: metadata, data location, lifecycle, shared object storage and modern catalog differences.
Likely follow-up: Follow-up: Is an external table always safer? Not automatically. Governance, permissions and lifecycle policies still need to be designed explicitly.

14. How do you ensure pipeline reliability and monitoring in production?

14

Interview-ready answer

Use durable checkpoints for streaming, transactional or idempotent sinks, deterministic transformations, retries where appropriate, durable storage, schema contracts, quality gates and observability. Monitor both technical and business metrics: source lag, throughput, latency, batch duration, failures, state size, data freshness, rejects and volume anomalies. Alerts should point toward an actionable cause rather than merely saying a job failed.

Key points to mention
  • Mention: SLA/SLO, Kafka lag, Spark stages, state growth, checkpoint health, sink failures, data quality, freshness, alerting, runbooks and incident recovery.
Likely follow-up: Follow-up: How do you identify the bottleneck? Compare arrival rate, processing rate and sink throughput, then use Spark UI/query progress to isolate source, compute, state, shuffle or sink delay.

15. SQL-heavy questions: 2nd highest salary and duplicate records

15

Interview-ready answer

For the second-highest salary, clarify whether the interviewer means the second distinct salary or the second row after ordering. Usually the expected meaning is second distinct highest, for which DENSE_RANK is robust with ties. For duplicates, first define the duplicate key. GROUP BY/HAVING reports duplicate keys; ROW_NUMBER identifies individual duplicate rows while allowing a deterministic row to be retained.

Key points to mention
  • Mention: ties, business key, window functions, null semantics and deterministic ordering.
-- Second distinct highest
SELECT salary
FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employee
) x
WHERE rnk = 2;

-- Duplicate business keys
SELECT employee_id, COUNT(*) AS cnt
FROM employee
GROUP BY employee_id
HAVING COUNT(*) > 1;

-- Identify rows to remove/retain
SELECT *
FROM (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY employee_id ORDER BY updated_at DESC) rn
  FROM employee e
) x
WHERE rn > 1;
Likely follow-up: Follow-up: With salaries 100, 100, 90, 80, the second distinct highest is 90. RANK, DENSE_RANK and ROW_NUMBER answer different questions, so state your interpretation.
